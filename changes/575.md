- Install without a terminal (item 575): download `Dot_<version>_universal.dmg`, drag Dot to Applications and open it.
  On a Mac that has no Dot, the window shows **Set up Dot**: what the Mac has (macOS 15.2 or later; Google Chrome, with
  a button to its download page when it is missing, and the setup goes on without it), the models (Ollama, when it
  answers on this Mac, or the API key of OpenAI, Anthropic, OpenRouter or OpenCode Go) and one **Install Dot** button
  that installs Python and Dot's package with the `uv` the app carries, sets up the model and the key, and installs the
  service with the small app that runs Dot already built and signed in the app, so that Homebrew, ripgrep and Xcode's
  Command Line Tools are not needed (the app carries `uv` and `rg`, and the service's `PATH` begins with their folder).
  Each step is listed and its output is kept in `~/Library/Logs/Dot/installer.log` with the key hidden; a step that
  fails says which, what it printed and what to do, and **Try again** goes on from it. The install is complete once the
  service is installed, whether or not the daemon had answered when the app was quit: the next start shows Dot, or the
  page that says it is down, and keeps the package in step; an install that stopped before that goes on from the step
  that did not finish, and with the models set up it asks for none and never runs `dotx setup` over your config. The
  installer never runs over another Dot: with a Dot service, a daemon that answers or a `config.toml` on the Mac, the
  app shows what it always showed. When the app updates itself, the package it installed follows it to the same version
  and the daemon restarts once no run works (an install the app made only, never a checkout; and only while the app runs
  from where it stays and the service is the app's own job: from the disk image it came on, or with another Dot's
  service in its place, nothing is touched and `installer.log` says why). `dotx service install` takes a prebuilt
  launcher (`--launcher PATH` or `DOT_APP_LAUNCHER`) in place of the clang build; typed in a terminal on an install of
  the app, with neither, it finds the app's tools in Dot's home (`runtime/app-tools`, put first on the job's `PATH`) and
  makes Dot.app again from the program the app keeps, so that it needs neither Homebrew's ripgrep nor Xcode's tools, and
  `dotx setup` does not ask for them. Only the installer's own window may call the install commands: the shell's other
  pages and the daemon's are refused by Tauri's ACL, and the `runtime` folder of Dot's home that the app installs in is
  closed to a run's commands, as Dot.app is. A release now publishes the package to PyPI before the app
  (`desktop/release.sh` ends with the order), and carries `uv`, `rg` and the launcher, pinned by SHA-256 in
  `desktop/tools.lock` and signed with the app. `dotx service restart --when-idle`, which that upgrade asks for, writes
  its job's property list to a new file and puts it in place in one step, and reads the old one without following a link
  or waiting for a FIFO, so that a link a command of a run left in Dot's home is not written through (the staging name
  was a fixed one, item 441).
