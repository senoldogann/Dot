### 534. Reading the clipboard asks, as a read of a protected location does

**Status: done (2026-10-22).** The audit of how Dot keeps the owner's passwords from a run (the owner asked whether
it is sure) found three ways a run reads the clipboard without a question in any preset: the
`desktop_clipboard_read` tool (low risk, no flag), `pbpaste` (on the list of commands that only read), and an
AppleScript that returns `the clipboard`. The clipboard is where a password sits for a minute after the owner copied
it from their password manager, which is what the manager is for: a run that read it then hands the password to the
model, whatever Dot does for the fields of a page.

**As built** (on item 531's flag `protected_read`, which a read that may reach a secret carries):
- Outside yolo the sandbox of a run's processes refuses the clipboard's service (`com.apple.pasteboard.1`, in
  `policy/sandbox.py`, a `(deny mach-lookup …)` rule of its own, `CLIPBOARD_SERVICES`): no command, terminal session
  or AppleScript can itself read what the owner copied or put text there, whatever the line says (`pbpaste` prints
  nothing and an AppleScript's `the clipboard` fails with -4960; measured). `pbcopy` fails in a run's command too; the
  tool `desktop_clipboard_write` runs in Dot's own process and is the way to put text there. What another application
  does for a process of a run is outside the sandbox (Apple Events: Terminal's `do script`, a keystroke that pastes
  into an application the run reads back). This is the hold, and the guard's names below decide whether the owner is
  asked before a run tries: the review of the guard's names went six rounds, each closing one spelling and opening the
  next layer (second-layer quoting of a name inside `sh -c`), and after the third the approach was to be reconsidered,
  which this is.
- `desktop_clipboard_read` is a medium-risk observe with the flag `protected_read`, so the aggressive preset asks,
  balanced asks (the flag joined its list), cautious asks. Its description tells the model it will be asked.
- `pbpaste` is no longer one of the commands that only read: the guard finds it a read of the clipboard
  (`policy/shell.py` `_reads_the_clipboard`), `pbpaste | head`, `$(pbpaste)` and the rest alike.
- An AppleScript or a JXA script that names the clipboard is judged the same way, as a tool of a run (`apple_script`)
  and as an `osascript` line of the shell: `the clipboard`, `clipboard info`, their raw events (`«event JonsgClp»`,
  and the `<<event …>>` spelling), JXA's `theClipboard` and `clipboardInfo` however they are called
  (`app.theClipboard()`, `(app.theClipboard)()`, `app.theClipboard.call(app)`, `a['\x74heClipboard']()`), any
  pasteboard (`NSPasteboard`, Carbon's `PasteboardCreate`) and `pbpaste` however the script runs it. A script that
  only puts text there is not told from one that reads it, so it asks too: three reviews each found a line that hid a
  read behind a write (`copy` in a string, a comment, the same line) and the approach was reconsidered after the
  third; the guard does not read strings, so a script that only names the words in one asks as well, and `run script
  "…"` is caught the same way.
- The line is scanned whole, as it is for a protected path (`_universal_findings`): any line that names `pbpaste` (in
  any letter case: this Mac's file system does not tell `PBPASTE` from it, and behind a wrapper the guard does not
  look through: `time -l pbpaste`, `arch -arm64e pbpaste`, `ssh -o ProxyCommand=pbpaste`), any line that runs
  `osascript` and names the clipboard anywhere (a pipe, a here-document, a here-string, a variable, a glued `-e'…'`),
  and any line that names a pasteboard (`python3 -c` or `swift -e` with `NSPasteboard`) asks; a line that only talks
  of one (`grep pbpaste notes`, `which pbpaste`) asks too, the price of reading names.
- Putting text on the clipboard with the tool `desktop_clipboard_write` asks nothing more than before; `pbcopy` and an
  AppleScript's `set the clipboard to` fail in a run's command outside yolo while sandboxed (the sandbox's rule).
  Without a sandbox `pbcopy` passes as before (nothing in the guard names it) and an AppleScript that names the
  clipboard asks, as any script that names it does. A yolo run asks nothing (item 443). `docs/safety.md` and
  `docs/browser-and-computer-use.md` say so.

Checked by `tests/unit/test_clipboard_reads.py` (each read asks in all three presets and carries `protected_read`,
not `destructive`; the writes carry no such flag; the desktop tool's action, prepared as a run would). They fail
without the change.

Not built: what the guard's names do not read gets through where there is no sandbox (a yolo run, which asks nothing
by design, and `[shell] sandbox = false`): a script in a file (`osascript r.applescript`), a name that the line or
the script builds as it runs (`printf 'pb%s' paste | sh`, `app['the' + 'Clipboard']()`), a quote the shell takes out
twice (`sh -c "pb''paste"`), a script typed into a session (`osascript -i`, then `terminal_send`), and a paste of
the clipboard into an application that the run then reads back (`⌘V`, `keystroke "v"`, `desktop_act`'s `key` step,
then `desktop_read`; `paste` as the run's own step puts the run's text there; the sandbox does not stop it, as the
application is not the run's process), all said in `docs/safety.md`; and a page that reads it
(`navigator.clipboard.readText()` asks Chrome's own permission). Found on the way, not this item's: the guard
compared a command's name exactly, so `RM -rf ~/x`, `SUDO` and `SECURITY` were judged as unknown commands (allowed
in the aggressive and balanced presets) on this Mac's case-insensitive file system, as `PBPASTE` was; item 538 folds
the name for every command.
