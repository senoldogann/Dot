### 534. Reading the clipboard asks, as a read of a protected location does

**Status: done (2026-10-22).** The audit of how Dot keeps the owner's passwords from a run (the owner asked whether it
is sure) found three ways a run reads the clipboard without a question in any preset: the `desktop_clipboard_read` tool
(low risk, no flag), `pbpaste` (on the list of commands that only read), and an AppleScript that returns `the
clipboard`. The clipboard is where a password sits for a minute after the owner copied it from their password manager,
which is what the manager is for: a run that read it then hands the password to the model, whatever Dot does for the
fields of a page.

**As built** (on item 531's flag `protected_read`, which a read that may reach a secret carries):
- `desktop_clipboard_read` is a medium-risk observe with the flag `protected_read`, so the aggressive preset asks,
  balanced asks (the flag joined its list), cautious asks. Its description tells the model it will be asked.
- `pbpaste` is no longer one of the commands that only read: the guard finds it a read of the clipboard
  (`policy/shell.py` `_reads_the_clipboard`), `pbpaste | head`, `$(pbpaste)` and the rest alike.
- An AppleScript or a JXA script that reads the clipboard is judged the same way, as a tool of a run (`apple_script`)
  and as an `osascript` line of the shell: `the clipboard` (`get`, `set x to`, `copy the clipboard to x`), `clipboard
  info`, JXA's `theClipboard()` and `clipboardInfo()`, and any use of `NSPasteboard` through the Objective-C bridge.
  What puts text there (`set the clipboard to ...`, `copy x to the clipboard`, `setTheClipboardTo`) is a write and stays
  as it was; the write is taken out of the script before it is read, so `set the clipboard to (the clipboard & "x")`
  still reads. The guard does not read strings, so a script that only names the words in one asks too, and
  `run script "…"`, which runs a string, is caught the same way.
- Putting text on the clipboard (`desktop_clipboard_write`, `pbcopy`) asks nothing more than before. A yolo run asks
  nothing (item 443). `docs/safety.md` and `docs/browser-and-computer-use.md` say so.

Checked by `tests/unit/test_clipboard_reads.py` (each read asks in all three presets and carries `protected_read`, not
`destructive`; the writes carry no such flag; the desktop tool's action, prepared as a run would). They fail without the
change.

Not built: a program a run writes that reads the pasteboard itself (a script, inline code), and a page that reads it
(`navigator.clipboard.readText()` asks Chrome's own permission); `desktop_act`'s `paste` puts the clipboard into a
field, not into the run's reading, and is judged as typing is.
