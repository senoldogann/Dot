### 1243. A stream is read in lines that only a line feed or a carriage return ends

**Status: done (2026-11-19).** The code review of 2026-11-19 (findings LLM-01, X3-01, X3-02, X3-03) found four readers
that split a stream or a file of JSON lines with httpx's `aiter_lines` or `str.splitlines`, which also end a line at
U+0085, U+2028 and U+2029. A JSON encoder leaves those raw in a string (Dot's own `model_dump_json`, JavaScript's
`JSON.stringify`, most providers), so a model's answer, a tool result or a command that held one was cut in two:

- `llm/http.py` `iter_sse` and `iter_ndjson` (every provider's stream): the half line was no JSON, and the step failed
  with a `ProviderProtocolError` that is not tried again;
- `cli_handoff.py` (`dotx run` reading the daemon's events) and `opencode/server.py` (OpenCode's events): the stream
  broke and the run with it;
- `repair/second.py` `read_transcript`: the second look skips a line it cannot parse, so a command of the session that
  held such a character was left out of what the look checks.

Seen for real while this change was pushed: its test file held the raw characters, the pre-push review read that
line, and the `dotx run` of the owner's checkout, the old reader, broke on the daemon's event ("an event of the Dot
daemon's stream cannot be read"). The test file now writes them as escapes.

`core/text.py` `stream_lines` splits text as it comes at `\r\n`, `\r` and `\n` alone (a carriage return at the end of a
piece waits for the next), and `file_lines` splits a file's text at `\n`; the four readers use them.

Checked: `tests/unit/test_stream_lines.py` (pieces broken anywhere, an SSE and an NDJSON event whose text holds the three
characters, a transcript line), the tests of the four readers (129; `test_model_wait.py`'s two-second wait failed once
under four workers on a loaded Mac and passes alone, as it did before the change).
