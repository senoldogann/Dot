### 1520. The web app keeps what it read of the chats, so that it opens with them drawn on a link that is bad or gone

**Status: done (2026-11-24); what was checked in a browser, and what was not, is listed at the end.** The owner's word of
2026-11-24 08:38: the iPhone app and the web app go forward at an equal pace, and if the iPhone app does not turn out as
wanted they may come back to the web app, so it must be as good as the iPhone app is becoming. The web app on the Home
Screen had the shell (the service worker keeps the page's files by build) and no data: a phone with no link opened the
shell and then "Dot cannot be reached", and a chat read a minute before was gone with the link. The iPhone app keeps the
list, the agents and each chat in files (item 1371); this item is the same rules for the page.

What was found first (the brief said "verify, do not trust"): `views/run.js` already keeps the six chats opened last in
memory (`keptRuns`: the run's record, the conversation before it and the stream's messages) and draws one at once when it
is over, reading what changed after it is drawn. The cache is that, kept through the page being killed: the same shape,
written to IndexedDB, and read at an opening before any read of Dot is made.

What changed:

- `js/cacherules.js` (pure, `tests/js/cacherules.test.js`): the layout version, the 24 MB budget, what a snapshot holds
  (the run the page was opened at and the 11 before it, the last 400 events of each, the queue; no live piece, which has
  no id and which Dot does not store), the size one chat may take (2 MB: the oldest events go first, then the oldest
  runs), which chat goes first when the budget is passed (the one read longest ago, never the chat on screen, ties by id),
  whether a record reads (layout, shape), which reads are kept as lists (the chats, the agents, the status, the activity,
  the approvals that wait, the assistant, the themes) and whose cache it is (the address and a fingerprint of the key).
- `js/datacache.js`: IndexedDB `dot-cache` (stores `meta`, `lists`, `chats`; a chat is one record put in one transaction
  with the index of what is kept and what the budget lets go, so it is whole or not there). A record that does not read
  is dropped and read again; all is dropped when the key is forgotten (`clearToken`) or when a key or an address claims the
  cache that it was not kept for; a write that began before a forgetting never lands after it. Nothing throws: a browser
  without IndexedDB, a full store or a blocked database leaves the page as it was.
- `js/api.js`: a read of one of the lists is kept as it is answered (written at most every 2 s, never when unchanged) and,
  when Dot cannot be reached, answered from the copy; a refusal of the daemon's is never answered from a copy. The
  cache answers only while the page holds the key it was claimed for, so a key that is only being tried (an address that
  brought one) never meets the chats of the key before it.
- `views/run.js`: `drawFromCopy` draws a chat from its record at once, as for a chat kept in memory (the stream goes on
  after its last event, the run's record, questions and lessons are read again); the chat is kept a moment after its last
  event, when the page is put away (`visibilitychange`, `pagehide`) and when it is left; a run Dot no longer has is dropped.
  A copy that cannot be drawn is dropped and the chat is read from Dot. `queue.js` shows the queue of the copy until the
  daemon's answer comes.
- `js/linkfacts.js`: says that what is shown is a copy, since when, and whether Dot was reached. A copy is dated by when
  Dot last said that this is how the chat stands (`verifiedAt`), not by when it was written, so a copy drawn again never
  looks fresher than it is. The line of item 1524 reads it.
- The service worker is not changed: shell only, nothing under `/api`.

Found by running it. A queue shown while the page is built called the capsule before it existed (`Cannot access
'capsule' before initialization`) and the copy was dropped as one that could not be drawn: it is shown once the page
stands. A `toSorted` of the rules did not pass the type check of the page (ES2022). WebKit under Playwright cannot be sent
offline: `context.set_offline(True)` makes every navigation fail ("WebKit encountered an internal error"), a service
worker's copy included, so the browser test uses a daemon that has stopped (connections refused: a link and no Mac) in
WebKit and `set_offline` in Chromium. A phone whose cache lacked one of the lists the page reads beside the status (the
themes, say) opened on the screen of a Dot out of reach, with no link and the chats it held unseen: `connect` waited for
the status, the agents' looks, the themes and Dot's name with `Promise.all`, and one that had no copy to be answered from
took the opening with it. They are settled one by one now (`main.js`): the status is what must be read, one of the others
that cannot be leaves the page with its defaults (and a warning in the console), and a refused key among them is refused
all the same.

Checked: `tests/js/cacherules.test.js` (22 tests: the twelve runs, the 400 events, the live piece, the size one chat may
take, the dated snapshot, the history, a record that reads and eighteen that do not, the eviction order, the chat on screen
kept, the index); `tests/smoke/test_phone_cache.py` (a chat read before is drawn from the phone with its answer, its title
and its composer at 390 by 844 and 320 by 640, in WebKit with the daemon stopped and in Chromium sent offline, and
no page says that Dot cannot be reached; another key at the same address finds the cache empty; a list read beside the

`tests/unit/test_static_ui.py` (the modules the page reaches are preloaded).
Not verified: a real iPhone, Safari's own handling of a Home Screen app's storage (its limits, and whether it clears
