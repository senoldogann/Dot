### 1313. The phone keeper outlives a failing devicectl, a question's wait says what failed, and a stream reads on after a drop

**Status: done (2026-11-22).** Three small faults the review of the server found.

The phone keeper (`keep_phone`) caught Dot's own errors only, and `devicectl` let an `OSError` out (`xcrun` missing, a
listing it never wrote), so one such round ended the keeper's task for the rest of the daemon's life, and a phone that
came back was never kept again. `run_command` and `XcrunDevicectl.is_available` now raise `PhoneError` for an `OSError`;
`keep_phone` catches anything a round raises (`BLE001`: logged with its traceback as `phone_keeper_round_crashed`, never
ended by it) and waits twice as long for each round in a row that failed, to ten minutes, and from `check_every_s` again
after a good one. `phone_relaunch_failed` carries the first line of what `devicectl` said (300 characters), not the
error's whole context. Which devices count as available is not changed: the repo's own test
(`test_devicectl_listing_says_whether_the_phone_is_available`) says a `disconnected` phone is available on purpose (a
phone on the network and awake lists so until the launch opens its tunnel), so counting only `connected` would stop the
relaunch of a phone that is reachable, and that is left as it is.

`ApprovalBroker.request` caught `TimeoutError` around the marking of the run as blocked and the emit of the question as
well as the wait, so a store that timed out there came out as "no decision before the deadline"; only the wait is the
deadline now, and the store's timeout goes to the caller after the question is closed. Its cleanup is guarded step by
step: a `decide_approval` that fails still runs `unblock_run` and emits `approval_decided`, and the failure goes on to
the caller. (`approvals.py` is under "Always needs a human" in REVIEW.md.)

A run's stream (`follow_run`, `follow_runs`) that had lost events to a full queue read the store again from the id the
page asked from, so a long run's whole history was read and passed over at each drop. It reads each run from the
newest event it sent of that run, less 64 ids (events stored at once can be told to the bus in the other order, so one may
be lost while one after it was sent), and a run that joined only now, or has sent nothing yet, from where the page asked,
as its first read is. The cursor is the run's own, not one id for all the runs: the events of a run a `dotx` command drives
reach the bus late (`relay_elsewhere` polls the store), so the newest id sent of a daemon run says nothing of what that
one lost, and a shared cursor skipped them for good. (The lifecycle
stream replays nothing and is as it was.)

Checked: `tests/unit/test_phone.py` (a program that cannot start and a listing that was not written are `PhoneError`s; a
round that raises `OSError` or anything else is logged with its traceback and the keeper goes on and looks again; the wait
doubles to ten minutes; the first line of stderr is what the log keeps; a phone that is up is looked at and left alone),
`tests/unit/test_approval_cleanup.py` (the deadline still expires an unanswered question, an answer is what the run gets;
a store timeout marking the run blocked is not a missed deadline; a store that cannot keep the decision still unblocks the
run and closes the question; the last two fail without the change), `tests/smoke/test_stream_reread.py` (after a drop
each run is read from the newest event sent of its own and every lost event comes once, for both streams; a helper that
joined during the loss comes whole; the events of a run relayed late, behind the newest id of another run, come: the
test fails with one cursor for all the runs).
