### 2039. The files search reads only the newest calls and attachments: 24 s to 0.1 s on a big store

**Status: done (2026-11-27).** The pre-push review of item 2032 noted that the files search (`GET
/api/threads/search/files`) read every attachment, every tool call and every tool result of the store, and walked every
run's line of helpers, on each search; the lead asked for a limit and an order the indexes can serve, measured.

Measured before, on a store made with the real schema and filled as a year of heavy use (20,000 chats, 60,000 runs with
their helpers, 2,400,800 events, 764 MB, filled by a script outside the repository; nothing of the owner's): 16 to 24 s
a search (`notes` 24.4 s, `invoice` 17.5 s, a word in no file 16.2 s, the best of three each).

What was built: `Store.search_chat_files` reads, through `events_kind_ts` backwards, the newest 50,000 tool calls (the
writes among them), the results of those writes since the oldest of them (an index range on `kind` and `ts`), and the
newest 5,000 `attachments` and `steer` events; it walks up the `parent_run_id` links only for the runs whose files match
(`_run_roots`, by primary key), where the recursive walk of every run stood. The folding of the words and what a find
says are as before. A file older than that window is not found, which the docs say.

How it was checked: the same searches on the same store, 0.10 to 0.12 s each (`notes` 117.6 ms, `invoice` 110.5 ms, a
word in no file 103.3 ms), the same finds; `EXPLAIN QUERY PLAN` shows `events_kind_ts` for both reads;
`tests/smoke/test_thread_sync.py`'s files search (an attachment, a helper's write under the owner's chat and run, a
refused write left out) passes as it did.
