### 1855. A schedule or a watcher may run a check first, without a model, and wake one only when it says so

**Status: done (2026-11-25).** Taken from the study of Hermes Agent (`reports/refs-2026-11-25/hermes-agent.md`, item 2:
its `cron/scheduler_prompt.py` `_parse_wake_gate`); the owner approved it on 2026-11-25. Every firing of a schedule
started a model run, and the watchers had three kinds (mail, calendar, GitHub): "tell me when the price drops" or
"when this page changes" cost a model run each time.

What must hold: a check runs without a model; only its exact "wake" verdict starts one; its output reaches the run as
data, fenced, the run tainted; a check that fails is said and told, never taken as "nothing to wake for"; a yolo or free
run asks nothing new.

The contract: an executable file in `DOT_HOME/checks/`, named by a plain file name; it ends with exit code 0, and its
last line that is not blank is exactly `{"wake": true}` or `{"wake": false}`; what it printed before is its output.
Anything else (missing, not executable, another exit code, past 30 s, another last line) is a `PrecheckError`.

What was built:
- `scheduler/precheck.py`: the contract (`parse_verdict`), the run (`run_check`: the run sandbox while it is on, the
  workspace, the run commands' environment, 30 s), the fenced opening.
- `ScheduleOptions.precheck` and its column; `plans.py` refuses a check on a one-time schedule and one that is not an
  executable file in the folder.
- `scheduler/runner.py`: a firing runs the check before its chat and claim; quiet moves the schedule on with the status
  `quiet: …` and is not counted as a skip (`Store.record_schedule_quiet`); a failure is a skip with its reason, told as
  a missed firing; wake starts the run with the output and `from_outside`. Run now runs the check for its output and
  starts the task whatever it says; a failure there is the request's error (422).
- Watchers: a kind `check` with the file name in `check`; its look is the check; its first look is a real one.
- `checks_dir()` joins what Dot loads and runs (`_dot_paths`), so a run changes a check only as it changes Dot's code.
- The web UI: the schedule form's **Check first** under When (repeating only) and a chip; the watcher form's **Check**
  kind.

Not done: the model's `schedule_create` cannot set a check (it would run code outside the gate on every firing). A
check is not run in parallel with the tick: a slow one holds the next firings back by up to 30 s.

Checked: `tests/smoke/test_schedule_precheck.py` (quiet, three failures, wake with a fence the output cannot close and
a tainted run, no check as before, refusals, a timeout, a check watcher), ruff, mypy, `npm run check`.
