### 1284. A `dotx run` in its own process cuts its skill work before it closes the store

**Status: done (2026-11-21).** Dot's own record showed `model_call_not_recorded` eight times, each a `playbook` call
cut off ("cancelled") a fraction of a second after a `dotx run` that worked in its own process (no daemon) had ended
its run. The traceback ended in `ValueError: no active connection` from the store. `run_here`, `cmd_resume` and
`cmd_chat` closed the runtime (the store last) without closing their `RunManager` first, so the skill work a run's end
starts in the background (its question to the review model) was still waiting; `asyncio.run` cancelled it once the
command returned, and the router's record of the cut-off call went to a closed store. The daemon, the evals and the
test fixture of `dotx run` all call `RunManager.shutdown()` before `close_runtime`; the command itself did not.

What changed: the three commands close through `close_here`, which drops the learning still drawn from the runs that
ended (`RunManager.drop_learning`: their lessons and skill work are cancelled and waited for, and a run that ends after
it starts none) and then closes the runtime. The cut-off call is recorded on the run while the store is open. Live runs
are left as they were: a run a second Ctrl-C left working still keeps the command no longer than five seconds and keeps
the end its stop gives it. `RunManager.shutdown` drops the learning the same way after its runs have ended. What the
command waits for is unchanged: it still waits for the lessons (Ctrl-C skips them) and not for the skill work.

Checked: `tests/smoke/test_cli_run_close.py`, a scripted run whose skill writer's question waits: with `close_here` the
question is cut before the store closes, its `model_call` event (purpose `playbook`, error `cancelled`) is on the run
and no `model_call_not_recorded` is logged; without it the question was still waiting at the close and the test's
teardown raised `ValueError: no active connection`, as in the record. A second test drops the learning while a run
works and finds the run still working and its model call not cut.

Checks made from reviews:
- The close does not shut the run manager down: a first version did, and a second Ctrl-C then waited for the run
  without limit and recorded its end as the daemon's stop (`test_dropping_the_learning_leaves_a_live_run_to_its_stop`).
- The cut-off call is read back from the store, not only the missing error log.

Log:
- 2026-11-21: `dotx run`, `dotx resume` and `dotx chat` drop their learning before closing the runtime.
