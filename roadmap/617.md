### 617. An answer's pictures go with it, and its text reads clean

**Status: done (2026-10-24).** The owner asked Dot from their iPhone, on iMessage, for a screenshot of the Mac's screen.
The answer came as one long text that began with the marker `◆ `, said "I sent the screenshot above, and saved it as a
file at /Users/dogan/Library/Application Support/Dot/workspace/screenshots/ekran-2026-10-24-1617.png", carried no
picture, and left its Markdown lists as `- ` lines. Their words: "Photos should be visible, texts in Markdown should
look clean, and the agent's command running, its thinking and the live flow: whatever we can show, we should show it in
the richest way." This item is the first two (the third is item 618).

**What must hold, and what only tells.** A picture is a file of the owner's that leaves the Mac, to their own devices
through Apple, and the model chooses the path (an answer written after a page was read may name any file). So what may
go is decided by the file, never by the words:

| An answer names | Verdict | Held by |
| --- | --- | --- |
| a regular file in Dot's workspace or the owner's home, no hidden folder on the way, not in `~/Library` outside the workspace, not in `[policy] protected_paths` or `sealed_paths`, whose first bytes are a PNG, JPEG, GIF, HEIC or WebP, up to 20 MB, one of the first four of the answer | sent after the text, one message each | `Pictures._open`, `_judged`, `_may_send_from` |
| a file elsewhere (outside both folders, in a hidden folder, in `~/Library`, in a sealed place), over 20 MB, whose bytes are no picture, or a fifth | not sent; one line at the end of the text says which and why | the same, and `Found.note` |
| a link in the workspace that leads to a file elsewhere | judged by the place it leads to | `realpath`, then the path the kernel names for the file that was opened (`F_GETPATH`) |
| a name that became a link, or a file that became another kind, between the look and the copy | not sent (`ChannelError`, logged) | `Pictures.copy_to` opens once with `O_NOFOLLOW` and judges the file it holds |
| a folder, a pipe, a device, a missing file, a web address | names nothing | `S_ISREG` before and after the open; `://` addresses are not paths |
| a path in a block of code | names nothing | `line_kinds` |

What only tells: the words of the line that says what was left out, and the shortening of a sent path to its file name.

**How Messages takes a file (the brief asked to find out, not to try).** Read, not run:
- `Messages.sdef` of this Mac (`/System/Applications/Messages.app/Contents/Resources/Messages.sdef`): `send` takes a
  `file` or `text` and goes `to` a `participant` or a `chat`. So `send (POSIX file "…") to participant …` is the form,
  as the text is sent now.
- MacScripter, "Sequoia: Messages send file" (Nov 2024, macOS 15.1): a file sent from `~/Documents` shows in Messages
  and then "Not Delivered"; copying it to `~/Pictures` made it go, and "no other folder seems to work".
- akostibas/apple-tools issue 85 (Oct 2026): a PDF in `~/Documents` sent by AppleScript fails with Messages error 34
  while the text of the message arrives; the same file attached by hand works (Messages copies it into
  `~/Library/Messages/Attachments`). Its fix stages a copy under `~/Library/Messages/Attachments/apple-tools/` and never
  deletes it, "the conversation references it afterward".
- Apple Community threads: files on external or network volumes fail where local ones go. Apple's own forums say
  nothing of folders.

So Dot's workspace (`~/Library/Application Support/Dot/workspace`) is not known to be a folder Messages reads, and the
one folder the reports found that works is `~/Pictures`. A picture is therefore never sent from where it is: it is
copied into `~/Pictures/Dot/<seconds>-<8 hex>/<name>` (a folder for each, mode 0700, the copy 0600, the name made safe
and the extension the one the type gives, so a name that lies is not believed by the app that shows it; a small file,
`.made-by-dot`, beside the copy says the folder is Dot's) and Messages is handed the copy. Not
`~/Library/Messages/Attachments`: that folder is Messages' own, writing in it needs Full Disk Access and an app that
keeps files there it did not make is a risk of its own. The copy is not removed at once: `osascript` returns when
Messages has taken the message, and what Messages does with the file after that is not known (copies it, or reads it
again while it uploads and shows it, as the issue above says), so it stays an hour (`STAGED_KEPT_S`) and a sweep of the
service (every minute while the daemon runs, the channel switched on or off) removes it then; a send that failed removes
its copy at once; the copies a daemon that stopped left are removed as the next starts. `~/Pictures/Dot` is the owner's
folder, so Dot removes only what it made: a real folder directly in it, named for the time and eight hexadecimal digits,
that holds the mark (a regular file, never a link, that starts with Dot's words); the files in it go with it, but a
folder in it is left whole, and so is anything else in `~/Pictures/Dot`.

**As built.**
- `channels/text.py` `as_plain_text` reads a line at a time, outside fenced code, whose lines stay as written: items
  marked with a dash, a star or a plus read `• `, a nested one `  ◦ ` (the level comes from how much deeper the item
  stands than the one open before it, whatever the width of the indent), a task `☐` or `☑`, a numbered item as it is; a
  heading is its words on a line of its own with a blank line before it; a horizontal rule and a quote's `> ` go; a
  table is one row to a line, cells joined by ` · `, an empty cell a dash, its rule line gone; bold, strike, one-star
  and one-underscore emphasis around words go (a lone star or underscore stays: `snake_case`, `src/*.py`, `2 * 3`); a
  code span keeps what is in it; a link reads `words (address)`; an empty item is left out. `line_kinds` says which
  lines are prose, fence or code.
- `channels/pictures.py` finds what the prose of an answer names: Markdown images (the address may be bare with spaces
  in it, in angle brackets or percent-encoded), paths written whole (spaces and all: the path is tried from each place a
  path may start up to each image extension, the longest first), `~/…`, `file://…`, and names with no folder, which are
  the workspace's. It looks at 80 places at most in an answer, skips a line over 4,000 characters, judges each as the
  table says, and cuts the sent ones out of the text (an image whole, with its line when it is all the line holds; a
  path down to the file's name, so the sentence still reads). `Found.note` is the one line. A file is called by the
  name the answer wrote for it, never by the name of what a link leads to, and the router masks the note and the
  line of what could not be sent as it masks the answer.
- `channels/staging.py` is the staging folder and the life of the copies; where it is, `~/Pictures/Dot`, is
  `staging_dir()` in `core/paths.py` (`DOT_STAGING_DIR` overrides it, as `DOT_CHROME_DIR` does for the owner's Chrome).
- `channels/imessage.py`: `PICTURE_SCRIPT` sends `POSIX file (item 1 of argv)` to `participant (item 2 of argv)`, the
  path an argument, never words of the script; `send_picture` stages, hands over, drops the copy when Messages did not
  take it (the same `_not_taken` as the text: Automation refused becomes the channel's problem) and keeps the time of
  the send in mind. `_dots_own_picture` (before `_dots_own_link` in `_handle`): a row that holds a file and no words,
  dated from five seconds before such a time to `OWN_LINK_S` (a minute) after it, is Dot's own and is let go, whether it
  is flagged sent or received. A picture of the owner's in that minute is let go with it (it would only have been told
  that Dot does not read attachments); one before or after is told as before; one with words is the command it was
  (item 611).
- `channels/types.py`: `Channel.send_picture`. `channels/router.py` `_say_answer`: for a run that ended done, the answer
  is masked first (so a file name that holds a secret names no file), the pictures are found off the loop, the text goes
  as a message (cut with the link to the room the note leaves), the pictures one by one, and a line for those that did
  not go (the log has `channel_picture_not_sent`). An answer that is only a picture sends no empty text. A router built
  with no finder sends text as before. `channels/service.py` builds the finder from the runtime's workspace, the owner's
  home and `Runtime.protected`, and takes `home` and `staging` so that a test never touches the owner's.
- Docs: `docs/channels.md` (how it works, what Dot reads, what leaves this Mac, if it does not work) and
  `docs/safety.md` (what leaves this Mac, messages from a channel).

**Left out, and limits.**
- A real Messages was not tried (the brief said not to): see the list below.
- A picture a step captured (a screenshot a tool returned) is not sent unless the answer names its file; a web
  address is not fetched; a picture of the owner's is still not read (item 611).
- The words around a path are the model's: "I sent the screenshot above" stays what it is.
- A run that read untrusted content may be led to name a picture of the owner's, which then goes to their own devices.
  Not a leak to anyone else, and the places above bound it; said in `docs/channels.md`, where the channel can be
  switched off while Dot works on content the owner does not trust.
