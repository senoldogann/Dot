### 694. The desktop app installs Dot with the versions its release was built and tested with

**Status: done (2026-10-26).** The desktop app's installer ran `uv --no-config tool install [--reinstall] --python 3.13
dotagent-macos==<version>` with no constraints, while `pyproject.toml` declares lower bounds only (`fastapi>=...`,
`mcp>=...`, `pydantic>=...`). Every new Mac therefore got the newest release of every dependency on the day it
installed: a compromised or breaking release of any of them reached the daemon that holds the owner's keys, and two
installs of one app version were not the same. The upgrade (`keep_in_step`) reinstalled in place with no way back: a
failure part way could leave an environment that does not start, and the daemon down at its next start.

**The change.**
- `desktop/release.sh` writes `constraints.txt` into the app's Resources (`resources/constraints.txt`, beside `tools`,
  named in `tauri.conf.json`, ignored by git, an empty stand-in from `build.rs` in a development build) with the `uv`
  the app carries: `uv export --locked --no-dev --no-emit-project --no-hashes --no-header --no-annotate --format
  requirements-txt`, a `name==version` line for each of the 112 runtime dependencies, with the lock's markers. It does
  that before the app is built and signed, and once the app is built compares the app's copy with a fresh export: the
  release stops when `uv.lock` is not what `pyproject.toml` asks for (`--locked`), when the export is empty, or when the
  app's file is not the lock's.
- The installer (`installer.rs`) gives the file to `uv tool install --constraints` at the first install and at the
  upgrade (`uv_install`, `Tools::constraints`). A build with no such file, or an empty one, installs as it did before.
- After a failed upgrade the installer starts the environment once (`python -P -c "import dotagent.server.daemon"`:
  the code review found that `--help` imports the command line alone, not the web server or the MCP client the daemon
  needs). When it does not start, it installs the version that was there before (`put_back`), under the same constraints
  and, only when uv says that older version cannot be installed under them (it may ask for a dependency at a version the
  new pins lack), without; a version read from the environment that is not a release's (`release_version`) is not handed
  to uv; and starts it once more. The words it returns say what is left, and the marker is never changed by a failed
  upgrade, so the next start tries again.

**What uv does with a constraints file** (uv 0.13.4, the version `desktop/tools.lock` pins, tried with `pycowsay` in
throwaway tool, bin, cache and Python folders): `uv tool install --constraints FILE` enforces the versions (a pin to
0.0.0.1 installs 0.0.0.1) and honours `; marker` suffixes (a pin for `sys_platform == "linux"` is not applied). It
**ignores the hashes**: a constraints file with a wrong `--hash=sha256:000...` installed the package all the same, also
with `UV_REQUIRE_HASHES=1` and `UV_VERIFY_HASHES=1`, and `uv tool install` has no `--require-hashes` or
`--verify-hashes` (only `--require-build-hashes`). So the file pins versions only and has no hashes; a file on PyPI
replaced under the same version number is not caught, and the docs say so.

Once the app is built and checked, the release removes the file from the checkout, so a development build made after
it carries the empty stand-in, not that release's pins (the code review).

**Checked.** `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` (86 tests) in
`desktop/src-tauri`, with new tests for the arguments at the install and at the upgrade with and without the file, a
development build's empty stand-in, and the way back after a failed upgrade (the environment still starts and is left;
it is broken and the older version is put back under the constraints; the constraints conflict and it is put back
without them; nothing can be put back and the words say so, with the marker left). `tests/unit/test_installer_files.py`
keeps `tauri.conf.json`, `build.rs`, the installer's constant and the order of `release.sh` equal (the file is made
before the app is built and compared with the lock before it is notarized). `bash -n desktop/release.sh`; the release
itself, the installer and `fetch-tools.sh` were not run.
