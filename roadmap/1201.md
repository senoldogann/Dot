### 1201. A run on the Claude plan is told to look a tool up before it first calls it, rather than guess its parameters

**Status: done (2026-11-16).** Dot's record showed `browser_find: Invalid arguments for browser_find` three times,
all in runs on the owner's Claude plan (`claude_code:sonnet`). The one whose call is still in the record sent
`{"query": "message body text"}`; `browser_find` takes `text` (and `limit`). The same run called `search_files` with
`query` too, which takes `pattern`. Since item 1053 the program puts only the door's tools' names in the prompt and
the model looks a tool up with `ToolSearch` when it needs one, but nothing told it that a tool it has not looked up has
parameters it does not know: it called tools it knew by name alone and guessed. In the record, 6 of 262 calls of runs
on the plan were refused for their arguments, against 10 of about 6,200 on Dot's own loop, 15 times the rate.

The prompt of a run on the plan now says that only the tools' names are in it, to look a tool up with `ToolSearch`
(`select:mcp__<door>__<tool>`, several at once) before its first call of it, and to call it with the parameters its
definition names, never guessed ones. The refusal itself already named the valid parameters, so a run lost one step,
not its work; it now should not lose that step.

Checked with a unit test of the prompt's words (`test_the_prompt_tells_the_model_to_look_a_tool_up_before_it_calls_it`),
which failed before the change. Whether the rate falls is to be read in the record after the change is live: the
`tool_result` events of runs on `claude_code:*` that begin `Invalid arguments for`.
