### 648. Web-research 1.4.8 in Dot: an empty Google answer no longer rests Google

**Status: done (2026-10-25).** The dot-0b session released web-research 1.4.8 (web-research PR #17, merged as c6a03b0,
tag v1.4.8, on PyPI). This item pins it with the lock.

**What 1.4.8 brings (its author's account).**
- **Google rests only after a bot check.** Every empty answer of Google used to raise an error whose words held "bot
  check", and the search took that for a wall. One slow page, or a query that found nothing, rested Google for ten
  minutes, or up to an hour when it came again. On 1.4.7, the last 4 of 23 searches in a chain failed for that reason
  while DuckDuckGo refused and Yahoo answered HTTP 500. Now only a backend that saw a CAPTCHA or "unusual traffic" sets
  the wall (`GoogleSearchBlocked.wall`). Any other empty answer is `no_results`, an ordinary failure, and three of
  those in a row rest Google.
- **D1 of item 638's security review.** A DuckDuckGo result's date is read only from DuckDuckGo's own span after
  `a.result__url`, and only when that span is the stamp alone. A site can no longer pass off a date in its shown address
  as DuckDuckGo's. The lite page's `span.timestamp` gets the same check.
- **Tooling with no effect at run time:** the provider evaluation script and its queries, and a CI wait for the first
  Chrome.

**What changes for Dot.** Its dependencies, the `WEB_TOOLS_*` names Dot sets and the tools' arguments are those of
1.4.7. A Google failure that is not a bot check now reads `no_results` in `tried[].reason` and in the error's `detail`.
Dot reads neither: the model reads the error.

**The change.** `pyproject.toml` pins `dotagent-web-research==1.4.8`. `uv.lock` moves that package alone, and its hashes
match PyPI's. `docs/extending.md` says when a provider rests, and gives the version, as `docs/development.md` does.

**Checked.**
- Dot's web-research tests, unit and smoke, pass on the installed 1.4.8. They cover the schemas Dot judges and the
  switches it sets.
- The installed package carries `GoogleSearchBlocked.wall` and DuckDuckGo's `_shown_date`.
- **The independent security review** REVIEW.md asks for a dependency read the 1.4.7..1.4.8 diff by its code. It
  took 13 tool calls and found no blocker.
  - The date fix held for both DuckDuckGo endpoints across 10 crafted inputs.
  - The new scripts are in the sdist only. The tool surface is unchanged, and the lock and `requires_dist` match PyPI.
- **One low finding went to web-research 1.4.9.** A bot check that only headless Chrome or the HTTP path saw does not
  set `wall`: the first sets its own hour of rest and returns nothing, and the second swallows a 429. Google is then
  asked twice more before three failures rest it. That holds on an Intel Mac, or where Camoufox's browser is not
  downloaded. Camoufox and the visible Chrome do set `wall`.
