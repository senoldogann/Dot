### 621. Dot's own vault of logins, cards and contacts

**Status: built (2026-10-24), narrowed by the owner's decision of 2026-10-25, not pushed.** It waits for the owner's
look and for an independent `/security-review`, as REVIEW.md asks of what it lists under "Always needs a human": this
item changes `secrets.py` and the shell guard (`policy/shell.py`), and adds the Keychain layer, the routes and a
second source of logins that hold credentials. The owner showed another assistant's Settings › Vault and asked for
"the same, integrated into Dot, working dynamically and solidly", and for everything to be easy "even for someone who
knows nothing about software". It is a page, **Settings › Vault**, with a tab for each kind (All, Logins, Cards,
Contacts) and its count, a search, and a **New item** menu (Login, Card, Contact, Import from CSV…); a dialog for each
kind; and, for a run, a tool that fills a login into a page and one that lists the contacts, without the model ever
seeing a secret. Dot's own vault is a second source of logins beside 1Password (item 493), filled the same way. **A
card is kept, shown to the owner by the eye, and filled into no page.** The first build filled a card too; the owner
took that out of this item (**What left the item**), and **Left for later** says what a card fill needs to be safe.
The contract below was written before the code, as item 540 asks, and is rewritten here as the item stands: what must
hold, where it is held, and what only asks.

**What Dot keeps, and where.**

| What | Where |
| --- | --- |
| A login's password and notes; a card's number, expiry, security code and name | the owner's macOS login Keychain only: generic password items of the service `dot-vault`, the account being the item's id, one item for each vault item (its secret parts as one JSON document, in base64) |
| A login's website and username; a card's brand, last four digits and nickname; a contact's fields (and the billing address of a card, which is an address as a contact's is); every item's kind, label and dates | Dot's database (`vault_items`): what a list needs and no more |
| Anything else | nowhere: not in a log, an event, a run's record, memory, a config file, `.env`, the shell's environment, a file, an upload kept for the import |

**What the contract does not promise.** Dot's tools and its policy keep the vault's values from the model, as they
keep Dot's own keys: the Keychain does not stop a program of the run's. A run that runs code of its own with the
owner's rights (`python3 -c`, `node -e`, a script it wrote) can ask it for `dot-vault` as it can for `dot-agent` and
`dot-oauth`, since an item written through `security` is read by any `security` process without a question and the
sandbox does not stand in its way. The shell guard reads the command `security` (refused) and the name `dot-vault` in
a line or a script (asked in every preset, as a read of a protected place is: in `auto` by the review model, and a
rule of the owner's that allows the command lets it through); it does not read a name put together from parts, a
script in a file, or a program that asks the Keychain another way, and in `yolo` it asks and refuses nothing.
`docs/safety.md` says the same. A structural stop is under **Left for later**.

**How Dot decides which tools a run has.** `browser_logins` and `browser_fill_login` while 1Password is connected or
the vault holds a login; `vault_contacts` (a group of its own, `vault`) while it holds a contact or a billing address
(`tools/browser.py` `withheld_vault_tools`, read from the database as a run starts). A run that started before an item
was added does not have them until its next one. No tool of a run lists a card or fills one.

**As built.**

- **Keeping an item.** `vault/items.py` `VaultItems` is the one door: `create` writes the Keychain first and the
  record after, and takes the Keychain item back when the record cannot be kept; `update` keeps what the request
  leaves out, in the record and in the Keychain, and puts the Keychain back as it was when the record cannot be
  changed (a card's label names its last four digits, so the number the Keychain holds is never one the label does not
  name); `remove` takes the Keychain item first. A change takes the lock of its item, and the lock is dropped when the
  item is removed and when a change or a removal finds no such item, so the locks do not grow with every id a request
  named. A card's number is stored as digits, its expiry as `MM/YY`; the label of a card is its nickname, brand and
  last four digits, of a login its site. `vault/secretstore.py` keeps at most 3,000 characters of base64 for an item
  and refuses an account (an item's id) the prompt would split; `said()` cuts every run that could be a value out of
  what `security` says before an error keeps it. `store/db.py` has the table `vault_items` and `store/models.py`
  `VaultRecord`. An import keeps its logins 40 at a time (`put_many`: one run of `security -i` for each batch), so a
  Keychain that refuses part way costs one batch and the report says how many went in.
- **The rules of a card.** `vault/cards.py` and `static/js/vaultcard.js` carry the same rules (the page checks as the
  owner types, the daemon again at the save): 12 to 19 digits, Luhn's check digit, the brand by its first digits
  (Visa, Mastercard, American Express, Discover, Diners Club, JCB, UnionPay, Maestro, Mir, Troy), the expiry written
  as `08/29`, `8/29`, `08 / 2029` or `0829` and good to the end of its month, at most 25 years ahead, and a security
  code of three or four digits. A card's nickname and a contact's label hold no run of twelve digits or more.
- **The import.** `vault/csvimport.py` tells the export by its header row, reads up to 20,000 rows, and leaves a row
  out for no website, no password, an address that is not a web page (`android://…`), a kind that is not a login (a
  card, a note), a password or username too long, or a login already there (by site and username, in the file or in
  the vault).
- **A card's photo.** `vault/ocr.py` runs Vision's `VNRecognizeTextRequest` (accurate, no language correction, which
  would change digits) over the picture in memory and takes the number that passes its check digit, the expiry on a
  line that says valid thru or expires, and the last line of capitals that is no brand word, for the dialog to fill in
  and the owner to check. It never reads more than 12 MB.
- **The tools.** `browser_logins` lists the logins of 1Password and of the vault in one list (a login of the vault is
  titled by its site and username, so that two of one site are told apart; the username is no secret in Dot's rule,
  item 493); `browser_fill_login` fills from either, and says which in its question; `vault_contacts` lists by id and
  label, with the fields. The prompt has a line for each of the tools a run has (`agent/prompt.py`), `loop.py` drops
  the tools of a vault that holds nothing (`withheld_vault_tools`), and `vault_contacts` is the group `vault`.
- **The policy.** Nothing in `policy/types.py` or `policy/engine.py`: a login of the vault asks as 1Password's does
  (`vault_fill`, item 493). `policy/shell.py` asks about a line that names `dot-vault`. `gate._refuse_carried_secret`
  judges by `known_secrets(filled=False)`; `secrets.hold_filled` notes a filled value for the masks.
- **Who asks for what Dot holds (round 5).** `known_secrets(*, filled)` has no default, so that mypy names every
  caller and each says which it is. The 48 calls (45 functions) are, by what they do: **masks** (`filled=True`: a
  reply, a summary, a stream, a record of a step, the tail of a log, the errors of a server, the messages to the
  phone, a skill a model wrote) 23 calls; **refusals** (`filled=False`: `memory_save` and `memory_update`, a pin, the
  lessons, the gates of the harness text and of the owner section in the reflection, the harness step and the
  proposer, the harness commands and routes, the checks of what the harness roles write, the owner's words for a
  skill, the export of an agent) 19 calls; **both** (refuse by the first, mask by the second: the gate of item 525,
  the loop's start of a run, the owner's words for a skill) 6 calls in 3 functions. What a refusal no longer stops is
  masked where it is stored or shown, once, at the place every such text goes through: `memory.service._checked_text`
  (a note is written there by a tool, a lesson, a pin or the owner, and is embedded from there),
  `harness.service.given_text` (the one way a stored habit reaches a prompt, a probe or a role),
  `memory.service.owner_prompt_lines` and `templates.agent_file`. `secrets.mask_filled` (in memory, no file read) and
  `core.text.mask_known` (the values alone, without `redact_secrets`' patterns) are the masks.
  `tests/unit/test_known_secrets_callers.py` reads the source and holds who asks which list, so that a new caller, or
  one that changes its list, is a line a review reads.
- **The browser.** `driver.fill_login_field` types a part after the checks of 493's (the field's own document judged
  by its address, a password into a password field alone, never a form that sends by GET, never an element that is
  edited) and tells `typing` the address of the document that holds the field, so that the value is scoped to its
  origin; `session.fill_from_vault` holds the value among those masked for the chat, kept out of the addresses a page
  sends, and marked again (`Tab.filled_values`), and shows the view of the page with every field Dot filled hidden.
  `capture_lines` hides such a field in every mode, `yolo` too: **this changes item 493's views for a login as well**
  (a filled login now reads `[hidden]` in a view where `yolo` read the masked text), and the text that masks a value
  in a result is now `[filled from your vault]` for both sources. A form with no method is a form that sends by GET: a
  password or a code is refused in it now, **which narrows item 493's 1Password fill as well** (a login form with no
  `method`, which a page of scripts often has, is refused and the owner types it; a field in no form keeps the guard
  of Dot's Chrome). `session._judge` is told the document that sent a request (`sending_document`: the Fetch session
  names it for the main frame's requests, the route names it from the request's frame) and whether the request
  navigates a tab's main frame.
- **The routes.** `server/routes_vaultitems.py`: `GET /api/vault/items`, `/counts` and `/items/{id}`, `POST
  /api/vault/items`, `PUT` and `DELETE /api/vault/items/{id}`, `POST …/{id}/reveal`, `POST /api/vault/items/import`
  and `POST /api/vault/card-photo`; `VaultRefused` (403) is what a reveal from another address meets.
- **The page.** `views/vault.js` (the tabs with counts, the search by every word of what a row says, the New item
  menu, Edit, Delete after a question, the report of an import), `vaultforms.js` (the three dialogs: the eye asks the
  daemon for a saved secret only when it is pressed, a saved secret left alone is kept, one shown and emptied is
  removed), `vaultitems.js` and `vaultcard.js` (pure), `countries.js` (the list of a contact's country) and the tab in
  `settingstabs.js`, with its count in the settings' nav and list. `formDialog` (item 615) got `valid()` (the main
  button is off while the form is not good), `revalidate()` and `accept(control)` (a value the page fills in, a secret
  the eye brought, is not a change that Cancel asks about). A secret the eye hides is out of the page's text (the
  notes hold no text while hidden). The name on a card has an eye as the security code has, so that a saved name can
  be read, changed, or removed by emptying it (the dialog sent a name only when it was not empty, and could never take
  one away). The page, its menu, its dialogs and the question before a delete are in the words of item 625, and a test
  of the page opens each, wide and on a phone, and finds none of the words of the program.
- **A file that is not there is no stand-in.** `security add-generic-password` given a keychain file that does not
  exist does not fail: it keeps the item in the default keychain, the owner's login keychain (a probe of this build
  left one there, and it was removed and checked gone). So `LoginKeychain._run` checks that the file exists before it
  starts any process (`put`, `put_many`, `get` and `remove` alike), and `test_vault_keychain.py` proves it with a stub
  that fails the test if a process starts. The smoke tests' `DOT_KEYCHAIN` (`tests/smoke/conftest.py`) names such a
  path, so a smoke test that forgot to stand in for the vault is refused and not let through to the login keychain. A
  keychain that refuses (locked, or a prompt left unanswered) now says so and what to do: unlock it and answer its
  prompt.

**What the reviews found, and where each went.** The pre-push review and the independent security review read the
first build and the rounds of fixes after it. What they found of a login, an item, the page and the eye is fixed in
what stands, each with a test of the repository that fails without the fix; what they found of a card fill left with
it.

- **After the first two reviews.** A part of a card went into a field the page called `cc-name`, `email` or `tel`
  (H1), a card's question named fields with characters that draw as nothing, and a page could echo a card's expiry:
  all of the card fill, gone with it. The bullet about item 628 (H2) was corrected. For a login: a tab that went back
  brought the value back into a new document, unmarked (`autocomplete="off"` and `remark_held`); a form with no method
  sent by GET and put the value in the address (refused now); Chrome's profile held what was typed in its session
  files (`clear_session_files`, and a test that closes Chrome and searches the whole profile as UTF-8 and as the
  UTF-16 of its session files, with a control that is found); a run could read the vault by an indirect `security`
  call (the shell guard asks, and the safety page says what it does not read); an address Python cannot read failed a
  save with a 500 that quoted it, and one such row stopped an import (`hosts._split` reads none); an import that
  stopped part way left items in the Keychain with no record (`VaultItems._take_back`); a secret the eye showed could
  be in a screenshot of the Mac (row 7).
- **After the third review.** An element that is edited (`contenteditable`, or a `role=textbox` box) took a password
  or a code and showed it in the view with nothing to cover it (`_NOT_A_FORM_FIELD`); `remark_held` looked into every
  frame of the tab, and a frame of another site that planted fields of candidate values read which Dot marked (row 5);
  the guard of addresses refused in every tab of the browser, so a page of another site found a weak password in 12
