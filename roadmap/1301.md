### 1301. A file git runs as code is asked about when a file tool writes it, and git's output and command options are judged

**Status: done (2026-11-22), reduced to its bounded parts after three BLOCKed review rounds.** The review of the shell
guard on commit 688f63322 found two ways a line that the guard read as `safe` or `low` made the next git command run
code the line wrote. Each of three review rounds then found a new spelling of the first (a shell line that writes into a
git directory: `cp -t`, `mv`, `tar -C`, `rsync` source folders, a global `--bare`, `--git-dir`, globs such as
`proj/.gi?/config`). CLAUDE.md says to take the structural option or split the change after three BLOCKs and not to
chase spellings, so the open-ended shell-side detection was dropped; what is kept has no spelling problem.

Kept:

1. The file-tool side. `policy/paths.py` has `runs_as_git_code(path)`: a git directory's `config` and `config.worktree`,
   and what is under its `hooks`; a git directory is a `.git` folder (also a submodule's `.git/modules/<name>`) or a
   folder that holds `HEAD` and `objects` on the disk (a bare repository); the data folders `refs`, `objects` and `logs`
   hold none. Every component is matched by `_named`, which takes a glob that can match the name, the `.git` component
   too (`proj/.gi?/config`). `write_action` in `tools/files.py`, which `write_file`, `edit_file`, OpenCode and the
   pipeline writes go through, makes such a write `self_change`, which asks in every mode but `yolo`. The path is the
   exact one a tool is given, so there is no spelling to chase. `.gitattributes` and `.git/info/attributes` are left
   out: they only name a driver, which the config defines.
2. The git option judgments. `_assess_git` ended at the subcommand, so `git diff --output=PATH`, `archive -o`,
   `format-patch -o`, `bundle create`, `checkout-index --prefix`, `rebase --exec`/`-x`, `bisect run`,
   `submodule foreach`, `filter-branch --*-filter` and `grep -O` wrote or ran anything as `low`.
   `_git_runs_and_writes` judges the path an option names as a redirect to it (`_writes_to`) and the command line one
   hands git (`rebase --exec/-x`, `bisect run`, `submodule foreach`, `filter-branch --*-filter`, `grep -O`,
   `difftool -x/--extcmd`, `--upload-pack`/`--receive-pack`) as `_assess_all` does the same line under `bash -c`.

Dropped: the shell-side detection of writes into a git directory (`_writes_git_code`, `_copies_contents`,
`_copies_a_git_folder`, the git-directory use of `_copy_ends`, `ShellScope.git_dirs`, `_made_git_dirs`, the bare
repositories a line makes, `lands_as_git_code`, `is_git_directory` and the tests only they had).

The approach: what must hold stays with the sandbox and the guard's questions; the guard reads by structure (where an
option puts a file, which options carry a line), not by lists of spellings. `git rebase -i`, `git bisect start`, a diff
into a workspace file and `git commit` keep their verdicts (`tests/unit/test_shell_guard_ordinary.py`).

Checked: `tests/unit/test_shell_guard_git.py` (the file tools ask for the paths that git runs, including globs in the
`.git` component, a bare repository on the disk and submodules, and for nothing else in a repository,
`test_the_file_tools_ask_for_what_git_runs_and_for_nothing_else_in_a_repository` and

Not covered, decision needed: a shell line that writes `.git/config` or `.git/hooks/*` by a redirect or a copy (`echo
... >> .git/config`, `cp evil .git/hooks/pre-commit`, `tar -C`, `rsync`) is still judged as any workspace write: item
1301 first tried to read those lines, and three reviews each found a new spelling of the same class (`cp -t`, `mv`,
`tar -C`, `rsync` source folders, a global `--bare`, `--git-dir`, a glob such as `proj/.gi?/config`), so the
shell-side reading was dropped instead of chased. Closing the class needs the sandbox to deny writes to
`**/.git/config` and `**/.git/hooks/**` for commands that are not git, or a write allowlist. That is a separate
decision for the owner: it can break `git clone`-style flows run through other tools.
