### 508. Questions that do not stop the work

**Status: done (2026-10-21).** The owner asked that a run which waits for their answer, or for a terminal's output, goes
on when the wait is not critical, reads the output when it comes, and shapes the work by the answer when it comes. A run
the owner started stopped at every question it asked (`ask_user`) for up to `approval_timeout_s` (15 minutes), as the
owner had decided on 2026-10-09 (item 10: a question is left only where nobody answers during the run); this item
changes that decision at the owner's word. **As built.** What `ask_user` does in a run is an `AskMode`
(`tools/context.py`): `leave` where nobody answers during the run (as `[agent] questions` says), `wait` in a run of a
`dotx` command, which no other process can reach while it works, and `choose` in a run of the daemon the owner can
answer (`question_mode`, `RunManager.answers_reach_runs`). Where the run chooses, `ask_user` takes `wait`: with it the
run waits for the answer as before; without it, the default, the question is left on the chat as a left question is
(`question_left`, the card under "Dot asked you"), the run is told that it goes on and must not guess the answer, and
the owner's answer comes to it through the path a left question's answer already takes (`RunManager.decide` →
`_carry_on`): at its next step while it works, as their instruction that clears no mark of untrusted content, as a
waited answer does not (`vouches` is false for a run that can ask, so the run's choice to wait never decides what the
answer does to its trust), or, once it has ended, as a new run on the chat. A step that only leaves such a question does
not count as acting (`_acts`), so text replies around it still end a task run. The system prompt of such a run says when
to wait, and the stall ladder's last question asks with `wait`. A run of a message sent with Plan first (item 318) waits
for every answer, whatever its call says, as it acts only once the owner agrees. For a long command, the shell tool now
sends one that takes minutes to a background terminal when there is other work to do, not only past `timeout_s`; its end
is told to the run at its next step (item 229), which reads the output then. The questions of the policy (approvals) are
not changed: they wait as before, and with `[policy] unanswered = "park"` a step nobody answers is kept (items 482-485).
Tests: `tests/unit/test_progress.py` (the mode by run), `tests/unit/test_run_modes.py` (the prompt line),
`tests/smoke/test_left_questions.py` (a question without `wait` in a run the owner watches goes on and its answer
reaches the same run; with `wait` it waits; text replies around left questions still end the run in either mode); the
tests whose runs wait for a question ask with `wait`. Docs: autonomy.md, safety.md, runs.md.
