### 1053. A run on the Claude plan looks its tools up instead of reading them all first

**Status: done (2026-11-08).** The second cause of item 1052's wait for a chat's first word on the owner's Claude plan.

A Claude Code run was given every tool of its mode through the door, 296 on the owner's Dot with their MCP servers,
about 160,000 tokens of definitions before the first word; Dot's own loop starts with the core group and opens the
others on `use_tools`. Measured on 2026-11-08 with Dot's `ToolBridge` and `claude_argv`, `claude` 2.1.319:

- MCP's `notifications/tools/list_changed` does not reach the model within its turn: a tool added after `use_tools` was
  called was "not available", so the door cannot open groups as Dot's loop does.
- Claude Code's own search of a server's tools (`ToolSearch`, `ENABLE_TOOL_SEARCH=true`) puts the tools' names in the
  prompt and their definitions only when the model looks one up: 296 tools, 10,800 tokens written to the cache instead
  of 99,000, the first word in 1.2 s (480 tools: 16,700 instead of 158,000, 1.1 to 1.5 s); a task that needed `list_dir` looked it up and called it through the door.

So a run's program has one tool of its own, `ToolSearch` (`--tools ToolSearch`, allowed with the door), and
`init_problem` takes it, and nothing else, beside the door's tools; it reaches the door's list alone. A look-up is not
a call of Dot's: it is not in a step's `tool_calls`.
