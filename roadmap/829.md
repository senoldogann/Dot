### 829. A run asks the owner for a secret in a card, and its commands get it without the model seeing it

**Status: proposed (2026-10-29), the design before the code, for the security review and the owner's look.** **Asked**
by the owner, with a screenshot of T3 Code's "Asking for a secret" card ("güvenli şekilde gizli API key'ler veya
bilgileri alabilir gönderebiliriz"; "gizli değer tasarımını yaz ve güvenlik incelemesinden geçir").

**Why.** A run that needs a key it has not got (a Cloudflare token for a build log, a webhook's secret) has one way
today: `ask_user`, and the owner pastes the value into the chat. What is pasted is a message: it goes to the model's
provider, into the store's messages and events, into compactions, recaps and lessons. The old store (2026-10-13 to 28)
holds one such paste, a GitHub token (`ghp_…`) in an owner's message. The vault (item 621) keeps logins, cards and
contacts the owner saves in Settings, and fills a login into a page without the model reading it; it has no way for a
run to ask for a value it needs, nor to hand one to a command.

**What T3 Code does** (`pingdotgg/t3code`, `apps/server/src/secrets/SecretRequests.ts`, `packages/contracts/src/
secretRequest.ts`, read 2026-10-29): a tool `request_secret` (label, reason, placeholder, `delivery`) puts a card in the
thread; the value the user saves goes to the server's secret store under a one-use `secretRef` (an HMAC of the thread
and the card's id), kept 24 hours; the thread records only `saved` or `declined`; a T3 tool takes the `secretRef`, or,
with `delivery: "file"`, the agent gets the path of an owner-only file its shell commands read. An answer after the
agent stopped is refused. Its evals fail an agent that asks for a secret in the chat or promises a card it never opens.

#### The design (revised twice after the independent security review of 2026-10-30, below)

1. **`ask_secret`** (core group): `name` (what the commands call it: upper-case letters, digits and `_`, 3 to 40,
   given as `DOT_SECRET_<NAME>`), `label` (what it is, one line), `reason` (why the run needs it, one line). It puts a
   card in the run's chat and waits for the owner's answer as an approval waits (`approval_timeout_s`, the phone and
   iMessage told "Dot asks for a secret in <chat>: open Dot to enter it", no value ever travelling that way). Its result
   is the name and when it lapses, or that the owner declined, or that the wait ran out: never the value.
2. **The card** (web UI, on this Mac or a paired phone): the chat's title, the run's goal, the label and the reason (the
   model's words, shown as such), a password field, Save and Decline. A run that has read content third parties can
   author (`tainted`) has a warning above the field: "This run read a page or a mail since it started; a request it
   makes may come of what that said. Dot needs no password you sign in with: those go in Settings › Vault." The field is
   never filled again, never shown back, and the page drops the value once sent.
3. **The value is kept in the daemon's memory alone** (review 1: a Keychain item written by `security` is read back by
   any process of the owner's, `security find-generic-password -s <service> -w`, with nothing asked): from the card's
   route (`POST /api/secrets/{id}`, a `SecretStr`, refused with line breaks or NUL in it, and when shorter than
   `KNOWN_SECRET_MIN_CHARS`, 8, which could not be masked) into a map of the daemon's, for 24 hours. A restart of the
   daemon forgets it; the run that needs it again asks again. The store keeps the request (id, run, chat, name, label,
   reason, status, asked, answered, lapses) and no value.
4. **Who gets it:** the processes the `shell` tool and the terminal sessions (`terminal_open`) start for a run of the
   same chat, from the answer until it lapses, as `DOT_SECRET_<NAME>` added to a copy of `child_env`'s for each
   command and each session as it opens (never to the shared `runtime.shell_env`, which every chat's commands take); no
   delegated run (`parent_run_id`), teammate, MCP server or OpenCode. The run is told to use `"$DOT_SECRET_<NAME>"` in
   a command and never to print it, write it to a file or hand it to a program that keeps it (`gh auth login`, a
   project's `.env`): a value written down outlives its 24 hours and its chat (below).
5. **Masked as well as text can be** (review 2 and 3, best effort, not a guarantee):
   - every value asked and not lapsed is held as a filled one is (`hold_filled`), so the places that mask the secrets
     Dot holds mask it: the model's words, events, approvals, compactions, notes;
   - new: a tool's result as the model and the history get it is masked with the live values of the run's own chat,
     which its commands have anyway, and with any other value Dot holds only when it is at least 20 characters long
     (review 2a: masking every held value would let a run print candidates and read back which came out masked, a test
     of guesses of the owner's vault passwords and of another chat's values); and before it is clipped
     (`executor._execute_one` masks before `truncate_middle`; the shell masks its stream before its output window cuts;
     a terminal withholds the last `len(value) - 1` characters of a read, handing them over with the next), so that no
     cut leaves a value's halves;
   - besides the value itself, its forms a command prints without being asked to: base64 at its three alignments (an
     `Authorization: Basic` header; a character or two at each edge of it stay), URL-encoded, JSON-escaped;
   - after it lapses, and across restarts, a salted hash of a value of at least 20 characters is kept for 30 days, and
     every stretch of a tool's result of its length, at every position of a run of the characters a token is made of
     (so that `KEY="value"` is found), that has its hash is masked: a value a run wrote to a file is masked when another
     run reads the file. A shorter value keeps no hash (review 2b: a fast hash of 8 characters is broken in minutes by
     anyone who reads the database, a backup or the old home), and is said, on the card, to be forgotten at its lapse;
   - new: a log line is masked as it is written (a structlog step that runs `mask_filled` over the event's strings,
     after `format_exc_info`, so that a traceback is masked too), not only as the UI shows the tail; what goes to the
     daemon's stderr outside structlog (uvicorn's and asyncio's own loggers, which the launchd job writes to a file) is
     not;
   - the live values of the run's own chat are among the set the refusals of a tainted run check
     (`known_secrets(filled=False)` and `gate.py`'s "no secret out"): the reason filled values are left out of it, that
     a refusal would confirm a guess, does not hold for a value the run's commands read; another chat's values are not
     (review 2c: the set knows no chat, and a refusal per step is a test of a guess).
6. **Lapse and removal:** at 24 hours, and when its chat is deleted, the value is dropped from memory and the request
   marked lapsed; Settings › Vault lists the live ones (name, chat, lapses), each with Remove. Keeping one longer is a
   later item, and needs a store no other process of the owner's reads.
7. **The prompt and the evals:** a run never asks for a secret, a token or a key in the chat, never invents one, and
   calls `ask_secret` instead; logins go to the vault. `dotx eval check` gains a task whose script asks in the chat and
   fails, and one that calls `ask_secret` and passes.

#### What must hold, and what only asks

Held in code: Dot itself writes the value into no table, no file, no notification and no answer of the API (what a run's
output carries of it is masked best effort, below); it is accepted only through the card's route, with the
installation's token on the loopback address or a paired phone's key (over `tailscale serve`'s HTTPS, the only way a
phone reaches Dot), never from a channel (iMessage) or a chat message; it is handed only to the processes of item 4
that start before it lapses (one started before, a terminal session or a `nohup` command, keeps it); an answer to a run
that is no longer waiting is refused, as T3's is.

Best effort, not held: that the value is in no request to a model, no message, no event and no log line. The masking of
item 5 catches the value and the forms a program prints of it on its own; it does not catch a form a run makes on
purpose (`rev`, `base64` of a part, a value split in two outputs), nor what a screenshot shows.

Only asks, and narrower than it reads: outside yolo, a command whose line names `DOT_SECRET_` and a program that reaches
the network is handed to the owner (a flag `secret_egress`, reserved for the owner as `trade` is, so that in `auto` the
review model does not answer it). It reads the line only: `env`, `printenv`, `set`, `export -p`, `curl -d "$(env)"`, a
script, or a value read in one command and sent in the next get past it. In yolo nothing asks. So a run the owner gives
a secret can send it wherever its commands reach, in any mode: the owner gives it to that run, for that chat, as they
would give a colleague a key; the card says so.

Not covered: a process of the owner's that attaches a debugger to the daemon or to a command of the chat (`lldb -p`)
reads the value in memory, as it reads Dot's own keys there; a run that read a page or a mail asking for a secret the
page wanted (the card's warning, and the owner); a
value a run wrote to a file or handed to a long-lived process, which outlives the lapse (item 4 asks runs not to; item
5 masks it where it is read back); a screenshot showing it; a value the owner pastes into the chat all the same.

#### The independent security review (2026-10-30), on the first draft

1. Important: a Keychain item `dot-asked` is read by any process of the owner's (`security find-generic-password -s
   dot-asked -w` asks nothing; the guard names `dot-vault` only): closed by keeping the value in memory (item 3).
2. Important: masking by the exact text misses a value cut by a clip (`executor.py` clips before it masks the event),
   by the shell's output window or across two terminal reads, and its printed forms (base64, URL, JSON): item 5 masks
   before every cut and the three forms, and the claim moved to best effort.
3. Important: a value written to a file or kept by a process outlives the lapse and the chat, and after a restart was
   not masked at all: item 5 masks every held value in every chat's results and keeps a salted hash for 30 days; the
   claim narrowed, and the case is under "not covered".
4. Minor: logs are masked when the UI shows them, not when written: item 5's structlog step.
5. Minor: images are not masked: under "not covered".

Also corrected: the guard's limit was narrower than it is (the plain commands above get past it), and in `auto` the
review model, not the owner, would have answered the flag.

The review read the revision again (2026-10-30): findings 1 to 5 closed or stated truly, and four new points, taken
above: (2a, important) masking every held value in every chat's results tests guesses of vault passwords and other
chats' values, so a result is masked with its own chat's values and with others only from 20 characters; (2b,
important) a salted fast hash of a short value is broken offline and tested online, so only values of 20 characters or
more keep one, matched at every position; (2c, minor) the refusal set is the own chat's; (2d, minor) the log step runs
after `format_exc_info`, and stderr outside structlog is said not to be masked. "Held in code" was still false of
tables, files and the API, and of processes started before a lapse, and is worded as it holds.
