### 1362. A delegated run starts with the state its parent already measured

**Status: done (2026-11-23).** From the owner's reading of GLM-5.4's Loop Transformer and a public write-up on agent
teams (`workspace/glm-54-loop-dot-cikarimlari.md`, move P0-2): a loop pays when the second pass sees what the first
learned and does not rebuild the world to see it. Dot's in-run loop already does that — the goal check reads the plan with the
evidence of each closed step and the facts the harness measured — but a delegated run started from its goal alone
("A child agent starts with your prompt and nothing else"), so it read the same files and ran the same checks its parent
had just run, and the parent paid to write that state out again when it did.

What changed: `delegate` hands the child, under its goal, the state its parent has already measured (item 1362,
`tools/delegate.py`): the parent's plan with the evidence of each closed step, the files it wrote or edited (the last
12), the newest result of each check it ran (4), and the failed calls it left unresolved (4) or resolved (3), each line
capped and the whole pack at 3000 characters. It is read from the run's own plan event and the facts the harness
measured — the model does not write it out again — and it says so: the child is told the state may be stale and to check
a file before relying on it. The plan is read once for the pack and for the step the call names.

Checked: `tests/unit/test_delegate.py` (four tests: the pack carries the plan, the written files, the checks and the
failed calls both ways; a parent with nothing measured hands over nothing and no opening; the pack keeps the newest
files and checks and stays at its size; a plan of 12 long steps does not crowd out the checks and the failures). The
existing five tests of the tool pass.
Not done: `message_agent` and work orders still start from their brief alone; the pack carries what the facts measured,
not the parent's continuity ledger.
