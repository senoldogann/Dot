### 2071. A message that leaves its choices out starts on the chat's: the chosen model is the one that runs

**Status: built (2026-11-28).** The owner's bug of 2026-11-28: "I chose claude-haiku-5-5, not DeepSeek." Their chat with
the JobHunter agent kept `{"model": "anthropic:claude-haiku-5-5", "effort": "medium", "approvals": "yolo", "goal_mode":
true}`, yet its three runs of that night (two follow-ups and a resume) ran on `opencode_go:deepseek-v4.1-flash`, the
daemon's `[models] main`.

Why: the iPhone sends a follow-up to `POST /threads/{id}/queue` with its text and key alone (`QueueMessage`), no choice.
The daemon took a choice left out as "the configured one", so the run named no model; the agent's own model was empty
("Main model"), and the run started on the main model, while the phone's inspector showed the chat's choice (Haiku)
under **Model for this chat**. A resume (`POST /runs/{id}/resume`) took the resumed run's model, DeepSeek again. Nothing
swapped a model the request named: no fallback, no routing by kind, no missing key was involved (the earlier Sonnet run
of that chat called the Anthropic API and ended on the goal check).

What changed:

- `agent/chat_choices.py`: `message_choices` gives a message each choice its request left out (pydantic's
  `model_fields_set`) from the chat's kept choices; a choice it names, `null` (the daemon's default) among them, stays
  its own, and a named model brings its own level and speed. `POST /threads/{id}/queue` and `POST /runs` with a
  `thread_id` apply it before anything else reads the request, so the chat's model wins over the agent's own and over
  `[models] kinds`. A level taken from the chat is given only when the model the message starts on offers it (as the
  composer gives it, item 116): the level a chat kept from its first run is the one that run resolved, which a model
  without levels refuses (`RunManager.chat_message_choices`).
- `resume_choices`: a resume starts on the chat's model when the chat names another one than the resumed run (with the
  chat's level and speed), checked by `check_model_answers` first; a chat that keeps none or keeps the default leaves
  the run's own.
- A chat whose model's provider has no key refuses the message by name (`ModelUnavailableError`, as before) and queues
  nothing; the resume is refused the same way.
- The iPhone's inspector shows **Model used** (the newest run's model) in its Run section, beside the chat's choice; the
  web's run page already names the run's own model under its title.

`anthropic:` is Anthropic's paid API (`ANTHROPIC_API_KEY`); the owner's Claude plan is `claude_code:` (`claude_code:haiku`
for Haiku), run through the `claude` program.

Checked: `tests/smoke/test_chat_choices_kept.py` (a phone follow-up in Dot's and an agent's chat, a message naming its
chat with a kind named for its words, `"model": null` staying the default, a resume, a keyless provider refused): the
first three fail on main and pass here. The approval mode and goal mode are the chat's too when a message leaves them
out: two tests that sent "plan first" with no approval mode to a chat whose first run was yolo now name `ask`, as the
web's composer would send the chat's own.
