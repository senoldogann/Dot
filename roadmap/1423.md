### 1423. The hand-off state: a step only the owner can do is told by its host and a fixed line, one for a chat

**Status: done as far as the data allows (2026-11-24).** Comes after items 1420, 1421 and 1422 in the same pull request. From the research of 2026-11-23: ChatGPT's "take over" (the agent pauses at a login, a code or a
CAPTCHA, tells you, and the credential never reaches the model) and Devin's "Permission request". I read how the browser
meets such a step today before building anything.

What the code already does, and this item builds on: the policy hands a **credential** (a password or a one-time code the
run was not given, a login) and a **payment** to the owner in every mode that asks (`policy.engine.hard_stop`, flags
`credential` and `financial`). The gate asks it as an approval of severity `handoff` and the run **parks** at it: its
status is `blocked` and `approval_requested` goes out; unanswered in time the step is refused or, with `[policy]
unanswered = "park"`, kept for the owner while the run goes on without it (`agent/parking.py`, item 482); the card closes
with `approval_decided` whatever ends the wait, and a run that ends releases it (`ApprovalBroker`). That is the hand-off state of the task: a record (the approval), parked run,
a push (`approval_requested` and `question_left` are `needs_you` since item 1421) and a close. Item 1422 lists it.

What changed: a hand-off in `GET /api/needs-you` is told by the **host** of the page its step is on (`args.target`, an http
or https address; nothing else of the address, not its user, path, query, fragment or port) in a fixed line, `Dot needs you
on <host>` (`Dot needs your help` when the step names no web page or an address that cannot be read), never the step's own
summary, which carries what the page showed. **One hand-off for a chat**, the newest; the ones kept before it wait behind
it and show once it is answered, and the count counts it once. Every item (of every kind) carries `route:
dotagent://run/<run id>`. The lock-screen text of its alert is what it was (the fixed title "Dot needs your help", the fixed
line, `#/runs/<id>`), which a test now pins for a hand-off whose step names a password and a bank. `docs/phone.md` has the
contract and says what is not a hand-off.

What is not done, and what is missing (the item said to stop at what the data allows): **a CAPTCHA** is not a hand-off:
Dot passes human checks itself as a standing instruction (`docs/captcha.md`), `browser_captcha` returns text, not a state,
and making a failed check park the run would change that instruction (an owner's decision). **A login page or a second
factor that the policy does not hand over** (the run meets it, has no login in the vault or in 1Password, and `ask_user`s or
finishes) leaves no sure sign in the data: the browser tools return the page as text and the typed judge's "login wall"
estimate is a model's guess and optional, so a hand-off made from it would push the owner's lock screen for pages that are
not walls. What it would take: a deterministic sign from `browser_fill_login` ("no login to fill", "no code"), a record
that the loop closes when the run's next browser step goes through or it ends, and the owner's word on how many false alarms
a push may cost. None was built; no policy, shell guard, sandbox or approval decision was changed.

Checked: `tests/unit/test_needs_you.py` (a hand-off told by the host alone with nothing of the step, the address's user,
path, query, fragment or port, what was typed or the page's words; the fixed line when the step names no page or an
unreadable address; one for a chat, the newest; the next one showing once it is answered; gone when the run ends; the route of
every item), `tests/smoke/test_needs_you.py` (the route's shape with `route`), `tests/unit/test_apns.py` (a hand-off's alert
is the fixed title, line and route and carries nothing of the step), `ruff format --check`, `ruff check`, `mypy src`. No
live browser or model was used.
Not checked: on a phone (no push was sent, the sender is the test's stand-in); a hand-off the browser raises on a real login
page or a real code (the tests make the approval the gate makes: a record, not the whole gate).
