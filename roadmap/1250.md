### 1250. The shell guard reads six more of zsh's ways as zsh does, and is checked against zsh itself

**Status: done (2026-11-19).** The code review of 2026-11-19 (findings K1-01 to K1-06) found six lines the guard read
wrong and passed as `safe` or `low`, while zsh ran a read of `~/.ssh` or a delete in the home folder. Each was shown
with the guard's reading alone and with zsh running `echo` in a temporary folder.

**What must hold, and what only asks.** Nothing here moves into the kernel: the sandbox does not close the home folder,
and sealing `~/.ssh`, `~/.aws` and `~/.gnupg` would break the runs that push with git over ssh or use the AWS command
line, which read those folders by design; that stays a choice for the owner (`[policy] sealed_paths`). What this item
changes is what the guard *asks*, in the presets that ask (`cautious`, `balanced`, `aggressive`). `yolo` and free mode
ask nothing new: they do not consult the guard's risk, and a tainted `yolo` run's review model already sees every step
the guard calls unreadable. So the rule is the one `docs/safety.md` already gives: what the guard cannot read is a
destructive step outside the workspace; what it reads, it reads as zsh does.

The six root causes, each closed where it lies rather than by spelling:

1. `NAME+=value` appends (K1-01): the guard kept the new part as another value of the variable. An append is now the
   old values (the line's, else the daemon's environment, else a part only the running line knows) joined with the new.
2. A substitution's end (K1-02): `_closing_paren` did not know comments or here-documents, so a `)` in either ended
   `$(...)` early and a quote after it hid the commands that followed. It now passes over a comment to its line's end
   and over a here-document's body, as the shell does, and reads `$'...'` with its escapes.
3. `cd OLD NEW` and `CDPATH` (K1-03): zsh's two-operand `cd` replaces `OLD` in the current folder with `NEW`, and a
   name that does not start with `/`, `./` or `../` is looked up in `CDPATH` too. Both places are now among the folders
   the line may be in; a `CDPATH` or an operand only the running line knows adds the home folder, as before.
4. Programs that run a line the guard did not open (K1-04): `csh` and `tcsh` (which ship with macOS) are read as the
   shells they are, a version suffix no longer hides an interpreter or a shell (`perl5.34`, `python3.13`, `bash5`),
   zsh's `-` precommand modifier is passed over, and `npx -c`/`npm exec --call`/`pnpm exec -c` read their line. (The
   report's `script -F p log rm …` needs nothing: this Mac's `script` takes `-F` as a switch, so that line runs `log`,
   as the guard reads it.) Structurally: a program the guard does not know, given `-c`, `-e` or one
   of their long forms with a value that holds a blank or a shell operator, has that value read as a command line; the
   program itself stays `low`. A single word (`gcc -c main.c`, `ffmpeg -c copy`) is no line and changes nothing.
5. Braces in the command's place (K1-05): `{rm,-rf,~/x}` is three words to zsh, not three alternative names. The head's
   braces are now spelled out into words, in order, before the command is judged.
6. `alias` (K1-06): it was a safe command whose value nobody read. Each `name=value` it defines (`alias -g` too) is
   now read as the command line it will be (as `trap`'s line is), so a later `eval x` runs nothing unread. (zsh 5.9
   parses a `-c` string whole, so a later line of the same string does not see the alias; the guard asks anyway.)

The independent security review of this item found five more of the same kind, closed the same way: zsh's `cdpath`
array (tied to `CDPATH`; its values, which the guard does not keep, stand for the home folder with the name under it),
`chdir` (zsh's `cd`), a `~` that the line's own `HOME` decides (`HOME+=/.ssh; cat ~/id_rsa`), an element of zsh's
`aliases`, `galiases`, `saliases` and `functions` tables (and their `dis_` twins) judged as the line it is, and a quote
or an escape right after `$K` that ends the name (`K=$K'sh'` read as `${K}sh`, not `$Ksh`).

**Checked against zsh itself (TS-04, 8.1 of the report).** `tests/unit/test_shell_guard_zsh.py` runs real `zsh -f` in
a temporary folder, with `HOME` there and a `PATH` that holds only recorder programs (each writes the words it was
given to a log; no real `rm` or `cat` is reachable, and the lines are given in files, never fed to a shell from the
test's own text). For the report's lines and their variants, every recorded run of a recorder that would delete
outside the workspace or read the protected folder must be a line the `balanced` preset asks about; ordinary lines
(git, uv, rg, python -c, bash -c with a readable line, an alias of a read) keep the verdict they had.

Not done here: K1-07 (the guard's own quadratic patterns, a medium finding), `printf -v`/`read` into `HOME`, and zsh's
named directories (`hash -d`), which the report lists as the documented "part only the running line knows" limit.

What may ask more in `balanced` and `cautious`: a line handed to a program the guard does not know with `-c` or `-e`
is now judged by what it does (`docker exec box sh -c 'rm -rf /app/build'` asks as `rm -rf /app/build` does), and a
shell or interpreter with a version in its name is judged as the program it is (`python3.13 -c …` as `python3 -c …`).

Checked: `tests/unit/test_shell_guard_zsh.py` (80: the report's lines and variants in real zsh, the ordinary lines,
yolo waiving them), the guard's other tests (`test_shell_policy.py`, `test_shell_kill.py`, `test_shell_release.py`,
`test_shell_senders.py`, `test_vault_shell.py`, `test_guard.py` and the rest that call `assess_shell`: 1,295 passed),
`uv run dotx eval check`, ruff and mypy.
