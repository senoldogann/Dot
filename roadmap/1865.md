### 1865. A scheduled task, a watcher's task and a helper propose what they would remember; the owner decides

**Status: done (2026-11-25).** The study of OpenClaw of 2026-11-25 (`reports/refs-2026-11-25/clawdbot.md`, item 2)
found that it keeps cron, heartbeat and sub-agent sessions out of lasting memory, by a session-kind gate. Dot had no
such rule: a schedule's run saved notes and lessons as a chat's did, and nobody watches such a run.

Approach (written before the code): a run whose origin (item 1864) is `schedule`, `watcher` or `helper`
(`store/provenance.py` `HELD_ORIGINS`) writes no lasting note on its own. Its `memory_save` keeps the note on the run as
a proposal, its `memory_update` waits as the change proposed for the note, and the lessons drawn from it stay proposed
whatever `[agent] lessons` says. The policy is not touched: the same calls are classified and asked as before, and a
yolo or free run asks nothing new and is refused nothing (the tool answers that the note waits for the owner).

Proposals or nothing, decided on the owner's data (`~/Library/Application Support/Dot`, read only, 2026-11-25): the 39
notes scheduled runs saved include some of the most handed lessons of all (zone.fi webmail's routes, handed 46 and 34
times; LinkedIn's company page, 31, 24 and 22), 14 of the 39 were handed to a later run, and 2 of them rest as repeats;
dropping them would lose the best of them. But all 282 lesson decisions stored were made by `auto` and none by the owner
on a run's page, so a proposal that waits only on the run is a note dropped in practice. So: proposals, listed on the
Memory page, where the owner looks at notes.

What changed (`memory/held.py`, `agent/held_notes.py`, `tools/memory.py`, `agent/lessons.py`, `memory/service.py`,
`store/db.py`, `store/provenance.py`, `agent/manager.py`, `server/routes_data.py`, `static/js/memorylife.js`,
`static/js/views/memory.js`):

- `memory_save` in such a run: a `note_held` event on the run with the checked words, tags, subject, the time it would
  hold and the run's mark; the same words held again are one; at most 20 a run, and the 21st is answered "Not kept"
  (the first cut answered with the 20th note's words, the pre-push review's finding); words the owner decided already
  are answered so, not as waiting. The answer says it was proposed,
  not saved, and to go on.
- `memory_update` in such a run: `propose_memory_rewrite`, the proposed change of the note (the columns item 1711's
  proposals use), shown under **Changes tasks proposed**; the note stays. A proposal keeps no days of its own: when
  `valid_days` is given the answer says the note keeps the time it has.
- `learn_from`: the lessons of such a run stay proposed (`lessons_held` in the log); `auto`'s second look and save are
  not run.
- **Notes tasks proposed** on the Memory page, `GET /api/memories/waiting`: the held notes and the proposed lessons of
  the runs of the last 30 days (the newest 40 runs that have something waiting: a run whose lessons `auto` decided
  takes no place, the second review's finding), with the task's origin and goal and "From outside content" when the
  run had read such content; Save
  (`POST /api/memories/waiting/<run>/<index>/save`, `save_replacing` as `memory_save` would have, with its tags and
  subject, unmarked: the owner vouches) and Dismiss; a lesson uses its run's lesson routes.
- Whether a run holds is read from the store (`origin_of_run`), not the model; a run id the store does not hold has no
  origin, as its notes would, and saves as before (only a tool test's made-up run id has none).

Not done: `memory_forget` of such a run still moves a note to the trash (the owner can restore it); the phone does not
list the proposals yet (`ios/` is not changed here; the API is there); proposals live in the run's events, so deleting
the task's chat drops them.

`docs/autonomy.md` says the lessons of these runs are not `auto`'s to decide.
