### 494. An MCP answer too long for one result is kept whole in a file

**Status: done (2026-10-21).** An MCP answer longer than the run's result budget lost its end: `render_call_result` cut
it with `truncate_tail`, and the model could not get the rest. A study of another agent's harness (its protocol returns
`output_file_path` and `output_length` for long tool answers) pointed at the fix, which `web_crawl` already made for its
pages. **As built.** `tools/mcp_result.py` writes an answer over the budget whole to
`<workspace>/mcp-results/<server>-<tool>-<time>-<id>.txt`; the result fences the whole lines at its start that fit and,
after the fence, says the characters, the lines, the path and the offset to read on from. An answer within the budget
writes nothing. Since a message of the owner clears the run's untrusted mark, a file of third-party content read back
later could have entered the run unmarked, as the crawl's pages could already: `tools/third_party.py` names the two
folders (`crawl`, `mcp-results`), and `read_file` of a file there, a `search_files` match there and a `shell` line that
names such a path or runs there return untrusted results. A failed `edit_file` of such a file names none of its lines in the error (an error marks
nothing). The shell check reads the words of the line, so a path it
builds otherwise is not seen (said in `docs/safety.md`). The files are not cleaned up, as the crawl's are not. Tests:
`tests/unit/test_mcp_pure.py` (the file, the shown lines, the note; no file within the budget; one line over the
budget), `tests/unit/test_third_party_files.py`, and `tests/smoke/test_mcp.py`, where the fixture server echoes 5,000
lines: the file holds them all, and `read_file`, `search_files` and `tail` of it are untrusted while `echo hello` is not.
