### 543. Teach a task writes the skill when the review model gives a list as text

**Status: done (2026-10-22).** The owner showed Dot a task in "Teach a task", pressed **Write the skill** and got "The
skill was not written: the arguments of write_playbook are not a valid verdict", every time. Read in `dotx.log` (the
`playbook_failed` events of 2026-10-21 and 22): the review model, `opencode_go:deepseek-v4.1-flash`, called the tool
with `steps` as one string (`list_type`, "Input should be a valid list"); Claude Haiku 5.5 did the same on the 21st and
left `parameters` out as well. The error said no field, so neither the owner nor the second ask could know what to fix.

**As built.**
- `agent/review.py`: `PlaybookDraft` reads `steps` and `parameters` through `_list_from_text` before it checks them: a
  JSON array written as text, or the lines of a text with the number or the bullet before each taken off (`1.`, `2)`,
  `-`, `*`, `•`), and null as an empty list. `parameters` may be left out (an empty list, as its description said:
  "an empty list when the steps name none"). The bounds are the same: a skill with no step, more than twenty or an
  empty item is still refused. The owner reads the skill before saving it, so a step the model ran together is theirs
  to see.
- A verdict that is still wrong says which fields were and how, in its message: `the arguments of write_playbook are not
  a valid verdict (kind: Field required; steps: Input should be a valid list)`, at most 200 characters, a field and its
  problem each (`_fields_wrong`). The panel's toast shows the message, the log line `review_answer_unusable` carries it,
  and the note that asks the model once more ("Your previous answer was not usable (...)") has it, so the second answer
  can be right. Every question to the review model reads the message that way, not only the skill writer.
- `docs/browser-and-computer-use.md` (Teach a task) and `docs/harness.md` say it.

**Tests.** `tests/unit/test_review_lenient.py`: the steps as numbered lines, bullets, a JSON array, lines with blanks, one
line and a bracketed text that is no JSON; the parameters as text, left out and null; the steps that stay refused (empty,
blank, null, a number, an empty list, an empty item, twenty-one lines); the writer taking a skill whose steps came as
text at its first answer (one question); a verdict that stays wrong, naming `kind` and `steps` in the error and in the
second question's prompt. Nine of them fail without the change.

Not built: an answer written in the reply's text instead of a tool call (`<<PLAYBOOK …>>` fences, seen once with Haiku
5.5 on the 22nd) is still asked for once more and not read; a text with the steps run together on one line is one step.
