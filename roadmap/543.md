### 543. Teach a task writes the skill when the review model gives a list as text

**Status: done (2026-10-22).** The owner showed Dot a task in "Teach a task", pressed **Write the skill** and got "The
skill was not written: the arguments of write_playbook are not a valid verdict", every time. Read in `dotx.log` (the
`playbook_failed` events of 2026-10-21 and 22): the review model, `opencode_go:deepseek-v4.1-flash`, called the tool
with `steps` as one string (`list_type`, "Input should be a valid list"); Claude Haiku 5.5 did the same on the 21st and
left `parameters` out as well. The error said no field, so neither the owner nor the second ask could know what to fix.

**As built.**
- `agent/review.py`: `PlaybookDraft` reads `steps` and `parameters` through `_list_from_text` before it checks them: a
  JSON array written as text, or a text of several lines with the number or the bullet before each taken off (`1.`,
  `2)`, `-`, `*`, `•`), and null as an empty list. `parameters` may be left out (an empty list, as its description
  said: "an empty list when the steps name none"). The bounds are the same: a skill with no step, more than twenty or an
  empty item is still refused. All the steps in one line are no list of them (two lines at least for `steps`; one line
  is one parameter): the model is asked once more and the answer refused after that, as a skill is not to be saved as
  one step because a model ran them together. A text that opens with a bracket, a brace or a code fence is structured
  or code: it is read as JSON or refused, as its lines would be the pieces of a broken array (a trailing comma, single
  quotes, an answer cut off) saved as steps. The owner reads a taught skill before saving it, but a learned one (the
  same `PlaybookDraft`, written after a run) is saved with no one reading it first, which the reviews found.
- A verdict that is still wrong says which fields were and how, in its message: `the arguments of write_playbook are not
  a valid verdict (kind: Field required; steps: Input should be a valid list)`, at most 200 characters, a field and its
  problem each (`_fields_wrong`). The panel's toast shows the message, the log line `review_answer_unusable` carries it,
  and the note that asks the model once more ("Your previous answer was not usable (...)") has it, so the second answer
  can be right. Every question to the review model reads the message that way, not only the skill writer. Only names
  of the verdict's own fields are said: a key the model made up (`extra_forbidden`) is its own text, which the message
  would carry, with control characters and a fence in it, into the note to the model, the toast and the tool results a
  run reads, so the place is said and the key is not (`verdicts.0: Extra inputs are not permitted`).
- `docs/browser-and-computer-use.md` (Teach a task), `docs/extending.md` (Learned skills) and `docs/harness.md` say it.

**Tests.** `tests/unit/test_review_lenient.py`: the steps as numbered lines, bullets, a JSON array (of one step too),
lines with blanks and a bracketed text that is no JSON; the parameters as text (one line too), left out and null; the
steps that stay refused (empty, blank, null, a number, an empty list, an empty item, twenty-one lines, all the steps in
one line, numbered or not, and the structured or code texts above); the writer taking a skill whose steps came as text
at its first answer (one question); a verdict that stays wrong, naming `kind` and `steps` in the error and in the second
question's prompt; a key the model made up, with a fence in it, quoted nowhere (at the top of the arguments and in the
verdict of a list). Ten of them fail on `main`, the others pin what stays refused.

Not built: an answer written in the reply's text instead of a tool call (`<<PLAYBOOK …>>` fences, seen once with Haiku
5.5 on the 22nd) is still asked for once more and not read; steps run together in one line with their numbers inside
(`1. a 2. b`) are not split; the real shape of what DeepSeek V4.1 Flash wrote is not known (the log keeps no input), so
if it was one line, the message now says `steps: Input should be a valid list` where it did not say anything.
