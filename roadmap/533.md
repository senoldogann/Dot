### 533. A script no longer reads a password a page holds, nor the cookies, and Shift+Insert is a paste

**Status: done (2026-10-22).** The audit of how Dot keeps the browser's cookies, passwords and history from a run found
that every view of a page a run reads hides the value of a password, one-time-code or card field (item 467: the
snapshot, a search, the text, a screenshot), but `browser_eval` did not: a script returns whatever the page's JavaScript
can read, a saved login that Chrome filled into a form among it, and `document.cookie` hands the model a session. The
docs said so ("a page script can still read a field's value"); a run that read a page with a sign-in form could take the
password from the page with one line.

**As built.**
- Outside `yolo` (`hides_secrets`, as for every view) `BrowserSession.run_script` is refused on a page that holds, in
  any of its frames, a field that takes a secret (`browser/driver.holds_secret_field`: `secret_selector()` counted in
  each frame, a page that does not answer in time counting as holding one). The error says why and what to do: use the
  other browser tools, which hide such values, or ask the user to take over. A frame of another origin counts too,
  though a script cannot read it: a payment provider's card field is the one place a script has no business.
- The values of the site's cookies (`context.cookies` for the address the script ran at, HttpOnly ones too) of eight
  characters or more are held for the chat as the values filled from the password manager are (item 493), read before
  the script runs and after it, so that one it deletes or overwrites is held too: no result of a browser tool of the
  chat shows them, as `[hidden]` (`vault/masking.masked` takes the word it writes, and the forms an address, a script's
  `encodeURIComponent` and JSON write a value in). The script's own value, the message and context of an error it
  threw, the address it led the tab to and the surprise that tells it, the refusal of a forbidden address (it names the
  address, which a cookie may be in) and, through the tool wrapper `masked_tool`, everything a later tool reads, a page
  or an address a script wrote a cookie into included. A call that cannot read the cookies fails. A yolo run reads all
  it is shown (item 443): its chats hold nothing back.
- `run_script` takes `hide_secrets` as the other views do, and the tool passes `hides_secrets(ctx.approvals)`. A yolo
  run reads all it is shown (item 443).
- `Shift+Insert` pastes as `Control+V` does, so it is refused in a secret field as typed text is
  (`browser/safety.key_enters_text`); `Insert` and `Control+Insert` (copy) put nothing in.
- `docs/safety.md` and `docs/browser-and-computer-use.md` say so, and the tool's description tells the model.

Checked by `tests/unit/test_secret_fields.py` (the keys), `tests/unit/test_vault.py` (a value masked under the word it
is given, an error naming it in its words, its context and the address a refusal names),
`tests/smoke/test_secret_masking.py` with a real headless Chrome (a script refused on a page with a password field and
on one whose only secret field is in a frame of another origin, and run when `hide_secrets` is false; the value of a
cookie hidden and a short one kept, in a string and in an object, in a thrown error and in the address a script led the
tab to, and shown in yolo) and `tests/smoke/test_browser_eval.py` (the tool: refused on a login page outside yolo, run
in yolo in a chat of its own, the cookie hidden outside it; a refused address that carries a cookie told without it; a
cookie the script overwrote hidden; the cookie a script wrote into the page and the address kept out of a later
`browser_read_text` and `browser_snapshot`). Everything of `run_script` that tests call passes `hide_secrets=False`, as
those tests drive pages and read nothing as a run does.

Not built: a script can encode what it reads (`btoa`, character codes) and read what a page keeps in local or session
storage, where many keep a token; the value of a field that is not marked secret (a password shown in a text field, or a
field masked by `-webkit-text-security` alone, which the page's marking does not say) is shown to a script and to the
views; Chrome's own saved logins stay on (a run never sees them, the owner's takeover uses them); and a script that
starts on a page without such a field is not stopped if the page adds one.
