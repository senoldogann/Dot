### 1067. The settings of Settings › Appearance have one copy of their rules

**Status: done (2026-11-09).** The owner, on 2026-11-09, pointed at a skill that untangles a codebase and said to use
it if it was needed; the recommendation put to them, which they took ("Olur"): not the whole codebase in one pass, which
this repository's rule of short changes forbids, but its method one area at a time, starting with a rule kept in two
places.

`boot.js` (the classic script that paints what this browser chose before the first paint) and `appearance/settings.js`
(the module that keeps and paints a choice once the page runs) each held their own copy of how every setting of
Settings › Appearance is read and painted: the stacks of the families, the legacy values, the sizes, the weights, the
contrast. They drifted twice in one day while item 1062 was built (the families of the four faces, and the kept size
of the answers, which `boot.js` dropped at the next reload); the reviews caught both, the code did not.

Now the rules are in one classic script, `appearance/rules.js`, loaded before `boot.js`: each setting's key, default,
reading and painting, and `paintAll`, which paints every kept value. `boot.js` calls `paintAll` before the first
paint (110 lines fewer), and `appearance/settings.js` builds its settings from the same rules (`painted`) and paints
with `paintAll` once the page runs. What either paints is the same by construction; nothing the owner sees changes.

Checked by `tests/js/appearancerules.test.js` (the rules run as a classic script on a recording element: nothing kept
paints nothing, each kept value its token or attribute, what a rule would not keep reads as nothing, the legacy values,
a kept size of the answers at its moving default, a phone's own sizes) and the browser tests of the settings and the
themes (`test_interface_settings.py`, which compares the page's first paint with main.js held back to the page once it
runs, `test_phone_text.py`, `test_themes.py`, `test_own_themes.py`).
