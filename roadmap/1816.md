### 1816. DotNext: Retry, Continue and Resume now go to the daemon's own routes, and a cut-off run says what cut it

**Status: done (2026-11-25).** Package W4 (`P1-gaps.md` §2 "Run-end card", "Usage-limit card", "Resume a cut-off run").
Before it, Try again under a failed run and Resume now under the usage limit both sent the run's old goal as a new
message of the chat (`retryLast`), so the failed answer stayed and a second copy of the message started; no run cut off
by a restart offered to go on.

What must hold (the web's own rules, `views/run.js`):
- Continue (`POST /api/runs/{id}/resume`) only where the daemon says the run can go on (`newest.resumable`: cut off,
  blocked or failed, the newest run of its chat) and no run works; a card of an older run offers none.
- Retry (item 1185) under a run that did not end done (failed, blocked, stopped), whenever its message the chat can go
  back to, as the web offers it under any answer of such a message; Continue never for a run whose model declined the
  task (item 1889, `end_reason` `model_refused`: the web restarts it on another model): the web's question (retry, or undo
  the file changes and retry), the rewind, then the words again as the chat's next run with the chat's choices
  (`POST /api/runs`, a fresh key), in the same chat even when the rewind left no run in it (the web opens a new chat
  then; the phone stays where the owner is); the chat's effort goes only when its model offers it (the web checks
  the level against the model's own; the daemon refuses another, which the first walk on the simulator hit); if the send fails after the rewind, the words wait in the composer and the toast says
  why, so the message is never lost between the two calls.
- A run a restart cut off says what cut it (the web's words of `resume.*`); the usage limit's card says when the plan
  resets and its Resume now is the same `/resume`. A run the owner stopped offers nothing.

What was built: `RunEndCard` (`Components/RunEndCards.swift`) for the transcript's `.ended` and `.limit` items, in place
of `RunEndedCard` and `UsageLimitCard` (removed from `WorkLog.swift`) and of `retryLast` (removed from
`ChatScreen.swift`). There is no "don't resume on its own" for the usage limit: the daemon keeps no per-run auto-resume
to cancel (its wake after a reset is for helpers' reports, item 1669), so nothing was invented.

Checked: `MessageActionsTests.testTheEndCardContinuesTheNewestResumableRunAndRetriesAFailedOne` and
`testRetrySendsTheRewoundWordsWithTheChatsChoicesInTheSameChat`; on the throwaway daemon the UI test taps Retry
under a failed run and then Continue, and the script reads that the failed run left the chat, the message went again
and a run of source `resume` started. The usage-limit card was not drawn on a device: the scripted model cannot hit a
plan's limit; its offer is the engine rule's.
