### 1967. Show rich cards in the conversation

**Status: partial (2026-11-26).** Daemon and web cards are implemented. Exact post publishing, the computer
hand-off card, and DotNext rendering are follow-ups.

Dot can already show HTML and sandbox its scripts with `show_page`, including charts, tables and links that fill the
composer. Markdown has inline tables, and web calls produce a Sources row. `draft_message` has its own editable
Mail and Messages cards and claims each draft atomically before sending. The standard approval card answers a real
gate request, including `public_post` and `message_send`; a display card carries no approval.

Use one `show_cards` call with an ordered list of discriminated cards. Each call emits one stored `cards_shown`
event with a version and the validated cards, following `page_shown` through live streaming and history. A batch
of post drafts gives the user the side-by-side proposals shown in the owner's reference. An event is replayable
with no new database table. A tool schema lets the model discover the card shapes and limits, and rejects malformed
data before it can reach either renderer. The system
prompt does not mention the tool until the phone's app and the channels draw cards (the review of the first push):
the schema and the tool's description are all the model sees, so the only change in a system prompt is the `pages` line
of the tool groups ("structured cards or HTML"), and the regenerated prompt surface records a larger tool catalogue (the fixtures hold the counts). Chart marks
take the five `--card-mark-N` tokens of themes.css, held to 3:1 on every surface by `test_css_tokens.py`.

- `post_draft` carries platform, account, exact text, and optional raster media with alt text. On the web, show
  initials and the account, preserve line breaks, and offer copy, edit, and cancel. Edits and cancellation are local
  to the browser tab. Existing Mail and iMessage sends keep their own draft workflow.
- `chart` carries a title, chart type (line, bar, area, pie, scatter), and named series of finite numbers against
  the supplied x values. Axis names and units are optional. Pie takes one nonnegative series. Native SVG elements
  draw the marks, with the values available as a table. Dot once loaded a vendored three.js module on demand
  (item 885, removed in item 1835). Fixed SVG geometry keeps this renderer local and dependency-free.
- `table` carries a title, headers and rectangular rows. Render as an accessible table in a scrollable section.
- `choice` carries a prompt and visible answers. Pressing one writes those words into the current chat's message box,
  as a page's choice does, and starts nothing: what a run wrote, one that read a hostile page included, never goes out
  as the owner's own word on a tap (the review of the third push).
- `image_gallery` carries a title and raster images with alt text. Resolve workspace files with the same scope
  as shown pages, store the snapshots with the existing image store, and fetch only those stored names through
  Dot's authenticated image reader. Cards accept data only. Their renderers never evaluate markup or scripts.

#### Computer hand-off card

A sixth kind, `handoff`, presents an existing hand-off as **Computer: action needed**. It has a title and the
instruction the owner needs, such as “Sign in to LinkedIn, Google and GitHub, then give the screen back.” Show a live
preview through Watch the Mac and say that sign-ins stay in Dot's browser. **Skip** and **I'm done** answer the
existing request, using the same skip and completion semantics as the current hand-off. **Take over** opens the
existing Watch the Mac takeover and leaves the request pending. Release the live preview when the card closes,
scrolls away or settles. History draws the instruction and the outcome from the approval record.

Build the card from the run's existing hand-off approval or parked `ask_user` request. The daemon or the UI derives
the reference from that record, with the run and approval id paired by the server. A model-emitted preview cannot
name a decision, claim a pending request or start a screen stream. Reuse the existing viewer's authentication and
input ownership. Test Skip, completion, takeover and cross-screen settlement through their current endpoints.
The card creates no new question and leaves the current free and yolo decisions in charge. Implementation follows
the five `show_cards` kinds.

#### Publishing follow-up

X is in Dot's connection catalogue as a browser sign-in. The browser gate can approve a click, while the edited
post body, attachments and logged-in account remain mutable page state. To make Share approval of an exact post,
the publisher needs a deterministic adapter that accepts immutable text and attachment bytes and verifies the
acting account. When the adapter is available, classify that exact request through the existing `RunGate` with
`public_post` (or `message_send` for a private sender). Bind any existing approval to the frozen payload and let
Share answer that pending approval once. A refusal, expiration, changed payload or wrong account must prevent
delivery. Claim before sending, record the outcome and leave ambiguous delivery for the owner to inspect. Test
two screens, both deciding orders, rejection, edits, free and yolo behavior, and unknown delivery. Preserve the
current gate decisions, including free mode's waiver and yolo's existing owner-chat exceptions. Until the adapter
exists, the web card can put the exact edited text in the chat composer as a publication request that the owner
can send through the ordinary run path. This carries no approval credit.

#### DotNext follow-up

Decode `cards_shown` alongside the other run events. Ignore unknown versions and kinds without dropping the
answer around them. Add the block to live reduction and history replay keyed by event id. Render draft batches
in a horizontal SwiftUI `ScrollView` with snap-aligned cards, Dynamic Type and VoiceOver labels, using initials,
the account and the full text. Use Swift Charts' LineMark, BarMark, AreaMark, SectorMark and PointMark, with
accessible labels and a data view. Use a scrollable native table, native buttons routed through the chat's
message sender, and the existing authenticated media loader. Use the same approval id for a future Share
action. Verify the rendered blocks on narrow and wide iPhones and with VoiceOver and large text.

Web verification used a scripted provider with the real daemon. The browser test checked the chart and its data,
draft carousel at 1,280 and 390 pixels, literal text, authenticated image loading, edits, cancellation, the draft
filled into the composer and a choice written into it with no run started until the owner sends. The next turn replayed the prior cards. The card schema,
prompt surface, freedom contract, offline eval, Ruff, mypy and web checks passed.
