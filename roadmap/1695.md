### 1695. A run on Zen's free models is told Dot's own prompt and ends with Dot's finish

**Status: done (2026-11-24).** The audit of 2026-11-24 (harness parity, A1) found that a run on `opencode:*` (Zen's free
models, OpenCode's own agent) heard nothing of Dot's: the prompt body held the owner's text alone, under OpenCode's own
agent prompt; no character, rules, owner profile, recalled notes or `finish` (the run ended "done" with the last
text). The owner: "with OpenCode's free models it is as if Dot's rules and logic are not accepted."

Step 0, a live experiment (2026-11-24, the pinned OpenCode 1.19.5 in a throwaway home, no owner config): the server's
API takes a `system` text with each prompt (`/doc` lists it) and a custom agent prompt in its config. On `big-pickle`
and `deepseek-v4.1-flash-free` each of four ways answered (HTTP 200, 1.4 to 3.8 s) and kept the rule the text gave
("begin every answer with PINEAPPLE"): `system` with the rule alone and with Dot's whole prompt (21 KB), the agent
prompt with each. Zen's free tier did not refuse a custom system prompt. Then one task run through Dot's real path with
this change on `big-pickle`: done, OpenCode's write and read, then Dot's `finish`.

What changed:

- `opencode/server.py`: `prompt(..., system)` sends `system` in the body of `/session/{id}/prompt_async`.
- `opencode/run.py`: the run gathers the prompt's facts as Dot's own loop does (`agent/handover.py: prompt_facts`,
  moved from `claude_code/run.py`) for the door's tools, and sends `build_system_prompt` of them, the free-mode line and
  `_HARNESS` (`harness_prompt`: which of OpenCode's tools stand for the shell, file and web tools the prompt names,
  where Dot's other tools are, that subagents are off, how the run ends) as the `system` of every prompt (the first,
  the limit note, an approval's note, the owner's messages: OpenCode keeps a prompt's system to its turn). The first
  message carries, under the owner's words, the started note, the notes recalled for it and the skills that fit its
  goal (`handed_notes`, moved from `claude_code/run.py`), stored in the chat as a message of its own as on the plan.
  `finish`, `update_plan` and `mark_plan_step` are bridged; the run ends as the agent's last `finish` says (done only
  when it succeeded, with `needs_from_user`), unless it called another of Dot's tools after it.
- Not done here: the goal check of a finish and the lessons for these runs (the run's follow has no record of the
  agent's own tool calls as Dot's loop keeps them); docs/models.md says so.

Checked: `tests/unit/test_opencode.py` (`finish` and the plan's tools bridged, the harness prompt; fail without the
change), `tests/smoke/test_opencode_run_ends.py`, `test_opencode_start.py`, `test_opencode_bridge.py`,
`test_opencode_confined.py`, the live experiment above. Found on the way, not changed: the Homebrew `opencode` is
2.4.1, whose `models` command takes no provider argument and no `--refresh`, the call Dot lists Zen's models with; the
owner's Dot runs the pinned 1.19.5 (`[providers.opencode] command`), which works.
