### 1370. `GET /api/runs/{id}/events` takes `tail`, so a client that was away through a long run reads the end of it

**Status: done (2026-11-23).** Found while making the iPhone app work on the worst network (item 1371): after a phone has
slept through a long run, the only way to catch up was `after=<last id>`, page after page of up to 2000 events, each page
one round trip, and the app drew every step it had missed although the screen shows the end of the run. A bad link made
that the slowest part of coming back.

- `EventsQuery.tail` (1 to 2000, none by default): `GET /api/runs/{id}/events?tail=N` answers the newest `N` stored
  events of the run, oldest first, without the kinds the pages leave out (`loop_state`, item 1170), and sets the header
  `X-Dot-Events-Tail: N`. Without `tail` nothing changes, so a client that sends only `after` and `limit` gets what it got.
- `Store.list_events_tail_without`: the newest `N` by `id`, read in one query and put in order.
- **The header is how a client tells a daemon that knows `tail` from one that ignores an unknown query**: an older daemon
  answers `?tail=400` with the run's first events (the default `after=0`), which are no tail; the phone finds no header
  and reads the pages as before. A refused `tail` (0, 2001) is a 422 like any bad query.
- `docs/daemon.md` and `docs/phone.md` say so.

Checked: `tests/smoke/test_events_tail.py` (a real in-process server on a scripted model: the newest events oldest
first and equal to the end of the full read, no snapshots, the header, a `tail` larger than the run, a run with few
events, a refused `tail`, and a read without `tail` carrying no header); `ruff`, `mypy`.
