### 1400. A run on the Claude plan that lacks a tool it cannot work without ends failed at once, and says which

**Status: done (2026-11-24).** Found by the autonomy audit (`workspace/autonomy-audit-2026-11-23.md`, finding 2). A
schedule's reminder, a run on `claude_code:haiku` with one step and no tool call, ended `done` with "I couldn't send
the notification: the Dot tools (including `notify`) are no longer available to me in this run, so nothing was sent";
the schedule's row, the Away card and the notice said done. `_outcome` ends a run that never called `finish` as done
with its last reply, and the run's first line (`init_problem`) was only compared with what a run must not have, never
with what it must have.

Why the tools can be missing, as far as it was found (the run itself is not reproducible from here, the owner's
database being out of reach for this work):

- **Dot's own list leaves one out.** The door's tools are the mode's, without a campaign's and a post's, without those
  a delegated run may not use, without those Settings withholds, and, for a run of an agent whose tools are a list of
  its own, only the ones it names with `AGENT_CORE_TOOLS` (`finish`, `ask_user`, `use_tools`, ...). `notify` is not
  core, so a reminder in the chat of such an agent had no `notify`, and nothing said so to the run or to its owner.
  Verified in the code and by the new test.
- **The bridge answers nothing for a door it does not know.** `ToolBridge` answers 404 to a secret that is not an open
  door, so the program lists none and its server says `failed`; measured with `claude` 2.1.330 against a throwaway
  bridge: `tools: ["ToolSearch"]`, `mcp_servers: [{"name": "dot", "status": "failed"}]`. `init_problem` already ended
  such a run, so this is not the reminder's case.
- **The program lists what the bridge gives it, whole.** Measured with the same program, the init line lists every
  tool of the door, the ones Claude Code defers (tool search) as well, so a list can be compared with what the run
  needs; and a session resumed with `--resume` through a new door finds `notify` again, so a resumed session does not
  hide it. What a small model does with a tool it only knows the name of (never looks it up, says it is gone) is not
  seen by either check and **not verified** as the cause of the audit's run.

What changed: `claude_code/run.py` works out the tools a run cannot do its job without (`tools_needed`): `finish` where
its mode has it (a chat has none), and `notify` when the run is a schedule's firing, which nobody reads as it ends, and
its goal asks for a notification (`goal_asks_notification`: "notify me", "send me a notification", "show me a
notification", "use notify", Turkish "bildirim gönder/at/yap/ver" and "bana bildir", Finnish "lähetä ilmoitus" and
"ilmoita minulle"; a goal that only mentions one, names another's ("a notification email to the leads") or refuses one
("do not send a notification", "älä lähetä ilmoitusta") asks for none: the pre-push review found that the first version,
any mention, would fail an agent's review of "the notification settings screen", and the second round that the phrases
missed the owner's usual ones and read a Finnish refusal as an ask). Dot's own list for the run is checked before the
program starts and outside the `try` whose end lets the chat's session go (`tools_not_given`, a plain `ClaudeCodeError`:
it needs a change, so no try again follows; the result names the agent whose list leaves the tool out and says to add
it), and the program's first line is checked when it comes (`tools_not_listed`, a `ClaudeCodeBroke`: a passing failure,
which a schedule tries once more), `listed_tools` reading the door's tool names from it. Either ends the run `failed`
before its model says a word, with the tool and the cause as its result, so the schedule's row says `failed` (and counts
it in a row) and its History's line for the firing is the reason. `NOTIFY_TOOL` joins `FINISH_TOOL` in `tools/meta.py`.
No rule on a run that calls no tool: a goal that is only an answer needs neither tool, and a run the owner watches is
not held to `notify`.

Checked: `tests/unit/test_claude_code.py` (seven new tests: the names a line lists, the notification requests in the
owner's three languages and the goals that only mention one or refuse one, what a run needs by source, what it lacks,
the words of both errors and how each fares with time) and `tests/smoke/test_claude_code_run.py` with the stand-in
program (four tests: a faked short bridge list ends a firing that asks for a notification failed at once, the program
started and no step taken, the session not kept, kind `passing`; the same goal runs on the whole list, and on a list
without `notify` a firing that only mentions a notification, a goal that is an answer and a run the owner watches run
all the same; a schedule whose run lacks `notify` says `failed` in its row and the reason in its History, and no try
follows; an agent whose list leaves `notify` out is named before the program starts, keeps its chat's session, and its
other runs go on). The behaviour tests fail on `origin/main`'s code, the control passes there. `ruff`, `mypy`,
`npm run check`, `dotx eval check`.
Not done: a model that has the tool and does not use it (not a rule of Dot's: the audit's own cause is not verified);
marking `finish` and `notify` always loaded in the door (`LOADED_TOOLS`, item 1341) is the owner's call, as it changes
the head of every run's prompt.
