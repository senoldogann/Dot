### 1692. A run on the owner's Claude plan has the core tools' definitions from the start

**Status: done (2026-11-24).** The audit of 2026-11-24 (harness parity, A1) measured "Invalid arguments" results in 24
of 124 runs on the plan (19 %) against 10 of 162 runs of Dot's own loop (6 %): `delegate` with `step` as a string (6),
`wait_until` with extra parameters (4), `notify` without its `title` (4). Behind Claude Code's search of tools (item
1053) the model saw only the tools' names and called many before it looked them up, though the prompt says to (item
1201).

The CLI's own switch was read first: `ENABLE_TOOL_SEARCH=false` would put every door tool in the prompt (107 tools,
about 94,000 characters of definitions in a default install, up to 296 with the owner's servers, the 99,000-token
cache write item 1053 removed). What Dot's own loop does is in between: a run whose tools come in groups gets the
core group whole and the others by `use_tools`.

What changed (`claude_code/run.py`): `loaded_tools(names)` marks `terminal_open`, `wait_until` (item 1341) and every
tool of Dot's core group (`group_of(name) == CORE_GROUP`: the files, the shell, the web, memory, notify, ask_user,
delegate, finish, the team's and others, 29 in a default install, about 27,000 characters) `anthropic/alwaysLoad` in
the door's list; the others are still looked up with `ToolSearch`. The prompt's harness section says that the core
ones are in the prompt and any other is looked up.

Checked: `tests/unit/test_claude_code.py::test_the_core_tools_are_in_the_prompt_whole_and_the_others_are_looked_up`
(fails without the change), `tests/smoke/test_claude_code_run.py`, `tests/smoke/test_opencode_bridge.py`.
Not measured: the error rate after the change on real runs; `scripts/harness_parity_probe.py` (item 1694) counts the
invalid-argument results of three fixed tasks.
