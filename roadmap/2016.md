### 2016. Unattended runs keep the sandbox: a run nobody started seals Dot's own files in yolo and free mode too

**Status: built (2026-11-27), waiting on the owner's look (it touches `src/dotagent/policy/`).** The owner approved it on
2026-11-27, from P0-2 of Grok Bot's review: the processes of a run started outside yolo under `sandbox-exec`, and `[initiative]
approvals` defaults to `yolo`, so a run of Dot's own initiative, a schedule's, a watcher's or a hook's (item 1970), the
runs nobody watches, started their processes with nothing between them and Dot's keys, token, store and emergency
stop, the least-watched run the least protected. `[shell] sandbox = false` (the owner's own choice) took the sandbox from
every run.

## Approach (written before the code)

What must hold, in the kernel: the processes of a run nobody started (a shell command, a terminal session, an
AppleScript and what it runs, a video tool's programs, a wait's check, OpenCode's server and what its agent runs, the
search tools' ripgrep), and the commands of a schedule's check and a watcher's check, start under the sandbox profile
that exists today (`sandbox_profile`, unchanged): no read or change of Dot's own files and `[policy] sealed_paths`, no
change of what Dot loads and runs, of Dot's home or logs but the workspace, of the folders above them, no hand-off to
launchd, Shortcuts or Launch Services, no clipboard. This holds in every approval mode, yolo and free mode included, and
whatever `[shell] sandbox` says, while `[shell] sandbox_unattended` is `true` (the default). The profile is not widened
or narrowed: what a task reaches (the network, the owner's files, their programs) is what it reached before.

Which run is unattended is decided by Dot as the run starts, never by a model or a caller, and kept on the run's gate
(`RunGate.unattended`), from where the tools read it (`ToolContext.unattended`):

- a run whose source is one nobody starts: `schedule` (a hook bound to a schedule fires it), `watcher` (a hook bound to
  an agent starts one), `initiative`, `reply` (a mail's reply handed on), `notice`, `reflection`;
- a run that goes on in a chat without a message of the owner's (`background`, `work_order`, `helper_report`,
  `welcome`) in a chat one of those sources opened, or after such a run in any chat (a schedule's firing in the owner's
  chat, `/loop`, left a command in the background: the security review);
- a resumed run: as the run it resumes, followed back through its resumes (the `resumed` event's `from_run_id`); one
  whose chain cannot be read is unattended (it fails closed: the sandbox only seals);
- a helper (delegated, a team's): as the run that delegated it, and a resumed helper whose parent ended as that parent.

Every other run is the owner's and starts as today: a message in the app, `dotx run`, a phone, iMessage from the owner,
a review, an eval's task; also one of theirs in a chat a schedule opened.

What only asks: nothing. The change adds no question in any mode; the gate decides every call as it did. A step of an
unattended yolo or free run that would read or change Dot's own files through a process is refused by macOS ("Operation
not permitted"), as the same step of a run outside yolo always was; that is the one thing such a run no longer does,
and `docs/freedom.md` names it under what still refuses.

What it does not cover (the docs say so): Dot's own file tools (`write_file`, `edit_file`) run in the daemon's process,
not in the sandbox, and in yolo the gate still lets them change Dot's files unasked; Apple Events; a hard link to a
sealed file made outside the sandbox earlier (item 561). Self-repair (items 919-921) runs Claude Code from the daemon
itself, in its own checkout, not through a run's tools, and is unchanged.

`[shell] sandbox_unattended = false` gives the old behaviour. Settings › Rules' switch of the sandbox changes the
sandbox of the owner's runs only. The daemon checks the profile starts at its start when either setting is on.

## Checked

- `tests/smoke/test_sandbox.py`: in every approval mode, with the owner's sandbox switched off, a run nobody started
  cannot read the token through a shell command, a search or a terminal; the owner's yolo run reads it.
- `tests/smoke/test_unattended_sandbox.py`: through the real manager on a scripted model, with `[shell] sandbox =
  false`, a schedule's yolo run is refused Dot's configuration and the owner's yolo run reads it; a run resumed three
  times goes back to the schedule's, and a chain that cannot be read gives no origin. With the rule taken out of
  `SwitchedSandbox.for_run` these tests fail (5 of them, measured).
- `tests/smoke/test_unattended_sandbox.py` (from the reviews): the run that tells a firing's background command ended
  keeps the sandbox in the owner's own chat (`/loop`), and after the owner's own run does not; `RunManager._origin`
  takes a resumed helper to the run at the top of its delegations and a resume to the run it resumes. A terminal line
  typed at a password prompt is refused in a session opened outside this run's sandbox, as any line is.
- `tests/unit/test_unattended_runs.py`: which sources and chats make a run unattended;
  `tests/unit/test_sandbox_profile.py`: `for_run` and `unattended` in every mode and switch position.
- `tests/unit/test_freedom_contract.py`: three new ways (yolo and free, yolo, yolo in a chat of Dot's own, each in a
  run nobody started) ask exactly what the contract names, as before; `dotx eval check` passes.
