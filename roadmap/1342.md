### 1342. A login refused in a frame of another site names that host and has the run tell the owner

**Status: done (2026-11-23).** Self-repair found it in Dot's record: `browser_fill_login: the field is in a frame of
another site`, three times in three runs. The one whose events are still kept (`run_mwrzx95t_f5ee0e`, an App Store
Connect submission) shows why: App Store Connect's sign-in page holds its form in a frame of `idmsa.apple.com`, and
the vault's login names `appstoreconnect.apple.com` alone.

The refusal itself is right: a login goes only into a document of the sites it names, by the address the browser
knows for the frame ([Safety](../docs/safety.md)), and whether the login should name Apple's sign-in host too is the
owner's to decide, as item 1208 left it for a page of another host. What was missing was what item 1208 gave the
refusal on a page: the run was told nothing but "a frame of another site", with no host and nothing to do, so it tried
other ways (it typed the username itself and went to the API), and the owner never heard that the login needs that
host to fill there.

- The refusal names the frame's host (or "a site Dot could not read" when Playwright names no frame, as a frame whose
  script spoofs its field's document makes it) and tells the run to fill it no other way, to tell the owner in one line
  that the site signs in in a frame of that host, which the login does not name (they may add the address to the
  login's websites), and to go on with what needs no sign-in.
- Nothing fills that did not before.

Checked: `tests/smoke/test_vault_fill.py` (a frame of another host on the login page, on real headless Chrome: the
refusal names `localhost` and carries the line for the owner; the spoofed frame is still refused); `ruff`, `mypy`.
