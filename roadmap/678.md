### 678. A phone's key is never this Mac, and cannot widen for good what runs do unasked

**Status: done (2026-10-26).** The whole-project review of 2026-10-26 found two gaps in what item 670 promised of a
phone's key. What is shown or connected on the Mac alone (the eye of the vault, which answers a password or a card's
number; 1Password's connect and a pasted token; a sign-in of Google or Microsoft; the microphone's pane) checked only
that the request's `Host` header named a loopback address, which any client writes: a phone's key sent through the
tailnet's proxy with `Host: 127.0.0.1:<port>` was answered as the Mac. And a phone's key could leave Dot doing more
without asking after the phone was removed: add a connected app by a command line (`connected-servers.json`, started
with the daemon outside the sandbox), switch the safe box of commands off, add an allow rule.

**What must hold, and where.** The guard is where a request's key is known: when a phone's key lets a request in, the
guard leaves the phone's id in the request's state (`PHONE_STATE`), which no client can write. "This Mac" is a request
with the installation's token to a loopback address (`on_this_mac` takes the request, not a header). The routes that
would widen for good refuse a phone's key with 403 (`refuse_from_a_phone`, `PhoneRefused`): adding a connected app; the
safe box or the extra checker (the typed judge) switched off; a rule that lets steps through (allow, pre-approved) added
or switched on, a rule that asks deleted or switched off, any rule moved (the order is what the policy reads first); a
server another agent of the Mac set up added from Skills › Found elsewhere (the security review of this item found
these). What narrows is open to a phone. A phone paired before item 670 holds the installation's token and is the Mac
to the daemon, as `docs/phone.md` says.

**`yolo` is not held from a phone (the owner's word).** The code reviews asked, round after round, that a schedule, a
loop of a chat, a campaign or an agent kept in `yolo` be made, switched on or let go on from the Mac alone. The owner
runs Dot from the phone when away from the Mac and said `yolo` is theirs to use from there; and a run in `yolo` started
from a phone could make such a schedule in its chat anyway. So none of them is refused to a phone's key, and
`docs/phone.md` says that a phone that may have been used against you is removed and what it changed looked over
(schedules, campaigns, agents).

**Checked.** `tests/smoke/test_phone_limits.py` (a served daemon: a phone's key with a loopback Host is refused the eye,
1Password, a sign-in and the microphone's pane, where the Mac's token passes; each widening refused to a phone's key and
done by the Mac's; a rule that asks made from the phone; a schedule, a loop, an agent kept in `yolo` made, switched on
or let go on from the phone, a campaign kept in `yolo` let go on), `tests/unit/test_oauth.py`, and the tests of the
routes changed.
