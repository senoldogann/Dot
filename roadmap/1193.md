### 1193. The queue test of a dead process's claim waits for the run's task, not only its end

**Status: done (2026-11-15).** Main's gate went red on 2026-11-15 (run 43730725342, after item 1190) on
`tests/smoke/test_queue.py::test_the_claim_of_a_process_that_died_holds_its_chats_queue`: `claim_queued` gave `None`
where the queued message was expected, and the run of that message, started meanwhile, hit the closed database as
the test ended. The same test failed so on the gate of #933 on 2026-11-14.

The cause is in the test. `RunManager.wait` returns when a run's end is recorded (`_close` sets `finished`); the
run's task then goes on, closing its tabs and giving the front of the Mac back, before it moves the chat's queue
(`_follow_queue`). The test let the queue go right after `wait`; on a slow runner the task's move of the queue came
after that, claimed the message and started it, and the test's own claim found it taken. Reproduced at will with two
probes (the task's move delayed 0.3 s, the test's claim 0.6 s after the release): the test failed every time; with
the fix it passed every time. Nothing in the product is wrong: a queue let go as a run ends moves on, as it should.

- `tests/smoke/test_queue.py`: the test takes the run's task before the run ends and awaits it whole before it lets
  the queue go.

Checked: the probes above, and `tests/smoke/test_queue.py`.
