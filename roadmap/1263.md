### 1263. A search embeds at most one batch of notes; the scheduler embeds the rest

**Status: done (2026-11-20).** A search or a save embedded every note that had no vector before it answered, one batch of
32 after another, on the path of the turn. A memory with many notes still to embed stalled the turn on that many
calls. The ranking still reads every stored vector; that is unchanged.

A search or a save now embeds at most one batch, then answers from the vectors already stored and from the words. The
note being saved, and the query, are one more call. When the embedding service cannot be reached, the note is still
kept with no vector and the search still returns what the words found (item 1254). The daemon's scheduler embeds the
rest in the background, one pass at a time, each note stored before the next batch, so a process that dies mid-way
leaves what it wrote and the next tick takes the rest. A second pass, when every note has a vector, makes no call.
`dotx memory reindex` still embeds every note.

Checked: `tests/unit/test_memory_backfill.py` (it failed first: 40 notes with no vector, a search made 3 embedding
calls; it now makes at most 2, returns the note the words find, and leaves the rest for the background pass, which
embeds those and nothing the second time), and `tests/unit/test_memory_embed_down.py`.
