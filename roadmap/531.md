### 531. The stores no program needs are sealed to a run's commands, and a path built from pieces is judged

**Status: done (2026-10-22).** An audit of how Dot keeps the owner's browser data, passwords and history from a run
(the owner asked whether it is sure) found that the shell guard, which reads a line, kept them from a run only by
their names: `cat ~/.s$(echo sh)/id_rsa`, `cat ~/Library/${X:-Safari}/History.db`, `env -C ~/Library cat
Safari/History.db`, `find ~/Library -name History.db -exec cat {} \;` and `grep -r x ~/Library/Application\ Support`
were all allowed, in every preset, on this Mac (`cat ~/Library/Safari/History.db` and `cat ~/.ssh/id_rsa` were denied).
Only Dot's own files and the data directory of the stable Chrome were closed to a command by the sandbox; the other
browsers' data, Safari's, Mail and Messages were the guard's alone.

**As built.**
- `[policy] sealed_paths` (new, `defaults.toml`): the stores no program a run starts has any use for — the data and
  caches of Chrome (and its Beta, Dev and Canary), Chromium, Safari, Firefox, Brave, Edge (and its channels), Arc,
  Vivaldi and Opera, the cookies, Messages and Mail. The sandbox of a run's commands closes them as it closes Dot's own
  files (`runtime._run_sandbox`), so no path, variable, substitution or script reaches them (macOS answers `Operation
  not permitted`); a yolo run, which runs outside the sandbox, still can. The guard refuses a line that names one, as
  it does `protected_paths` (`PolicyConfig.refused_paths` is both, which the runtime hands the guard and the search
  tools). They moved out of `protected_paths`, which keeps what programs read there (ssh and git their keys, a cloud
  CLI its own), so sealing it would stop them: the guard keeps those by reading the line. `protected_paths` gained what
  1Password, Bitwarden and Dashlane keep on the Mac (the 1Password agent's socket lies in its group container, which a
  command may use, so that stays guard-only).
- A word with a part only the running line knows (a substitution, `${x:-y}`, `$1`, a variable filled with what a
  command prints) that begins as a protected location's path, letter case aside — `~/.s` of `~/.s$(echo sh)/id_rsa`,
  `~/Library/` of `~/Library/${X:-Safari}/History.db` — is asked about in every preset, as a step the guard cannot read
  is (`_leads_toward_protected`; it fetches nothing). A part that begins the word stands for the home folder, as before.
  Such a step carries a flag of its own, `protected_read`, which the aggressive preset asks about like its other flags
  and a yolo run that read outside content has the review model check (`policy/types.py`, `policy/engine.py`); it was
  `destructive` at first, which told the owner on the approval card that a read destroys.
- A command that reads every file under a folder that holds a protected location is asked about
  (`_walks_over_protected`): `grep`, `egrep` and `fgrep` with `-r`, `-R` or `-d recurse`, `rg`, `ag` and `ack` (`rg
  --files` lists names only), `cp -r` and `rsync -r` or `-a`, `ditto`, `tar` creating an archive (and its `-C`), `zip
  -r`, and `find` or `fd` that runs a command on what it finds; a folder only the running line knows stands for the home
  folder. `grep -r x ~`, `rg token ~/Library`, `find ~ -exec cat {} +` and `cp -R ~/Library copy` ask; the same on a
  project folder, `find ~ -name '*.pdf'` and `ls ~/Library` do not. A listing piped into `xargs` is the twin of the
  `find` that runs the command itself (`find ~ -name id_rsa | xargs cat`, through a `sort` too; `fd` and `rg --files`
  as well), asked about unless `xargs` runs a command that only prints names (`ls`, `echo`, `stat`, `du`, `file`...).
  Options bundled with a digit (`grep -rC3`, `zip -r9`) read as the bundle they are, `git grep --no-index` is a
  recursive grep, and a search's pattern is no folder it walks (`grep -r ~ ./notes`; `rg` walks the directory the line
  is in only when it is given no path).
- An option that moves a command to another folder (`env -C`, `git -C`, `tar -C`, `make -C`, `--directory`, `--cwd`,
  `--chdir`, `--working-directory`, `--workdir`, `--prefix`) has the words of the command judged from there, as after a
  `cd` (`_moved_scopes`, read for every command): `env -C ~/Library cat Safari/History.db` is the file of
  `~/Library/Safari`, and so is `git -C ~/Library diff --no-index Safari/History.db /dev/null`; both are denied.
- `docs/safety.md` says so (what is protected, what is sealed, what the guard reads).

Checked by `tests/unit/test_shell_policy.py` (the lines above, in each preset, and the lines next to them that stay
allowed; the default lists; the new default locations) and, with a real `sandbox-exec`, by
`tests/smoke/test_sandbox.py` (a sealed store read whole, by a substitution, by a recursive grep and by a script is
refused, a yolo run's command reads it, a search is kept out). They fail without the change.

Not built: a path whose beginning the line does not show at all (`$(pwd)/x` is the folder the line is in, and a word
that begins with a part only the running line knows stands for the home folder) cannot be told from any other; the
credentials of ssh, git and a cloud CLI stay the guard's, which reads the line (a program that builds the path in its
own code, a script, inline code that assembles it from pieces, is not read); `ls -R`, `du` and `tree` list names, which
no rule here reads as a walk, nor a loop that reads what a search lists (`find ~ | while read f; do cat "$f"; done`) or
`parallel`; the guard and the sandbox do not cover a yolo run, which asks nothing (item 443).
