### 570. A morning brief that Dot writes each day and sends you the first line of

**Status: done (2026-10-23).** The owner asked for Dot to come to them, as the always-on agents of 2026 do: a brief each
morning, not only answers when asked. A **Morning brief** card at the head of Schedules has a switch, a time (08:00, in
the zone the schedules are read in), every day or the weekdays, and a box "Also tell me about…" for the owner's own
lines. Switched on, Dot runs at that time a run whose answer is the brief, and the phone gets the push of its first line,
which opens the brief in its chat (one chat, "Morning brief", for all briefs: each day a new run in it).

**The approach.** The brief is not a new loop: it is a schedule of the scheduler the owner already has, marked as the
brief, so that it shows in the list with a label, switches off there, fires once, skips when overdue and counts its
failures as any schedule does. What differs is held in three small hooks of the scheduler and one module.
- *Marked.* The mark is the id of the schedule in the settings of the brief (`proactive.brief` in the kv table: the id,
  the time and days a brief that is off keeps, and the owner's lines), not a column of `schedules`: `ScheduleRecord` and
  `ScheduleOptions` are built in many places, and a change of them would touch every one. While the schedule exists its
  cron says the time and the days, so that a change in the list is the card's too. `ScheduleView.brief` tells the page
  which row it is. Settings that cannot be read are logged and read as the defaults: every schedule asks whether it is the
  brief as it fires, and none may fail for a thing that is not its own.
- *Read-only.* Its mode is `research`, and `prepare` sets the mode again at each firing, so a `PATCH` of the schedule
  through the API cannot make a brief that acts. It is unattended and takes `[policy] approvals`, as a schedule's run
  does; it is told always (`notify` "always").
- *The goal is built when it fires* (`proactive/brief.py` `prepare`, called from `Scheduler._briefed` at a firing and at
  Run now). Two parts, as the digest of a schedule's earlier runs is kept apart from its goal (item 257): the **goal**,
  which the reviewer takes as the owner's instruction and the chat shows, is Dot's one line ("Write my morning brief
  for Friday 23 October 2026.") and the owner's lines; **what the run reads before it**, in the digest's place, is
  Dot's own instructions and its record of itself in a `<dot_state>` fence: what waits for the owner (questions and
  approvals runs left, drafts waiting to be sent), the runs that failed since the last brief, the campaigns at work with
  their next session and last note, the schedules that fire today. Each line a run or a campaign wrote is quoted
  (`proactive/text.py`: one line, secrets masked, 160 characters, `<` escaped), so nothing in it passes for an instruction
  or closes the fence. **The run takes the taint of the runs those lines quote** (item 243: a run that reads another's
  words starts as untrusted as that run ended; the review of this item, F1): `prepare` names them as the digest's
  `run_ids` (the run of each question, approval and draft it lists, each failed run it names, the run of each campaign's
  last note), and `Scheduler._carried` returns them with the chat's last run for a firing that goes on in its chat, as it
  already returned a digest's runs for a chat made for the firing. Without them the first brief, or one with no account
  signed in (which reads no mail), started untainted while it read what a tainted run had written. A schedule that is not
  the brief has no digest in a chat it goes on in, so for it nothing changes. The names of schedules and the titles of
  campaigns come with no run's taint: a campaign's title is the owner's, and saving a schedule asks the owner when the
  run had read outside content. The failed runs are read among the newest 200 (the store has no query by time), and
  the title of that part says so when they did not reach back to the last brief.
- *What it reads.* With accounts signed in the instructions give the run the calls to make for each (`calendar_events`
  for today, `mail_search` for the last day, as many days as passed since the last brief, at most three: a weekday
  brief on a Monday reads the weekend) and ask it to tell only what needs the owner. With none it says so in one line,
  which is not a failure. The mail is the tools' own, fenced and marking the run untrusted as for any run.
- *One chat, told in its own words.* `same_chat` is on, so the runs go on in one chat, titled "Morning brief" (the
  scheduler titles a first firing's chat by its name and the time otherwise). The end of a done brief goes through
  `tell_owner` with the title "Your morning brief" and the first line of the answer, opening the run; any other end
  (a failure) is told as every schedule's is.
- *`tell_owner(bus, title, text, url)`* (`notify/owner.py`), the one place Dot tells the owner something it has to say on
  its own, for the brief and, in item 571, the watchers. It emits `owner_told`, an event of Dot itself (live only, like
  the other notices), which `notify/push.py` turns into the push (`notice_message`), the lifecycle stream carries to
  the pages, and `attention.js` shows as a desktop notification where those are on; a channel added later listens for the
  same event. `url` must be a route of Dot's own pages (`#/runs/<id>`), so that no tell sends the owner elsewhere. The
  signature takes the bus first: the brief named `tell_owner(title, text, url)`, and a function that reaches nothing
  without one has to be given it.

**As built.**
- `notify/owner.py` (`OWNER_TOLD_EVENT`, `OwnerTold`, `told`, `tell_owner`), wired into `notify/push.py` (`PUSH_KINDS`,
  `notice_message`), `server/stream.py` (`LIFECYCLE_KINDS`) and `static/js/attention.js` (`tellAboutOwner`).
- `proactive/` (`__init__.py`, `text.py`, `brief.py`): the settings, the cron and its reading back, the owner's lines
  (blank ones dropped, a line over 300 characters or more than 20 refused, never cut), `set_brief` (serialized by a
  lock: two settings at once make one schedule; a brief never switched on makes no schedule), `brief_view`, `prepare`,
  `tell_brief`.
- `scheduler/runner.py`: `_briefed` (the goal, the context and the chat's title, at a firing and at Run now) and the
  brief's own words for a done end in `_tell_end`.
- `server/routes_proactive.py`: `GET` and `PUT /api/brief`; `server/views.py` and `server/routes_data.py`: `brief` on the
  schedule's view.
- Web: `static/js/briefcard.js` (the card: the switch and Save write at once and the list is read again; the fields of a
  card being typed in are left alone when it reads again; Write one now; a note when the schedule was changed in the list
  to a time the card cannot show), `views/schedules.js` (the card at the head, a **Brief** label on its row, its pencil
  leading to the card), `css/settings.css`.
- Docs: `docs/proactive.md` (new), `docs/memory-and-schedules.md`, `docs/daemon.md` (the REST table and the
  notifications), `docs/safety.md` (what leaves this Mac: the record the brief's run is given and its first line on the
  phone), the README's list.
