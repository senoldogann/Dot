### 1038. Replay of learned browser flows: reviewed, and not built now

**Status: decided (2026-11-07).** **Asked** by the CI/CD session as the first step of the speed work: a flow Dot
finished well replayed the next time the same work comes, without model calls, checking the page before each step and
handing back to the model at the first mismatch, through the same gate, policy and approvals.

**The design reviewed.** Recording a successful run's `browser_open` and `browser_act` steps (the target by role, name,
frame and URL path; typed text as vault references or spans of the goal), keyed by site, normalized goal and account,
replayed before the model's first step, the model writing the answer.

**Red team (independent review).** Safe replay needs no change to `policy/` or the approvals, but only without two
parts of the draft, and only with a new rule the owner must agree to:
- Every browser run is tainted from its first page (`policy/types.py` `TAINTING_KINDS`, `agent/gate.py`), and in yolo
  a plain click, Connect or Follow is never checked: a step an injected instruction caused, once recorded, would repeat
  on every daily firing with no model looking. The only boundary that holds: each recording replays only after the
  owner saw and approved its steps, and a repaired one needs a new yes; docs/safety.md would have to say so.
- Vault references typed on replay would be a new way for a secret to leave the Mac (`secrets.py`, the egress rule):
  dropped; a login is a mismatch the model handles with `browser_fill_login`.
- Reading the signed-in account from cookies is a new credential read: dropped; key by profile and agent, never replay
  in the owner's attached Chrome.
- Recorded URLs can carry tokens (reset links, OAuth codes, invites) or an injected beacon: only goal spans and landing
  pages, no query strings, the learned-text gate on every stored string.

**Browser automation (independent review), on the owner's store (read only, 30 days).** Replay would rarely fire:
- 70 runs had a goal repeated at least 3 times with browser steps, but their steps differ run to run: the customer
  mail's 35 runs made 23 distinct tool sequences, mostly `browser_eval` scripts; the job pipeline loops over different
  postings (4 of 67 opened URLs shared by three runs); the job hunt and the Gistsmith distribution share none.
- Refs are per-snapshot (`f11e…` became `f24e…` after a navigation) and 83% sit in frames; names carry counts and times
  (LinkedIn's "(1) Mesajlaşma"), lists repeat names, Slack and the webmail virtualise rows. Act results keep refs, not
  roles and names, so no past run can become a recording.
- The pipeline types text the model wrote (a 325-character application message): recorded as drafted, the next day's
  replay would send it to another company.
- Expected: under 10% of the owner's browser model time; most of the speed set (static pages) would replay, which would
  overstate the win.

**Where the time goes instead** (the same review, 8,427 step calls on the main model): 3.7 s a call, 1.4 s of it to the
first token, about 600 output tokens; 100k of the 109k input tokens came from the provider's cache. So about 2.3 s of a
call is the model writing, and a smaller context would save cost more than time. 68% of `browser_act` calls carry one
step.

**Decision.** The owner, 2026-11-07: the second step first (more work per model call, fewer output tokens per step);
replay is not built now. If it is built later: owner-approved recordings, the safety contract updated, no secrets, no
attached Chrome, live recording with a multi-attribute identity, URL templates, `browser_eval` steps recorded, model-
written text never recorded, and a speed set whose pages change between recording and replay.
