### 1886. A pull request runs the Linux checks alone; the macOS suites run on the push to main

**Status: done (2026-11-26).** The account runs five macOS runners at once, and every pull request that changed the
package ran five macOS jobs (`gate`, `gate (part 2)`, three browser parts: about 50 macOS minutes) and, for `ios/`, the
iPhone app's: pull requests waited one to two hours for a runner (the lead's count, 2026-11-26). The owner left the call
to the lead, who decided: no macOS job on a pull request.

What must hold: a pull request runs the Linux jobs alone (`prose`, `changes`, `checks`: the format check, the lint,
mypy, `npm run check`, the item records, the unit tests Linux runs; the desktop checks and zizmor when their files
change), and its `ci` is those. The push to main that merges it runs the macOS jobs its files can affect: `gate` and
`gate (part 2)` by `scripts/python_ci.py`, the browser parts by `scripts/browser_ci.py`, ios.yml's short set by its
paths; the files are those changed since main's last green gate run, as runs of main that wait replace one another
(item 1011) and the push before may never have run; a decision that cannot be made runs everything. Runs of main are
never stopped halfway, and pushes that come meanwhile wait as one run, the newest. A release (the push of its tag,
which the called gate sees as its own push event: the `changes` job reads main's ref only) and a run by hand run every
job. The nights run the whole browser suite (`browser.yml`) and the whole iPhone suite (`ios.yml`).

What was built (`.github/workflows/gate.yml`, `ios.yml`): the macOS jobs of the gate skip a pull request; the
`changes` job runs for a push to main too, its base the commit of the gate's last green run on main, read from the API
(the job reads `actions`). ios.yml no longer runs for a pull request (its `ios-full` label is gone with it: a branch's
whole iPhone run is `gh workflow run ios.yml --ref <branch>`); its whole run is the night's and a run by hand's. The
browser parts were dealt again by the times item 1874 recorded (run 45657128269, tests alone: pages 9.6 minutes, the
first phone part 7.4, the second 12.5): `test_phone_type.py`, `test_phone_fit.py` and `test_phone_back.py` (2.7
minutes) moved to the first. CLAUDE.md "Checks" and "Keeping a change short", CONTRIBUTING.md, docs/development.md,
ios/Next/README.md, `scripts/python_ci.py`, `scripts/browser_ci.py` and `scripts/merge_pr.py` say so.

What it costs: a break only macOS shows, or one two pull requests make together, reaches `main` before a macOS job
sees it; item 1899 makes it seen at once and keeps the owner's Dot off such a commit.

Measured before: a pull request that changed the package ran about 50 macOS minutes, its `ci` 13 to 20 minutes with no
queue and one to two hours with one; the 28 pushes to main of 22 to 25 November ran 55.7 macOS minutes each, 16.2 had
they been read by the push's files. After: the pull request's own `ci` (the pull request says how long).

Checked: `tests/unit/test_release_workflow.py` (the jobs' conditions, the `changes` job's events and ref, the release's
tag push), `tests/unit/test_browser_ci.py` (every browser file in one part); actionlint and zizmor on the workflows.
