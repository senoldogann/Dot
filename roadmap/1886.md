### 1886. A push to main runs the Python gate its files can affect and no browser part; whole suites at night

**Status: done (2026-11-25).** The owner, the evening of 2026-11-25: "no need to be that strict; don't keep running the
long tests; on GitHub only when really needed". Every push to main ran the gate whole (`gate`, `gate (part 2)` and the
three browser parts: 42 to 76 macOS minutes each, 55.7 on average over the 28 pushes of 22 to 25 November), and a push
that changed `ios/` ran the whole iPhone suite (about an hour on two runners).

What must hold: a push to main runs `gate` and `gate (part 2)` only when a file changed since main was last green can
affect them (`scripts/python_ci.py`, as for a pull request), and a decision that cannot be made (no green run found, a
base that does not fetch, a check that fails) runs them; it runs no browser part; a release (the push of its tag) and a
run started by hand run everything; what main no longer runs is run each night and when asked: `browser.yml` every
browser test (it did already), `ios.yml` the whole iPhone suite.

What skipping the browser parts on main costs (the lead's decision on the owner's word, 2026-11-25): main's own
run was what showed two pull requests that pass alone and break `main` together through files neither shares (item
1011; `scripts/merge_pr.py` brings a branch up to `main` only when they share a file). Such a break now shows in the
night's `browser.yml`, up to a day after the merge, and a pull request opened meanwhile runs its browser parts on the
broken `main`. A red night is fixed as a red `main` is. `scripts/merge_pr.py`'s docstring says so.

What was built (`.github/workflows/gate.yml`, `ios.yml`): the `changes` job runs for a push to main too (by its ref:
the release calls the gate from the push of its tag, which the called gate sees as its own push event). Its base for a
push is the commit of the gate's last green run on main, read from the API (the job reads `actions`): runs of main
that wait replace one another (item 1011), so the push just before may never have run, and the files changed since
main was last green are those this run must test. The jobs' conditions no longer ask whether the event is a pull
request: a job whose decision was not made (the `changes` job skipped, as in a release or a run by hand) or failed
runs. The browser parts skip a push to main. `ios.yml`'s whole run (the long UI parts and `e2e`) is the night's, a run
by hand's and a pull request's labelled `ios-full`; a push to main runs the short set as a pull request does.
CLAUDE.md "Checks", docs/development.md, `scripts/browser_ci.py`, `scripts/python_ci.py` and ios/Next/README.md say so.

Measured: the 28 pushes to main of 22 to 25 November, read by the new rule against the same files (those changed since
the previous green run): 4 would have skipped every macOS job, the others changed the package and run `gate` and
`gate (part 2)` alone; 1,560 macOS minutes would have been 453, 55.7 a push on average 16.2. Path selection alone, with
the browser parts still asked of `scripts/browser_ci.py`, would have made it 48.3: a merge of several pull requests at
once, which is most of main's runs, almost always holds a file of the package.

The browser parts were dealt again by the times the parts recorded (item 1874's artifacts of run 45657128269, tests
alone): pages 9.6 minutes, the first phone part 7.4, the second 12.5; `test_phone_type.py`, `test_phone_fit.py` and
`test_phone_back.py` (2.7 minutes together) moved to the first, about 10 minutes each, the same minutes in all.

Checked: `tests/unit/test_release_workflow.py` (the jobs' conditions, the `changes` job's events and ref, the release's
tag push), `tests/unit/test_browser_ci.py` (every browser file in one part); actionlint and zizmor on the workflows.
