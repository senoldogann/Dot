### 1849. DotNext opens a new chat as soon as its first message is sent

**Status: done (2026-11-25).** The owner, on his iPhone with the build of item 1759: "I started a new chat; as soon as
I sent the message it threw me back to the chats list."

What was there: the pencil opened a sheet with the composer; Send put the message in the outbox (`newChat`, keyed by a
client key, no thread id yet) and closed the sheet, which left the owner on the list, where the chat showed first as
a pending row and then as the daemon's row, to be tapped open. `RealDaemonWalkUITests` did exactly that tap.

What must hold: the chat is on screen from the send on, with the owner's words and where they stand; it becomes the
real chat in the same screen once the daemon answers (`POST /api/runs` gives the run and its thread); Back leads to
the list; a refused start says so in that screen.

What changed (the app and its engine; nothing in the daemon):
- `AppModel.startChat` returns the outbox key and remembers the first words of the chats this phone started
  (`startingChats`, in memory for the session).
- The sheet closes and the chat list selects that key at once; the key opens `StartingChat`: the owner's message with
  its delivery line ("Sending…", "Waiting for the link", or why it was refused), the words as the title, "Starting".
- The engine's store keeps, for the session, the thread each new chat's first message started, by its outbox key
  (`EngineSnapshot.startedChats`, set from the daemon's answer to `POST /api/runs`). When it names the key's thread, the
  list's selection becomes that thread: the same navigation destination draws `ChatScreen` in place (no pop, no push).
  The store's accepted message was not enough: it was dropped as soon as the list had the chat's row, which can come
  first; a chat this phone started now keeps that overlay until its own picture shows the words, so the owner's
  message never gives way to "Syncing…" across the swap (the pre-push review's two findings;
  `SyncTests.testANewChatsThreadAndWordsAreKeptWhenTheListHasItsRowFirst`, red without the change).
- Until the chat's own title is read, its title is the owner's first words, as `StartingChat` showed them, never blank.
- `RealDaemonWalkUITests` no longer taps the new chat's row in the list: the chat is open already.
- `ChatScreen` draws the chat's pending messages before its picture is opened (an empty projection of the thread), so
  the owner's message stays on screen across the swap rather than a "Syncing…" blank.

How it was checked: `StreamingLiveUITests.testANewChatStaysOpenAndBecomesTheRealChat` against the throwaway daemon
(`scripts/e2e_streaming.sh`): the pencil, a message, the owner's bubble within 10 s, the run's answer in the same
screen, the chat list never shown, Back leads to the list, the owner's bubble on screen at every
read (every 200 ms) from the send to the answer (passed); the owner's bubble, from the
test's element frames, stands at the same place before and after the swap (x 170.3, y 122.7, 219.3 × 51.3 pt both
times: a jump of 0 pt; the test fails over 1 pt), and on the screenshot at 3x its fill ends 16.0 pt from the right
edge, the chat's gutter (the element's accessibility frame reaches 3.7 pt past the drawn fill, so the inset is
measured on the pixels). It was not run against main, where the
sheet closes onto the list by design.
