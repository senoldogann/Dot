### 586. Reactions on Dot's messages, which Dot acts on while it works and after

**Status: phase 1 done (2026-10-23); phase 2, learning, waits for items 584 and 585.** The owner: "As in Grok Bot, I
want to add reactions to the agent's messages, and the agent should act on them, during the session or after it ends."
Under each message of Dot's in a conversation (its answer, and what it said in a step of a run) a button opens a
palette of seven reactions (👍 good, ❤️ love it, 👎 not right, 🔁 do it again, 📌 remember this, ❓ explain, ✋ hold on);
the ones that stand are chips, a second press takes one back. While the run works a reaction reaches it at its next
step, and ✋ holds it; after the run ended 👎, 🔁 and ❓ start a follow-up run in the same chat, 📌 keeps the message as a
note, and 👍 and ❤️ are kept as feedback. This phase builds all of that and the settings; what learning does with the
reactions is phase 2 (below). It was numbered 583 until its first push; the memory and skill items it will call are
now 584 and 585.

**What must hold, and what only informs.** A reaction is a small word of the owner's, and Dot runs with their rights,
so the point of the design is what a reaction must never do. The code under "Always needs a human" in REVIEW.md is not
touched: the properties are held in the run's inbox and in the manager, and each has a test that fails without it.

| What must hold | Held by | What only informs |
| --- | --- | --- |
| A reaction never vouches for what a run read: a note to a run at work clears no mark of untrusted content and is no instruction to the reviewer | `RunManager.tell` makes `UserInput(vouches=False, said="", reaction=…)`; the loop clears no taint and adds no instruction for it (`test_a_not_right_on_a_message_of_a_working_run…clears_no_taint`, whose control, a message of the owner, clears it) | the note's last sentence says a reaction approves no step, so a 👍 on "may I delete it?" is not a yes: the policy asks as before |
| The words of the follow-up that a reviewer takes as the owner's instruction are the owner's alone: no word of Dot's, which may repeat what a stranger wrote | the goal is a fixed sentence per reaction (`follow_up_goal`); the quote of the message goes only into the run's first message (`FollowUpOf.context`, `RunOpening.text`) (`test_a_not_right_after_the_run_starts_one_follow_up…`: the goal holds no word of the answer) | the quote is marked as Dot's own earlier text and no instruction |
| A follow-up starts as untrusted as what it follows up | `RunOpening.carried` is the run of the message and the chat's newest run (`RunManager._carried_by`), read at the start, also for one that waited in the queue (`test_a_follow_up_takes_the_chats_taint…`) | |
| A reaction is the owner's, from the page behind the API's token | the routes are under `/api`, which the guard answers only with the token (`test_the_routes_answer_only_with_the_token`); the owner's own click is the only caller | |
| A reaction cannot start a flood, or hold the daemon's places for ever | one follow-up per message and reaction, and `[reactions] follow_ups_per_hour` in one write of the store (`Store.claim_follow_up`); a burst on one run is one note; a hold stops its run after `[reactions] hold_minutes` | the page says when a limit kept a follow-up from starting |
| A 📌 is the owner's note, and marked when the run read outside content | `save_memory(…, tainted=Store.run_read_outside(run))`, a note of the owner's (no source run: it never rests) | |
| A 📌 never writes a secret into memory | the check of the memory tools (something that looks like a key, or a secret Dot holds) before `save_memory`: the pin is refused and stays off (`test_a_pin_on_a_message_that_holds_a_secret_is_refused…`) | |

**What was built.**
- *The store.* A table `reactions` (one row per run, message and reaction, kept when taken back so that a reaction put
  back starts no second run: `removed_at`; `follow_up_at` and `follow_up_run_id`; `note_id`), created for an older
  database by the schema that opens the store, and a column `queued_messages.follow_up` (a `FollowUpOf` as JSON),
  added as the other columns of the queue were. A deleted chat takes its reactions. `Store.put_reaction`,
  `take_reaction`, `message_reactions`, `thread_reactions` (a run a rewind took out of the chat is left out),
  `claim_follow_up`, `release_follow_up`, `link_follow_up`, `keep_reaction_note`, `assistant_text` (what a run said in
  a step) and `run_read_outside` (a run read outside content at any point: `run_queued` and `tool_result` events that
  say so, or what `dotx prune` recorded).
- *What a message is.* The run and a key: `answer` for the answer a run ended with (its `result`), `step-<n>` for what
  it said in its step `n` (the `assistant` event of that step). The key is in the page's timeline and the history, so
  a reaction stays on its message after a reload, in the turns before the run and on another screen.
- *The words (`agent/reaction_words.py`, pure).* The palette, the quote (one line, Markdown marks left out, secrets
  masked, no guillemet of its own), the note a run at work reads for one reaction and for several, what it does to the
  run (`ReactionAct`: `quiet` for a 👍 or ❤️, `note` for a 👎, 🔁 or ❓, `hold`, `release`), the owner's words of a
  follow-up, and what the follow-up reads under them.
- *At work.* `RunManager.tell(run_id, text, reaction)` puts the note into the run's `RunInbox` (the path a steer
  takes) with `vouches=False` and `said=""`. A `quiet` note does not give the step under way up (`RunInbox.asks`,
  which `arrival()` and the run's end read) and is dropped when the run ends first; the others do, as a message does
  (item 509). The service (`agent/reactions.py`) gathers the reactions on one run for 2.5 seconds (`BURST_S`) into one
  note, drops a reaction taken back that still waits, tells the run so when one it was told of is taken back, and
  tells a ✋ at once. A run that ended before the note reached it is told nothing: the reaction is done as after the
  run (`Reactions._missed`), and the pages hear `reaction_added` again with what it came to, the run it started.
- *The hold.* There is no pause of a run in Dot (`tests/smoke/test_agent_pause.py` is the pause of an agent's
  schedules, item 465; the only hold of a run is the takeover's, which waits at a tool call and is tied to the
  browser). A ✋ is a note with `reaction="hold"`: the loop, at the top of its next step, reads it, emits
  `reaction_hold`, and waits on its inbox (`_held_by_the_owner`) for a message of the owner (`reaction` none), a ✋
  taken back (`release`) or a stop; each ends it with `reaction_hold_ended` (`message`, `released`, `lapsed`). The
  wait is bounded by `[reactions] hold_minutes` (60): then the run ends cancelled with its own words
  (`RunHoldLapsed`), which keeps a forgotten hold from taking one of the `max_concurrent_runs` for ever.
  `RunInbox.holding` says a run waits, which `RunManager.holding` and `GET /runs/{id}` (`holding`) tell: the page's
  box then sends a message to the run at once (a message queued behind a run that waits for it would never start), and
  `RunManager.queue` lets a held run go on when a message is queued from another screen.
- *After the run.* `RunManager.follow_up_reaction` starts the follow-up as the chat's next run, as a message typed in
  the box would (`source` `ui`, the chat's kept choices, the chat's agent) or, with a run at work, queues it (`queue`
  takes the `FollowUpOf`, and `_start_queued` starts the run with its context and the files the owner put on it in
  the queue, within an agent's bounds for the chat of an agent, and links the reaction to it). A chat of
  a campaign and the thread of a delegated run take none: the reaction is kept as feedback. A queued reaction that
  the owner sends on to the run at work with Steer goes as a note that vouches for nothing (`RunManager.tell` with no
  `reaction`: it gives the step up and lets a held run go on, as a message does, and carries the files put on it).
  Its `steer` event holds `owner_text`, the words the owner sent, which the timeline and the history draw as their
  message, and which the page's "Sending to the run" line waits for.
- *The pin.* `save_memory` with the message's words on one line, cut at a word to `[memory] max_chars`, tagged
  `from-chat`, one of the owner's notes; marked tainted when the run read outside content; refused when the message
  holds something that looks like a key or a secret Dot holds, as `memory_save` refuses such a note. Taking the 📌 back
  forgets the note when it is as it was made, and leaves one that was there before or that the owner changed.
- *The record.* `reaction_added` and `reaction_removed` events of the run (the chat, the message, the reaction, what
  it did, the run it started), in `LIFECYCLE_KINDS` so that every page hears them, also after the run's stream ended;
  the page reads the chat's reactions once (`GET /threads/{id}/reactions`) and again on such an event, so the chips of
  a reload or of another screen are what the store holds.
- *The routes* (`server/routes_reactions.py`): `GET|POST /runs/{id}/messages/{message}/reactions`,
  `DELETE …/reactions/{reaction}`, `GET /threads/{id}/reactions`, `GET|POST /reactions/settings`, listed in
  docs/daemon.md.
- *The settings.* `[reactions]` in `defaults.toml` with comments (`follow_ups`, `follow_ups_per_hour`, `hold_minutes`,
  and what 👍, ❤️, 👎, 🔁, ❓ and ✋ do after a run: `follow_up` or `feedback`; the defaults are the owner's: 👎, 🔁 and ❓
  start a run), `ReactionsConfig`, `config_edit` (`[reactions]` keys, so the comments of the file stay), and live: the
  service holds the settings and the page's change is written to the file and rolled back when the file cannot be
  changed. Settings › General › Reactions has the switch and a choice for each of the six.
- *The page.* `static/js/reactions.js` (the palette: a menu of seven buttons that opens above or under its button,
  never past the window; arrow keys, Home and End, Enter and Space, Escape, Tab; ticked choices; the chips, which a
  press takes back; one palette at a time), `messages.js` (the answer's foot), `timeline.js` and `history.js` (the
  foot of what Dot said in a step, the lines of a hold, no line for a note, the owner's Steer press as their
  message), `views/run.js` (the model of the chat, the lifecycle events, the box's steering while held),
  `views/system.js` and the styles.

**Tests.** Unit: `test_store_reactions.py` (the rows, the claim and its limits, the chat's list, deletion, the queue's
column, the words of a step, outside content, a store from before), `test_reaction_words.py` (keys, quotes, notes, the
owner's words, the inbox that does not give a step up for a quiet note), `test_reactions_config.py` (the settings in
the file, their bounds). Smoke with the scripted model (`test_reactions.py`, `reaction_stand_ins.py`): a 👎 on a
working run's message reaches it as a steer at the next step and its taint stays (and a message of the owner clears
it); a 👍 is read at the next step and gives none up; a burst is one note; a reaction taken back; ✋ holds the run until
the owner writes, until the ✋ is taken back, until a message is queued, and stops it after the time of a hold or the
owner's Stop; a 👎 after the run starts one follow-up as the owner's message, once, with the quote in the run's first
message and not in its goal, as untrusted as the run it is about, queued behind a working run and started when it
ends, with the file the owner put on it in the queue (also in a chat of an agent), and Steered into it as the owner's
message to draw (a note that vouches for nothing, files along, a held run goes on); a reaction that comes as the run
ends, done as after the run, with its event; the limits (an hour's, one per message and reaction, the switch, a
setting); the pin (a note, marked when the run was tainted, taken back, a note that was there or changed, a message
that holds a secret refused). `test_reaction_routes.py`: the routes, their refusals, the token, the event every page
hears, the settings and a file that cannot be changed, the page's `holding`. Browser (`test_reactions_page.py`, Chrome
wide and WebKit on an iPhone): the palette and the chips, a press and a second press, after a reload and on another
screen, in the turns before the run, by keyboard, the foot of a step's message, a hold that holds the run until the
owner writes (the message is sent, not queued), a 👎 that reaches a run at work and leaves no line in the turns before
a later run, a follow-up the page goes on at, a queued follow-up sent on with Steer that is the owner's message on the
run's page and in the turns before, the pin, and the settings card. Mutations of the code (a reaction that vouches, a
quiet note that wakes the step, a hold that never holds, a follow-up that carries no taint, a note drawn as a line, a
Steer press with no line, a reaction done after the run with no event) each fail a test.

**Questions.**
- *The hold is mine, not the pause the brief named.* There was no pause of a run to reuse; the loop's hold is small
  and bounded (`hold_minutes`), and a ✋ on a run on one of OpenCode's models gets the note and no hold (OpenCode's own
  agent is not Dot's loop).
- *The hold stops the run when nobody writes for an hour.* Waiting for ever would take a place of the daemon for ever,
  and going on by itself would not be a hold. The stopped run keeps what it did in its chat, and the owner's next
  message there starts a run; its queue is held as after any stop. `hold_minutes` is in the file only.
- *The follow-up's words are generic* ("your answer above", "your message above"): the message is named in the quote
  the run reads, not in the owner's bubble, because a quote there would reach the reviewer as the owner's instruction.
  The bubble does not say which message when the chat has gone on since.
- *A reaction pressed in the last moment of a run*, before the run reads its note, is done as after the run (a 👎
  starts a follow-up); a 👍 or ❤️ in that moment, which asks nothing, is kept and told to no one.
- *A Steer press on a queued follow-up is the owner's message to draw, not to vouch.* The words they sent stand as
  their message in the conversation (a page that drew nothing left their press without a trace), and the press lets a
  held run go on, as a message does; but the note the run reads around them is Dot's, so it clears no taint and
  tells the reviewer nothing, as the reaction it came from would not. The words are a fixed sentence per reaction
  unless the owner edited them in the queue.
- *Reactions on what a delegated run said, or a campaign's session,* are kept and start nothing after the run; while
  it works they steer it as any run is steered.
- *Not built:* a reaction on a message of a run of a `dotx` command at work (kept as feedback), the quote of the
  message in the owner's bubble, a count of reactions (there is one owner), a setting of what 📌 does.

**Phase 2: learning, after items 584 and 585** (memory and skill lifecycle, branch `items-584-585-lifecycle`). What
the reactions give it, and what it will call, nothing of which is built here:
- the evidence: the rows of `reactions` (`run_id`, `message`, `reaction`, `created_at`, `follow_up_run_id`) and the
  run a follow-up started, whose status and result are the follow-up's outcome; a read `Store.reactions_since(since)`
  is what the nightly reflection asks for the reactions of the day;
- *proposing a lesson from the owner's words* (item 584): the nightly reflection reads a 👎 with the outcome of its
  follow-up, and may propose a lesson that waits for the owner's approval, as every lesson does;
- *pinning a note* (item 584): `Reactions._keep_note` calls the pin where it calls `save_memory` now, and taking the 📌
  back calls the unpin;
- *proposing a rewrite of a learned skill* (item 585): on a run that read a learned skill (the run's `skill` calls), a
  👍 or ❤️ counts as a success of that skill and a 👎 proposes a rewrite from the reaction and the message, for the
  owner's yes; this is `Reactions._after_run` and `_tell_run`, which already hold the run and the message;
- nothing learned skips the owner's approval.
