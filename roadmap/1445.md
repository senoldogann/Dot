### 1445. The Live Activity starts by push: the app gives Dot its push-to-start token

**Status: done (2026-11-24).** A run that begins on the Mac, or by a schedule, opened no Live Activity on the phone: only a run
the owner started in the app did (the app opens the activity itself). Since iOS 17.2 the phone can hand the daemon a token that
lets it start the activity by push; the daemon side (items 1425: `POST` and `DELETE /api/phone/live-start-token`, and the start
payload it posts to APNs) was waiting for the app to send it. Research of 2026-11-23 (Apple's "Starting and updating Live
Activities with ActivityKit push notifications": the token comes from `pushToStartTokenUpdates`, and a start carries an
alert).

What changed: `PushRegistrar` watches `Activity<DotFleetAttributes>.pushToStartTokenUpdates` (and reads the token iOS already
holds when it starts) and sends each token to `POST /api/phone/live-start-token` (`DaemonClient.registerStartToken`, five
tries as the other registrations, the phone's key). `Core/LiveStartToken.swift`, `StartTokenGate`: a token the daemon already
has is not sent again, one that is not lowercase hex of 64 to 512 characters (the shape the daemon refuses whole with a 422) is
not sent at all, and a token is noted only once the daemon took it, so one whose request failed is offered again when iOS says
it again or the app starts. `DELETE` (`DaemonClient.forgetStartToken`) goes when the phone's key is forgotten:
`AppModel.forgetKey` calls `PushRegistrar.forgetStartToken` **before** it stops the registrar and deletes the key, and the
request is made with the key read at that moment and kept out of the tasks that `stop()` cancels (a changed address forgets the
key through the same call); it also goes when Live Activities are switched off for Dot (`activityEnablementUpdates`: the
daemon would start nothing, and a start's alert would only ring), and switched on again the token iOS holds goes again.
A `DELETE` that does not get through (no link) leaves the token with the daemon until the phone is removed there, which
forgets it too (`docs/phone.md`). The device's registration is as it was (`start_token: null`: a token in it is kept and never
read), the activity's own token that ActivityKit gives once the activity started goes the way it did, and
`Shared/DotFleetAttributes.swift` is unchanged. The deployment target is iOS 18, so the iOS 17.2 requirement needs no
availability check.

Checked: `ios/DotTests/LiveStartTokenTests.swift` (9 cases: a token sent once and again when it changes, one not taken offered
again, the same token after a forget, the shape the daemon takes at 64 and 512 characters and not at 62 or 514, capitals,
non-hex and empty, the hex of a token, the `POST`'s route, key and one-key body, the `DELETE` with no body, a 422 not tried
again, the device's registration still carrying `start_token: null`). `xcodebuild test` on the iPhone 17 Pro simulator (iOS 26.5), the whole suite: 373 tests, 0 failures, this item's 9 new cases among them.
Not checked: on a phone. The simulator gets no push-to-start token and no APNs, so no token was sent from a running app and no
start was received; whether iOS yields the token it already holds when the sequence starts (the app reads
`pushToStartToken` first for that reason, and the gate makes a second send harmless); that the `DELETE` on a forgotten key
reaches the daemon before the process is suspended (it is sent at once, with up to five tries).
