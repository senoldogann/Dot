### 1425. The Live Activity starts by push on a phone that shows none (push-to-start, iOS 17.2 and later)

**Status: done as far as the rows allow (2026-11-24).** Comes after items 1420, 1421, 1422 and 1423 in the same pull request, whose watch it edits. From the research of 2026-11-23 (recommendation 9). The daemon only updated and
ended an activity the app opened (item 1096 had taken the push-to-start away because Apple requires an alert with it); a
run that went on while the owner was away from the app never reached the lock screen.

What changed: `POST /api/phone/live-start-token` (`{token}`, lowercase hex; the phone's own key, the Mac's token is a 403;
204) keeps ActivityKit's push-to-start token for the phone whose key sent it, apart from its device token (`notify/live_start.py`,
the `kv` table), so neither registration waits for the other or erases it; `DELETE` (204) forgets it; a removed phone takes it.
`ApnsWatch` starts the activity (`_start_where_none_shows`) on a phone that has the token, no activity registered, a lease that
is not foreground (item 1420) and no start in the last ten minutes (`START_EVERY_S`, held in memory), when a row at work is
worth it: a command that ended in the background (`START_AT_ONCE`) at once, any other row once it has worked `START_AFTER_S`
(30 s); it looks when a run starts and every five seconds. The push is `live_start_payload`: `event: start`, `timestamp`,
`content-state` as `live_update_payload` builds it, `attributes-type: DotFleetAttributes`, `attributes: {fleetId: fleet}`,
`input-push-token: 1`, the **required** alert (fixed title "Dot is working" and the fixed line, no sound) and `stale-date`, to the start token with
`apns-push-type: liveactivity`, `apns-topic: <bundle id>.push-type.liveactivity` and `apns-priority: 10`; the activity that
starts sends its own token the way it always did (`POST /api/phone/apns/activity`), and no start is sent again for the runs it was
sent for. A token APNs calls gone is forgotten (the device is not); a start that could not be sent (unreachable, refused)
counts as the try for the ten minutes, but not for its runs: they are tried again when the ten minutes are over, and only a
start that APNs took is recorded for them (the pre-push review found the runs recorded before the send).
What I rely on, from Apple's "Starting and updating Live Activities with ActivityKit push notifications" (read 2026-11-24,
https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications):
"Start Live Activities with ActivityKit push notifications" (the token from `pushToStartTokenUpdates`, which iOS 17.2 introduced:
Apple's page of the property; sent to the server; the system starts the activity, wakes the app and the app receives the update
token); "Construct the payload that starts a Live Activity" (`event` `start`, an `alert` and `attributes-type` and `attributes`
required, with `content-state` and `timestamp`; and, on iOS 18 and later, `input-push-token: 1` "to start a Live Activity and
receive a new push token", which the payload carries so that the started activity has a token of its own to send back: a key
iOS 17.2 does not read, and the page names no refusal for it there); "Construct the ActivityKit remote push notification payload" (the three headers);
"Determine the update frequency" (priority 5 or 10; 10 counts toward the hourly budget, so a start, at most once in ten minutes for
a phone, goes at 10). `docs/phone.md` has the contract.

What is not done: **a schedule's or a loop's run cannot start one.** The item asked for a start "only for a run that is
unattended (schedule, loop, background) or has worked 30 s", on "the first row", but a schedule's run (a loop's too: its runs
carry the source `schedule`) is no row of the activity by design (items 1093 and 1096: the owner's own runs, not a schedule's), so
it can never be a first row, and a start with the rows empty would open an empty activity. Only a command in the background (at
once) and any other row of the activity that works long qualify: a run of the owner's, or the run that goes on in their chat when an
agent's order came back (`work_order`) or a run was resumed, which are rows too (`follows_live`: no parent, no source of
`UNWATCHED_SOURCES`, no eval). To light the lock screen for a schedule, `follows_live` has to let its runs be rows
(which changes what an open activity shows, and means a notification for each schedule that fires): the owner's call, not made
here. The ten-minute limit is in memory: a daemon that starts again forgets it (at most one extra start).

Checked: `tests/unit/test_apns.py` (the payload, whole; the one at-once source pinned to the manager's `BACKGROUND_SOURCE`;
a start to the right token with the right headers, priority and alert, once in ten minutes and not again for the same runs; the
