### 655. One web search, in the owner's order, with the search APIs that take a key

**Status: done (2026-10-25).** The owner asked (in Turkish) whether web-research is a pointless feature unless Tavily
or Brave are used, why there is no settings page for the keys of web search, and that they want to change the order
(for example Ollama, then DuckDuckGo). They chose a lasting order in Settings and one search tool.

**What was there.**
- **Two search tools side by side.**
  - Dot's own `web_search` (SearXNG → Ollama → Anthropic → DuckDuckGo and Brave pages → Dot's Chrome,
    `[web] search_backend`).
  - web-research's `mcp__web-research__web_search` (Brave or Serper with a key in its environment, then DuckDuckGo,
    Google in Camoufox, Yahoo).
  - The owner's runs used both, 41 and 36 searches.
- **The orders were not the owner's to change.** Dot's was in `config.toml` only. web-research's keyed providers could
  not be given a key at all: Dot passes the built-in server no keys.
- **Tavily and Exa searched only as connectors.** They are in Customize › Connectors, each with a key, as tools of
  their own beside the two searches.

**The change.**
- **`web/keyed.py`** asks the search APIs as their documentation says: Brave's Search API (GET, `X-Subscription-Token`),
  Tavily (bearer), Exa (`x-api-key`, a highlight of each page and its date) and Serper (`X-API-KEY`, Google's results
  with their dates).
  - The key is in a header and nowhere else: not in an address, a body, a log line or an error.
  - A 429 benches the rung for a minute, and a 401 or 403 says the key was refused and where to check it.
  - The answers are parsed into hits, their HTML marks taken out.
  - `WebClient.get_json` is the GET of an API, as `post_json` is its POST.
- **The rungs.** `SearchEngine` gains `brave_api`, `tavily`, `exa`, `serper` and `web_research`.
  - `[web] search_order` is the ladder when set. An engine whose key is not set stays in it and is passed over, saying
    "no key: set X in Settings › Web search".
  - The browser rung only with Dot's own browser, and the web-research rung only while that server runs.
  - With no order, the auto ladder puts the APIs whose keys are set and the web-research search before the scraped
    engines.
- **One search tool.**
  - The built-in web-research server's `allow` list offers a run its other seven tools, and not its search or
    `web_health`.
  - Its search is the `web_research` rung. Dot asks it with the query the run gave `web_search`, which Dot's policy
    judged, and the count alone (`McpHub.call_unoffered`, read-only). Its compact answer comes back as hits with
    their dates.
  - A tool a later version adds is offered once Dot names it (`OFFERED_TOOLS`), after its arguments are judged.
  - A server of the owner's named web-research keeps all its tools.
- **Live.** `SearchKeys` keeps which APIs have keys and the order, so a change holds from the next search with no
  restart.

**Tests.**
- **`tests/unit/test_search_keyed.py`:**
  - each API's request, with the key in a header only;
  - its answer read;
  - a 429 benches, and a refused key is said without the key;
  - an engine with no key is passed over saying so;
  - the web-research answer is read;
  - the order and the auto ladder;
  - the config refuses an engine twice or an unknown one.
- **`tests/smoke/test_builtin_mcp.py`:**
  - the server lists nine tools and a run is offered seven;
  - `web_search`'s rung asks the server with the query and the count alone, and its dates come back;
  - every query is judged by Dot's rule, since there is no search but Dot's.
- `dotx eval check` passes.

**The reviews.**
- **The pre-push review's first pass** found that an order holding Ollama or Anthropic with no key ended every search
  with the key's error. Each is now passed over saying so, as a search API with no key is
  (`test_ollama_and_anthropic_with_no_key_in_an_order_are_passed_over_and_the_search_goes_on`, which fails without the
  change). It also found that `docs/extending.md` still told of the server's search as a run's tool.
- **The independent security review** (22 tool calls) found nothing that gets through. It checked these:
  - keys only in a header, with no redirect followed;
  - the four variables alone written, a value of printable characters only;
  - every route behind the token;
  - the query judged before the rung, which sends `{query, limit}` alone;
  - the server's search unreachable by a run;
  - the APIs bound by the host lists as the Ollama rung is;
  - every rung's hits fenced as untrusted.
- **The pre-push review's third pass** found four places that still told of the old search, and they were all put
  right:
  - `dotx doctor` showed the ladder of `search_backend` whatever the order was. `_search_row` now climbs as a run does,
    and names the keys an order lacks (`test_the_doctor_shows_the_order_a_run_climbs_and_the_keys_it_lacks`).
  - `README.md` and the comment of `[builtin_mcp] web_research` in `defaults.toml` still described the server's search
    as a tool.
  - `docs/safety.md` did the same.
  - The connectors page test now expects the seven tools offered.

  One rebuild of the branch, on a main that had moved, had taken back items 651 to 653. The pass caught it before
  anything reached origin, and the branch was rebuilt from this change's own diff.
- **A web-research rung whose server stopped** between the ladder and the search ended it with a `KeyError`. It is now
  passed over.
- **Its hardening is taken.**
  - A key an API echoes in an error body is masked (`redact_known`).
  - `McpHub.call_unoffered` says that its one caller names its server and tool as constants.
  - An order whose only rungs cannot be climbed here leaves the search to the auto ladder rather than to no engine.
