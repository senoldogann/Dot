### 1360. `GET /api/runs` takes `before`, so a client walks a long chat back a page at a time

**Status: done (2026-11-23).** Found while writing the second slice of the iPhone app (item 1361): a chat on the phone
holds its newest twelve runs and reads older ones as the reader scrolls up. `GET /api/runs` had `limit` and `thread_id`
only, so the only way back was a bigger `limit` (up to 200), which reads again every run already held at each page.

- `RunsQuery.before` (a time in epoch seconds, greater than zero, no NaN or infinity), `Store.list_runs(limit, thread_id,
  before=None)`: with it only the runs that began before that time (`created_at < ?`), still newest first and still
  without the runs a rewind took out of their chat. Left out, nothing changes: the newest page, as the web UI and every
  other caller read it.
- A client that pages writes the cursor with every digit of the oldest run's `created_at`: a time rounded up to the
  microsecond lets the run it was read from through again. (Found by running the app against a real daemon: the first
  page of the phone's reading repeated its last run; the phone now writes the double as Swift prints it, which reads back
  exactly.)
- `docs/daemon.md` says so.

Checked: `tests/unit/test_runs_before.py` (a chat of seven runs walked back three at a time reads each once, newest
first; a time before the oldest holds none and one after the newest holds all; no `before` is the newest page; another
chat's runs are never read; the query takes a time and refuses zero, a negative one, NaN and infinity); the same page
read over HTTP from a scratch daemon with 26 runs (twelve, then fifteen before the twelfth, `before=-3` refused 422);
`ruff`, `mypy`.
