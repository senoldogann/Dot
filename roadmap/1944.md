### 1944. The daemon no longer freezes on a path's classification or a log line

**Status: done (2026-11-26).** Item 4 of the review of 2026-11-26 (`reports/review-2026-11-26/A-runs.md`, problem 5):
12 `loop_stalled` in a week, seven stalls of 9.6-14.8 s in two minutes on 11-26. The stacks ended in
`policy/paths.py` `_is_temp`, `os.path.realpath(tempfile.gettempdir())`, reached from `tools/base.py` `classify_now`
on the event loop, and in `core/logs.py`, `self._handle.flush()` (2.1-3.2 s).

What must hold:
- Every path is classified as before: the same class for every path (`workspace`, `temp`, `system`, `home`, `dot`,
  `protected`). The workspace is resolved on every call as before, since a run can change what it holds; the system's
  own places and the temporary folder are resolved once, as nothing a run does moves them.
- No log line is lost on the way out: the lines still waiting are written before the process exits, and a line logged
  after that is written by its caller. The lines keep their order. A log call still never raises.
- A slow disk holds no caller: a log call returns without touching the disk.

What changed:
- `policy/paths.py`: `_resolved_roots` resolves a set of prefixes once (`functools.cache`); `_is_temp` and `_is_system`
  use it, `_is_temp` keyed by the folder `tempfile.gettempdir()` names (which Python reads from `TMPDIR` once for the
  process). A link a run later puts in place of the temporary folder no longer moves it.
- `core/logs.py`: `QueuedLog` puts each line on a queue that a thread of its own writes through `RotatingLog`;
  `configure_logging` registers its `close` at exit, which writes what is left. A line that finds 100,000 lines waiting
  is dropped and counted, as a line the disk would not take is (`log_lines_dropped`), so a disk that takes nothing does
  not grow the daemon without bound. A process killed outright (SIGKILL) loses the lines still queued.
- The pre-push review found that a line whose write failed with anything but an `OSError` ended the thread: a lone
  surrogate (a file name of bytes that are no UTF-8) failed it with a `UnicodeEncodeError`, and every later line was
  lost and the exit waited on a full queue. The file is opened with `errors="backslashreplace"`, so such a character
  is written as its escape; any other error of a line is said on stderr (`daemon.err.log`) and counted among the lines
  lost, and the thread goes on; `close` puts its last item only while the thread reads.

Measured (the micro-benchmark in the pull request's body, on the owner's Mac): `classify_path` 340 µs a
call before, 78 µs after; a log line costs its caller 13.5 µs before and 0.9 µs after on a normal disk, and on a disk
whose flush takes 50 ms, 52 ms a line before and under 0.01 ms after, with every line written.

Checked: `tests/unit/test_kernel_paths.py::test_a_classification_resolves_the_system_and_temporary_places_once_and_names_them_as_before`,
`tests/unit/test_log_rotation.py` (a line returns at once on a slow disk and every line is written in order by the exit;
a full queue drops and counts; a line that cannot be encoded or written leaves the thread writing the next, and the
exit returns, named in REVIEW.md as a check made from a review), ruff, mypy. `docs/configuration.md` says how the log is written.
