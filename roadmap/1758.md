### 1758. Settings › Phone shows a QR code that opens Dot Next with the address and the code, and one tap pairs it

**Status: done (2026-11-25).** The lead's order of 2026-11-25, after the owner called DotNext's pairing screen shabby:
the iPhone's camera on the Mac's screen should pair the app, as the reference's does.

What was there: Settings › Phone showed the code to type and a QR of Dot's address (`GET /api/phone/qr/dot`), which
filled the address and left the code to type.

What must hold:
- `pairing.py` and `guard.py` ("Always needs a human") are not changed: the code is made, redeemed and refused as
  before; the new route only draws the code that is good now.
- The picture holds no words of the caller's (it is not a QR of any text asked for) and is drawn only for the Mac's
  own key: a phone can make no code, so it gets no picture of one (403 `PhoneRefused`).
- No code on screen, or no address on a tailnet: 422 with what to do.

The design: `GET /api/phone/pair-qr` in `routes_phone.py` draws `dotnext://pair?host=https://<[server] reach>&code=<the
current code>` with the existing Core Image generator (`dotagent.qr`); `views/phone.js` shows it under the code each
time a code is shown, with one line ("scan it with the camera, and the app opens with the address and the code
filled"); without an address it says why there is none. The app's side is item 1759 (`pairingStart` of item
1757).

How it was checked: `tests/smoke/test_phone_reach.py::test_the_pair_qr_opens_dot_next_with_the_address_and_the_code_on_screen`
(422 before a code, the QR read back by macOS's detector, the code then pairs, a phone's key refused, 422 without an
address) and `::test_a_shown_code_comes_with_the_qr_code_for_dot_next` (browser: Show code, then the picture and its
line); both fail without the change (404, no picture).
