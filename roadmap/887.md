### 887. wait_until: a run waits in code, not in model turns

**Status: done (2026-10-31).** **Asked** by the owner, who asked to read milind-soni/OpenMausBot and take what Dot can.
Its waits were second on the study's list: probes run by code, with no model. On the owner's Mac, in the week to
2026-10-31, runs slept and polled 131 times in 41 runs (`sleep 60; gh pr checks 97`, `sleep 20; tail …; curl …`). Each
poll was a model turn, and a long one was a shell call held for its sleep.

**What holds.**
- `wait_until` names exactly one condition: a command, an address or a file. `contains` narrows it. The tool checks
  every `every_s` seconds (2 to 600) for up to `within_minutes` (at most 60), then says the condition held, with the
  time and the count of checks, or that it did not hold, with what the last check saw.
- Each condition is classified as the tool it stands for, under that tool's name: a command as `shell`, an address as
  `web_fetch`, a file as `read_file`. The owner's rules for those tools bind a wait as they bind the tool.
  - The first push classified a wait under `wait_until`. The pre-push review found that a rule written for `shell`
    commands did not bind a wait's command.
- A command is a check only when the shell guard reads it as reading: risk `safe`, no flag, no changed file. Any other
  line is refused before it runs, since it would run again and again.
  - The first push also took `low`. The review found that `low` is not reading: `git pull`, `git commit` and a script
    run are `low`. A network check (`gh pr checks`) is `low` too, so a command that reaches the network is no check.
    The wait is on its result instead, a file or a public address.
  - The second review found the field's own example was `gh pr checks 12`, which the tool refuses, and that
    `git ls-remote`, which the guard reads as safe but which fetches, was let through. Now a line that fetches is
    refused whatever its risk, and the texts the model reads give only examples the tool takes.
- An address goes through `checked_address`, where `web_fetch` may go. Only its status and whether the page holds the
  text come back, never its words.
  - An address on the local network, with `[web] allow_private_hosts` off, ends the wait at once. The refusal is a
    `PrivateHostRefused` (`core/errors.py`, raised by `web/client.py`), told apart by its type and not by its words,
    as the review's nit asked.
- A file is classified as `read_file` classifies it, so a protected place asks. It is opened as `read_file` opens
  one (`_opened`, item 681), with no link followed along its path. A link that came there after the call was allowed
  ends the wait, and it is not read.
  - The third pre-push review found the first pushes followed links. A file awaited is usually not there yet, so it is
    classified as a plain workspace read. A link that a background command of the run put there later, to a protected
    file, would have been read again and again for `contains`: a secret guessed one try at a time.
- It is in a tool group of its own, `waits`, as the core group stays about a third of the tool definitions. `shell`'s
  description points to it in place of sleep.
- The owner's stop and the emergency stop end it as they end any call.
