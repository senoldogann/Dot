### 462. A schedule runs as one of the owner's agents

**Status: done (2026-10-21).** The fifth of the nine ideas taken from OpenBot (item 449 has the plan), its fourth part:
"a schedule runs as one of the owner's agents". Until now every schedule ran as Dot, with every tool, so an agent made
for one job (its instructions, its tools, its model) could not do that job on a schedule. The design was split in three:
this item is the core; a schedule made in an agent's chat keeping the agent (`chat_options`, a tool, so `dotx eval
check`) is item 463, and the templates' suggested schedules, whose ten goals the owner reads before they become real,
item 464. **As built.** `ScheduleOptions.agent_id` (a column; NULL is Dot, as every schedule of an older database), in
the form's **Agent** (Dot, then the agents) and `agent_id` in `POST` and `PATCH /api/schedules`. Saving a schedule
refuses an agent that does not exist (404) and Dot named as one (422, `plans._check_agent`). A `PATCH` that leaves
`agent_id` out keeps the schedule's agent (`model_fields_set`), so a page or a script that does not know of it never
makes an agent's schedule Dot's, with every tool; `null` does. `Scheduler._start` starts the run of a firing, at its
time and by hand, with `RunManager.start_firing_for_agent`, whose bounds are `agent_bounds`, shared with
`start_for_agent`: the schedule's own model, reasoning level and approvals, else the agent's, else the configured ones;
never `stricter_approvals` (the critique), so a yolo schedule of an agent that asks runs yolo, and one left on Default
takes the agent's mode, which the form's Default names ("Default (the agent's: …)") and the row's approvals chip shows.
The run carries the agent's id, so the loop adds its instructions and offers its tools only, and the row wears the
agent's face with an "As <name>" chip (`ScheduleView.agent`: id, name, look, approvals). `Store.delete_agent` switches
the agent's schedules off in the same write (`AGENT_DELETED_STATUS`, "switched off: its agent was deleted", no agent
named, no next time), so none fires as Dot nor fails at every tick; switching one on again clears that status as it
clears item 458's, and the agent page's delete dialog says how many are switched off. The critique's pre-existing nit
taken: `RunManager._resume` keeps the run's agent, so a cut-off run of an agent, of a schedule or of a chat, goes on as
that agent. `dotx schedule list` says "as agent <id>". Yolo is untouched: a schedule without an agent runs as before, an
approval mode chosen is kept as it is, and the agent's mode is the owner's own choice for that agent, as for a chat with
it. Tests: `tests/unit/test_agent_bounds.py` (the order, yolo chosen over ask, Default taking the agent's yolo or the
configured mode), `tests/unit/test_store_schedule_agent.py` (deleting an agent switches its schedules off and leaves the
others; a store from before the column has every schedule Dot's), `tests/smoke/test_schedule_agent.py` (a real
scheduler, the routes and a stand-in model recording the tools each request offered: four schedules of agents run as
them, offered the agent's tool and the core ones only, with yolo over ask, the agent's yolo, the configured yolo and the
agent's ask; Dot's schedule as before; a `PATCH` without the agent keeps it, an unknown one 404, `null` Dot's, Dot named
422; deleting the agent switches its schedule off and a tick after starts nothing; a cut-off run of an agent resumes as
it; the page at 1280 px light and at 390 px dark as a touch screen: the row's chips, the form's Agent and the Default it
names; the keep and resume checks fail without their fixes). Docs: `docs/memory-and-schedules.md`,
`docs/agents-and-campaigns.md`, `docs/autonomy.md`.
