### 1354. The goal check goes on to a standby model when the review model cannot answer

**Status: done (2026-11-23).** Found by the autonomy audit (`workspace/autonomy-audit-2026-11-23.md`, finding 1). In the
owner's own database five of the nine failed goal-mode runs failed for one reason: the goal check could not run. On
2026-11-23 the review model was `antigravity:gemini-3.8-flash-high`, its quota answered HTTP 429 "resets in 116 h", and
`loop.py` ended each run `failed` with "the check could not run (...); this answer is not verified" although its work was
done (a mail sent and read back in Sent, videos rendered, a release submitted). `events` holds five `goal_check` events
with `decision: "error"`, each of a run that ended `failed`. Dot's learning already passed a question to another model
when the first was spent (`_decide_passing_on`, item 249); the goal check, the one question every unattended run ends
on, asked one model only.

What changed: `agent/goal_chain.py` asks the review model and, when it cannot answer for a while
(`llm.router.unavailable_reason`: credits, window, quota, rate, a refused key or access, no key), each model of `[models]
standby` after it, as a run moves to a standby model when its own is spent (item 1225). Any other error is raised as it
comes; when none can answer the first error is raised and names every model asked. `loop.py` and the campaign's claim
(`tools/campaign.py`) build their checker through it. `agent/review.py` (the review of a run's actions) is untouched and
still asks its one model.

Checked: `tests/unit/test_goal_chain.py` (seven tests: passes on a spent quota and on a refused key, asks one model when it
answers, raises another error at once, names every model when none answers, leaves a lone model's error as it was).
Not done: the ending of such a run is still labelled `goal_check_refused` ("refused by the goal check") when no model could
check, which says more than happened; a new ending touches every reader of `Ending`.
