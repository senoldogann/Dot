### 1741. A hop count across agents: a runaway chain of hand-offs is stopped for a run that asks, and reported in yolo and free mode

**Status: done (2026-11-24).** The market research of 2026-11-24 (M2, idea 4; agent-autoloop's hop-count TTL) found no depth
limit for `message_agent`, work orders, delegation or Dot's own initiative: two agents that keep handing each other work
cost tokens until the owner notices. The first cut refused in yolo and free mode too; the owner's standing word (nothing new
refused there, [Freedom](../docs/freedom.md)) won, so there the limit only reports.

Measured first, read-only on the owner's store (530 runs since 2026-10-28; counts only): 441 runs began a chain, 89 were
hand-offs (73 `delegate`, 16 `team`); the deepest chain is **1** (no hand-off started from a hand-off: a delegated run gets
no `delegate`, `message_agent` or work-order tool, `NOT_FOR_DELEGATED_RUNS`); 10 work orders, each assigned by a run of
depth 0; one run woken by its answer; the widest fan-out of one run is 14, which is not depth. The longest chain
a lead's wake after an answer can make adds one a cycle (the lead's run woken by its agent, which hands out again).

What must hold:

- (a) Every hand-off between agents is one hop further than the run it came from: a delegated or messaged run, a work
  order's attempt (all three through `RunManager._launch_helper`), the lead's run woken by an answer (it keeps the count
  of the furthest run it reads: a hand-back does not begin a chain), the run a helper's reports wake, and the run that
  does a thing a run put on Dot's list (`TodoRecord.source_run_id`). A resume of a run keeps the run's count. A message of
  the owner, a schedule's firing, a watcher's alert, the look for work: 0.
- (b) No run can set or lower it: the count is a column of `runs` written by the manager from the run the hand-off came
  from; no tool takes a count.
- (c) Past `[agent] max_hops` (default 8, `0` off), **for a run that asks** (`ask`, `auto`, `supervised`, with free mode
  off) the hand-off is **not made**: logged (`hop_limit_reached`), the caller gets `HopLimitReached` (the tool's error,
  which tells the run not to retry and to say the chain stopped), a thing on the list is let go with that reason and the
  owner is told, a woken lead is not woken (the lead finds the order with `work_orders`), and the owner gets **one** card
  on the run it came from while one stands: "Allow once" or "Stop".
- (d) "Allow once" is the owner's answer: `RunManager._carry_on` sets the asked run's count, and the run at work in its
  chat, back to 0 (`Store.set_run_hops`, the one place a count is lowered, reached by the owner's answer and by no tool)
  and hands the run the answer as their message, or starts a run from it; any other answer leaves the count.
- (e) **In yolo and free mode nothing is refused**, whether the run hands off or is handed to (the mode of the run the
  hand-off comes from counts too: a yolo lead messaging an agent set to ask) (the owner's standing word, `docs/freedom.md`; the lead's decision of
  2026-11-24 after the first cut refused there too and the review asked who had agreed): past the limit the hand-off is
  made, logged (`hop_limit_passed`) and the owner is told once (a notification, at the first hand-off past the limit,
  opening the run it came from, where Stop is; once for each run that hands off). No question goes through the approval broker and nothing waits; what
  bounds a runaway chain there is the owner's own budget setting. `_leave_hop_card` is therefore a gate-kind place
  (`GATE_SITES` of the freedom test), reached by no yolo or free run, and no row of `KNOWN_ASKS`.
- What only asks: nothing new in yolo and free mode. The default is above every chain measured, so a run that worked
  before is denied nothing in any mode.

What changed (`store/db.py`, `store/models.py`, `config.py`, `defaults.toml`, `core/errors.py`, `agent/loop.py`,
`agent/limits.py`, `agent/manager.py`, `proactive/initiative.py`):

- `runs.hops INTEGER NOT NULL DEFAULT 0` (an additive defaulted column), `RunRecord.hops`, `RunOpening.hops` and
  `from_run_id`; `RunManager._keep_to_the_hop_limit` at the head of `_launch_run` (the one place every run starts through),
  `over_the_hop_limit` (pure), `_tell_of_the_hop_limit` (yolo and free), `_leave_hop_card` (an `ask_user`-shaped question with the two options, so the pages need
  nothing new).
- `start_own` takes the run that put the thing on the list; the initiative lets a thing go when the limit stops it, not
  to try it at every tick, and tells the owner (a yolo initiative run is not refused).

Checked: `tests/smoke/test_hop_limit.py` (a real manager and the scripted model: the delegated run has hops 1, the run
woken by its answer keeps 1, and in yolo its next `delegate` is made and the owner told once; an `ask` run is refused with
one card for three tries, a yolo run and a run in free mode are not; Allow once resets the count and another answer does
not; no tool takes `hops`; fails with the yolo exemption taken out and with the wake resetting the count), `tests/unit/test_hop_limit.py`, `tests/unit/test_store_schema.py` (the
pinned digest with the column), `test_freedom_contract.py` (the card's place is listed with the gate's), the initiative, wake, delegate and resume
tests; `dotx eval check`.

Not done: `send_to_chat` notes (a run sends six at most, and a note starts nothing); a schedule a run makes (a firing
starts a chain at 0, as a person's schedule does); no per-chain view of the count in the pages.
