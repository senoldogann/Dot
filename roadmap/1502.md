### 1502. The tools of a run as files: a typed function for each tool a code may call, found with `search_tools`

**Status: done (2026-11-24).** The "tools as files" and "load on demand, for code" parts of Anthropic's note (the design is
in `roadmap/1500.md`): the model's code finds its tools as it finds a library, and no definition of any of them goes into a
prompt.

**As built.** `codemode/toolfiles.py` makes, from the tools a code may call (`deny.callable_from_code` of the run's tools,
item 1501), a package for `dot_tools`: `servers/<server>/<tool>.py`, one function each. The signature is keyword-only and
made from the tool's flattened JSON schema (`tools/schema.py` has no `$ref` left): `string`, `integer`, `number`, `boolean`,
`null`, `array` (of what its items are), `object`, an enum or a const as `Literal`, `anyOf` and `oneOf` and a list of types as
a union, `Any` for what a schema does not say or Python has no name for; a required parameter has no default, an optional one
is `T | None = None` and is left out of the call when it is `None`; a tool that takes more than it names (`additionalProperties`)
takes `**more`. A parameter Python cannot take as it is (`from`, `a-b`, `2fa`, one that two make the same) is renamed and the call
carries the tool's own key. The docstring is the description (cut at 6,000 characters, the catalogue holds it whole), the name
the bridge calls the tool by and its parameters, each with its type, whether it is required and its words cut at 400; it is a
string literal made by `repr` as the first statement of the function, so that a description, which for an MCP tool is third
parties' words, is never anything but text, whatever quotes, escapes, braces or code it holds (a test tries eight such, and
one of 20,000 characters, and reads the file's syntax tree: the function holds the docstring, one assignment and one return).
A server's `__init__` imports a tool's file when it is asked for and gives the function, not the module (`from
dot_tools.servers.github import create_issue`), lists its tools for `dir`, and says so for a name it has not. `catalog.py` (item
1501) makes the names: valid, unique and the same for the same tools, and an MCP server named `dot` is `dot_mcp` (a test found
the first version putting its tools beside Dot's own). `dot_tools.search_tools(query, detail, limit)` (at most 25, the
whole query as a name first, then each word in a name, then in a description) and `dot_tools.list_servers()` read the
catalogue; `detail="description"` adds the import line and the name `dot_tools.call` takes, `"schema"` the parameters.

*Written once.* `_prepare` writes the files only when the digest of the catalogue (and the form of the files, `FORMAT`) differs
from `dot_tools/.digest`; the static files (the launcher, the bridge, `dot_tools`) are written before every start. When the
tools differ, `install` first removes the `servers` folder with `Tree.remove` (a new function of item 1500's `tree.py`: it
enters no link, removes the link and not what it leads to, and a link in the folder's place is removed as the link it is), so
that a tool the run no longer has is not left to be imported: the first version left the stale file, and `from
dot_tools.servers.github import class_` then gave the old module, found by a test that expected an `ImportError`.

*The model's side.* `code_run`'s description (1,186 characters, under the 1,200 the brief asks) teaches the import form,
`search_tools`, `list_servers`, `call`, the refusal and the error, and what is not callable; it does not depend on how many tools
the run has (a test compares its definition before and after 300 tools are made into files).

**Measured** (this Mac): 300 tools, ten servers of 30 with eight parameters each and descriptions of 2,000 characters: 313
files, 2.5 MB, made in 10 ms; the first `code_run` of a run, which writes them and runs the sandbox probe, 84 ms, the next
29 ms.

**Checked by** `tests/unit/test_code_tool_files.py` (19 tests): the mapping of every kind of schema to its annotation and the
renamed parameters (read from the file's syntax tree, and compiled); a tool with no parameters and ones that take more; a
description in eight forms; the call (a function made from the file, called with a stand-in for the bridge: the tool's name,
only the arguments given, the tool's keys, `TypeError` for a missing or an unknown keyword and for a positional one); a server's
lazy imports (the real files as the daemon writes them: the function and not the module, `dir`, the error for another name);
300 tools made fast and the same in any order; and, in the real sandbox through the real executor: a code that imports tools of
Dot and of two MCP servers, calls them with keywords, reads a docstring and a signature, and is refused what it should be
(`TypeError`, `ImportError` for `finish`); the files written once and again for other tools, and a tool the run is not given
having no way in; `search_tools` and `list_servers`, the 25 of the cap, the ranking, the errors. `test_code_sandbox.py` holds
`Tree.remove` against links. `test_code_run_gate.py` (item 1501) runs through the typed files too, and holds the deny list:
each name of it, its reason, that it names a tool Dot has, and that the gate is not asked.

Not verified: a real MCP server's schemas (the stand-ins' are of the shapes tried; the schemas Dot hands a provider are
flattened by `tools/schema.py`, which the files rely on), a server of hundreds of tools beyond the 300 measured.
