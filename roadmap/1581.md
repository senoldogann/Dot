### 1581. A run whose Claude Code program is cut off from outside goes on in place: the same run, the same session, told what happened

**Status: done (2026-11-24).** Item 1580 says how a program was cut; this one stops a cut from losing the run. On
2026-11-24 at 10:44:04 four helpers of 67 to 371 steps each and the owner's chat run ended `failed` with "Claude Code ended
before it answered"; their parents heard a failure and hours of their work stayed uncommitted in worktrees. A program that
ends before its result with nobody ending it is now started again with `--resume` in the same run.

Measured before the design (Claude Code 2.1.331 installed, the brief said 2.1.330; the cheapest model; a stdio MCP server
whose one tool sleeps 40 s; the program started as Dot starts it, `-p --input-format stream-json --replay-user-messages`;
the probe was run outside Dot, `/tmp/cut-probe/probe2.py`, a few thousand tokens in all):

- *SIGKILL of the program's group 6 s into the call*: return code -9, stderr empty, and the session file ends with an
  assistant `tool_use` that has no result. `--resume <id>` with one user message: the same session id, an init line, and
  Claude Code itself wrote into the session file a user `tool_result` ("[Tool call interrupted: the session ended before
  this call's result was recorded, so its outcome is unknown. Check whether it took effect before relying on it or running
  it again.]", an error) and an assistant "No response requested.", before the message. The model answered that its last
  call was interrupted and that it had not run it again; the result was not an error. **No API error.**
- *SIGTERM of the group*: Claude Code exits 143 (not -15), and the call's result in the session is "Connection closed",
  an error; the resume went the same way.
- *SIGKILL as the model's step began* (nothing complete in the session): the resume works, and the model said it had made
  no call, so nothing was lost.

So Dot does not repair a cut session: Claude Code's own resume closes the dangling call. A first try with a program that
could use its Bash tool moved the sleep to the background and was cut inside a poll of it, with the same result.

*A real run through Dot's own runner* (a runtime on throw-away folders, the real `claude` 2.1.331 on Dot's real HTTP door,
a run on `claude_code:haiku` told to run `sleep 40; echo finished-sleeping` with Dot's `shell` tool, the program killed with
SIGKILL from outside 4 s into the call): the cut line said return code -9, SIGKILL, 2 steps, `silent_s` 4.1; Dot started the
program again 2.0 s later with `--resume` of the same session; the model, told by the note, wrote that the call was cut off
before it had its output, checked with `pgrep` that no `sleep 40` was still running, ran the command again and called
`finish`; the run ended `done` after 6 steps, one run record, its session kept (`clean`).

What changed (`claude_code/cut.py`, `claude_code/run.py`, `config.py`, `defaults.toml`, the web timeline, `dotx run`):

- When a `ClaudeCodeCut` (item 1580) reaches the run, `_Cuts.after` decides. The run goes on when nothing of Dot's own
  caused the cut and nothing the program did may be done twice (`why_not_continued`): continuing is on
  (`[providers.claude_code] continue_cut`, 2; 0 turns it off), the run was not stopped (`agent.cancel`, which the owner's
  Stop, the emergency stop and the daemon's shutdown all set; a Stop racing the death ends the run `cancelled`, not
  failed), the program ended by itself (not ended by Dot after its output closed), it had said what the model has
  (`follow.inited`, but a program that was itself a continuation may be cut before its init, which a new session
  replaces) and its session is known, and no call of an **outward action** began since the model's last step.
  The plan's limit, the run's limits, the silence watch and a program refused at its init are other errors that never
  come here (`ClaudePlanLimitError`, `ClaudeCodeError`), and a stop raises `RunCancelled`.
- *Outward* is the policy's own class, not a list of tool names: the call's action raises `message_send`, `public_post` or
  `financial` (`policy.engine.owners_guard`, what yolo still asks the owner). The registry the door's calls go through
  notes it as each tool classifies the call (`_noting_outward` wraps `prepare`, the same classification the gate reads; a
  call made inside `code_run` goes through the same registry), and the first step that begins afterwards clears it: the model
  read the results of the calls before it. Nothing asks, refuses or waits there (checked by the freedom gate).
- The program is started again after 2 s, and after 10 s the second time (`CONTINUE_AFTER_S`; a Stop cuts the wait
  short), with the same door, config file and prompt and `--resume <session id>`, in the same Dot run: the run id, the
  events, the steps, the limits, the parent's wait and a background helper's entry are the run's, untouched. What the owner
  sent that the cut program had not taken in (`_Follow.pending`, emptied by each `Taken`) goes to the new one first, as
  sent, then the note: the program was cut off at HH:MM:SS by something outside this run, the result of its last call may be
  lost, look at the real state (git status, the files, the tabs, Dot's own lists) before repeating anything, go on from where
  its plan says. The step that was streaming gets a `reset` delta, so the page drops its half words.
- Each continuation is one event, `claude_code_continued` (the exit of item 1580, `attempt`, `of`, `fresh_session`,
  `waited_s`), one log line (`claude_code_run_continued`), one line on the run's page ("The program was cut off at 10:44:04;
  Dot continued the run", the exit opened) and one in `dotx run`. The iPhone's `ChatState` and the web timeline show an
  event kind they do not know quietly (`default: break`, `handlers[record.kind]` undefined): read in the code, not run.
- A cut after the model's `finish` is the run's end: the run ends as the finish says (done or failed), not failed with
  "ended before it answered", and its session is not kept.
- A run that is not continued ends failed as before, its context now saying `continued`, `not_continued` (why) and, when
  there were several, `cuts` (the exit of each).
- *A resume the API refuses*: if a program that was itself a continuation fails before any step of its own with words that
  say the session cannot be taken up again (`No conversation found`, an `invalid_request_error`, a 400 about `tool_use` or
  `tool_result`), or is cut before its init, the next program is a NEW session. Its first message is the run's goal, its
  notes and what the chat said (as a run of a chat with no session gets them), what the cut one had done (Dot's own record
  of the run: its first words, its last 40 calls and how each ended, its last words, what the owner wrote meanwhile) and
  the note. It counts as one of the continuations. Not seen with 2.1.331; the stand-in program exercises it. A new
  session that is itself cut before it took its brief in (it said what the model has, `follow.taken` is 0) has heard
  nothing of the run, so the next program is a new session again with the brief, not a resume of a session that has no
  goal (the pre-push review's nit). The stream a program printed before a failure that is no cut is masked too, since the
  new session's event carries it (the review's finding). The program a refused resume leaves was running when it said so and Dot ends it, so
  its exit is none of its own (`returncode` null, `exited` false): the event and the lines carry what it said instead
  (`said`, the start of it), and neither the page ("Ended with API Error: 400 ...") nor `dotx run` says "exit code None"
  (the second review's finding). The brief reads the run's oldest step when more than 400 were stored, so "its first words"
  are the plan and not the first of the newest 400 (its nit). A stop that comes after the new program is started and before the run holds it ends that program there
  (`_go_on` retires it), so no `claude` is left at work on the plan. The queue of what was sent and not yet taken in
  (`_Follow.pending`) has one entry for each message sent, a placeholder for Dot's own note, because the program takes
  the note in too: a note counted as taken in place of a message the owner wrote while Dot waited had lost that message
  when the next program was cut before it read it (the third review's finding). What a refused program said is masked
  like its stream (`_masked`), since the event carries it (the same review).

Decisions taken where the brief said two things: it says both "at most twice per run, after 2 s and 10 s" and "a second cut
ends the run failed". The first is taken: `continue_cut = 2` continues the first and the second cut, and the third ends the
run (with all three exits in its context); `continue_cut = 1` is the other reading, and the one-line change if the owner
wants it. The key is `[providers.claude_code] continue_cut`, beside `silence_s`, where the plan's other keys are, not a
table `[claude_code]`, which Dot's configuration does not have.

words of the note and of a refused resume, the registry that notes an outward call and runs it as before, the queue a gone
