### 2089. Desktop shell check-over: the menu bar item is set only when what it shows changes

**Status: done (2026-11-28).** A check of the desktop shell (`desktop/src-tauri`) by reading its code and running its
checks: the window, the menu bar item, the shortcut, notifications, start at login and updates. On the branch's base
(`4e4692da4`), with the toolchain of `rust-toolchain.toml` (`rustup run 1.100.0 cargo ...`, to a scratch target
folder), `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` (93 tests) all passed. The
owner's Dot.app was not started, stopped or replaced; nothing was run against it.

Fixed here:

- **The menu bar item was set again every second** (`watch` in `desktop/src-tauri/src/lib.rs`): each poll decoded the
  icon's PNG (`tray_icon`) and set the icon, the count beside it and the tip, also when none of them had changed. That
  is three calls AppKit runs on the app's main thread each second (10,800 an hour) and a PNG decode each second, for a
  shell that stays open for days. What the item shows is now one value (`tray_look`: the face, the count, the tip), and
  the item is set only when it differs from what was last set in full; a set that failed is tried again at the next
  poll. With nothing changing, that is no call at all. The CPU cost before and after was not measured on a running
  shell: the owner's Dot.app was not to be started for it.

Found and left to the owner (none is in a path under "Always needs a human", so no diff waits here):

- **A notification's click may not bring a closed window back.** The web UI sends notifications through the shell
  (`attention.js` `tell`), and `docs/daemon.md` says that a click brings Dot to the front. Closing the window only hides
  it (`on_window_event`), and the shell answers only `RunEvent::Reopen` (a click on the Dock icon) by showing it again.
  A click on a notification activates the app; whether macOS also sends the reopen that shows the window was not tried
  (the owner's app was not to be run). The plugin can tell the shell of a click (`Notification::on_action`), but on
  macOS that waits on a thread of its own for every notification until it is clicked or cleared, and polls the
  Notification Center from the main thread twice a second while it waits, so it was not taken unasked.
- **The update is looked for only as the shell starts** (and from Check for Updates…), as `docs/daemon.md` says. The
  shell stays open for weeks, so a release can go unseen until the owner quits it. A look once a day would close that;
  it would show its dialog at any hour.
- **Install and Restart shows nothing while it downloads** (`offer_update`: `download_and_install` with empty progress
  callbacks): the dialog closes and nothing is seen until the app starts again, which can take a minute; Check for
  Updates… meanwhile says that Dot is looking already.
- **The shell does not start at login.** The daemon's launchd job runs at login (`RunAtLoad`), but nothing opens
  Dot.app, so after a restart of the Mac the menu bar item, its count and ⇧⌘Space are missing until the owner opens
  Dot. The docs do not promise otherwise.
- **The window keeps no size or place**: every start opens it at 1280 × 860 where macOS puts a new window.
- **The shell's own words are English** (the menu, the tip, the down page, the update dialogs) while the web UI is
  turning Turkish.

Checked and found right: the window (overlay title bar, traffic lights, drag regions, links to the browser, the
microphone only for the daemon's own pages, the installer window refusing other pages); the shortcut (registered once,
the menu says so when another app holds it, New chat on `#/runs` with `window.focusComposer`, which `main.js` still
sets); notifications (`notification:default` for the shell's and the daemon's pages only, `isPermissionGranted`,
`requestPermission` and `sendNotification` as `attention.js` calls them); updates (one look at a time, signatures
required, the engine kept in step after an update); the macOS app menu (Tauri's default one, with Edit and Quit).

How it was checked: `rustup run 1.100.0 cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and
`cargo test` in `desktop/src-tauri`, with the new test
`the_menu_bar_item_shows_the_count_and_changes_only_with_what_it_shows`.
