### 1982. Several tasks at once in one chat: design

**Status: design (2026-11-27), nothing built.** **Asked** by the owner (2026-11-26), from Grok Bot: it took "go to x.com
and improve my account" while a Gistsmith form task in the same chat waited on the owner's e-mail address, and the
answer, sent later, went back to the form task. In Dot a chat runs one run at a time. This item is the design only; the
slices below are their own items, each with its own pull request.

#### What happens today

- A chat (`threads` row) has at most one run at work, in any process (`RunManager._active_on`, the queue's `_drain`, the
  409 of a second run, `docs/runs.md`). A message sent while it works is first put to the fast model
  (`agent/busy.py`, item 915): a request of its own starts **in a chat of its own** (`start_beside`), the chat at work
  shows *Started in a chat of its own*; anything else, and every doubt, waits in the chat's queue, where the owner can
  **Steer** it into the run at work.
- The answer to a question card a run left (`ask_user` in yolo or free mode) goes "to the question's thread, into the
  run active there, or else a new run with the goal of the run that asked" (`RunManager.decide` / `_carry_on`).
- A question asked in prose ("Which e-mail address should I write?") ends the run `done`; the owner's answer is simply
  the chat's next message, which starts the next run with the chat's history.

The owner's case, step by step, today: run A (Gistsmith form) ends asking for the e-mail address. The owner sends "go to
x.com and improve my account": no run works, so it starts run B in the same chat. While B works (many minutes), the
owner sends the address. The fast model compares it with B's goal; either it says *part of the work* and the address
waits in the queue until B ends, or it says *separate* and the address starts a new chat that knows nothing of the form.
Both are wrong, and the second is silent. And with item 915 the x.com task would itself have gone to another chat had A
still been at work: the owner's chat is split in two, which is the opposite of what they asked.

What must change, then, is not only that two runs may work together; it is that a chat knows its **open tasks** (one at
work, one waiting on the owner) and sends each message to the right one.

#### Terms

- **Task**: one line of work in a chat, from the owner's request until it ends without an open question. In the store a
  task is a **lane** (below). A chat with one task is today's chat.
- **Open task**: a lane whose run is at work, or whose newest run ended asking the owner something (a question card left,
  or a reply that ends with a question to the owner) within `[agent] lane_open_s` (default 24 h).

#### Options for the store

1. **Runs side by side in one thread** (`runs.lane_id` inside the chat's thread). The model's history is one
   append-only table per thread (`messages(thread_id, seq, body)`, read whole by `Store.load_messages` for every run,
   `agent/loop.py`), and compaction replaces it whole (`Store.replace_messages`): two runs in one thread would
   interleave their tool calls and results in one history and overwrite each other's on compaction. Beyond that, every
   invariant keyed on the thread has to be keyed again: the one-run guard of `create_run` and `claim_queued`, the
   queue's claim and hold (`queue_claims`, `queue_holds`, keyed by thread), `list_runs(1, thread)` read as "the run at
   work" (eight callers in the manager), `can_resume` of the newest run, `rewind_chat`'s linear order, `thread_taints`,
   the browser's tabs (`browser/session.py` counts and closes "only the chat's own tabs"), `_instructions_for`, and
   `office`, `team`, `consult` and `/btw`, which read the whole thread. Rejected: the blast radius is the daemon.
2. **Keep item 915 and only fix the routing** (separate chats, answers routed by the open question). Cheap, but it does
   not give the owner one chat, which is the ask. Rejected as the end state; its routing fix is slice 2 below.
3. **Lanes as child threads (recommended).** A lane is a `threads` row with `lane_of = <chat id>` (one nullable column);
   the chat itself is lane 0. Every thread-keyed invariant holds unchanged *per lane*: one run at work, its own queue,
   its own browser tabs, its own resume, taint and continuity. What is new is a view: the chat's page shows the
   time-ordered merge of its lanes' messages, and the sidebar lists only chats (`lane_of IS NULL`). Item 915 already
   starts a run in a thread of its own; this makes that thread a lane of the chat instead of a chat in the sidebar.

#### Context between lanes

- A new lane's history starts with a copy of the **chat's transcript** up to that moment, all lanes merged: the
  owner's messages and Dot's replies, no tool calls or results, under the continuity pin, as compaction writes a
  history today. So a task sent to a new lane by mistake can still see the question another lane asked.
- After that a lane sees its own history only: two tasks never read each other's tool work, and one's steers never
  reach the other.
- A lane's final reply reaches lane 0's history by the rules of `note_chat` (a note between chats): it vouches for
  nothing, and a tainted lane's note taints the run that reads it; appended when no run works there (as
  `_tell_ended_commands` does), told to the run at work otherwise. So a later task knows what it found. (Item 915 left
  exactly this for later.)
- The instructions a run's gate trusts (`_instructions_for`) are the goals of its own lane plus the chat's owner
  messages before the fork; never another lane's later messages.
- Taint: a lane starts as tainted as any run whose replies it is given, by today's rule for a follow-up in a chat (item
  952). No new taint rule.

#### Routing a message

In order; the first that applies decides.

1. **A question card's answer** goes to the run that asked (`question.run_id`): steered into it if it works; else it
   is put in a lane's **delivery ledger** that carries the question's id, and becomes the next run of the asker's lane
   with the asker's goal, at once when the lane is free, after the run at work there otherwise (today's `_carry_on`
   delivers to "the run active on the thread", which with lanes may be another task). Every card left and not
   answered counts as an open question, not only the newest run's.
2. **A reply or quote** of a message (swipe-to-quote on the phone, reply on the web) goes to that message's lane: a
   steer when it works, its queue when it is held, its next run when it ended.
3. **New task**, explicit: the composer's menu item *New task* (and `/new <text>`) starts a lane.
4. **No open task**: lane 0, as today.
5. **A message that is only a stop** ("dur", "stop", "durdur", matched by words, no model) while lanes work stops
   them all, as the Stop button does (below). A wrong stop costs a resume; a missed one breaks the contract.
6. **Open tasks**: the fast model is asked once (`agent/busy.py` extended). It is shown the new message and, for each
   open task, the owner's own words only: the task's goal, and its open question when the run that asked was not
   tainted (a tainted lane is shown as *waits on you*, without its words, so that a page it read cannot steer the
   router). It answers `route(task: <n> | "new")`. A verdict for a task sends the message there (a steer if its run
   works, the next run of its lane if it ended asking); `new` starts a lane. **A doubt, a failure or 12 s without a
   verdict** sends it where today's rules would: the queue of the chat's newest working lane, or lane 0's next run.
   **A message the model routed vouches for nothing** (`vouches=False`, the owner's words shown to the reviewer as
   `said`): it clears no taint and widens no task's authority. Only the explicit routes (card, quote, New task) and a
   chat with a single open task vouch, as a steer does today.
7. **The cap**: at most `[agent] chat_lanes` (3) lanes at work in a chat, held by an atomic chat-level claim in the
   store (a conditional insert, as `create_run`'s one-run guard is), so two `/new` sent at once cannot both pass. A
   new task past the cap waits in the chat's **task queue** (its own table, not lane 0's queue, which would start it
   at once while lane 0 is free), marked *waits for a free task*, and starts when any lane of the chat ends.
   `max_concurrent_runs` stays the daemon-wide bound.

Every routed bubble shows where it went (*→ Gistsmith form*) with one action, **Move**: to another open task, or to a
new one. A Move before the run read it re-routes the message; after, the run gets a `tell` note ("that message was not
for you, ignore it", vouching for nothing) and the message is sent where the owner moved it. **Move is a correction, not
an undo**: what the run did with the words before the note is done. That is why a routed message vouches for nothing
(rule 6). Moves are counted, but they count only the errors the owner saw.

##### Why a hybrid, and not one of the two

- **Explicit UI alone** (reply vs New task): no model, no wrong guess, but the owner must remember to quote every
  answer; on the phone a plain typed answer, the common case in the screenshots, would still land in the wrong task.
  Grok does not ask for that.
- **Classifier alone**: the owner just writes, but every guess can be wrong, and a wrong `steer` hands one task's words
  to another run.
- **Hybrid** (recommended): the explicit paths (card, quote, New task) never call the model and always win; the model is
  asked only when there is more than one place a message could go and the owner did not say. Its cost is what item 915
  already pays: one fast-model call (~1–2 k tokens in, a few out) per message sent while a task is open; zero
  otherwise. Its error rate is unmeasured: slice 2 builds an eval set from the owner's real chats (pairs of open tasks
  and the message that came next, labelled by where the owner's next runs show it belonged) and the router goes on by
  default only at ≥ 95 % on it **and** no message of the set routed to a wrong *working* task (the dangerous error,
  counted apart from a wrong `new`, which costs a run). The cost is more than item 915's: the router is asked also
  while a task waits on the owner after its run ended, and each new lane's first step reads the copied transcript
  (bounded by the compaction size).
- **What a wrong guess does**: a wrong `new` starts a lane that still has the chat's transcript, so it usually finds the
  question it answers, at the cost of a second run; a wrong `answer`/`steer` gives a run words that were not for it,
  which **Move** corrects with a note. Neither asks anything or spends past a cap; each run still meets its own gate,
  and in yolo or free mode that gate lets a step through, so the protection is rule 6: routed words vouch for nothing.

#### Streaming, the live lines and the controls

- Events stay per run. The chat's stream (`GET /api/threads/{id}/stream`, `server/thread_sync.py`) already carries
  every run of the chat, each from its own cursor, and runs that start later; it is extended to the runs of the chat's
  lanes. DotNext already follows that stream. The web chat page today is one run's page (`/runs/{id}`, `views/run.js`:
  one `/runs/{id}/stream`, one `active`, it jumps to the newest run of the thread): it moves to the chat stream, which
  is the largest piece of slice 3.
- Over the composer, one live line per working lane (*● Gistsmith form — waits for your e-mail*, *● x.com — reading your
  profile*), each with its own **Stop**. The composer's **Stop** stops **every** lane of the chat: "stop at once when
  told to" (the contract) does not become "stop one of them". It is a chat-level stop with an epoch, kept in the store:
  it cancels the lanes at work, holds every lane's queue and the chat's task queue, and makes a router verdict or a
  capacity start that was decided before it start nothing.
- Questions, approvals and drafts carry their lane's name; their answers go by run id (rule 1).
- The transcript is merged by time. When a chat has more than one lane, each of Dot's bubbles shows its task's short
  name, and a tap on the name filters the chat to that task.
- Phone (DotNext): the capsule over the box gets a segment **2 tasks**; a tap opens a sheet with each lane's live line
  and Stop. The pill and *Waiting for you* read "any lane waits" rather than "the run waits".

#### Queue, Stop and the other controls

- Each lane has its own queue, with today's semantics (edit, order, steer, hold on stop, resume). The chat's queue pane
  shows them grouped by task.
- Rewind: within a lane only, and refused in the chat while another lane works (a merged rewind is not designed here).
- Resume: per lane, as today.
- Deleting a chat deletes its lanes.

#### Budget and the freedom contract

- No new ask. Routing never asks the owner which task a message is for: a doubt falls back to today's behaviour. Yolo
  and free runs in a lane ask exactly what they ask in a chat (`tests/unit/test_freedom_contract.py` must stay as it
  is). A lane inherits the chat's choices, agent, team and source, so a chat Dot opened (item 850) keeps its
  initiative asks in every lane.
- Spend: each run keeps its own caps; the day caps are daemon-wide already; the lane cap bounds what one chat runs at
  once. No per-chat cap is added (`[budget]` is the owner's).
- Shared resources are not solved by lanes. Browser tabs are per lane (they are per thread), but two lanes on the
  same site and account can still undo each other's changes. The desktop session's lock serialises single calls, not
  a copy and a paste made by two calls (`desktop/session.py`): a lane's clipboard write and its paste must become one
  locked call, or lanes take the clipboard in turns. These go in slice 1's done criteria; a same-site conflict between
  two lanes is a known limit, written in the docs.

#### What breaks and must be changed with it

- Everything that reads "the run of the chat": DotNext's `ChatScreen.activeRun` (`ownRuns.last { $0.isActive }`), its
  Stop, steer, capsule and composer state, `ChatProjection.newestFollowedRun`, `WorkLine.workNow` behind *Waiting for
  you* (DotNext's transcript is built per run and needs no change); the web page's single `active`, `stopRun`,
  `syncControls`, `createWorkStatus`, the capsule and the queue pane; `_carry_on` and `_carry_kept`, which deliver to
  `_active_on(thread)`; the work log (grouped by lane), the sidebar's working/waiting dot (any
  lane), notifications (name the task), search (a lane's messages are the chat's), titles (a chat's title is lane
  0's), the iMessage channel (one chat per channel; lanes come later there), item 915's line *Started in a chat of its
  own* (replaced by the lane's chip).
- The API: `GET /threads/{id}` and its messages return the merged lanes; the queue route says which lane it put a
  message in (`lane_thread_id`) instead of `beside_thread_id`.
- A store migration: `threads.lane_of`, the chat-level lane claim, the chat's task queue, the delivery ledger and the
  stop epoch. Not one column: the owner's own rule asks for their look at a migration.

#### Recommendation and slices

Lanes as child threads, routed by the hybrid. Slices, each its own item:

1. **Answers go to the run that asked** (`_carry_on` by `question.run_id`, the delivery ledger) and lanes in the store
   and the manager (`lane_of`, the atomic lane claim, the task queue, the chat-level stop epoch, `start_lane`, the
   merged transcript API, the clipboard as one locked call), with item 915's `start_beside` making a lane, behind
   `[agent] chat_lanes = 0` (off: today's separate chats).
2. **The router**: the fast-model question over open tasks (owner's words only), the stop words, routed words that
   vouch for nothing, the open-task rule, the eval set from real chats and its measure; explicit routes (card, quote,
   `/new`).
3. **Web UI**: lane chips, one live line and Stop per lane, Stop-all, *New task*, **Move**, the grouped queue.
4. **DotNext**: the capsule's task segment and sheet, the pill and *Waiting for you* over lanes, quote-to-route.
5. **On by default** (`chat_lanes = 3`) once slice 2's measure passes and a week of Moves on the owner's Mac stays
   under 5 %.

#### Second opinion

Codex CLI 0.172.0 (GPT, another model family), read-only on this worktree, asked to red-team the first draft against
the code (2026-11-27). Its verdict: child threads are right for keeping histories apart; the routing's authority, Stop
and the chat-wide scheduling were not defined. Its findings, and what this design took from each:

1. **Critical: a wrong steer moves a trust boundary, and Move does not undo it.** `steer` delivers with `vouches=True`,
   which clears a run's taint; the later `tell` vouches for nothing and takes back no step already made. In free mode a
   form task's "yes, send it" routed to the wrong lane can act before Move. *Taken*: a message the model routed vouches
   for nothing (rule 6); only explicit routes and a chat with one open task vouch; Move is written as a correction, not
   an undo.
2. **High: Stop-all is more than cancelling the runs at work.** A router verdict arriving after Stop, or a capacity
   start when a cancelled lane ends, would start work again; a "stop" message the classifier calls part of the work is
   only queued. *Taken*: a chat-level stop epoch in the store; stop-only messages stop every lane by words, no model.
3. **High: the lane cap and the fourth task are not held by today's invariants.** Two `/new` at once both see two lanes;
   lane 0's queue starts at once while lane 0 is free. *Taken*: an atomic chat-level claim and a task queue of the
   chat's own; the migration is larger than one column, and the doc says so.
4. **High: the router would read outside content.** Today's judge sees only the owner's two messages (the safety reason
   in `busy.py`); showing a task's last reply lets a page steer the router; a lane's result told to lane 0 by `tell`
   skips `note_chat`'s taint rules. *Taken*: the router sees the owner's words only, a tainted lane's question is
   withheld; lane results go by `note_chat`'s rules.
5. **High: an answer bound to a run collides with a newer run in the same lane.** *Taken*: the delivery ledger keeps the
   question's id and starts the asker's continuation after the run at work; every card left counts, not only the
   newest run's.
6. **Medium: shared resources are not solved.** Same-site conflicts and a clipboard race across two locked calls.
   *Taken*: the clipboard becomes one locked call (slice 1); same-site conflicts are a known, documented limit.
7. **Medium: cost and the measure are optimistic.** The router runs more often than item 915's; each lane copies the
   transcript; 95 % overall bounds nothing about dangerous misroutes, and Moves count only the errors seen. *Taken*:
   the bar adds zero wrong routes to a working task on the eval set; the cost sentence is corrected.

Its alternative was child threads as the unit of execution, a task record, an atomic scheduler and a delivery ledger,
with the model's guess never counting as authority: that is now this design. **The dissent that stands**: Codex would
leave every ambiguous message in today's queue rather than let a model route it at all. The answer: the owner's case is
exactly an unquoted answer typed while another task works; queueing it is the failure they reported. The design keeps
the model's route but strips it of authority (it vouches for nothing), so a wrong guess costs a wasted step or a
confused run, never a cleared taint; the owner can switch the router off (`chat_lanes = 0` keeps today's behaviour) if
the eval set shows otherwise.
