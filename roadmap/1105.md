### 1105. A schedule counts a run the daemon's stop cut off, and keeps why it was switched off

**Status: done (2026-11-10).** From the review of the implicit state machines, two moves of a schedule's `last_status`
and `runs_failed_in_row` that went wrong:

- A run that was under way when the daemon stopped was marked `interrupted` as the scheduler started again, but the
  row of failed runs counted only `failed`: a schedule whose run brought the daemon down was never switched off. Now a
  run left `running` counts as a failure in the row (`record_schedule_outcome(…, "interrupted")`), and the schedule is
  switched off at its limit as one whose runs fail is; one left `starting`, whose run never began, does not count.
- `record_schedule_outcome` wrote the last status whatever it was: an end that came after the switch-off (a run by
  hand, a late watch) wrote `done` over "switched off: its last 3 tasks failed", which the page and the test of a
  one-time schedule's completion read. Now a status that says it was switched off is kept until the owner switches the
  schedule on again.

Checked: `tests/unit/test_schedule_stop.py`, `tests/smoke/test_scheduler.py` (the interrupted runs; three other tests of
the file are `live` and call the Mac's Ollama, out of its month's use on 2026-11-10).
