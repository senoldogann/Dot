### 1073. A short code goes as a message when a secret card cannot hold it

**Status: done (2026-11-09).** The owner, on 2026-11-09: "Dot bana secret sordu, 8087 yazdım ama approve çalışmıyor;
kısa gönderemiyor muyuz?". Asked with the options put to them, they chose to send a short code as a message
(recommended), over holding short secrets (which masks those characters in every text for a day) and a warning alone.

Why: a secret card (`ask_secret`, item 857) holds 8 characters or more, as a shorter value cannot be masked where a
command prints it without masking those characters in every text; the card refused a shorter one by focusing its box
again, saying nothing, so Save securely seemed broken.

Now: Save securely waits until 8 characters are typed; under that the card says why and offers **Send as a message**,
which declines the card with the code as its note. `ask_secret` tells the run a declined card's note in the owner's
words, to use as it is (it is in the chat then, as any message), and its description says a short code may come back
in words. The daemon still refuses a value under 8 characters on the card's own route. A card left for the owner (no run waits
on it) offers no such button and says to write the code in the chat, whose next run reads it; a note is the owner's
words only when the page declined the card (a command that cannot ask declines with a note of its own). (The pre-push
review.)

Checked by `tests/smoke/test_ask_secret.py` (the card in a browser: Save waits, the words and the button under 8
characters, gone at 8; a 4-digit code refused on the secret's route and sent as the card's note, which the run is told
in the owner's words), the context budget and `dotx eval check`.
