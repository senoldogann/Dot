### 1190. Dependabot's patch and minor pull requests merge by themselves, one at a time

**Status: done (2026-11-15).** Every Dependabot pull request waited for the owner's click: 27 in a month, every one
that merged merged by hand, some a week after `ci` had passed (#682 to #684). Those that closed unmerged were replaced
by a newer one. The safeguards were already there: a version a week old (`cooldown`, item 487), one pull request per
kind of dependency, every browser part run when a lock changes (`scripts/browser_ci.py`), and since item 1189 the
desktop checks and zizmor inside `ci`.

`.github/workflows/dependabot-merge.yml` has two jobs:

- `label`, on each of Dependabot's own pull requests (by the author's login, from a branch of this repository), reads
  what it raises with `dependabot/fetch-metadata` and marks it `dependabot-merge` when the largest step is a patch or a
  minor one. The mark of an earlier head is taken off first, read from the pull request as it is, so a head whose
  metadata cannot be read stays unmarked; one with `dependabot-hold`, which a person or `merge` puts on and which stays
  through Dependabot's rebases, is not marked. A major version, in a group or alone, waits for a person, as before.
- `merge`, every twenty minutes and on demand, one run at a time (a concurrency group that is never cancelled), merges
  at most one marked pull request of Dependabot's whose `ci` passed, the oldest, with `--match-head-commit`, if it
  changes nothing but the locks and manifests of Dependabot's ecosystems, the Rust version and the CI's workflows and
  actions (`pyproject.toml` is not among them: its dependencies are under "Always needs a human", and a security update
  can move a requirement there; such a pull request is put on hold and told why; so is one that changes more than the
  100 files the list holds), and only when main's gate passed on main's head as it is: a run that waits or runs is let
  finish, a red one keeps everything waiting (a red main is fixed before anything else is merged; the desktop checks'
  last run on main counts too, as they run only when desktop/ changes), and a head with no run ten minutes after it
  landed (a push of prose alone, which the gate's `paths-ignore` spares) gets one started. A merge made with a
  workflow's token starts no workflow, so after the merge the job starts main's gate itself with `gh workflow run` (a
  workflow_dispatch is the one event that token may start), and `desktop.yml` and `zizmor.yml` when the pull request
  changed what they read; `gate.yml` and `desktop.yml` take `workflow_dispatch` for it. The next run sees that gate
  waiting or running and merges nothing until it passed, so a second merge never lands before the first one's run. A
  merge refused because Dependabot pushed meanwhile is looked at again by the next run; any other that fails puts the
  pull request on hold and says why in a comment, so the pull request waits for a person instead of failing every run. A
  token of a workflow may be refused a merge that changes `.github/workflows/` (it cannot hold the `workflows`
  permission); if so, the actions' pull requests end up there, and the first one shows it. Both labels are the
  repository's, made by hand with this item (`gh label create`).

Two designs came before, both found wanting by the pre-push review: GitHub's auto-merge, which merges the moment `ci`
passes, cannot hold a merge for a red main, and nothing starts main's run after it; and a job per pull request that
waits for `ci` and main's gate, where two jobs a few seconds apart could both see main's gate passed and merge one
after the other, the first one's run never seen. One scheduled job that merges one at a time cannot race itself.

Checked: zizmor 1.31.1 with no finding, at the auditor persona too; actionlint with shellcheck over the scripts; the
jq that picks a pull request and reads main's runs against Dot's own pull requests and runs;
`tests/unit/test_release_workflow.py`. The first Dependabot pull request after the merge shows it working end to end.
