### 1891. Item numbers are reserved, and every place that holds one is read

**Status: done (2026-11-25).** On 2026-11-25 item numbers clashed seven times or more between sessions working side by
side on this Mac: `scripts/next_item.py` gave 1881 while 1881 and 1882 were on other branches, 1875 while a closed and
reopened pull request held it, and the same number to two sessions renumbering at the same moment. It read only
`origin/main`, open pull requests and the pushed branches whose name held a number past main's highest; a number in a
commit subject, a closed pull request, a pull request's body, a local branch of another worktree, an entry not yet
committed, or one another call had just given, was not seen.

What must hold: two calls, at the same moment or one after the other, never give the same number; a number held only by
a local branch, a commit subject, a pull request title or body (open or among the last 100 closed) or an uncommitted
entry in any worktree is skipped; a source that cannot be read gives no number, as before.

What was built: the script reads every branch on `origin` and every local branch (names, the subjects of their commits
not on main and the entries those commits add, in two `git log` calls over all of them), each worktree's checked-out
commit and its `roadmap/` and `changes/` folders, and the open and the last 100 closed pull requests' titles, bodies and
branches. The numbers it gives are written, with the branch and the time, to `item-reservations.json` in the
repository's common git directory (shared by every worktree), read and replaced under an exclusive `flock` on
`item-reservations.lock`; a reservation holds its number for three days. As each call now reserves, it is run once,
when the work starts; CLAUDE.md and CONTRIBUTING.md say so.

Checked: `tests/unit/test_next_item_and_pr_body.py`: 32 callers on 16 threads take two numbers each and get 64
different ones (the test fails with the lock taken out); a number only in a local branch's commit or name, a closed pull
request's title or a body is skipped; an uncommitted entry in another worktree is skipped; a reservation older than
three days is dropped. A real run read every source in about 4 seconds and gave 1891 (1890 was held by a pull request).
