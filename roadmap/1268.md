### 1268. The database has a version, copied before it changes and refused when newer

**Status: done (2026-11-20).** A store from an older Dot was given the columns added since at every open, each added
only where it was missing. Nothing said which version wrote a database: a change that was not a new column had no
order to run in, nothing copied the database before it changed, and an older Dot opened a newer database and wrote to
it. Taken over from a session that stopped before writing it.

- `PRAGMA user_version` holds the schema's version, `SCHEMA_VERSION = 1` (`store/db.py`). Every open still makes the
  tables and adds the columns and indexes added since, each only where missing (`_add_missing_columns`), so a new
  column needs no new version; `_MIGRATIONS` holds the steps that cannot repeat, each under the version it brings
  (none yet). The tables are made inside the migration's transaction, statement by statement (`executescript` commits
  first, outside the lock).
- At an open, a database below the version is copied first with the copy of the backups (item 526: SQLite's online
  backup, `quick_check`, gzip, 0600) into `<home>/backups-before-upgrade/v<version>`, which keeps its newest two: a
  migration that fails at every start does not fill the disk, and a database used again since its copy (gone back,
  then upgraded again) has a copy of now. Whether it changed cannot be told from its file, which a failed start writes
  too. A copy that cannot be made stops the open with what failed and the free space; a full disk says so. Then the database takes the tables, the columns, its pending steps and its new version in one
  `BEGIN IMMEDIATE` transaction, rolled back on any error; the version is read again inside it, so the daemon and a
  `dotx` command opening at once do the steps once. A new database is made at the version with no copy.
- A database of a later version is refused (`StoreError`, with the version found and the one supported) before any
  table is made or written.
- The copies are guarded from runs as the other copies (`runtime._guarded_files`), and `make_backup` takes the folder
  of the copy under way beside the database, so a test's database never writes into the real Dot home.
- `test_store_schema.py` pins a digest of the tables, columns, indexes, triggers and views: a change of the tables
  fails there until it is pinned again (an added column) or comes with a step and a new version.
- The tests that make "a store from before X" by dropping columns now set its version to 0, as such a store has.
- The pre-push review and an independent review found the copy unguarded, its partial file in the real home in tests,
  one copy per start for a migration failing at every start (then a re-upgrade left with no copy of now), a column added the old way skipped once a database is at
  version 1, and the tables made outside the lock: all fixed as above.

Measured on a copy of the owner's database (320 MB, version 0): the first open made a 91 MB copy and migrated in
11.7 s, `quick_check` ok, its chats read; the next open took 0.03 s.

Checked: `test_store_schema.py` (new database, an old one copied and migrated with its rows and its copy restorable,
a newer one refused and left unchanged, a failing migration keeping two copies, a database used again copied again), the unit tests, the copy of the owner's database.
