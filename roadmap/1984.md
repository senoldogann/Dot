### 1984. Several tasks in one chat, slice 1: lanes, the answer's queue, Stop for the whole chat

**Status: built (2026-11-27), off by default; waits on the owner's look at the store change before it merges.**
Slice 1 of [item 1982](1982.md)'s design, which the owner decided the same day (five tasks a chat, Stop both ways, a
routed answer runs tainted). Nothing changes while `[agent] chat_tasks` is 1, its default: the pages do not show lanes
yet (slice 3), and the router that sends an unquoted answer to the task waiting on it is slice 2.

**Built.**
- The store: `threads.lane_of` (the chat a thread is a lane of; an added column with its index, which every open adds
  where it is missing, so no new schema version and no copy, as item 1268's rule says), and `queued_messages.answers`
  (the question card a queued message answers). `Store.create_lane` makes a lane with its chat's source, team and
  agent in one `INSERT ... SELECT ... WHERE` that counts the chat's tasks at work (the chat and each lane with a run
  of its own at work, and a lane with no run yet, whose first run is about to start), so that two lanes asked for at
  once cannot both pass the cap; `drop_unstarted_lane` deletes a lane whose run could not start. The chat list
  (`_thread_summaries_sql`) leaves lanes out; `delete_threads` deletes a chat's lanes with it and refuses while one of
  them works, as for the chat.
- `RunManager.start_beside` (item 915): with `chat_tasks` above 1, a request of its own starts in a lane of the chat
  (`_start_lane`), its first message what the chat said so far (`_chat_so_far`: the owner's words and Dot's reply of
  the newest 12 runs of the chat and its lanes, not their helpers', each cut to 1,500 characters) in front of the
  owner's words, which stay the goal; a full chat returns `None` and the message is queued as before. A Stop of the
  chat while the fast model was asked starts nothing.
- `RunManager._carry_on`: with `chat_tasks` above 1, the answer to a question card whose run's thread has another run
  at work is queued there (`Store.add_queued_answer`, the choices of the run that asked) instead of steered into that
  run, and starts the asker's continuation (`_launch_answer`, as before) once that run has ended. Steering it is
  refused (422).
- `RunManager.stop_chat` and `POST /api/threads/{id}/stop`: stop the chat's own run and each lane's, as each Stop
  would (each holds its own queue); a lane names its chat.
- `docs/runs.md`, `defaults.toml`, `docs/schemas/thread-sync.schema.json` (two optional fields: `answers`, `lane_of`;
  the iPhone app's `ContractSchemaTests` pass).

**Left for the next slices** (item 1982): the router (slice 2), the chat's own task queue past the cap (here a request
past it waits in the chat's queue, which starts it only after the chat's own run), the stop words, the pages and the
phone (slices 3 and 4), a lane's result told to the chat's next run. The clipboard taken by two calls of two tasks is
not new to lanes (two chats run side by side today, item 915) and is its own item.
