### 769. A network that drops is found in a minute, waited for, and asked again as soon as it is back

**Status: done (2026-10-28).** **Measured:** the night of 2026-10-28 the owner's network dropped for about ten minutes
while a run on `openrouter:deepseek/deepseek-v4.1-flash-1017` was at step 27. The step's call sent nothing for 420 s,
until `model_call_timeout_s`, while the page said "Working…". The run then waited for its model (item 158), and the
page said it asked again in 10, 20 and 40 s. Each ask was really six tries of the connector, each a 10 s
`ConnectTimeout`, with the pauses between them: 83 s and 79 s, all of it silent. The network came back while the run
slept on its schedule. The step answered at 01:43, 12 minutes after it was asked.

**The change.** A call that broke tells only that it broke, so Dot now checks whether it can still connect to the
model's server. The check (`llm/reach.py`) resolves the name and opens a TCP connection to the port, within 5 s, and
sends nothing. Like the connectors' own connections, it tries the host's next address beside one that does not answer
after 0.25 s ("happy eyeballs"), so a network whose IPv6 route drops packets is not taken for one that is down. A
lookup of the name that outlasts its check (the system's resolver goes on in a thread) is waited for by the next check
of that host rather than made again. Behind a proxy (`HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`) it always says yes. The router gives each
model's address (its provider's `base_url`). OpenCode's agent and a connector given through `register` have no address
and are not checked. The check is used in three places:

- **The connector.** A connector whose call or JSON request broke, and whose server cannot be connected to, raises at
  once instead of retrying in silence. Its error says "cannot connect to <host>" and names the host in its context
  (`offline`).
- **The step.** A step's call that has sent nothing for `[agent] connection_check_s` (45 s) has the connection checked,
  then every 15 s while it stays silent. The call is given up once two checks in a row fail, rather than at
  `model_call_timeout_s`: one check can fail on a lookup that hiccups while the call's own connection holds, and
  cutting it would throw away minutes of thinking. A slow model whose server is there is waited for as before. The
  seconds offline the page shows count from when the call fell silent.
- **The wait.** A run that waits for a model whose server it cannot connect to checks every 5 s and asks the same step
  again as soon as the connection opens, within the same `model_wait_s`, instead of on the 10/20/40/60 s schedule. The
  schedule still applies to a server that is there but fails.

The `model_waiting` event names the host in `offline`, with `retry_in_s` null. A new `model_reconnected` event (host,
step, seconds offline) says the connection is back. The run's page rewrites its one line for the wait accordingly:

- "No connection to openrouter.ai; Dot asks … again as soon as it connects, until 01:53:28."
- "The connection to openrouter.ai is back after 4m 10s; Dot asks … again."

A wait on a schedule now names the clock time of the next try rather than a count of seconds that is out of date by the
time it is read. The tests check the connection on this Mac alone: `tests/conftest.py` takes any other host to be there.

**Checked.**

- `tests/unit/test_reach.py`, on servers of this Mac:
  - a listening port is reached; a closed port is not;
  - a proxy or an address without a host counts as reached;
  - a broken call to a closed port is told as one that cannot connect, and is tried once, not four times;
  - one to a listening server is retried as before;
  - the connection is opened with the next address tried after 0.25 s;
  - two checks while a lookup hangs make one lookup.
- `tests/smoke/test_model_wait.py`:
  - a call that hangs while the server is out of reach is given up at the second failed check, waited for, and asked
    again after the fourth check, when the server answers, with its time offline counted from when it fell silent;
  - a model silent for 0.6 s with its server there is not cut, even when one check fails;
  - a connector's "cannot connect" is asked again 0.05 s after the connection is back, not 10 s later;
  - the earlier tests of the wait pass unchanged.
- `tests/smoke/test_connection_wait_note.py` in Chrome: the page shows the three lines as the events come.
- `dotx eval check`, the unit suite (6,143 passed), the smoke suite without the browser (1,104 passed), ruff, mypy and
  `npm run check`.
- Of the smoke suite, `test_find_help` named the broken connection in the old words; it now finds "cannot connect to
  127.0.0.1:<port>:" before them. `test_left_questions` failed once on a Mac loaded by other sessions' tests, and passed
  three times out of three alone.

**Not done.**

- `dotx chat` in a terminal does not show the wait. It never showed `model_waiting`.
- The tools that need the network (`web_fetch`, the browser) are not held while it is down. In 21 days, the owner's
  runs had 11 tool results that failed for a name that did not resolve or a network that was gone, against hundreds of
  model calls.
