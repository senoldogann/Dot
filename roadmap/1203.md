### 1203. `dotx run` hands its run to the daemon of its Dot home, which drives it in its own Chrome and shows it

**Status: done (2026-11-16).** Agents on this Mac hand Dot work with `dotx run --approvals auto --no-input -`. Such a
run worked in the command's own process, with a Chrome of its own process on Dot's profile, which only one process
holds: on 2026-11-15 the log showed four runs failing with "Dot's browser is in use by a run of another Dot process"
and five 116 s waits for the daemon's chats to let go of it. The pages showed such a run as *Working elsewhere*, its
screen not shown, on the phone neither.

While a daemon of the command's Dot home runs (its token is in the home, something answers at `[server]`'s address and
proves it holds the token), `dotx run` now starts the run there (`POST /api/runs`) and follows it over the daemon's API
(`cli_handoff.py`): the run is the daemon's own, in its Chrome beside the chats' tabs, its screen on the pages. The
command prints what it printed: the steps (the same `TerminalUi`, which now takes its decisions through a desk, the
broker of its process or the daemon's API), the answer, what the run needs, the questions it left, the campaign's line,
and ends 0 for a run that ended done. With no daemon of the home it keeps the run in its own process, as on a Mac
without one; a daemon of another home at the address is said and sent nothing. The log says which path a run took
(`run_path`, `path=daemon|in_process`).

What a run of the command's process had is kept, as the API now lets the command say so: the run's source is `cli`
(`POST /api/runs` takes `source`, `ui` or `cli`, `ui` by default; the two weigh the same for the policy, and `cli` is
not among the owner's sources the plugin scout reads), and the terminal's decisions are recorded as the terminal's
(`POST /api/approvals/{id}/decision` takes `by`, `ui` or `cli`; both are the owner's, and a no from `cli` carries no
words of theirs to a card that asks for a secret). With `--no-input` every approval is denied and a question the run
waits on goes unanswered, at once, so the caller is never kept waiting. `GET /api/approvals/{id}` tells how one was
decided, which the terminal says when an answer came from the pages. Ctrl-C asks the daemon to stop the run, a second
quits; SIGHUP and SIGTERM stop it too. Unlike a run of the command's process, a handed run is a run of the daemon:
`ask_user` may leave a question on the run's page and go on (item 508), the lessons are drawn by the daemon and shown
on the run's page, and a killed command leaves the run working there. `dotx resume` and `dotx chat` stay in their own
process.

Checked by `tests/smoke/test_cli_handoff.py`: a real server with the scripted model, `cmd_run` itself; the run is the
daemon's (its bus told the start, none elsewhere), its source `cli`, the answer printed and 0; a question the run waits
on is denied by `cli` with "no answer was given"; Ctrl-C stops the run; with no token or nothing listening the run stays
in the command; another home's daemon at the address is refused.
