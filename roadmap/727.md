### 727. A NUL character in a step is refused for what the step gave, never a crash

**Status: done (2026-10-27).** From the outside review of 2026-10-27 (its finding 3): `browser_host` caught only
`OSError`, and `socket.inet_aton` raises `ValueError` for a NUL, so `check_url("http://a%00.com/")` raised; so did
`expand_path("a\x00b")` (`os.path.realpath`) and `assess_shell("echo \x00")`. A web fetch ended as a crashed tool with a
traceback in the log, and an OpenCode run, whose permission handler had no step to refuse, failed whole. No step ran
in any of them: the fault was the kind of the failure, not a way past a check.

**The change.** `browser_host`: a host with a NUL is one that cannot be read (None), and `ValueError` is caught with
`OSError`; `check_url` then refuses the address as it refuses any unreadable host. `expand_path` and `assess_shell`
raise `NulCharacterError` for a path or a line with a NUL: a `ToolInputError`, which a call of Dot's own tools reports
to the model as what it gave, and a `ValueError` as `os` raised before, so that what caught that (a page's files that
leaves such a link out and names it) still does. OpenCode's permission handler refuses the step when it cannot be
described (`ToolInputError`), and the run goes on. The check of an answer's paths (`agent/verify.py`) skips a path with
a NUL.

**Checked.** `tests/unit/test_nul_refused.py`: the address is refused, the path and the line raise `ToolInputError` (a
`cwd` with a NUL too), and an OpenCode `bash` and `edit` asked with a NUL get `reject` with the reason, not a failed
run; each fails on the code before.
