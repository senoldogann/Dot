### 2095. Desktop shell: opens at login, keeps its window's place, speaks the web UI's language, looks for updates daily

**Status: done (2026-11-28).** The follow-up the owner chose (2026-11-28) from the gaps item 2089 left: four of them,
not the notification click that might not reopen a closed window.

- **Opens at login.** `[desktop_app] start_at_login` (on by default), switched in Settings › General › Desktop app ›
  Open Dot.app at login (`GET`/`PUT /api/desktop-app`, `routes_desktop_app.py`, which reads the file each time, so a
  hand edit is seen). The shell reads it from config.toml at
  each poll (it reads that file each second already) and, when it changes, writes or removes its own login item
  (`desktop/src-tauri/src/login_item.rs`): `~/Library/LaunchAgents/dev.dot.desktop.plist`, a job that runs once at
  login, `/usr/bin/open -g -a <Dot.app> --args --at-login`, so the app starts through LaunchServices as a click would,
  in the background. Started with `--at-login`, the shell makes its window hidden: the menu bar item, its count, its
  menu and ⇧⌘Space are there after a restart without opening Dot. Writing the file starts nothing now; a file already
  holding the job is left as it is, and a new one is written beside it and renamed over it (a link at the name is
  replaced, not followed). Only an app run from its bundle where it stays has a login item: not from the disk image
  (`/Volumes/`), the copy macOS makes of a downloaded app (`/AppTranslocation/`), nor a build run from `target/`, so a
  development shell and the tests never touch the owner's LaunchAgents. A login item through `SMAppService` was not
  taken: it gives the app no way to tell a start at login from a click, so the window could not start hidden.
- **The window keeps its place** (`window_place.rs`): its frame and whether it was zoomed, in logical points, in
  `~/Library/Application Support/dev.dot.desktop/window.json`, saved as the window hides, loses the focus, or the app
  quits or restarts for an update, and only when it changed (nothing while it moves). A place no display shows enough
  of its bars to grab (a display taken away) is not used; a zoomed window keeps the frame it had before.
- **The shell's words follow the web UI's language** (`words.rs`, English and Turkish): the menu, the tip, the down page
  (`desktop/ui/down.js`, told `lang=tr` in its fragment) and the update dialogs. The web UI's language is kept in the
  window's own storage, which the shell cannot read, so the page in the shell (`data-shell="desktop"`) writes it into
  `[desktop_app] language` when the config holds another (`shelllanguage.js`: one read as it opens, a write only on a
  difference); a page in a browser writes nothing. The shell redraws its menu within a second (Tauri runs the menu's calls on the main thread itself). Words of the system and
  of the TOML parser it quotes stay as they are; the installer's words (`installer.rs`, a path under "Always needs a
  human") were left English.
- **Updates once a day, and a download that shows.** The watch loop looks at the releases once 24 hours have passed
  since the last look, by the wall clock, so a day the Mac slept counts (a monotonic sleep would not). While Install and
  Restart downloads, the menu bar item shows how far it is beside the count (`2 · ↓ 45%`, or the megabytes when the
  release gives no size) and its tip says it downloads, then installs; Check for Updates… meanwhile says how far it is.
  The progress is read at the next poll, so the item changes once a second at most, not once a chunk.

No path under "Always needs a human" changed: no capability, `tauri.conf.json`, `build.rs` or `installer.rs` (the login
item and the window's place are written by the shell's Rust, with no plugin and no command a page could call), and no
dependency was added. The phone app has no such card (it shows only what works away from the Mac).

**Cost.** The daily look adds no thread or timer: one comparison of two times in the poll that already runs each second.
Saving the place runs only on those window events. Measured (release build, `cargo test --release`, a test written for
it and not kept): the work each poll gained (`[desktop_app]` from the parsed config, the language and download locks,
`SystemTime::now` and the comparison) takes 72 to 75 ns per poll (two runs), and parsing config.toml with the `[desktop_app]`
table 1.8 to 1.9 µs against 0.95 to 1.0 µs without it; together about 1 µs more each second, a millionth of a core. The running shell's CPU was not
measured: the owner's Dot.app was not to be started, replaced or restarted.
