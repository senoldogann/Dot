### 736. An eval of tool use made of the moments Dot's runs got wrong

**Status: done (2026-10-27).** **Asked by the owner:** do in Dot what another agent's maker did with its own tools: an
eval made of the failures of real use, then the tool descriptions climbed per model, then trimmed with no regression.
Item 735 measures what a run's first step carries; this is the eval.

**The change.** `dotx eval tools [--model M] [--case ID] [--repeat N]` (`evals/toolcalls.py`, `toolcalls_play.py`,
`tool_cases.py`). A case is a moment of a run: its goal, the steps before it (a call and its result), and what the next
call must be (one of some tools, with the arguments that fit, never one it forbids). In a throw-away home each case's
goal is started as a task run of the scripted model, whose first request is kept as Dot made it (the system prompt and
the tools' schemas), the steps before are put after it, and the model under test is asked: again while it only plans
(`update_plan` and the like, twice at most); an answer with no call passes where finishing fits. The request is captured
in `yolo`, so that no case waits on an approval. The model's key comes from the environment and the home's `.env` alone,
and the Keychain is not asked while the cases play (`no_keychain`; pre-push review round 1: the runtime they play in
looked for the keys it did not find there): a key in neither is missing, and the command says so before the first case.
A model that only plans fails the case. One call a case.

The eight cases come from the owner's own failures of 2026-10-13 to 27, told with made-up pages and files:
`browser_wait_text` waiting for text a page never showed (72 of 237 calls failed), `edit_file` with another agent's
argument names or a text not copied, `web_fetch` of a guessed address (33 times HTTP 404) or again after HTTP 403 (17
times from one site), a ten minutes' test suite in `shell` (killed at 120 s), `browser_eval` on pages whose scripts
throw, code searched with a shell glob zsh aborts.

**Measured** (2026-10-27): Claude Haiku 5.5 passed 16 of 16 attempts (two of each case, 367,818 input tokens) and
Ollama's gemma4:cloud, the model the owner's schedules ran on that day, 16 of 16 (321,075). Told as Dot tells it, the
refused site's moment is passed too: Dot's own answer to a 403 says what to do next. So a moment told alone, in a fresh
context, is no longer where these models fail; the owner's failures came deep in long runs (60,000 tokens and more
before the first step) and on their main model, which could not be asked: OpenCode Go answered HTTP 402, insufficient
funds, to every call, and their runs had moved to the standby model since 11:00. The next step replays the failing
moments of the owner's runs with the conversation they had (a later item). Two faults of the first version were found by
playing it: the scripted model that captures the requests is Ollama's provider and answered for an Ollama model under
test (the requests are now captured in a runtime of their own), and a case told a refusal in other words than Dot's.

**Checked.** `tests/unit/test_toolcalls.py`: the judge (the tool, the arguments, the forbidden calls, planning first, an
answer where finishing fits); every case has its id, its failure and a reachable answer.
`tests/smoke/test_tool_eval.py`: the cases played end to end with the scripted model as the model under test; the keys
come from the environment and the `.env` file alone; the Keychain is not asked while the cases play; a model that only
plans fails.
