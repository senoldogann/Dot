### 1888. A scope is one command, not a toml block: `dotx scope add`, `list`, `remove`, `check` over a store every call reads

**Status: done (2026-11-23).** Item 1887 made an authorised target a scope in the config file. The owner's answer was
the right one: "bu çok karışık, her seferinde ben orayı nasıl yazacağım". A scope that has to be hand-written in
`config.toml` is a scope nobody adds, so the run goes back to refusing — the code was fixed and the daily path was not.

- `dotagent/scopes.py`: the scopes live in `scopes.toml` in Dot's home, written by Dot and read by its stamp on every
  call, so a scope added while a run is working holds on the next call and needs no restart. `add_scope` (an upsert by
  program, case-insensitively), `remove_scope`, `load_scopes`, `save_scopes`, and `authorising(host, recon)`,
  which asks the owner's own list, then the config file's scopes, then the store.
- `dotx scope add --program … --hosts … --url … --note …`, `dotx scope list`, `dotx scope remove <program>`,
  `dotx scope check <host-or-url>` — a new family in the CLI (`cli_scope.py`, four command models), so the owner
  types one line and a yolo run can register a program itself (under the sandbox Dot's home is closed to a run's
  commands, so there the run hands the owner the one line).
- A `scopes.toml` that cannot be read raises `ScopesFileError` with the file and what is wrong, never drops a scope in
  silence; the port scan and `security_scan` stop on it, the passive audit goes on. The file is written whole
  (`write_whole`). Who allows a test is a `ReconAuthority` (``program`` ``None`` for the owner's own list), not a
  marker string a program could share.
- `recon` (`depth = "ports"`) and `security_scan` ask `scopes.authorising` instead of the config alone, and the refusal
  a call gets names the command and offers `dotx scope check`, instead of a toml block to paste.
- The prompt says a scope is one command: read the program's published scope, `dotx scope add` it, go on, and don't
  hand the owner a toml block. The tool descriptions and the group line say the same.
- `docs/recon.md` carries the four commands and where the file is; `docs/security.md` points at them.
