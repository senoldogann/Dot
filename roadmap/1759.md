### 1759. DotNext's Settings, whole: every page of the web app reachable, the hop-by-hop diagnosis, and pairing as a first run

**Status: done (2026-11-25).** Wave N3 of the iPhone rewrite (the plan in the owner's workspace,
`ios-rewrite-2026-11-24/PLAN.md` §4.4, §13 S7, §14 N3, §17 #14), the app's part (`ios/Next/Settings/`), on item
1757's engine. The owner tried the build of #1091 on 2026-11-25: "the pairing screen is very shabby, no Settings menu
works"; both are what this item replaces.

What must hold:
- No control of Settings does nothing: every row opens its native page or the Mac's own web page in the app (the "Web"
  mark), every button, switch and menu of a native page changes something on screen (`SettingsControlsUITests` taps
  them all and fails on one that does not).
- This Mac checks that the paired daemon holds this phone's key (`GET /api/proof`, the web's HMAC) and sends the key in
  its own probe only when it did. It is a check, not a gate: the engine's reads and streams send the key from the first
  request, as before; gating them on the proof, as the web's `api.js` does, is the engine's follow-up.
- A write the daemon refuses to a phone says so with the Mac's place to do it (403 `PhoneRefused` + `context.phone`);
  nothing is refused locally on the daemon's behalf, so the phone never claims a rule the daemon does not hold.
- A switch flipped is put back when the Mac refuses it or is not reached.
- The web view loads the Mac's own origin only (anything else opens in Safari or is blocked) and keeps the page's
  copy of the key in memory (`websiteDataStore = .nonPersistent()`).
