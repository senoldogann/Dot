### 695. The MCP servers Dot offers start a version pinned by Dot, not whatever is newest

**Status: done (2026-10-26).** Each service of `mcp/catalogue.py` that Dot starts on this Mac (35 of them: `npx -y
<package>`, `<package>@latest`, a bare `uvx <package>`) ran whatever version its registry had newest at each start,
with the owner's rights and the keys the server is given. A release of any of those packages that was compromised or
broke reached the owner the day it was published, with no change of Dot's to read or revert. (`connections/directory.py`
starts nothing: its ways name the catalogue's services by id, so the catalogue is the one place that pins.)

**The change.** Every one is written with one exact version, the newest its registry had on 2026-10-26 (`npm view`'s
`latest` for npm, PyPI's `info.version` for PyPI): `name@x.y.z` after an npm package and `name==x.y.z` after a PyPI one
(`uvx name==x.y.z` works as `uvx name` did: tried with a throwaway package in a throwaway uv home), the other arguments
of each entry as they were. `@azure/mcp` is at `4.0.0-beta.3` and `markitdown-mcp` at `0.0.1a8` because those are the
versions their registries call latest, which `@latest` and a bare name ran before. `catalogue.py` gains `package_of`
(the registry, name and version a service's arguments write) and `unversioned`; `service_of` (which marks a server as
a service's) now compares the packages without their versions, so that a server added while the catalogue wrote
`@latest` or no version is still its service's in the list. `scripts/catalogue_versions.py` prints, for each pinned
package, the pinned and the newest version (the network; no test runs it), for the owner who bumps them, and
`docs/development.md` and `docs/extending.md` say so.

The test of the registries (`tests/smoke/test_catalogue_reachable.py`, marked `internet`) asks each registry for the
version pinned, not the newest, so a pin to a version that does not exist fails there (run 2026-10-26: all 35 exist);
the script says "newest not known" when a registry does not answer (the code review).

**Checked.** A unit test loads the catalogue and the directory and asserts that every package started by `npx` or `uvx`
pins one exact version, written as its registry reads it, with no `latest` and none unversioned; another that
`package_of`, `unversioned` and `service_of` read `@scope/name@x.y.z`, `name==x.y.z`, `--from`, and the old forms.
`tests/unit/test_mcp_connect.py` and the other tests of the catalogue and the directory, `ruff`, `mypy`. The pinned
servers were not started: a version is the newest, not one tried here (`tests/smoke/test_catalogue_reachable.py -m
internet` still checks each package is on its registry and not deprecated). A server already added keeps the arguments
it was added with; remove it and add it again to move it to the pin.
