### 1199. An upload whose control the page drew anew since it was read goes to the one alike control the page shows now

**Status: done (2026-11-16).** Dot's record showed `browser_upload` failing four times with *the ref is not in the
latest snapshot (the element changed or the page re-rendered); take a new snapshot*, in a webmail composer and in
LinkedIn's post composer, two of them in runs that had read outside content, where an upload waits for the owner's yes
or the review model (item 561). Playwright ties a ref to the DOM element it was given to: a composer that redraws its
toolbar puts a new button of the same role and name in place of the old one, and the ref of the old one names nothing.
The run had the right control; the page had only drawn it again, and the upload taken again asked once more.

- `core/errors.py`: `RefGoneError`, the `BrowserError` `live_locator` raises for a ref the page no longer has.
- `browser/snapshot.py`: `redrawn_ref`, the ref a control of the last view has in a new snapshot: its own while it is
  there, else that of the one line of the same role and name in the same frame; none for an unnamed control, or for no
  alike line or several.
- `browser/session.py`: `upload`, on `RefGoneError`, takes a new snapshot of the whole page (`_redrawn`) and gives the
  files to that control, saying so in the page's notes; not when the page is at another address than the view's or
  either snapshot was a partial one.
- `docs/browser-and-computer-use.md` says so.

Checked with a browser smoke test of a page whose script redraws its upload button after the snapshot: the files reach
its field (the test fails without the change, with the record's error), and a redraw into two alike buttons, or into
none, still fails.
