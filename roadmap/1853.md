### 1853. Proof before done: a task run or a campaign can carry checks that must pass before Dot marks it done

**Status: done (2026-11-25).** Taken from the study of Hermes Agent (`reports/refs-2026-11-25/hermes-agent.md`, item
1, "quality gates" of its `/goal`, `hermes_cli/goals.py`), on the owner's word of 2026-11-25. Until now "done" was a
model's word every time: the goal check reads a digest of the run (`docs/autonomy.md`), and a campaign's claim is the
goal checker's (`docs/agents-and-campaigns.md`). A proof check takes that word from a machine: a command (a test run,
a `curl`, a `test -f`) with a time limit, which has to exit 0 before the run or the campaign is done.

The approach, written before the code:

What must hold:
- A task run that carries proof checks never ends `done` while one of them did not exit 0 in the run's last look;
  a campaign that carries them is never `achieved` while one did not. There is no fallback: a check that cannot run
  does not leave the decision to the model.
- A proof check runs as a `shell` call of the run itself, made by Dot instead of the model: the same tool, the same
  gate (the owner's rules, the mode, the taint, the review, the caps), the same sandbox, the same events, masking and
  time limit (the check's own `timeout_s`). Dot adds no rule to the gate and takes none away, so a `yolo` or free-mode
  run asks nothing it would not ask for that command typed by the model, and refuses nothing it allowed
  ([Freedom](../docs/freedom.md)); a run in `ask` asks what that shell command asks there.
- Checks are only added, never changed or removed by a run: a run that could soften its own proof would make it the
  model's word again. The owner's checks and a run's are kept the same way and both hold.
- What a check printed reaches the next step: the run sees the call and its result in its conversation, and a check
  that failed sends the run back with its exit and the end of its output.

What may ask: only what the gate asks of that shell command in the run's mode, as for any shell call.

What was built:
- `agent/proof.py`: `ProofCheck` (a command of 1 to 2000 characters, `timeout_s` from 1 to `[shell] max_timeout_s`, which the shell would cut a
  longer one to, so one past it is refused when set and does not run; `by` owner or run), at
  most 5 per run or campaign, kept as `proof` events of the run (a resumed run takes over those of the run it goes
  on from) and as the new `proofs` column of a campaign (JSON, `'[]'` for every campaign before); the pure reading of
  outcomes into passed, failed and could not run, and the notes.
- The owner sets them: `proof` in `POST /api/runs` (with `standing`, the campaign's), `dotx run --proof CMD`
  (repeatable, `--proof-timeout S`, 300 by default). A run sets them with the new `add_proof` tool, offered to task
  runs only (it adds to the run's checks, or, in a campaign's session, to the campaign's, with the `persistence`
  flag as `campaign_targets`). A chat or research run is refused proof (no `shell`, no `finish` to hold), and so is a
  run on the Claude plan or OpenCode, whose turns Dot's loop does not settle; `add_proof` refuses there too.
- Dot's loop (`agent/loop.py`): at a finish with success, after the plan reminders and before the goal check (with or
  without goal mode), and at a finish past the run's limit, the run's checks run as one step of `shell` calls in the
  conversation (as item 1118's skill read is). All passed: the goal check, when on, decides as before and sees the
  passing runs among the facts. One failed (exit not 0, or killed at its time limit): the run is sent back with each
  failing check's command, exit and the last 3000 characters of its output, which counts toward `goal_patience`;
  past it, or at the limit, the run ends failed and says the proof did not pass. One could not run (the gate, the
  owner or a cap refused it, or the run has no `shell`): the run ends failed and names why, as sending it back would
  be refused the same way.
- A campaign: `campaign_achieved` runs the campaign's checks first, as calls it makes (the executor hands it the
  nesting `code_run` has, item 1501, with `via: proof` on their events), before the typed judge and the goal checker.
  A failed check refuses the claim with its output and the campaign goes on; one that could not run refuses it and
  tells the session to write a setback and ask the owner.

Checked: `tests/unit/test_proof.py` (the pure reading and the notes), `tests/smoke/test_proof_checks.py` (a scripted
model: a run sent back by a failing check and done once it passes; a yolo run's check asks nothing; a check the gate
refuses ends the run failed; a campaign claim refused by its check), `tests/unit/test_freedom_contract.py`, `dotx eval
check`.
