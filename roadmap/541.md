### 541. A pull request carries a batch of items

**Status: done (2026-10-22).** After item 540 shortened the pushes, the owner asked for the next step: not a pull
request for every feature. Each pull request costs a review of several minutes, a gate of ten or more and a merge;
the items of one session (531 to 538 were eight of them) paid that eight times.

**As built.**
- CLAUDE.md says a session's work goes in one branch and one pull request: several roadmap items, each its own commit
  `Item N: ...` with its own `roadmap/<n>.md` and `changes/<n>.md`, the numbers taken together. A batch is merged with
  `gh pr merge --rebase` (the repository allows it), so that each item stays one commit that can be reverted alone; a
  pull request of one item may still be squashed. A part stays out of the batch when it needs the owner's look (a change
  under "Always needs a human" waiting on them must not hold the rest) or is a risk that should be reverted alone.
- `scripts/next_item.py [count]` gives consecutive numbers for a batch, and `scripts/pr_body.py <item>...` makes the
  title (`Items N, M and K: ...`) and the body (a section for each item) from the entries. REVIEW.md asks the review to
  name the item of each finding and to check each entry against its own commit; CONTRIBUTING.md and the pull request
  template say a pull request may carry a batch.

Checked by `tests/unit/test_next_item_and_pr_body.py` (the title and the body of one item and of a batch, the numbers
of a batch).
