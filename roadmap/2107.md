### 2107. A queued message sent on into the run no longer reappears under the answer

**Status: in progress (2026-11-28).** The owner's report of 2026-11-28 (iPhone, DotNext, screenshot): after a finished
run ("Worked for 2m 6s", 13.29) an earlier message of theirs and a "Starting…" line stood at the bottom of the chat.

Root cause, read from the owner's store (read-only): the phone queued the message at 13:28:00 (`que_mx0btj0u_1eccbe`) and
two seconds later the queue's Send now steered it into the run at work (`POST /queue/{id}/steer`, the run's `steer`
event at 13:28:02); the run ended done at 13:29:28. DotNext keeps the owner's accepted message as an overlay until the
chat shows it in its place, and for a queued message waited only for a run started with its words. A steered message
starts no run, so the overlay stayed "Sent" for good, sorted after the transcript, and with no run at work its
`.delivered` state drew the "Starting…" line. The web was not affected: its queued messages stand in the queue, and a
steered one waits only for its `steer` event.

What must hold:
- A queued message that left the queue is in its place, and its overlay goes, once a run of the chat holds a `steer` of
  its words that came after it was sent (the newest event id of the chat then is kept, as the runs are, and event ids
  only grow, so an older steer of the same words, "continue", does not count, even one read later), as well as once a run of its words started (`delivery(of:in:)`).
- A queued message this phone took out of the queue drops its overlay when the Mac took the removal.

How it was checked: DotEngine `ChatRulesTests.testAQueuedMessageSteeredIntoTheRunAtWorkLeavesTheOverlayOnceItsSteerShows`
and `SyncTests.testAQueuedMessageSteeredIntoTheRunAtWorkLeavesNoOverlayOnceTheRunEnds`, which queue, steer and end a run
against the fake daemon; both fail without the fix with the owner's state (the message `.delivered` under the answer).
`SyncTests.testAQueuedMessageRemovedFromThisPhoneLeavesNoOverlay` checks the removal.
