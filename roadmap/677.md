### 677. OpenCode's agent works in Dot's sandbox, and a patch is weighed by every file it writes

**Status: done (2026-10-26).** The whole-project review of 2026-10-26 found the run on one of Zen's free models
(`opencode:`) to be the one way outside `yolo` whose commands ran with no kernel sandbox: `opencode serve` was started
with plain `create_subprocess_exec`, so a script its agent wrote (allowed in the workspace) and ran ("runs a script",
low) read Dot's key file or token, or wrote the shell's startup files. Three holes of the policy's reading came with it:
OpenCode's `apply_patch` asks one `edit` for all the files of a patch, its `patterns` each file and its `filepath` their
names joined by commas, which Dot read as one path inside the workspace (`ok.txt, ../.ssh/authorized_keys` was low); a
command's own folder (`workdir`) was not read, so `cat .ssh/id_rsa` in the home folder was weighed as a read of the
workspace; and the server's password, in its environment, reached every command its agent ran, which could answer its
own asks at the server's port.

**What must hold, and where.** In the kernel: outside `yolo` the server starts under `sandbox-exec` with the profile of
the run's commands (`policy/sandbox.py`, `confined_server`), so it and everything it starts are held as Dot's own
commands are, with two rules added after it: the server may write its own data, state, cache and home folders, not its
config (Dot writes that), and no process of it may connect to its own port on this Mac (`(deny network-outbound (remote
tcp "*:<port>"))`), so the password is of no use to a command that reads it. The confined server has a home of
its own (`opencode/sandboxed`, started from the catalog the other server refreshed), so nothing its agent leaves there
(OpenCode runs programs it keeps in its cache) is ever run by the server of a `yolo` run, which stays as it was. In the
policy, by what it can read: an edit is weighed by each of its patterns and takes the most the policy asks of any of
them, with all their flags; a command is weighed in the folder of its call (the `workdir` OpenCode showed with the call,
or the ask's metadata). The tools OpenCode's agent has stay its own.

The daemon makes that home's folders and copies the catalog into it with no link followed, replacing a link the
agent put in a folder's place (never what it names), so neither a write through it nor a server that cannot start
follows (the code review and the security review of this item); and the rule on the port names every address, as an
IPv4 address written in IPv6 (`::ffff:127.0.0.1`) passed a rule of loopback's names (the security review).

A patch's action names every file it writes in its target, one a line, so that a rule of the owner's and the
review model read each of them, not the worst file alone (the third code review).

OpenCode writes a `.gitignore` in its own config folder at the start of each project, which the confined server may
not write (it would be a way to plant a plugin that answers the agent's own asks): before the confined server starts,
Dot runs `opencode models` once outside the sandbox with the confined home's config and fresh data, state and cache
folders of its own, so OpenCode writes there what it wants and nothing the confined agent left anywhere runs outside the
sandbox. Without it every session of the confined server failed (500), which the live tests of OpenCode showed
(`tests/smoke/test_opencode_live.py`, run against Zen's free models on 2026-10-26: five of six passed; the sixth, a
refused command, fails now and then on main too, as the model words its answer).

The home where OpenCode looks for a `.opencode` folder of settings is Dot's alone too, not the confined server's to
write: a settings file its agent left there would be read at the server's next start (the fourth code review). The
confined server writes its data, state and cache folders only, and the live tests pass so.

**Checked.** `tests/unit/test_opencode.py` (a patch with a file under a protected folder is high with
`secret_access`; a command in the home folder reads `.ssh`; one confined server per sandbox, the server of a yolo run
apart; the profile's added rules); `tests/smoke/test_opencode_confined.py` (a stand-in server started as Dot starts a
confined one: what it starts reads no sealed file, writes its data folder, not its config, and cannot connect to its
port); `opencode serve` 1.19.4 itself started under the profile and answered its health check (2026-10-26), once its
`config/opencode` folder was made beforehand, which Dot now does.
