### 575. Dot installs from its desktop app: no terminal, no Homebrew, no Xcode tools

**Status: done (2026-10-23), except what only the owner can run: building, signing and notarizing the image, and an
install on a Mac that has no Dot (see "Not run here").** Before, the README asked for Homebrew, uv, ripgrep, Xcode's
Command Line Tools, a git clone, `uv sync` and `dotx setup`. The desktop app is signed, notarized and updates itself,
but it connected to a daemon it does not contain. Now, with no Dot on the Mac, its window shows **Set up Dot** (a page
bundled with the app, in the look of the down page), and one button runs the install from Rust with the `uv` the app
carries. The change touches `desktop/src-tauri/capabilities/` and `tauri.conf.json`, which REVIEW.md lists under
"Always needs a human" (the owner reads it, and an independent `/security-review` reads it from the first push). The
"what must hold" table was written before the code, as item 540 asks; two rows moved while the code was built, and the
log says which.

**The approach, in short.**
- The window `installer` is a window of its own, not the window `main` shown a page: Tauri's ACL decides by window and
  origin, so the one capability that grants the install commands names that window and local pages and nothing else.
  The window `main` keeps today's capabilities and the grant to the daemon's pages, untouched.
- The page polls (`installer_status`, every half second) rather than listens: no event or channel permission is
  needed, and no message carries what a step printed except the answer to that poll, which is masked.
- The steps are plans (program, arguments, environment, what goes on stdin) that pure functions build and one runner
  runs, with the output of every step written to `installer.log` in Dot's log folder. A test runs the whole sequence
  with stand-in programs, so the order, the masking, the resume and the marker are tested without a network.
- Dot.app (the launcher launchd runs) is not built on the owner's Mac: the app bundles it, universal and signed, and
  `dotx service install --launcher <path>` (or `DOT_APP_LAUNCHER`) copies it into Dot's home in place of the clang
  build and signs the bundle ad hoc as before, so Xcode's tools are not needed. The app keeps the program it was
  made from (`Contents/Resources/launcher.program`, beside its hash), so that `dotx service install` typed in a
  terminal, which is not given the launcher (the variable is the installer's own), makes the app again from it
  and does not fall back to clang (round 1 of the review).
- The service's `PATH` gets `rg` and `uv` of the app's tools through a folder of two links in the runtime folder that
  the app makes again at every start where the app is (`DOT_APP_TOOLS`, read by `launchd.service_path`, which with
  the variable unset finds the folder in Dot's home: `runtime/app-tools`), so that moving the app does not lose
  `rg` and nothing else the app carries is on the `PATH` (the job's `PATH` names the folder).

**Not run here.** The installer was not run end to end: building and notarizing the image needs the owner's Developer
ID, and `dotx service install` loads a launchd job, which this work does not touch. What was run for real: uv 0.13.4
installing `dotagent-macos` 0.1.0 into the three folders (the layout and the metadata folder the app reads, `--no-config`

**Left for later, and not in this item.** A Mac App Store build; running without Chrome at all (the installer says so

`runtime/bin/dotx`): a repair button on the down page, which the app could answer with the same steps, is for later.

Two things the independent review named and this item leaves, said here so that they are not forgotten:
- **Unhashed dependencies.** The app installs the package's dependencies from PyPI without hashes, unlike a checkout,
  which `uv.lock` pins by hash. A later item could ship the release's requirements, exported from `uv.lock` with their
  hashes, in the app, and install with `--require-hashes`.
- **The guard and `dotx service install`.** The shell guard rates `dotx service install --launcher <path>` as low risk.
  What stops a sandboxed run from installing a Dot.app of its own is the kernel profile (Dot.app, its build folder and
  `runtime/` are closed to a command's writes); with `[shell] sandbox = false` it is as open as any script, as
  `docs/safety.md` says. A policy rule that asks the owner for `dotx service install` belongs to `policy/`, a path that
  needs the owner, and to a later item.
