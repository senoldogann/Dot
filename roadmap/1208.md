### 1208. A login refused on another page sends the run to its own site, and names the site it should be

**Status: done (2026-11-17).** The owner's run read App Store Connect: its login of Dot's vault is for
`appstoreconnect.apple.com`, and Apple signs in on `account.apple.com`, so `browser_fill_login` refused ("the login ...
is for appstoreconnect.apple.com, and this page is https://account.apple.com/sign-in") and the run had nowhere to go.
The owner asked that Dot, when the page is the wrong one, go to the right page.

What holds: where a login fills is unchanged (`vault/hosts.py`, `fills_on`: the login's host or one under it, over
https, or http on this Mac). Only the words of the refusal change (`elsewhere_advice`):

- **Another page:** the run is told to open the login's own site (`browser_open` its host and port, over https or, on
  this Mac, http; no path or query, which a website may carry) and fill there. If the site sends it back to that page
  or to another site to sign in, it does not fill: it tells the owner in one line that the site signs in on that page,
  which the login does not name, and goes on with what needs no sign-in.
- **The login's own host over http or on another port:** the run is told to open the login's own address.
- **No widening is proposed.** Whether a login should also name the page it was sent to is the owner's: no list of the
  suffixes names are sold under is read, so two hosts that end alike (`co.uk`, `github.io`) say nothing of one owner,
  and a page that names itself a sign-in is what a phishing page does too (the pre-push review).
