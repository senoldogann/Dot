### 1208. A login refused on another page sends the run to its own site, and names the site it should be

**Status: done (2026-11-17).** The owner's run read App Store Connect: its login of Dot's vault is for
`appstoreconnect.apple.com`, and Apple signs in on `account.apple.com`, so `browser_fill_login` refused ("the login ...
is for appstoreconnect.apple.com, and this page is https://account.apple.com/sign-in") and the run had nowhere to go.
The owner asked that Dot, when the page is the wrong one, go to the right page.

What holds: where a login fills is unchanged (`vault/hosts.py`, `fills_on`: the login's host or one under it, over
https). Only the words of the refusal change (`elsewhere_advice`):

- **Another site:** the run is told to open the login's own site (`browser_open https://<its host>`, no path or query,
  which a website may carry) and fill there, and, if that site sends it to a page of another site to sign in, not to
  fill and to tell the owner.
- **Another host of the same name** (the last two labels alike, as `same_site` of the browser reads a site): the same,
  and if the site brings the run back to that host, it tells the owner in one line that the login's website should be
  that name (`apple.com`) or name that host too, in the vault it comes from, and goes on with what needs no sign-in.
  Widening the login is the owner's: a page that names itself a sign-in is what a phishing page does too.
