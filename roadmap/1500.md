### 1500. Code mode's sandbox: the code of a `code_run` runs in a deny-default macOS profile, behind a bridge of two pipes, and fails closed

**Status: done (2026-11-24).** The owner decided on 2026-11-24 ("bunu kesinlikle uygulayalım") that Dot gets what
Anthropic's note "Code execution with MCP" describes: the model writes code that calls its tools, instead of calling them
one by one through its context (150,000 tokens of tool definitions down to 2,000 in the note). The note has six parts. Two
of them Dot had: loading tools on demand (a run on the Claude plan looks tools up with `ToolSearch`, item 1053; Dot's own
loop starts with the core group and opens the rest with `use_tools`). Four are new: tools as files, filtering in code,
loops in code, private by default (PR-B, 1504), and skills as code (PR-B, 1505). This item is the ground the other seven
stand on: the sandbox, the runner and the bridge. Safety is the point of all of it: code mode must not widen what a run can
do.

**Design** (written first, then checked against the code; what the check found is under it).

1. *One tool, `code_run`* (`src/dotagent/codemode/`, a folder of its own; nothing under `policy/`, `agent/approvals.py`,
   `agent/review.py`, `secrets.py`, `server/guard.py` or `undo/` changes): the arguments are the Python 3.13 `code`, a
   one-line `title` for the step's row and `timeout_s`. The model reads only what the code prints (stdout and stderr, as a
   head and a tail), and a footer with the number of tool calls and the seconds.
2. *It is an action like the shell.* `ActionInfo(kind="shell", risk="medium", body=<the whole code>)`, summary
   `Run code: <first line> (N lines)`: every approval mode, the owner's rules (which read the summary, the target and the
   body) and the review model treat it as they treat a shell line. No new policy path. Checked: the shell guard reads
   `python3 -c '...'` as `risk=medium`, reason "python3 runs inline code" (`assess_shell`), and the engine decides by kind
   and risk; the code is such a line, run where it can do nothing but compute and ask.
3. *Every tool call from the code is a call of the run's own.* Checked against the code: a tool's `run(args, ctx)` gets a
   `ToolContext` whose `gate` is only `authorize` and `add_instruction` (the executor wraps it so that the tool's own clock
   stands still while the owner decides), and the path of a call (validation and classification by `tool.prepare`, the
   check against the other runs, `RunGate.authorize_recorded`: the refusal of a secret sent out, the mode gate, the rules,
   the preset, the taint, the question to the owner or the review model; then the tool under its own time limit, the
   taint after it, the masking of every secret Dot holds, the events) is `execute_calls` → `_execute_one` →
   `_run_checked` in `agent/executor.py`, which the loop and the doors of Claude Code and OpenCode all use. It is not in
   `loop.py` and it is not in `PreparedCall`, which is only its middle. So the second path is not written: the executor
   hands a tool that nests calls (`code_run`) a `NestedCalls` (item 1501) that runs one more call through `_execute_one`
   itself, with the run's own context and gate and two fields added to the events (`"via": "code"`, `"parent_call_id"`).
   A refusal comes back to the code as `ToolRefused` with the gate's words; an approval asked from code is the owner's
   question as any other.
4. *The code has no ambient authority* (this item). It runs under `sandbox-exec` with a profile of its own, `(deny
   default)`, and the profile is the other way round from the shell's (which allows everything but Dot's files): the code
   is text a model wrote and a page may have shaped. Allowed: starting the interpreter, reading its installation and the
   system's libraries, reading the run's `tools` folder, reading and writing the run's `scratch` folder. Not allowed, and
   so refused by the kernel whatever path, link, letter case or library the code uses: the network (a socket is made and
   every connect, bind and send is refused), a process (`fork`, `exec`, `posix_spawn`, so `subprocess` and `os.system`), a
   signal to another process, every Mach service (the clipboard, the keychain's, Launch Services), a file anywhere else
   (the owner's, Dot's home, `~/Library`), a page that is both writable and executable, the name of the Mac
   (`os.uname()`, `socket.gethostname()` and `pwd` are refused, so `import ctypes` and `import platform` fail, which is a
   cost). The interpreter is the base interpreter of the daemon's own, by its real path (never a virtual environment's,
   whose packages are Dot's), run as `python -I -S -u -X utf8` by a launcher of this package that sets `sys.path` itself,
   with a clean environment (`HOME` and `TMPDIR` are the scratch folder; only `TZ`, `LANG`, `LC_ALL` and `LC_CTYPE` of the
   daemon's pass, and none that `hides_secret` of `tools/env_filter.py` holds back), in a process group of its own, with
   limits the kernel holds the process to (CPU time, the largest file, open files, one process, no core) and a watch in the
   daemon, many times a second, for the code's own time, its resident memory, its output, its scratch folder and the run's
   Stop, that kills the whole group. **Fail closed:** the only words that start the code (`launch_words`) start the sandbox
   first; a probe that runs once and is kept starts Python in a throwaway sandbox and checks that the code can use its two
   folders and that a file outside, a write outside, `/Users`, the network, `fork` and a spawn are each refused by the
   sandbox itself (`PermissionError`, not another error); if it cannot, `code_run` says "code mode needs the macOS sandbox,
   which did not start: <why>" and runs nothing, never unsandboxed; `dotx doctor` has a row for it (item 1503).
5. *The bridge is the only way out* (this item): two pipes the process inherits, JSON lines. The code writes
   `{"id", "tool", "args"}`; the daemon reads it as exactly that (a line longer than 32 MiB, no JSON, another key or type,
   a number out of its turn is a malformed frame and ends the code) and answers `{"id", "ok", "text", "images"}` or
   `{"id", "ok": false, "error", "refused"}`; at most `[code] max_calls` calls (200), and the 201st ends the code; the next
   request is not read until the code has read the answer, so a code that never reads cannot make the daemon hold replies.
   What the code prints is the process's own stdout, never the protocol.
6. *Not callable from code* (a deny list with a test that names each, item 1502): `code_run` (no recursion), `finish`,
   `ask_user`, `ask_secret`, `use_tools`, the plan and the reaction, the team, agent and campaign tools, `delegate`,
   `consult`, `message_agent`, `terminal_*`, `meeting_*`, `phone_*`, `browser_captcha`. Everything else the run's mode and
   its tool list allow is callable.
7. *Tools as files, load on demand for code, filter and loop in code* (1502, 1501): on the first `code_run` of a run the
   daemon writes `dot_tools/servers/<server>/<tool>.py` for each tool the run may call from code, a typed function (from
   the tool's JSON schema, keyword-only) with the description as its docstring and one call into the bridge, and a
   catalogue that `dot_tools.search_tools(query, detail="name"|"description"|"schema")` and `dot_tools.list_servers()`
   read. A result is a Python object (JSON parsed when it is JSON, else text; a picture is saved in the scratch folder and
   replaced by its path) and is never cut to the model's result budget: only prints reach the model. `code_run`'s own
   description is short and names these; no definition of a callable tool goes into a prompt.
8. *Where it is offered*: the core group of Dot's own loop and a door tool for the Claude plan (found by `ToolSearch`),
   modes `task` and `chat` as the shell's; a few static lines in the system prompt.
9. *Private by default* (1504), *skills as code* (1505), the prompt, the evals and the measurements (1506) and nesting the
   inner calls in the web UI (1507) follow in the second pull request.

**What the check against the code changed.** (a) The brief pointed at `agent/loop.py` and `PreparedCall` for the path of a
call; it is `agent/executor.py`, and the tool cannot reach the real gate through its context, so the nested caller is
handed to the tool by the executor rather than found by the tool. (b) macOS refuses `RLIMIT_AS` and `RLIMIT_DATA`
(`setrlimit` answers EINVAL, measured), so the memory limit is a watch of the resident size (`proc_pidinfo`, two
microseconds a look), not a wall: a single allocation larger than what is read between two looks (25 ms) goes over before
it is seen; measured, a 3 GB `bytes` allocation against a 300 MB limit was killed at 463 MB. (c) `RLIMIT_NPROC` set to 1
is what makes a `fork` fail with `EAGAIN` before the profile is asked; the profile refuses it too (`EPERM`, what the probe
reads), so a fork bomb dies at its first fork on two grounds, and threads are not counted as processes (measured: 50
threads under it). (d) The time of a tool call the code waits for, and the time the owner takes to answer, are not the
code's own time (`[code] max_seconds` bounds what the code itself runs, a `time.sleep` included); each tool has a limit of
its own and the step's is an hour. (e) The folders of the code are in the workspace, where the run's commands may write, and
the daemon writes into them with the owner's rights, so every write of the daemon there goes through a descriptor of the
folder above it with `O_NOFOLLOW` (`tree.py`): a link a command left where a folder or a file is to be is a failed write.

**What this item built.** `codemode/sandbox.py` (the profile, `launch_words`, the base interpreter, the probe and its
cache: a success is kept, a failure for five minutes), `codemode/runner.py` (`run_code`: the start, the bridge served one
request at a time, the watch, the kill of the group, the output kept as a head and a tail), `codemode/bridge.py` (the
frames), `codemode/watch.py` (the resident memory and the scratch folder, from outside), `codemode/tree.py` and
`codemode/install.py` (the folders and the files of the tools folder), and the three files that run inside the sandbox,
standard library only, copied into the run's folder before every start: `child_launcher.py` (limits, `sys.path`, the bridge,
the code as `__main__` with its source in tracebacks, an exit when the daemon is gone), `child_bridge.py` (`call`,
`ToolError`, `ToolRefused`) and `child_tools_init.py` (`dot_tools`: `search_tools`, `list_servers`).

**What the pre-push review found, and what changed** (round 1 of the pull request: one Important, three nits). *Important:* the
code of a start was the one file the daemon wrote under the run's folder without `Tree` (`mkdir` and `write_text` followed a link
a command of the run had left at `tools/snippets` or at the next file's name, which would have written the model's Python at
any path the owner's account reaches); it is written through `Tree` now, an `OSError` there is `unstartable` ("the code could
not be written") and not a crash, and the same descriptor-based walk empties a scratch folder that is over its quota
(`Tree.clear`, which enters no link and refuses a link in the folder's place). *Nits taken:* the page said `exec` was refused
while the profile allows it for the interpreter's own path (a fresh interpreter in the same sandbox: a test shows it reads no
more), so the page says so and the probe now also tries an `exec` of another program, on a line of its own after the rest (where
it is allowed the process becomes that program and the line never comes, which reads as not refused); the probe asked whether
the daemon could read *itself*, which is not the right the limit needs, so it starts a process and reads that one, and `_watch`
stops a code whose memory cannot be read for half a second instead of taking nothing read for nothing held. *Found beside:* the
launcher let a limit it could not set go (a code could run with fewer guards than promised), it now ends with a message and
exit 72 before the code runs; the watch killed a process group by a number the process might no longer hold, and now only while
the process is not reaped.

*Hardened beside:* `layout_for` refuses a run id that is not letters, digits, `_` and `-` (a run's id is made by Dot; one that named another place would have been joined into the folder's path), and the package's docstring named a function that does not exist.

**What the sandbox profile needed, measured on macOS 26.6.2 (25G83, Darwin 25.6.0, arm64) with uv's Python 3.13.16.** With
`(deny default)` alone the interpreter is refused at its exec. These lines took it to a start: `process-exec` of the
interpreter (literal); `file-read*` of its installation (subpath); `file-map-executable` of that, `/usr/lib` and
`/System/Library`; `file-read*` of `/usr/lib`, `/System/Library` and `/usr/share/locale`; `file-read-data` and
`file-read-metadata` of `/` (literal; without it the interpreter aborts at its start, `deny file-read-data /`);
`file-read-metadata` of `/var`, `/etc`, `/tmp`, `/System/Volumes/Data`, `/System/Cryptexes/OS`; `sysctl-read` of twelve
names and `hw.optional.*` (`security.mac.lockdown_mode_state`, `kern.bootargs`, `kern.osproductversion`,
`kern.osvariant_status`, `kern.iossupportversion`, `hw.pagesize_compat`, `hw.pagesize`, `hw.ephemeral_storage`,
`hw.ncpu`, `hw.activecpu`, `hw.physicalcpu`, `hw.logicalcpu`; the interpreter starts without them, and `os.cpu_count()`
is `None` without the counts); `file-read*` of `/private/etc/localtime`, `/private/var/db/timezone` and
`/usr/share/zoneinfo` (without them the local time is UTC); `/dev/null` (read and write), `/dev/urandom` and `/dev/random`
(read); then the run's two folders. With those, all of the standard library imports (84 modules tried, among them
`asyncio`, `sqlite3`, `hashlib`, `ssl`, `zoneinfo`), threads and `concurrent.futures` work, and `tempfile` finds the scratch
folder. Refused, measured: `open` outside, `os.listdir` of `/Users`, `~` and `/dev`, `stat` of the home folder, every write
outside, a symbolic or hard link to a file outside, `socket.connect`, `bind`, `listen`, a UDP send and a Unix socket
connect (a socket can be made, a `socketpair` works), `gethostbyname`, `urllib`, `subprocess`, `os.system` (returns a
failure status), `fork`, `execv`, `posix_spawn`, a `ctypes` call to `system` and to `open`, `launchctl`, `pbpaste`,
`security dump-keychain`, `os.kill` of the parent, a read-write-execute `mmap`.

**Checked by** (`tests/unit/test_code_attacks.py` (19 tests), `test_code_bridge.py`, `test_code_sandbox.py`, `test_code_watch.py`;
macOS 26.6.2, the real interpreter in the real sandbox): each attack is an input with its verdict and its twin's, and
first it is made with no sandbox (the control), so that an attack the control cannot make is no test: open a file outside
and write outside (the tools folder read-only), a socket, `urllib`, `bind` and a UDP send, `subprocess`, `os.system`,
`posix_spawn`, `execv` and `fork` (a marker file shows whether a program ran), `ctypes`, Dot's home and `~/Library` and the
keychain's folder, the environment (six decoy secrets in the daemon's), an infinite loop and a sleeping loop, a memory bomb,
a huge print (60,000 lines; kept as a head and a tail) and an endless one, a fork bomb, a scratch folder filled with files,
a file past the size limit, malformed frames (seven kinds, and half a frame, and one past the size), the 201st call, the
run's Stop and a cancelled step (the process is gone), a code that never reads its replies, a sandbox that does not start
(`/usr/bin/sandbox-exec` missing: `unstartable`, a marker file shows the code did not run), a profile the kernel refuses
and one that does not hold (`(allow default)`: the probe names what it saw), a link where the daemon writes the code and one in place of the scratch folder
(nothing is written or emptied through it), an `exec` of the interpreter itself (it stays in the sandbox) and of another
program, a memory that cannot be read, a limit that cannot be set, and the twin of each. Mutation, run once: with
the profile replaced by `(allow default)` and the daemon's whole environment handed over, 8 of the 15 attack tests fail
(file read, write, network, programs, ctypes, Dot's home, the environment, the probe); the other 7 are held by the runner's
own watch and the kernel's limits, not by the profile, and their controls show the attack is a real one (the loop never
ends, the memory is held, the print is that large).

**Not verified.** Another macOS than 26.6.2 (the profile's `sysctl` and `mach` needs differ between releases: the
probe says what it sees on the Mac it runs on, and the gate's macOS runners run these tests); an Intel Mac; a Python that
is a framework build or Homebrew's; the Python of the desktop app's `runtime/python` folder (its prefix is checked by
`prefix_problem` against a folder too broad to be read whole or one that holds the owner's home, Dot's home or the run's
folders, by tests with made-up prefixes only); memory above the limit between two looks; that a hostile code cannot find a
hole in `sandbox-exec` itself (the profile is the kernel's, and `sandbox-exec` is deprecated by Apple but is what the
shell's sandbox of item 531 already uses).
