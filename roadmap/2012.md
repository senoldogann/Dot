### 2012. Several tasks in one chat, slice 2: where a message goes

**Status: built (2026-11-27), behind `[agent] chat_tasks` (1 by default).** Slice 2 of [item 1982](1982.md)'s design,
after slice 1 ([item 1984](1984.md)); the pages and the phone show the tasks in slice 3. The owner's case it serves: a
form task ended asking for their e-mail address, they asked for x.com work meanwhile, and their plain answer, sent
while x.com works, must reach the form task and not wait behind x.com or start a chat that knows nothing of it.

**Built.**
- `agent/lanes.py` (pure): `split_quote` reads the quote the pages and the phone write (item 1972), `is_stop_only`
  ("dur", "durdur", "durun", "stop", "halt"), `new_task_words` (`/new <words>`), `quoted_task` (the one task whose
  messages hold the quote's first 80 characters, folded; none when two do or the quote is under 8 characters),
  `prose_question` (a reply ending with "?").
- `agent/busy.py`: `route_message`, the fast model's question (`route_message` tool, `task` 0 for a new one), shown
  each open task's goal, whether it works, and its question only when shown; the call's purpose is `route`.
- `RunManager.route_message`, from `POST /api/threads/{id}/queue` when `chat_tasks` is above 1 (it replaces item
  915's question there): the rules of `docs/runs.md` in order. The model's verdict never vouches: for the thread the
  message was sent to it is the owner's follow-up as before; another task at work gets it in its queue
  as words carried from its run (`_queue_carried`, `queued_messages.carried_from`, an added column:
  `_start_queued` starts them carried whenever they start); another task that ended asking starts its next run as carried words
  (`_continue_task`, `RunOpening.carried`: as tainted as that run ended); `0` starts a lane. A quoted stop of a task
  that does not work stops nothing. The router is shown each task's newest run of the owner's own words. The open tasks are each thread's newest run
  of the owner's that works, or that ended with a card left (`Store.left_questions`) or a reply ending with a
  question in the last 24 hours. A Stop of the chat while the model answered sends the message to the held queue.
- The cap: `Store.chat_tasks_at_work` counts as `create_lane` does; a task that would start past it, by a route
  or where it was sent (`hold_for_free_task`, from the queue's route), waits in its thread's queue held for `tasks` (a new reason of `hold_queue`), which `_free_tasks` releases as a task of the chat
  ends (`_follow_queue`); `stop_chat` turns such holds into the owner's. This closes slice 1's first nit (the chat's
  own thread starting past the cap). Slice 1's other nits: an empty lane counts only for its first 60 s
  (`LANE_START_GRACE_S`), and a new lane is told "(stopped)", "(failed)" or "(blocked)" for a run with no reply.
- Move: `POST /api/queue/{id}/move` and `POST /api/runs/{id}/move` (`MoveRequest.to_thread_id`, `null` for a new
  task), the owner's own word, as a quote; refused for another chat's task (422) and for a run not at work (409).
- `QueueView.routed` (`RoutedMessage`: kind, thread, run, message), in `docs/schemas/thread-sync.schema.json`.

**Not done here.** The web's message while the chat's own run is idle still starts it through `POST /runs`, which
does not route: slice 3 sends a chat with tasks through the queue route, as the phone does already. A new task past
the cap starts in the thread it was sent to once a place is free (the chat's own, usually), not in a lane.

**The pre-push review** (first round, BLOCK) found the cap missed on the ways a message goes where it was sent, a
model's verdict queued for a busy task clearing a thread's mark when it started later, and a quoted stop of a task at
rest stopping every task; all three fixed here, with tests, and its three nits (a routed run id read as a start on a
message sent again, a redundant test, words of a run not the owner's shown to the router).

The second round (BLOCK) found the router's queued words skipping a queued message's checks (`_check_queued`, now
shared with `queue()`, and the ✋ release) and Move taking a message out before any check; Move now refuses what a
steer refuses, checks first and puts the message back on a failure, and a run is checked before it is stopped. Its
nits: a hold for a free task waits for the owner after a restart (`recover`), and a lane dropped before its run
started frees what waited for its place.

The third round (BLOCK) asked for the checks that round 2's Move fixes hold (`test_a_move_that_fails_loses_nothing`,
named in REVIEW.md with round 2's), a moved run's end waited for before its words start a new task, and a failure
to free a place logged so that a lane's own failure is the one told.

**Checked.** `tests/unit/test_lanes.py`; `tests/smoke/test_chat_routing.py`: the owner's case (a new request beside a
task that waits; the answer back to it), an answer routed to another thread's waiting task starts its next run, a
message routed to a task at work is queued and never steered, a doubt is queued where it was sent, a stop, a quoted
stop, a quote and `/new` ask no model, Move steers into the task named and refuses another chat, a task past the cap
waits in a queue held for a free task and starts when one ends, as does a message the model cannot place;
words routed to a task at work start its next run carried, marked and leaving the thread's mark; a quoted stop of a
task at rest stops nothing; a routed message sent again with its key says no start; a routed message for a model
with no key is refused and nothing queued; Move refuses a message with picks, which stays. `tests/smoke/test_chat_lanes.py` (its fast model now
answers the router), `test_busy_parallel.py`, the queue's, the questions', the thread sync's and the freedom
contract's tests.
