### 493. 1Password: logins filled without the model seeing them

**Status: done (2026-10-21).** Asked by the owner after Grok Bot's 1Password connector: the agent should use the
owner's passwords. Until now a password was the owner's to type outside yolo (item 429), and a run that typed one had
it in its context.

The design follows 1Password's guidance for agents ("avoid passing secrets to the model") and Grok's flow:
- a dedicated vault and a service account that reads only it, since a service account cannot read the owner's
  Personal vault (1Password's docs, read 2026-10-21);
- the model names a login and its fields, and the daemon types the values.

**As built.**
- `vault/onepassword.py`: the `op` connector, run with a few variables of the environment and the token as
  `OP_SERVICE_ACCOUNT_TOKEN` alone.
  - It reads the logins of the vaults the token reads (titles and websites, kept a minute, as 1Password limits
    reads) and, at the moment of a fill, a login's username, password and code (`SecretStr`).
  - `connect()` makes the vault "Shared with Dot" and a read-only service account with the owner's `op` through
    the 1Password app.
  - What `op` answered is in no error, and a validation error stays out of the chain: it may hold a value.
  - Its JSON shapes are `op` 2's as documented. They were not seen from a real account here (no 1Password on this Mac).
- `vault/hosts.py`: `fills_on`: a page of one of the login's websites or a host under one (of a site of a dot), on
  the port the website names (its scheme's own when it names none), over https, plain http on this Mac alone.
- `vault/masking.py`: the values (four characters and longer), masked in text and in JSON, as typed, as an address
  writes them (as a browser writes a form's field, as `encodeURIComponent` and `encodeURI` write them, as Python's
  `quote` does), as a JSON string escapes them, and each with its blanks made one space, as a line of a view is
  written. `BrowserSession.read_text` masks a page's text before it cuts it into slices.
- Browser:
  - `driver.fill_login_field` reads the field's marking, and its frame's address from the browser's frame tree
    (`owner_frame`), since a script of the frame can make the element name another document; then it fills that
    element: a password into a password field alone, nothing into a frame of another site, a password or a code
    into no form whose method, or a submit button's, names GET or a word no browser knows (the address would hold
    it, in every view and log, and a shortened one a part of it), Playwright's log out of the error.
  - The guard of Dot's own Chrome (`BrowserSession._judge`) refuses every request whose address carries a password
    or a code filled from the vault (`vault/masking.in_address`): as it is, or once its escapes are read back as
    UTF-8 and as Windows-1252, with `+` as a space and as itself, and escapes of escapes a few times over: a value as
    a form or a script escaped it. A form that names no method sends by GET, and so can a script. A password is kept out for as long as Dot
    runs, a code for five minutes. Such a request is named by its host alone in the refusal and the log, or by its
    scheme when the value is in the host.
  - In the owner's own Chrome (attach mode), whose requests Dot does not guard, a fill of a password or a code is
    refused: the owner's password manager fills them there.
    The field it fills is marked (`data-dot-vault`), and every screenshot of the browser covers it, in every mode.
  - `BrowserSession.fill_from_vault` checks the page, keeps the thread's values to mask from the first one on, and
    marks the tab (`Tab.vault_held`).
  - `run_script` refuses while any tab of the thread is marked, for as long as the tab is open: going back can bring
    the filled page back whole from Chrome's cache of pages, so another document does not clear it.
  - A fill is refused once a script of the run ran in a tab of the thread (`ThreadTabs.scripted`), until the thread
    has no tab left: the script could have left a listener that copies what is typed, in its page, in a tab it
    opened, or in a page Chrome brings back from its cache.
  - The values to mask are the session's, by thread (`BrowserSession._vault_values`), apart from the thread's tabs,
    which an idle thread lets go of while its chat goes on.
  - The hold and the values to mask are kept only once a field passed its checks, just before the value goes in.
- Tools:
  - `browser_logins` and `browser_fill_login`, offered only while a token is kept (`loop.py`).
  - Every browser and web tool is wrapped (`masked_tool`): its text, its errors' words and context (the model reads
    `str(error)`), errors of its classify, and its action's summary and target, which the approvals, the policy's
    events and the review model read, all mask the thread's values. The web tools read pages in Dot's Chrome, signed
    in once a login was filled. So do the typed judge's facts of a page and of a click.
  - A title two logins share is refused: an id tells them apart, and the card names the login's sites.
  - The token is read from Dot's `.env` alone (`kept_token`), not the environment or the Keychain, so Disconnect
    ends it and no run's start asks the Keychain.
  - The prompt names the tools when the run has them.
- Policy:
  - the flag `vault_fill` and the source `vault` (`vault_guard`): asked in every mode but yolo, whatever the rules
    say, a hand-off rule alone stricter;
  - `route_for` sends it to the owner in `auto`, as own files;
  - rule replay knows it as settled before the rules;
  - the shell refuses `op` (`secret_access`).
- `routes_vault.py`: `GET /api/vault`, `POST /api/vault/connect` and `POST /api/vault/token` (both from this Mac's own
  address only), and `DELETE /api/vault`. The token is in Dot's `.env`, a guarded file, under `DOT_ONEPASSWORD_TOKEN`.
- The UI:
  - 1Password under Password managers, with a key in the brand's blue;
  - its page: Connect 1Password, a token instead, Disconnect;
  - the approval card names the fill as asked in every mode but yolo.

**Tests.**

- `tests/smoke/test_vault_fill.py`, with a stand-in `op` (`tests/fixtures/op_stand_in.py`) and a real Chrome:

  - the script refused meanwhile, on the next page of the tab too, and run again in a new tab once it is closed;

- `tests/smoke/test_vault_routes.py`: a pasted non-token refused; Connect making the vault and keeping the token, which

**Not covered.**
- In yolo the review's refusals are waived, so a run may read any file, Dot's `.env` among them; the fill itself still
  shows no value.
- What is kept from the model is the password and the one-time code: the owner's word of 2026-10-21, after the
  fourth review found the username again where a signed-in site shows it. The username is no secret: the files a
  crawl writes and an MCP tool show it as they find it.
- The desktop tools are not wrapped: their screenshots show Dot's Chrome as the screen does, and Chrome's
  accessibility values of a plain field (a username, a code, a password a page shows as plain text) can be read with
  them, and so can what a copy puts on the clipboard. A password field's value is never read there.
- A page in another legacy charset (Shift_JIS, KOI8-R and the like) writes the escapes of a value Dot does not
  read back, and a page's own script can change a value before it puts it in an address. Only the login's own site,
  which has the values, does either.
- A page of the login's own site can write a value into its own words: Dot masks it where it shows it whole, and
  a line it shortens can keep a part of it. Only that site, which has the values, can.
- Dot's log keeps a page's address as it was: with a password or a code kept out of addresses, a username sent by
  GET can be in it. So does Chrome's history.
- The values to mask are kept in memory while Dot runs: a chat that goes on after the daemon restarted masks them no
  more, though no tool shows a password field's value and the page's own words rarely hold one.
- An error that is not Dot's own, once values were filled in the chat, is told masked without its chain
  (`browser_tool_failed` in the log names its kind).
- The owner's real account was not tried: `op` is not installed on this Mac.
