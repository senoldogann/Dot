### 1353. Dot for iPhone is a native SwiftUI app: chats, approvals, helpers, the queue and schedules (first slice), with the web UI one tap away

**Status: done as a first slice (2026-11-23); the screens it leaves are listed below.** The owner's word: the phone's
side of Dot is rewritten as a native Swift app, the web UI stays as it is. A web view of the web UI kept giving trouble
that is the web view's own (scrolling, the swipe back that switched chats, scroll indicators, layout), and the app had
to be fast: a chat that opens at once, a stream that comes back on the second the app does, an answer that is seen as it
is written. Dot is not a coding harness: it is an autonomy that does what a person does on a computer, so what the app
puts first is what the owner must answer (approvals, questions), the helpers a run waits for, the schedules and loops
that run by themselves, the agents, and how the run stands.

**What the daemon gives a phone (read before writing any of it).** All of it under `/api`, with `Authorization: Bearer
<phone key>` (the key a pairing code buys, item 670), nothing to add for the first slice but one header:

| What the phone needs | Route |
| --- | --- |
| pair | `POST /phone/pair {code}` → `{token}`, no token needed; the code is `POST /phone/pairing` on the Mac |
| chats | `GET /threads?limit=` (title, status of the latest run, `unread`, last words, `loop_cron`); `PATCH /threads/{id} {seen}` |
| agents | `GET /agents` (each with its newest run and its home chat) |
| a chat's transcript | `GET /runs?thread_id=` (newest first), `GET /runs/{id}` (children, open questions), `GET /runs/{id}/events?after=&limit=` (stored events, ids are one order for every run) |
| live | `GET /runs/{id}/stream?after=` (SSE: stored events after `after`, then live ones; the words being written have id 0 and are not stored; ends after the run's last event), `GET /stream` (the lifecycle stream: replays nothing, `resync` when it fell behind) |
| send, queue | `POST /threads/{id}/queue {text, key}` starts a run when none works there and queues behind the one that does; `GET`/`PUT /threads/{id}/queue` (`PUT {ids}` reorders), `DELETE /queue/{id}`, `POST /queue/{id}/steer` |
| stop | `POST /runs/{id}/cancel` |
| approvals, questions | `GET /approvals?status=pending`, `POST /approvals/{id}/decision {approve, note}` (the note is a question's answer; a card that asks for a secret is refused a yes there) |
| helpers | `GET /threads/{id}/helpers`; their events are on the root run's stream (`run_queued` with a `parent_run_id`, `run_finished`) |
| schedules, loops | `GET /schedules`, `GET /threads/{id}/automations`, `POST /schedules/{id}/enable` and `/disable` |
| models | `GET /models`, `GET /status` (`models.main`, `models.review`), `POST /models/main {model}`, `POST /models/roles {role, model}` |
| push | `POST /phone/apns`, `POST`/`DELETE /phone/apns/activity` (already in the app) |

*Resume.* The run stream resumed from `?after=<id>` already (Dot's pages use it); it did not read the standard
`Last-Event-ID` header. Item 1352 adds that, backwards compatible; the app sends both. The lifecycle stream replays
nothing, so after a break the app reads the list and the open chats' deltas again. Deltas (the words being written) have
no id: the stored `assistant` event of their step replaces them in place, which is why a drop never leaves a half
sentence.

**What the reference app does that fits here** (its mobile client, read from a clone, not copied): one decision per
layer (router, shell, screens, design system, native), the chat list as the root with pages pushed on a phone, the
inspector as a sheet where there is no room for a column; connections woken by the app coming to the front and by a
change of the network path (not only online/offline), a cache of the shell (list) and of each thread that opens a screen
before the network answers, with a schema version on what is stored. All of that is taken; its stack (React Native,
Effect) is not.

**Architecture** (`ios/Dot`, SwiftUI, iOS 18 as the project already is, Swift 6 strict concurrency, no packages):

- `Core/` pure and without UI: the records the daemon writes (`Models`, `JSONValue`), `ChatState` (the reducer that turns
  runs and events into rows: stable ids, a streamed message that grows in place, a tool step as one line, approval cards,
  helpers, the plan, the one line over the composer), `QueueOrder`, `MessageBlocks`; the shell's address parsing and
  navigation policy stay and are reused.
- `Data/`: `APIClient` (URLSession; the shell's `DaemonHost`, `PhoneKeyStore` and `DaemonRequestError` reused),
  `SSEParser` (any chunking, comments, CRLF, last id) and `EventFeed` (resume from the last id as `after` and
  `Last-Event-ID`, exponential wait 0.5 s to 15 s with jitter, a `kick` that reconnects at once, ends with the run),
  `ChatCache` (JSON files per daemon host: the list, and for each chat its newest runs and the last 400 stored events,
  atomically, with a schema number), `ChatSession` (one open chat, off the main actor: reads the disk, asks the daemon for
  the delta after the last event id, follows the stream, hands the screen a new state at most every 40 ms),
  `NativeStore` (the list and agents drawn from disk at the first frame, the lifecycle stream, the network path monitor,
  warm states of the chats read before).
- `Features/`: `ChatListView` (agents strip, rows with working / waiting on you / unread, pull to refresh), `ChatView`
  (one scroller of rows; the queue, the status line and the composer under it, outside the scroller), `Composer`,
  `QueuePanel`, `RunInspector` (a sheet: run, plan, helpers, the chat's schedules and loops with switches),
  `SettingsViews` (models, schedules with switches, address, forget the key, "Open web UI"), `PairView`, `Theme`.
- `Views/DotWebView` and the address screen stay: the web UI is a full-screen fallback ("Open web UI") and the way to
  pair in the page. The Live Activity, the share sheet and the push registration are untouched; a notification that names
  a run now opens that run's chat natively.

**Rules that were implemented, with what was measured** (iPhone 17 Pro simulator, iOS 26.5, Debug, a scripted daemon on
this Mac; a real iPhone on the tailnet was not available):

- A chat opens from what is held in one frame: a chat read before this launch is a value in memory (`NativeStore.warm`,
  set in `ChatModel.init`, so its first body draws the rows); the first eight chats are read from disk at launch off the
  main actor. A chat with no cache shows an empty transcript and no spinner. Building the state of a full cache (400
  events) takes 1.2 to 2.1 ms; reading and decoding its file 27 to 32 ms, off the main actor.
- The first delta after a cache is read, decoded, reduced and written off the main actor (`ChatSession` is an actor);
  the screen gets one assignment of a value. Words stream at most every 40 ms.
- The transcript follows new words only while the reader is at the bottom: a growth of the content under the reader is
  not the reader leaving (the scroll metrics ignore a change of the content's height), a button brings back a reader who
  scrolled up.
- The stream comes back when the app does and when the network path changes: `kick` cancels the dead connection and opens
  a new one from the last event id at once (10 to 25 ms on loopback; on the tailnet it is a TLS handshake and one request,
  not measured). A drop waits 0.5 s, then 1, 2, 4, 8 and 15 s. A reconnect reads no history again (`after` and
  `Last-Event-ID`); a daemon that cannot resume is read by delta (`GET /runs/{id}/events?after=`), as the app does when it
  opens a chat.
- The phone keeps no state of its own about an approval: a card changes when the daemon took the answer (its reply says how
  the card stands) or when the daemon's own list of what waits says so, in both directions (`setOpenQuestions`); a refused
  answer is settled by reading that list, and what cannot be read from the daemon (an event that does not decode) is a
  row of the chat that stays, not a notice that goes.
- A queued message is moved by an up and a down arrow (and removed), `PUT /threads/{id}/queue` with the new order; no drag.
- A link in a message is plain words in `Theme.link`, the text's ink tilted toward the accent, with no underline, border,
  chip or background (`LinkStyle`, markdown links and bare addresses).
- Design: near-black surfaces, hairline borders at 8 % white, one calm blue, an 8 pt radius, 10/11 pt metadata, dark only.

**Not in this slice, in the order they should come:** (1) new chat and an agent's chat from the strip when it has none,
the per-chat model and effort in the composer, the mic (a placeholder button is there); (2) older messages (the chat shows
the newest two runs from their events and the older ones from their records) and a step's detail (its arguments and
output) on a tap; (3) a message's actions (copy, reactions, edit from here, rewind), drafts and the cards of a secret;
(4) agents (make, pause, resume) and teams, campaigns; (5) the Live Activity row and the lock-screen approval opening
the chat; (6) iPad and landscape layout; (7) a SwiftData or SQLite store if the JSON files outgrow their 400 events.

**Checked:** `xcodegen generate` and `xcodebuild … build` and `test` (64 XCTest: the reducer, the SSE parser at every
chunk boundary, the feed's resume and kick against a stand-in network, the cache and its trimming and schema, the queue
order, the link style, the requests); the app run in the simulator against a daemon on a scratch home with a scripted
model: the list, a chat that streams with a queue of three, a run waiting on an approval, a run waiting on two
subagents, the inspector, the schedules with their switches, pairing. The CI of the repository does not build Swift and its
workflows were left alone: the Swift is checked on a Mac by the commands in `ios/README.md`. Debug builds take
`-DotDevOrigin http://127.0.0.1:PORT -DotDevKey <phone key>` (and `-DotOpenChat`, `-DotShowInspector`, `-DotShowSettings`,
`-DotShowSchedules`) so that a simulator, which has no Keychain entitlement and no tailnet, can be pointed at a
test daemon.
