### 529. The import of a Chrome profile's sign-ins is all or nothing, keeps the session cookies and says what happened

**Status: done (2026-10-22).** The owner asked whether the browser's cookies, passwords and history are taken
correctly, and an audit of `dotx browser import-chrome` (read, and run on a real Chrome 155 and on synthetic profiles)
found defects in what happens around the copy. What it copies was right: on Chrome 155 a profile keeps its cookies in
`Default/Cookies` (also the owner's own profile, which has no `Network` folder), and a cookie a real Chrome wrote
reaches Dot's Chrome through the import.

**As built.**
- All or nothing (`chrome_import._swap_in`). The staged cookies and local storage replace the profile's, and the
  keychain marker is written with them; what the profile held goes aside in the staging folder first and is put back
  when a step fails. Before, the cookies were put in one file after another and the marker came last: a failure between
  them left cookies written with the real key under a marker that says mock, which Chrome cannot decrypt and deletes,
  and a failure at the first move deleted the old cookies and put nothing in. The docstring said a failure left the
  profile as it was; now it does (a test fails each of the six steps in turn).
- The staging folder never stays silently. It held a plain copy of the owner's local storage (and of the cookie file)
  after a failure, and after the refusal for a profile with no valid cookie. It is removed on every path now, and a
  removal that fails is said (an error after a failed import, a warning of the CLI after a made one: `staging_left`),
  not ignored. A failure that cannot be put right (a new file that stays, a file of the profile not moved back) raises
  an error that names those files, and keeps the staging folder with what the profile held; the next import refuses to
  remove it until it is moved back or deleted by hand.
- The session cookies are kept. Chrome deletes the cookies that have no expiry as it starts unless the profile's
  preferences say its last run crashed (item 453), and the first start of Dot's Chrome on a profile that was just
  imported is the check that ends the import: a profile that never ran had no preferences, so the cookies of the
  owner's Chrome without an expiry (Microsoft 365 without "stay signed in", single sign-on) were copied and then
  deleted by the check. The import writes the word (`keep_session_cookies(..., create=True)`). A smoke test with a real
  Chrome fails without it (1 cookie read, not 2).
- `has_stored_cookies` counts rows. Chrome makes an empty cookie file as it starts, so a profile that had only run
  asked for `--replace` and said it "already holds sign-ins". An unreadable file still counts as holding some.
- The Incognito profile is refused before anything is copied (`require_importable`): Dot's Chrome empties it as it
  starts, the sign-ins were gone before the check, and the check blamed the Keychain.
- The CLI says what to do when Chrome could not read the copy (allow the Keychain, then `--replace`, as Chrome has
  dropped what it could not read), and notes when Chrome reads fewer cookies than it was given: `ImportReport.loadable`
  counts the cookies that last and those with no expiry, which Chrome gives back, the set Chrome's count is of.
- `docs/browser-and-computer-use.md` says so.

Checked by `tests/unit/test_chrome_import.py` (a failure at each of the six steps leaves the profile, its marker and
no staging folder as they were; the staging folder after a failed copy and after no valid cookie; the preferences'
word; `has_stored_cookies` for no file, an empty file, no row, a row and an unreadable file; Incognito; a failure that
cannot be put right and a staging folder that cannot be removed, which say so; what an earlier import kept is not
removed) and by `tests/smoke/test_browser_profile.py` with a real Chrome (a session cookie survives the first start).
They fail without the change.

Not built, left to the owner or a later item: `Clear` of a profile deletes the cookies and caches only (a site that
keeps its sign-in in local storage or IndexedDB still knows the owner, though Settings says the sites are signed
out); `browser_eval` hands the model `document.cookie` and the page's storage whole, and the stored copy masks the
names a secret has but not session-id names (`sessionid`, `JSESSIONID`, `connect.sid`); `dotx browser import-chrome`
against the real Keychain has never run anywhere, and a denied or locked Keychain costs the copied cookies;
`connections/web.py` looks for `Default/Network/Cookies` before `Default/Cookies`, which Chrome 155 never makes.
