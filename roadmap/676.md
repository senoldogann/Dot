### 676. A command of a run can leave nothing in Dot's home but in the workspace

**Status: done (2026-10-26).** The whole-project review of 2026-10-26 found the one way out of the sandbox it knew of.
The daemon opens `daemon.pid` in Dot's home at each start with the owner's rights, following a link, and empties it and
writes its pid there after it has read its token. Neither the pid file nor the mark `daemon.running` was among the files
the sandbox seals, and the profile closed Dot's home only to a rename of the folder itself ("a file can still be made
inside such a folder"). So a command of a run could put a link to `api-token` in place of `daemon.pid` (tried with
`sandbox-exec`: the token could not be read, the link could be made), end the daemon, and after two starts the API token
was the daemon's pid, which `pgrep` shows a command: the whole API from inside the sandbox. A link to the database or to
`.env` would have emptied them. The logs folder held the same: the daemon opens `opencode.log` and the MCP servers' logs
with `"w"` there, following a link.

**What must hold, and where.** In the kernel, not by names: the sandbox profile denies every write in Dot's home and in
its logs folder (`(deny file-write* (subpath …))`), allows the workspace back right after (`(allow file-write* …)`, so
every rule below it holds inside the workspace too), and denies a write of the workspace folder itself (`literal`), so
the workspace cannot be removed, moved or replaced by a link. Every file the daemon writes in its home or its logs is
then out of a command's reach, whichever one it is, and no list of them is kept. The pid file and the mark are sealed as
well (read and write), so a command cannot take the pid file's lock and keep the daemon from starting, and the daemon
opens both with `O_NOFOLLOW` and refuses anything but a regular file, should one ever be a link (a `yolo` run, a run
while `[shell] sandbox = false`). Nothing here only asks: the shell guard is not changed.

What a command loses: it can no longer write Dot's downloads folder, its screenshots or its logs; a downloaded file is
copied to the workspace instead of moved. A `dotx` a command runs logs to stderr, as it cannot write `dotx.log`, and
`ensure_layout` changes the mode of Dot's home only when it is not private already.

A process whose log file cannot be opened (a `dotx` in a command's sandbox, a full disk, a link in its place) logs
to stderr and says so there once, with why (the code review of this item: the first version kept quiet about it).

**Checked.** `tests/unit/test_sandbox_profile.py` (macOS holds a command to the profile: no link in place of the pid
file, nothing new in the home or the logs, the workspace neither moved nor removed, everything inside the workspace as
before; the order of the rules), `tests/unit/test_daemon_mark.py` (a link in place of the pid file or the mark is
refused and the token stays as it was), `tests/smoke/test_sandbox.py` (a run's shell command cannot link the pid file).
