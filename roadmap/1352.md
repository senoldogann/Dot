### 1352. A run's stream goes on after the `Last-Event-ID` a client sends, as it does after `after`

**Status: done (2026-11-23).** Found while reading what a native phone client could count on (item 1353): a run's
stream (`GET /api/runs/{id}/stream`) and the stream of several (`GET /api/runs/streams`) resumed only from the `after`
query, which Dot's own pages send. An event stream that reconnects by the standard (a client library, a proxy that
keeps the header, the phone app, which sends both) names the last id it read in `Last-Event-ID`, which the daemon
ignored, so such a client was sent the run's whole history again at every drop.

- `resume_after(after, last_event_id)` in `server/stream.py`: a stream goes on after the later of `after` and the header;
  a header that is no plain number is no id (the stream is not refused for it, and starts where `after` says, as it
  did). Both stream routes use it. Nothing else changes: the ids, the frames, the `stored` and `after` of the pages and
  the lifecycle stream (which replays nothing) are as they were, so a client that sends only `after` gets what it got.
- The daemon's page of the stream says so (`docs/daemon.md`).

Checked: `tests/unit/test_stream_resume.py` (the later of the two, a space, a minus, a non-ASCII digit, a number that
is too long); `tests/smoke/test_stream_last_event_id.py` (a real server on a scripted model: the stream of a finished
run read with the header, with `after`, with both in either order and with a header that is no number); `ruff`, `mypy`.
