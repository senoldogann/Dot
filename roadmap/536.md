### 536. A recap of the run at the head of its Run tab

**Status: done (2026-10-22).** Asked by the owner, after the settings of another agent: of its features, those worth
building here. Its task monitor's recap came first, as nothing on a run's page said in a few lines what a long run had
done and what waited.

**As built.**
- `agent/recap.py`, built as a side question is (`agent/aside.py`): the fast model (`[models] fast`) writes the recap,
  the run's own model when the fast one fails (a provider's error, no key, a timeout, no text), from the run's record:
  its task, status and steps, its plan, the questions that wait for the owner (pending, and left for later, item 508)
  and its conversation, the middle cut past 40,000 characters. No tools; the prompt takes the record for data, never
  for instructions, so a page the run read can at most word the recap, not act. The text is clipped to eight lines and
  1,200 characters, the secrets Dot holds masked in it (`redact_known`, as a compaction's note), and kept as a `recap`
  event of the run, which the run never reads and the timeline does not show; its call is counted with the purpose
  `recap` (`llm/calls.py`).
- **When.** `is_due`: the first once the run took `[recap] first_after_steps` steps (4), then every `every_steps` (8)
  more, and once more when the run ended after the last; `[recap] enabled = false` writes none. A run of no step has
  nothing to recap (422). Two asks for one run at once write one: the second waits for the first's task, which a page
  that goes away does not cut off.
- **The API.** `GET /api/runs/{id}/recap` (`RecapView`: the newest recap or none, the run's steps and status, whether
  one is due, whether recaps are on); `POST /api/runs/{id}/recap` writes one when due, or with `{"force": true}`
  whether or not.
- **The page.** `static/js/recap.js`: the Run tab's first section, the recap's lines, the step it is as of and its
  model, and a button that writes it again. It asks only while the section is in sight (an `IntersectionObserver`, so
  the panel beside the conversation, the drawer and a phone's sheet are alike): as it comes into sight, and as the run
  takes steps at most every 20 seconds; a `recap` event on the stream, written by another page, is painted.
- `docs/daemon.md` (the side panel and the API table) and `docs/models.md` (what the fast model writes) say so.

**Tests.** `tests/unit/test_recap.py`: when one is due, the record (what waits, an answered question left out, an
ended run said so) and the clipping. `tests/smoke/test_run_recap.py`, with the scripted model: none before a few steps;
written once due from the run's record, with the prompt that takes it for data, kept as an event and counted as a
recap; asked again before the run moved on, no model call; the button writes another; two asks at once write one; a
secret Dot holds masked; the run's own model writes it when the fast one fails; a run of no step and recaps off
refused with why. `tests/smoke/test_run_recap_page.py`: the Run tab of an ended run opens with its recap at 1280 and in
the phone's sheet at 390, and its button writes it again.
