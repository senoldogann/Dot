### 1142. A click at a pixel that focuses a field is a change

**Status: done (2026-11-13).** **Found** in the browser's report of what a click did (item 739). A click on a field's
ref that only puts the keyboard there is a change, so a run does not click it again. A `click_at` names no ref. The
same click, the way a run reaches a field the element list does not name (a canvas beside it, a widget drawn by the
page), was told "the page did not change", and the run clicked again or gave up on the caret it had just placed.

**Cause.** `holds_field_focus` reads the element the step named. A click at a point has none, so the watch never asked
whether the keyboard had landed in a field. Ticking a box was already seen: the page's `input` event counts. Focusing
a field and opening a dropdown do not.

**Built.** Each frame of the page says where its keyboard is when that is a field, caret included (`driver.focus_landed`).
A click, a double click, a click at a point or a drag that leaves the keyboard in a field it was not in changed the
page. Taking the keyboard off a field, and nothing else, did not: a button that does nothing is still told so, also
when a field had the keyboard before it. A click on a ref that the field already held is unchanged (`holds_field_focus`).

**Checked.** `tests/unit/test_browser_focus.py`: landing, a caret moved, a field in a frame, staying put, leaving.
`tests/smoke/test_browser_effect.py`: a `click_at` on an empty pixel is no change, one on a text field and one on a
dropdown are, and a `click_at` that only takes the keyboard off the field is no change again. The smoke test fails on
the code before.
