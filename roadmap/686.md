### 686. Deleting a chat no longer reads the whole database while holding the write lock; a prune keeps unsent drafts

**Status: done (2026-10-26).** The whole-project review found two things in the store. `delete_threads` and
`delete_campaign_with_sessions` released the screenshot files of what they deleted inside the write lock: `_release_images`
asked `referenced_images()`, which loads every message, kept-aside message and event body into Python and matches
the names there (the owner's database is 165 MB), so every other writer waited for it; and a file that could not be
removed raised a `StoreError` after the delete had committed, so the delete read as failed. Also
`delete_events_of_runs_ended_before` deleted every draft of the runs it pruned, the ones the owner had not sent or
discarded too.

**The change.**

- `delete_threads` and `delete_campaign_with_sessions` are not writing methods any more: each calls one that is (the
  transaction, which returns the files the delete named once it has committed), lets the lock go, and then releases the
  files and returns the free pages.
- `_release_images` reads the stored text once: the messages and the kept-aside messages each in one question (their
  rows have no key that only grows, so a compaction between two parts could give a new row the number of one read
  already, the code review's second look), the events 2,000 at a time by their id; the write lock is held for one
  question only, so a read never sees half of another writer's transaction and the writers go on between the parts,
  and the names are found off the event loop, instead of reading the database whole into
  the daemon under one hold of the lock. On a 165 MB table it takes about a second in all; asking SQLite about each
  name with `instr` took a quarter of a second a name under the lock, and one pass with every name a row checked took
  17 s for a hundred (the code review of this item). The mtime grace of `remove_images` still keeps a fresh file. A
  read or a removal that fails is logged (`screenshot_files_not_released`, `screenshot_files_not_removed`) and leaves
  the files: the delete is done. `referenced_images()` stays for `orphan_images`.
- `_return_free_pages` hands the pages back 1,000 at a time, taking the write lock for each part, and logs a part that
  fails instead of failing the delete.
- A prune deletes only the drafts that were sent or discarded; those waiting, failed or being sent stay.

**Checked.** `tests/unit/test_store_images.py`: a delete never calls `referenced_images`, the files are removed with
the write lock let go, and a refusal to remove is logged while the delete is done; `tests/unit/test_retention.py`:
the drafts a prune keeps and deletes. The docs of drafts and of retention say it.
