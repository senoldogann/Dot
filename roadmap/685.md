### 685. A reply that puts finish before other calls no longer ends the run with those calls unrun

**Status: done (2026-10-26).** The whole-project review found that `execute_calls` skipped every call after a `finish`
("Skipped: the run already finished.") and that the loop's check of the calls that did not work looked only at the calls
before it, so a reply of `[finish("sent the mail"), send_email(...)]` ended the run `done` with its answer saying the
mail was sent and the mail never sent.

**The change.** A `finish` that is not the last call of its reply is not taken: its result is an error saying that
`finish` must be the last call of a reply, which calls after it were run, and that the model calls `finish` again, last,
once it has read their results. The other calls run as any call does and keep the order of their results. The loop
already ends a run only on a `finish` whose result is not an error, so the run goes on to the next step. A `finish`
that is the last call of its reply behaves as before; nothing comes after it, so nothing is skipped any more.

**Checked.** `tests/smoke/test_finish_beside_failure.py` plays `[finish, shell]` and then `[finish]` through the real
loop and store: the first finish fails, the shell call runs, and the run ends on the second finish. `dotx eval check`.
`docs/runs.md` says it.
