### 571. Watchers that tell you when a mail, an event or a GitHub notification you care about comes

**Status: done (2026-10-23).** The second half of what the owner asked for in coming to them (item 570 is the first): a
word when something they care about happens, not only answers when asked. A **Watchers** panel under the brief on
Schedules lists the watchers, with **New watcher**. A watcher has a kind (**New mail** in a signed-in Google or
Microsoft account, **Calendar**, **GitHub**), what the owner wants to hear of in their own words (needed for mail,
optional for the others), how often it looks (5 minutes; for the calendar, 15 minutes before an event) and what it does:
**Tell me** (a push, and a line kept in the chat "Watchers"), or **Tell me and start a run** with the owner's goal.

**The approach.**
- *A loop of the daemon, no webhook.* `watch_loop` (`proactive/watching.py`) runs beside the scheduler from the daemon's
  clock (`[watchers] tick_s`, 15 s): each tick looks at the watchers that are due. The daemon stays on the loopback
  address; a push of GitHub's or a mail provider's to it is left for later and said so in the docs.
- *The place is kept in the store.* The book of watchers is one JSON value of the kv table (`proactive.watchers`),
  written by `kv_update`, an atomic read and write of the whole book: the owner's change and the loop's state write
  (`change_watcher`, `update_state`) cannot undo each other (a test runs fifteen of each at once). A watcher's state is
  its cursor (mail: when the last look began; GitHub: the `Last-Modified` of the last answer), the keys of what it
  handled (the newest 400), when it told and started runs within the hour, its next look and its failure. The first look
  after a watcher is made takes what is there as handled and tells nothing (no flood of old mail); a restart neither
  repeats (each tell is written down as it is made) nor misses (mail asks from five minutes before the last look and not
  further back than a day; an event is told while it is still ahead).
- *Mail* (`proactive/looks.py`): `search_gmail` (the inbox, `after:` the cursor) or `search_outlook`, which the mail
  tools use, over the same `AccountApi`; unread mail only; each new one is one question of the fast model
  (`proactive/judge.py`). The mail is fenced as the tools fence it (`account_content` with a nonce), alone in its
  question and with the owner's words outside the fence, and the model answers with one tool call, a verdict
  (`watcher_verdict`: `tell`, `why`); so one mail cannot change another's verdict. A mail the model cannot judge (no key,
  a pause, a failure, a reply with no verdict) is told, not dropped, and says so. Past `[watchers] judged_per_look` (25)
  in one look the newest are judged and the rest are handled unjudged and not told, which the row says.
- *GitHub* (`proactive/github.py`): the notifications API with the token Dot keeps when GitHub is added on Customize ›
  Connectors (`MCP_GITHUB_GITHUB_PAT`, which a test holds to `kept_secret_names`); a conditional request, no oftener than
  `X-Poll-Interval`. With none the row says to add it, and a 401 or 403 says what GitHub needs (a classic token with the
  notifications scope). Without words: a review asked, a mention, an assignment, a check that failed; with words, the
  fast model judges each one.
- *Calendar*: no model. The events inside the lead, timed, not cancelled or declined, with the words in title, place or
  notes when given; told once for the time they have; the next look when the next event comes inside the lead.
- *Limits.* `[watchers] tells_per_hour` (20) tells from one watcher an hour and the rest in one line ("and 7 more");
  `runs_per_hour` (5) runs; one look is cut at three minutes; a watcher that fails says so on its row (the error, never
  a token) and tries again no sooner than five minutes later, and the others look on; nothing looks while the emergency
  stop is engaged.
- *The tell* goes through `tell_owner` (item 570): a push, and a line in the chat "Watchers". The line is a run that no
  model made (`RunManager.keep_notice`: source `notice`, chat mode, stored as it ends done, its `run_queued` published so
  the pages list it, its end not published, since the push and the desktop would tell it twice). Its goal is Dot's words
  (which watcher, which kind) and the third party's words are in its result only, because the reviewer of a later run in
  that chat reads the goals of its runs as the owner's. A tell that cannot be kept (a run of the owner's is at work in
  that chat) goes out and opens Schedules.
- *The run a watcher starts* (`RunManager.start_alert`): source `watcher`, a task, the configured model and approvals,
  unattended (`progress.py` and `prompt.py` count the source as one nobody watches), and **untrusted from its start**
  (`RunOpening.tainted`, which `_starts_tainted` honours first). Its **goal is the owner's text and nothing else**; the
  item is in its first message, in the mail tools' fence, with where it came from, how to read more (the message's id)
  and the goal after it. The brief wrote the goal as holding the item; it is the first message that does, since the
  reviewer takes a run's goal as the owner's instruction (the scheduler keeps its digest out of the goal for the same
  reason). A run that cannot start is said in the tell and leaves no chat.

**Left for later.**
- An inbound webhook (a push from GitHub or a mail provider) instead of looking: the daemon stays loopback-only.
- A watcher looks in the inbox of one account; labels, folders and the other mailboxes are left out.
- GitHub notifications need a classic token; a fine-grained one cannot read them. Reading them with an app's sign-in
  would need a client registered with GitHub.
- A mail told while the fast model is down is told with its sender and subject and no judgement, up to the hour's
  limit: a mailbox that fills while the model is down fills the chat Watchers with them.
- The line in the chat Watchers is not in the history a follow-up in that chat is given (it is a run that no model
  wrote, kept for reading): the owner cannot yet answer a tell from there as a conversation.
- A watcher's run in `yolo` asks nothing but is checked by the review model while it is untrusted (`yolo_taint_check`);
  whether a watcher's run may be yolo at all is the owner's choice of the default approvals.
