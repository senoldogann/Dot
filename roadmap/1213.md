### 1213. A video or a voice message sent in iMessage is kept for the run, which watches it with `watch_video`

**Status: done (2026-11-17).** Until now the iMessage channel told the owner it could not read a voice message or a
video (item 806), and a run was told part of the message was not read. With `watch_video` (item 1212) both can be seen
and heard, so they are kept with the message as an upload is:

- `agent/attachments.py`: two kinds more, `video` and `audio` (by the declared type or the name, for a file whose
  first bytes are not text: a browser calls a TypeScript file `video/mp2t`), kept as they came,
  with no text read out of them and a limit of 200 MB (`MAX_MEDIA_BYTES`; a document keeps 20 MB). The run is told,
  inside the attachment's fence, that `watch_video` on its path sees it and writes down what is said, and to name the
  language spoken.
- `channels/inbox.py`: a video or a sound (a voice message: `.caf`, often with no type in Messages' row) is read from
  the folder of attachments under the same rules as any file (no link on the way, a regular file), up to that limit.
  The channel's words and the note to the run no longer say videos and voice messages are not read.
- `video/media.py`: ffmpeg opens AMR too (an older voice message's format).

The files of one message hold at most 300 MB in all as they are read into memory (`MESSAGE_BYTES`): a file past it is
too large, so ten videos are not held at once; a file read while another is still coming down is not read again.

The composer keeps its own limit of 20 MB (its uploads go as base64 in JSON), so a short clip or a voice memo can be
attached there too.

Checked: `tests/unit/test_media_attachments.py`, the two tests of `tests/unit/test_imessage_channel.py` that said a
voice message and a video were not read (now that they are kept), the channel and attachment tests, and a real
Opus voice message in `.caf` (made by `afconvert`, as an iPhone's is) written down word for word in 2.4 s.
