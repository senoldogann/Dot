### 647. The daemon keeps SQLite's planner statistics

**Status: done (2026-10-25).** This item comes from the same request as item 645.

**What was measured.** The owner's database was read-only, with a copy for the experiment, deleted after.
- The six queries of a run's bill (`store/stats.py`) took 32 ms on a copy of the owner's database for a run of 603
  events, and 125 to 390 ms through the live daemon.
- `EXPLAIN QUERY PLAN` showed four of them reading the events of one kind (`model_call`, `tool_result`, ...) of every
  run through `events_kind_ts`, then keeping that run's.
- The database had never been analysed: it had no `sqlite_stat1`. Without statistics SQLite guessed the kind to be the
  narrower index.
- `PRAGMA optimize=0x10002` on the copy took 3 ms. After it the four queries read through `events_run`, and the six
  took 3.4 ms. The cost before grew with the history, and now it does not.

**The change.**
- `Store.open` runs `PRAGMA optimize=0x10002`, as SQLite advises for a connection that lives long. It covers the tables
  with no statistics or grown much since.
- `Store.close` runs `PRAGMA optimize`. One that fails, such as another process holding the database past the busy
  timeout, is logged (`store_optimize_failed`) and the store closes. The next open makes the statistics. The connection
  is closed in a `finally`, so a close cancelled at shutdown, or a second close, still ends its thread (item 556).
- `docs/configuration.md` says so.

**Test.** `tests/unit/test_store_planner.py` fills a store with 60 runs of 120 events each. Without statistics the
bill's query takes the kind's index; reopened, it takes the run's. It fails without the pragma. A second test makes the
close's optimize fail: it is logged, and the store's thread ends.
