### 1304. A plugin archive that is refused no longer stops the plugins after it, and one that never comes is not downloaded every night

**Status: done (2026-11-22).** The log of the plugin scout showed nine `scout_lead_failed` lines in a night, all
`FileExistsError` on `.../dot-scout-xxxx/archive-9`. The scout made the staging folder of an archive as
`archive-{number of archives held}` before the fetch, and held the archive only once the fetch had succeeded, so one
archive that was refused (larger than 100 MB) left its folder behind and every later new repository took the same name
and failed. Separately, `_archive` ran before the `try` that turns an unusable plugin into a record, so an archive that
can never be had (too large, a commit GitHub answers 404 for) was counted as a failure, never written to `looked`, and
downloaded again (up to 100 MB) every night.

Each archive is now downloaded into a folder made with `tempfile.mkdtemp` under the night's staging folder, and the
folder is removed when the fetch fails. `download_archive` raises the new `ArchiveRefused` (a `GalleryError`) for what
never changes (over the size limit, a 4xx but 403, 408, 425 and 429); a timeout, a 5xx and those four stay plain
`GalleryError`s. The scout turns `ArchiveRefused` into `Unusable` for a new plugin and for an update, so the reason is
logged, the plugin is counted unusable and written to `looked`; a plain failure still counts as failed and is tried again.

Checked: `tests/unit/test_scout_night.py` (a refused archive and then a good one both work and every staging folder is
its own; an oversize archive is recorded and not fetched again the next night; a 503 is a failure tried again; the
download tells 404 and 410 from 429, 403, 500 and 503), and the rest of that file.
