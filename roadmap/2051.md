### 2051. The iPhone's calendars, reminders and location, from Dot Next

**Status: done (2026-11-28), unproven on the owner's real iPhone.** The owner's backlog item PH1 (2026-11-27, from
Grok Bot's review): Dot Next gets EventKit and Core Location, each permission asked the first time it is needed, as
phone-side tools the daemon calls through the phone link; a write follows the run's approval mode.

- Four tools in a group of their own, `phone_app` (off at a run's first step, as every group but core):
  `phone_calendar_events`, `phone_calendar_add`, `phone_reminder_add`, `phone_location`. The WebDriverAgent tool
  `phone_status` stays in `phone`; nothing of it is reused, since it drives a different link. The events are written as
  `calendar_events` writes an account's (`event_lines`, `fence_account`), so one path writes every calendar a run reads.
- The link: the phone holds `GET /api/phone/asks/next` open while Dot Next is in front (20 s, then again) and answers at
  `POST /api/phone/asks/{id}` (`dotagent.phone.asks.PhoneLink`, `server/routes_phone_asks.py`). A long poll rather than a
  frame on the list's stream: that stream is the same for every client (the web too), and an ask is one phone's. No
  change to the guard: a paired phone's key reaches every `/api` path but the Mac-only ones.
- A run has the tools only while a phone is paired (`withheld_tools`), as the accounts' tools only with an account. So a
  fresh home's first step carries none of them, and `tests/smoke/test_context_budget.py` (full surface, no phone) is
  unchanged. With a phone paired the four definitions are about 900 tokens (2,879 characters), offered only once the
  group is turned on; the grouped prompt's group list gains one line.
- The policy: a read is `read`/low, an add `app_control`/medium with no flag. Yolo and free mode ask nothing new
  (`tests/unit/test_freedom_contract.py` has a row for each); cautious and Supervised ask before an add; a research run
  is not offered the adds.
- What the phone names is fenced: the events, a calendar's or a list's name in an add's answer, and a refusal's words
  when it failed (it may list calendars' names), each as content others wrote, so the run is tainted by them; Dot's own
  head line says what happened, and a refused permission is said in Dot's words alone. An answer the run could not read
  (another kind, times not as the contract says) is a 422 at the door and ends the run's wait at once.
- Dot Next: `PhoneAsks` (EventKit full access for the calendars and for Reminders, `CLServiceSession` when in use), the
  engine's `PhoneAskLoop` (started when the app comes to the front, stopped when it leaves, each ask answered in a task
  of its own so a permission question does not hold the next ask), the usage descriptions in English and Turkish, and
  the tools' row words, the same as the web's.

How it was checked: `tests/unit/test_phone_asks.py` (the asks' times, the fence, the broker's rules),
`tests/smoke/test_phone_asks.py` (a served daemon and a fake phone over HTTP: the Mac's token refused, no phone open
fails at once, an add, a read, a refusal, an answer of the wrong kind), `tests/unit/test_freedom_contract.py`,
`tests/smoke/test_context_budget.py`, `dotx eval check`; DotEngine `PhoneAskTests` (the contract both ways, the times,
the loop against the fake daemon, an older daemon); one `build-for-testing` of DotNext and the String Catalog check.
Not yet tried on the owner's iPhone (docs/maturity.md; PV1 proves it).
