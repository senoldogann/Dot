### 662. What repeats forever stands still while Dot's window is away

**Status: done (2026-10-26).** After item 645, Dot.app at rest still kept its web process at about 10 % of a core and
its GPU process at about 12 %. This was measured with `top` on 2026-10-25, with no run at work and Dot not the app in
front. The page itself, in WebKit with no window, used about 2 % at rest, and with every animation off 0.5 % less. What
was left was the endless animations: the loop marks' glow and spin, the faces' breath, and a working dot's ring. A real
window draws them at the screen's rate, up to 120 Hz on ProMotion, with nobody looking. The owner left the choice to
Dot: "Ne olması gerekiyorsa o olmalı" (whatever should be).

**The change.**
- **The page marks itself away.** `main.js` sets `data-away` on `<html>` while the window is not in focus or the
  page is hidden, from `blur`, `focus` and `visibilitychange`, and clears it again.
- **Every endless animation takes its play state from `--endless`.** That is 19 rules in `app.css`, `shell.css`
  and `run.css`. The variable is `running`, and `paused` under `:root[data-away]`.
- **An animation that ends by itself is not touched,** whether a fade, a slide or a single blink, so nothing stands
  half-faded.
- **The moving faces stop drawing too.** The home's face is no CSS animation: a frame loop
  (`character/ticker.js`) redraws its SVG at the screen's rate. It stopped only while the page was hidden, and now it
  stops while the page is away. The pre-push review found this, and it is likely the larger part of the cost.
- **One state for both.** `js/infront.js` holds whether the page is away and tells `main.js` (the mark) and the
  ticker. A `blur` is read again once the focus has settled, so focus moving into a frame of the page (a page Dot shows,
  a preview) does not count as away. Focus in such a frame hides a later switch to another app from the page (the
  frame loses it, and the page hears nothing), and so does coming back to the frame: the page looks again every two
  seconds whether it is away, either way, and the events only make it sooner. The pre-push review found both.
- **A face whose run just ended still blinks once** while away (`animation-play-state: running, var(--endless)`), and
  only its breath after waits.
- **In front, everything moves** as it did, and reduced motion still stops it all.

**Tests.**
- `tests/smoke/test_character.py::test_a_window_not_in_front_stops_the_loop_and_one_in_front_resumes_it`: the
  faces' frame loop stops once the page is away, and the face moves again in front.
- `tests/unit/test_css_tokens.py::test_what_repeats_forever_stands_still_while_dots_window_is_away` checks that
  every endless animation declares the play state and that the away rule exists. A new endless animation without it
  fails.
- `tests/smoke/test_chat_loop.py` checks, in a real browser, that the loop mark's glow runs in front, is paused once
  the page is away, and runs again in front. A test's browser is always in front, so the page is told it is not.

**Not measured yet: Dot.app's own numbers after the change.** Dot.app's page loads the new style sheets once it reloads,
which happens when it is next out of sight after the daemon's update (item 328).

A first draft named the new module `away.js`, which is the Away card's (item 572). The web UI checks caught the
overwrite before anything was committed, and the module is `infront.js`.
