### 1206. A schedule's task that a restart cut, a passing model error or a stall ended is tried once more on its own

**Status: done (2026-11-16).** A schedule's task that Dot's restart or crash cut off, or that failed on an error of the
model service that passes, waited for the owner: the daemon resumes only the runs of the web UI by itself
(`resumes_on_start`), so a morning brief cut by a restart at 08:01 never ran that day. OpenMausBot (studied 2026-11-16,
read, not run) starts such a run once more after 15 s, puts one that met a usage limit back to just after its reset,
and never runs again a turn that sent something. The owner decided (2026-11-16): a schedule's task cut by a restart or a
crash, or failed on a passing provider error or a stall, is tried again once by itself; one the Claude plan's usage
limit stopped starts again just after the reset; one that already did something outward is never tried again, the
owner is only told; the try runs as the schedule's run, so its messages go to the review model as a firing's do.

What must hold, and where it is held:

- **Never after an outward action.** Before a try is queued, the ended task and every helper it delegated are read
  from the store (`scheduler/recovery.py`, `outward_tools`): a step whose action raised one of `OUTWARD_FLAGS`
  (a message or mail, a post, an upload or data sent out, a payment, a trade, a release), whatever its result and
  whether or not the policy let it through, or a step that handed work to a run outside the family (a work order, a
  team's or office's task, a reply handed on), keeps the task from being tried again. So does a call the cut left
  unfinished that may have done one: a call of the task cut while it ran whose action raised such a flag or cannot be
  classified (`interrupted_calls`, which now keeps the flags), any call of the task whose `tool_call` event has no
  result and that its chat's messages do not hold as told apart (a run on the Claude plan or OpenCode keeps its calls
  in its events alone: `calls_without_result`), and any call of a helper that has no result. Nothing in
  between is guessed: what the policy flags is what counts as outward, as for every other rule of a run.
- **One try only, never twice.** A run of a try is told apart by its `schedule_retry` event and, for the moment
  between its start and that event, by the store's record of tries (`schedule_retries`, one key/value row, written in
  one step): a try is claimed there (the pending entry moved to `started`, with its chat) before its run starts, as a
  firing's claim is, so a crash between the claim and the run loses the try rather than repeating it, and a run that
  is a try, or that a try already went on from, is never queued again. One pending try per schedule; a firing of the
  schedule (on time, late, by hand or by the market) supersedes it. A try's chat is written as the schedule's last
  (`record_schedule_hand_run`), so a crash while it works finds it, not the task it tried, and tells the owner.
- **The source stays unattended.** The try is a new run of source `schedule`, started by the same path as a firing
  (`Scheduler._start`, `RunManager.start_firing`): the schedule's own mode, model, approvals and agent, the chat a
  firing goes in, the digest and the earlier runs it carries (so a cut task that read outside content leaves the try
  tainted). Its messages and posts are judged by the review model exactly as a firing's are; it is not a resumed run
  (`resume` source), which docs/safety.md takes as the owner's. Nothing of the policy, the gate or the review
  changes, and the owner's own chats are not tried again (only runs the scheduler started and follows are).
- **Visible.** The try's chat (one made for it) is titled `… · retry`, which the schedule's History lists; its run
  page shows a line that says it is a try and why, with the way to the task it tries again; its first message says so
  to the model. The schedule's status says `retrying at …` while one waits.
- **The owner told when not tried.** A task that would have been tried but is not (it did something outward, it was
  itself the try, the plan's reset is not known or more than 12 hours away, the try could not start or waited past
  `[scheduler] catch_up_s` while Dot was off, the emergency stop is engaged when it is due) is told with `owner_told`,
  whose tap opens that task's page, whatever the schedule's notice level; the schedule's status says why.

What only asks, and is not held by this item: a task whose cut is not one of these (the owner's stop, the emergency
stop, its limit of minutes or tokens, its own report of failure, a goal check that refused it, an error of Dot's) is not
tried again. A switched-off repeating schedule, a deleted one or a paused agent drops its try. A failure of the try
counts in the schedule's row of failures as any run's does.

Why a fresh run and not a resume of the cut transcript: a resumed run is told to "pick up where it left off" and reads
calls the cut left half done, which invites it to run them again (`resume_note` says "check what a call that was cut
off may have changed"); a run the provider or the watchdog ended has nothing worth going on from. A fresh run with the
goal, told that an earlier try was cut and may have changed things on the Mac, starts from what is there; in a
schedule that goes on in its own chat it reads that conversation as any firing does.

When a try is due: 15 s after the end (`RETRY_AFTER_S`) for a cut, a passing error and a stall; for the Claude plan's
limit, a minute after its reset (`AFTER_RESET_S`), read from the plan's `rate_limit_event` or the error's words
(`limit_resets` in `claude_code/stream.py`) and now carried by `ClaudePlanLimitError`, when that is at most 12 hours
away (`RESET_WAIT_MOST_S`). A passing error is one of `failure_kind`'s (`core/errors.py`): a broken connection or
stream, a provider's 429 or 5xx, a payload out of form, a Claude Code session that broke off or went silent
(`ClaudeCodeBroke`); the run's `run_finished` event keeps it as `error.kind`. A stall is the watchdog's stop or empty
replies.

Checked with smoke tests on the real store, manager and scheduler with a scripted model
(`tests/smoke/test_schedule_retry.py`): a task cut by a crash is tried once and its try, cut again, is not tried and is
told; one that failed on a passing provider error is tried once; one that sent a message is not tried and is told; one
the plan's limit stopped starts after its reset, not before; the try's run is of the schedule's source and its send is
asked of the review model. A unit test covers the pure decisions (`tests/unit/test_schedule_recovery.py`).
