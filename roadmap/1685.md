### 1685. The owner's own message ends a `wait_until`, in Dot's own loop and on the Claude plan

**Status: done (2026-11-24).** The daemon half of the phone's "sent, but no work" report (the iPhone rewrite's R-e §2):
a run on the Claude plan sat 13.7 and 12.7 minutes in `wait_until` while the owner's message waited, because nothing in
the wait read the run's inbox. The phone drew exactly what the daemon had.

**Step 0, the experiment (PLAN §10.1), before any code.** A throw-away home and an in-process daemon (a real runtime and
`RunManager`, `DOT_HOME`/`DOT_LOG_DIR`/`DOT_CHROME_DIR` in a fresh `mktemp` folder), a run on `claude_code:sonnet`
(Claude Code 2.1.331) told to call `wait_until` once on a file that never comes (`every_s` 5, `within_minutes` 1), a steer
5 s after its `tool_call` ("put the word PINEAPPLE in your very next reply"), and every line of the program read with
its time. What happened (seconds from the start):

| s | what |
|---|---|
| 16.5 | `tool_call` `wait_until` |
| 21.5 | the steer: the `steer` event stored, the message written to the program's input |
| 72.0 | `tool_result` (the minute ran out), and in the same instant the program's `user` line with `isReplay: true`: it took the message in |
| 74.1 | the model's next step: "PINEAPPLE: the wait timed out ..." |

So the program takes a message written to its input in at the end of the tool call at work (the next tool-result
boundary), not at the end of its turn, and the model's very next step answers it. Ending the wait early therefore has
the model read the owner at once: the Claude Code half was built. (Item 1013's note had seen the same on 2.1.318: "a
message sent while a tool worked was taken into that turn".)

**As built.** `ToolContext.owner_words` (an `OwnerWords`: `owner_unread`, `heed_owner`, `owner_arrival`) is what a wait
gives way to; `wait_until`'s pause between checks waits on it as well as on the clock, and once it holds (checked after
each check, so a message that came before the wait began ends it at its first check), the wait returns, not as an
error: "The owner wrote while you waited; their message follows this result. Read it and answer before waiting again.
The condition had not held after N checks; the last saw: ...". `heed_owner` marks the messages a wait gave way to: a
second wait that begins before the model read them runs its course (no zero-length wait loop).

- Dot's own loop: the run's `RunInbox` is it (no new flag): it counts the owner's own messages put and taken
  (`UserInput.owners_own()`: not `of_dot`, no `reaction`: a message, the answer to a question, a queued message sent on
  with Send now; not a reaction's note, a helper's report, a work order or a chat's note), and the loop takes them at the
  next step.
- Claude Code (`claude_code/run.py`): the inbox is drained to the program at once, so the run keeps its own count
  (`OwnerUnread`): an owner's message sent counts until the program's `Taken` line (`isReplay`) for it; the messages not
  taken yet (`_Pending`) carry whether each is the owner's, so one sent again to a program that goes on after a cut (item
  1581) stays unread until that program takes it in; one folded into a new session's brief no longer waits.
- OpenCode: not done (no signal of when the program takes a message in was measured); `owner_words` is `None` there.
- The tool's description says "The owner's message ends it." (`dotx eval check` passed); its sentence on refused
  commands is shorter ("changes or fetches anything"), so the description stays the length it was:
  `test_scaffold.py`'s small-window run sits at the edge of its budget and compacted at two steps in a row with the
  longer one.

**Checked by** `tests/unit/test_owner_words.py` (the inbox's and the program's counts, what counts as the owner's own,
a note that does not wake a wait), `tests/smoke/test_wait_until.py::test_the_owners_own_message_ends_a_wait_once_and_dots_notes_do_not`
