### 1106. An install whose step panicked can be tried again

**Status: done (2026-11-10).** From the review of the implicit state machines: the desktop app's installer keeps its
phase (`Idle`, `Running`, `Failed`, `Done`) and, beside it, an atomic `running`, which the worker thread cleared only
after `run_steps` returned. A step that panicked (a bug, an unexpected answer of a tool) left `running` set and the phase
`Running` for ever: the page polled a spinner, and every retry was refused with "The install is running already". A
panic while the state was held would also poison its lock, and every later read of the status panicked too.

Now the worker holds a `WorkerEnd` guard: however the worker ends it lets go of `running`, and a panic fails the step at
work as a refusal of it would, with words that say to try again. The state's lock is read through a poisoning, so the
page still reads it. The step's program is ended with the step when it panics (`EndsOnPanic`), so that a retry
never runs the same step beside a program still at work; a panic between two steps fails the first step not done and
undoes no step done (both from the independent security review). This path is under "Always needs a human" (`installer.rs`); the owner asked for the review's fixes
on 2026-11-10.

Checked: `cargo test` (a worker that panics while it holds the state fails its step, lets go and is read; one that ends
keeps its phase; a panic between steps keeps the done one; a step that panics ends its program), `cargo clippy --all-targets -- -D warnings`, `cargo fmt --check`.
