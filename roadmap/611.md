### 611. The iMessage channel honours the stop, holds its notices, and says what it could not do

**Status: done (2026-10-24).** The final review of main (`d7347e52`) found six defects in the iMessage channel (items
572, 582 and 595), in its sections 1, 2, 4, 6, 7 and 8. The channel's rules for who the owner is were sound; what it did
after a message was read was not. The first is a safety defect: while the owner's emergency stop was engaged a message
on iMessage still started a run and its answer went back, though no schedule fires, no campaign starts a session and no
watcher looks. The others: a notice for a run that blocks inside the 20 seconds after an earlier line was dropped, so
the run sat `blocked` and the phone said nothing; a cursor above the newest row of Messages' database (rebuilt, restored)
read nothing from then on and said nothing; only the exact text `/stop` stopped a run, "stop" was queued behind the run
it meant to stop, and a stop said "The run was stopped." twice; a picture sent with words ran on the words and was
answered as if it had been looked at; and every link in a message was `http://127.0.0.1:<port>/…`, which a phone cannot
open.

**What must hold, and what only tells.** The channel starts runs, so the stop is held where the run starts, not where
the owner is told.

| Input | Verdict | Held by |
| --- | --- | --- |
| a message on a channel while the `STOP` file exists | no run starts and nothing is queued; the owner is told once for the message | `ChannelRouter._post`, before the chat is looked at, by the file's existence: the check of `Scheduler._fire`, the campaigns' sessions and `look_due`; and again once the run is started, which ends it as an emergency stop if the file appeared meanwhile (as `Scheduler._track` does) |
| `/stop` or a message of the stop words while the file exists | stops the run at work: it only reduces what Dot does | `is_stop` is tried first, as `/stop` was |
| pairing a number and typing its code back | works: it is the owner's way to be reached, and starts no run | not the router's: `IMessageChannel.send_code` and `confirm`, unchanged |
| what Dot tells of a run that ended, and the stop's own end among it | still sent | the router's outbound side, unchanged |

What only informs: the tab's facts (*Moved down*, *Links in messages*), the log lines, and the words of the notices.

**As built.**

1. *The emergency stop holds the channel* (`channels/router.py`). `_post` reads `is_stop(text)` first. A message that is
   no stop, with the `STOP` file there (`_emergency_stop_engaged`, `failsafe_path().exists` off the loop, as the
   scheduler and the watchers read it), is answered with `STOPPED` and nothing else happens: no chat is made, no run
   starts, nothing is queued (a queued message starts its run when the one at work ends, stop or no stop).
   Each message gets the one answer, so a second message is not met with silence; the flood limit of the intake still
   holds. The answer says that the emergency stop is engaged, that nothing was started, and that the banner at the top
   of any page of Dot has the button that releases it. A run started while the file appeared is ended with
   `end_by_emergency_stop`, whose result the owner reads as *The run was stopped. Emergency stop: every active run was
   stopped.* `docs/safety.md` lists the channel among what the stop holds, and what it leaves open.
2. *A wait is held, never dropped* (`channels/router.py`). The wait of a run (`approval_requested`, `question_left`) is
   kept in `_held_asks` and told by `_tell_held`, the path the tells of the brief and the watchers take: the first goes
   at once, and one that comes inside the window of `ASKS_APART_S` is told when the window ends, from the same wait in
   `watch` (`_held_for` counts both). Held together, they are one line: the newest of those that still wait, *(and N
   more)*, *Answer them in Dot*. A wait that is no longer open when its window ends (the owner answered it in Dot, or it
   expired with its run: the approval's record says `approved`, `denied` or `expired`) is not told, as the line would
   be false; one the store does not know is told, since nothing says it was answered. A channel switched off or
   unpaired meanwhile is told nothing.
3. *A cursor above the newest row comes down* (`channels/imessage.py`, `channels/seen.py`). `read_new` no longer keeps
   `max(newest, after)`: a newest row below the cursor is returned, and `_poll` moves the cursor to it, logs
   `imessage_cursor_reset` once with both numbers (`cursor`, `newest`), tells `Watch.reset`, and reads on at the next
   poll. Nothing above the newest row was ever read, and what the database holds already is not run (the first poll of a
   channel does the same). `Seen.cursor_reset` (`from_row`, `to_row`, `at`) is in `GET /api/channels` and the tab shows
   it as *Moved down* beside *Read up to*, until the daemon starts again.
4. *Plain words stop a run* (`channels/types.py`). `is_stop` takes a message that is only `/stop`, `stop`, `dur` or
   `durdur`, in any case, with a closing dot or exclamation mark at most; a sentence that holds one is not. The set is
   `STOP_WORDS`. The router stops the run at work for it, the channel runs it inside the window of a step that sends
   and joins no link to it (both were exact `/stop` before), and `Intake` leaves it unchanged when a picture came with
   it. The notice of a queued message ends *Send /stop to stop it.* A stopped run's end said *The run was stopped.* as
   the lead and as its result: `_answer` says it once, when the result starts with the lead.
5. *A picture or a file sent with words is said* (`channels/intake.py`, `channels/router.py`, `channels/imessage.py`).
   `Intake.judge` accepts the words with `UNREAD_NOTE` after them ("this message came with a picture or a file, which
   Dot cannot read on this channel yet. Only its words reached you. Do not guess what the attachment shows."); the
   router finds the note at the end of the finished run's goal, so a message that waited in the chat's queue is told
   the same, and starts the answer with `UNREAD_ANSWER`, a line of its own. A run that failed or was stopped says how it
   ended and nothing of the picture: it gave no answer to be mistaken for one about it. The picture that a link preview
   shows, which Messages may flag as an attachment of the preview's row (a `URLBalloonProvider` row, as the tests of
   item 572 make it), is no file the owner sent: `_handle` does not count it, and `_joined` no longer carries it to the
   words it joins. The attachment itself is not read: that is its own feature.
6. *Links that open on the phone* (`channels/service.py`, `channels/router.py`, `channels/text.py`). The link of a
   message is `https://<[server] reach[0]>/#/runs/<id>`, which is what `dotx url` prints for the phone and what the
   daemon serves as an origin; with no `[server] reach` the router's `base` is `None` and no link is sent. The push
   notices never choose an address: they carry a route (`#/runs/<id>`) and the phone's service worker opens it at the
   origin of its own page, the name it reaches Dot by. A message in iMessage has no such page, so the daemon builds the
   address from the one name a phone reaches it by. Without it, an answer cut short ends *The rest of the answer is in
   Dot on your Mac.* (`cut_with_link(…, None)`), a wait says *Answer it in Dot on your Mac, not here.*, and a line of
   tells is the tell and nothing after it. The tab says why once, in its facts (*Links in messages*, from
   `ImessageView.links`), and the log says it as the daemon starts (`channel_links_not_sent`). The channel is still
   told this Mac's own address for the rule that a row that is only a link into it is Dot's own, never a command.

**Left out, and limits.**
- The chat's own queue (`RunManager._drain`) does not read the stop file: a message queued before the file was touched by
  hand starts when the run at work ends done. The button and `POST /api/failsafe` end the runs, so the queue is held
  and nothing starts. The queue holds the owner's own messages from every page, so it is not the channel's to change.
- The cursor comes down on one look. A read of the database that came out stale (behind the write-ahead log, which part C
  of item 595 may change) would move it down and read the rows between again; the 15 minutes after which a message is not
  run (`STALE_S`) tell the owner of those that are old.
- The attachment is not read. A message with a picture and no words is still told *Dot does not read attachments yet*.
- Nothing here changes the policy, the shell guard, the approvals or the sandbox.
