### 742. A call of a tool whose group is off runs at once

**Status: done (2026-10-27).** **Measured:** in the owner's runs of the last 30 days, a call of a tool of a group that
was off came back as "X did not run: it is in the tool group G, which was off. The group is on now: call X again", and
the model called it again: nine extra model steps, each about 145k tokens of context.

**Why it refused.** The grouped tool surface offers a run only the core tools, so the model calls an off tool without
ever having seen its parameters, and the call was turned into a turn-on of the group. Nothing forbids running the call:
the tool is in the run's registry whatever the tool list offers, its arguments are validated by the tool as any call's
are (a wrong guess fails with the tool's own words), and the policy, the approval and the run's gate judge the action
the call makes, not the list it was offered in.

**The change.** `executor._execute_one` no longer answers a call of a hidden tool with a refusal; it goes through
`_run_checked` as every call does (classify, policy, approval, taint, the secrets read of its words), and the result
starts with a line saying the tool's group was off and is on now. The loop turns the group on for the next step as it
did (`_turned_on`), so the tool list grows as before. The call's event now carries its own action and risk instead of
the "Turn on the tool group" meta action.

**Checked.** `tests/smoke/test_tool_groups.py`: the first call of `schedule_list` in a grouped run is a result that ran
(ok, its own action), starts with the note, and the next step offers the group; once the group is on, a call has no
note. It fails on the code before.
