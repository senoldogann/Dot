### 2004. A run's start no longer reads every skill again, nor waits minutes for an embedding

**Status: done (2026-11-27).** On the owner's store a run's start took p95 13.6 s and p99 35.2 s to its first model
call (three days, 89 runs; seven days: p99 305.6 s). Its reads are made at once since item 1918, and the `memories`
event, which the last of them ends with, came 2.5 to 26 s after the start; in the slow ones the daemon's first embedding
request reached Ollama 7 to 23 s after the start, so the time was Dot's. Measured on the owner's own files (read-only):

- The skills catalog was read and parsed from disk at every start: 560 skills in 810 files, 1.4 to 3.3 s on the
  owner's Mac (a loaded one; the parse holds the interpreter's lock, so the loop of every other run slowed with it),
  and 0.1 to 0.5 s more for the learned skills' list.
- The notes' recall waited for Ollama as long as it took: the embedding call has a 300 s read timeout and three tries.
  On 2026-11-23 a start waited 304 s: Ollama's log shows the embedding held 3 min behind a local chat model's request
  (qwen3 8b) that ran out at 5 min. On 2026-11-22 a cold load of `bge-m3` held another 12.7 s.

What changed: a SKILL.md is parsed once per process while its file stays as it is (its modification time in
nanoseconds, size and inode); one that changed or was replaced is read again, so the catalog is still the files'
(`_remembered` in `dotagent/skills/catalog.py`; a skill reached through two links is told apart by its device and inode,
one stat where resolving the path took one per part of it). The start waits for its notes by meaning
`[memory] start_recall_s` (15 s) at most, and as long again for the skills it picks by meaning (`_close_skills`, which
embeds the chat's title and goal on the same server), then finds them by their words, as it does when the embedding
service fails (item 256), and says so in the same `embedding_failed` line. Only the deadline's own timeout is read so; a
timeout raised inside the recall for another reason stays that reason's. A skill whose file is gone is dropped from
what the process keeps. Each read of the start records its seconds
(`start_reads`: profile, agent, agents, accounts, skills, notes, last call, secrets and harness), which
`dotx perf` (item 2003) lists, so the next slow start names its read.

Before and after, the owner's skills, the same Mac and minute: `load_skills` 1.4 to 3.3 s at every start before; 3.3 s
at the first start of the daemon and 0.2 to 0.5 s after it. The 304 s start is cut at 15 s for the notes and 15 s for the skills.

How it was checked: `tests/unit/test_skills.py::test_a_skill_file_is_parsed_once_while_it_stays_and_again_once_it_changes`,
`tests/smoke/test_start_speed.py` (a stand-in Ollama that holds every embedding 20 s, and more skills than the prompt
lists: the run of the real loop finds its note and picks its skills by their words after 0.5 s each, says so twice,
records its reads and ends done), the freedom contract, `dotx eval check`, ruff and
mypy.
