### 553. Stop stops: a background command's end, the emergency stop of runs dotx drives, a campaign's stop, and a delegated run keeps its agent's tools

**Status: done (2026-10-23).** Found by the audit of 2026-10-23 at `96e8c750` (F1, F2, F52, F53, F55, F56, F57, F58,
F59, F54, F11, F165), each read again in the code by a second reader. The contract of the product is that Dot stops at
once when told to, and that what the owner bounds stays bound; these are the places where a run went on after Stop, or
where a bound of an agent was not kept.

**Fixes.**
- F1, *a background command's end starts a new run in a chat the owner stopped*: `_tell_ended_commands` starts nothing
  when the chat's newest run did not end done (a stop, a failure: the notice waits for the owner's next run, whose first
  step is told, as `_follow_queue` has it) and nothing while the `STOP` file exists. Before, only the order "the command
  ends first, then Stop" was held; the reverse started a yolo run in the stopped chat.
- F2, *the emergency stop does not end the runs `dotx` drives*: `RunManager.emergency_stop` is async and asks the
  process that drives each run of another process (`elsewhere_run_ids`) to end it as the emergency stop: it marks the run
  in the store's key/value table (`emergency_stop_asks`), then asks it to stop as the Stop of the pages does; the
  process that answers (`_answer_asks`) ends a marked run with `end_by_emergency_stop` (so a campaign session of it
  stops its campaign) and takes the mark away; a mark nobody answered lapses after a day. `POST /api/failsafe` awaits it
  and lists those runs among the ones it stopped. No change of the store's schema.
- F52, *a campaign whose opening session fails to start on an existing chat leaves that chat's newest run pointing to a
  deleted campaign*: `Store.delete_campaign` also clears the `campaign_id` of its runs, in the same write.
- F53, *the campaign page's Stop and Mark achieved do not stop a session that a `dotx` command drives*: `stop_session`
  asks the process of a command to stop it (`RunManager.stop`) as it cancels a session of the daemon.
- F55, *a schedule's run resumed after a restart is not tracked as in flight*: when a firing comes due, the scheduler
  (and a run by hand) finds in the schedule's chat a working run that resumes a run of a firing and follows it as the
  schedule's own (`_adopt_resumed`): the firing is skipped as for any run still going, and the end of that run is
  written to the schedule. A resumed follow-up of the owner's own is not the schedule's.
- F56, *a session's end during daemon shutdown is never followed*: `_record_end` skips `_follow_session` only for the end
  that the shutdown itself cut off (`daemon_shutdown`), which `resume_campaigns` plans when the daemon starts; a session
  that ended done as the shutdown began is followed as ever (its session limit, its wait for the owner's answer).
- F57, *an overdue firing after the Mac slept is reported as "the daemon was not running"*: it says "the daemon was off
  or the Mac slept", the docs' own words.
- F58, *a stale comment in `RunManager.__init__` describes a lock that no longer exists*: the two lines are gone.
- F59, *a run whose end the store refused does not keep its chat*: `_claim_thread`, the queue's drain and the notice of a
  command's end refuse a thread with a run in `_left_ends` (`_ending_on`), until `store_left_ends` has stored the end;
  the chat takes the next run after, and the comment of `store/db.py` about it is true.
- F54, *the schedules doc says the form offers a "chat" kind of run*: "task or research", and that a chat that only talks
  schedules tasks.
- F11, *a delegated run started by an agent's run escapes the agent's tool bound*: `RunManager.delegate` gives the helper
  the parent's `agent_id` (its source, model and approvals stay a delegation's), so the loop bounds its tools as the
  agent's and its prompt holds the agent's instructions.
- F165, *the docs and the delegate tool say the delegated run takes the parent's mode and tools*: a research run's helper
  does research and any other run's helper is a task run; the tool's description, the prompt's section on delegation and
  docs/runs.md say so, and that an agent's helper keeps the agent's tools.

**Left.** Nothing of the item's findings. Noted, not changed: the emergency stop does not reach a `dotx` run that starts
after it (the STOP file holds back its desktop steps alone, as before) and a run resumed by hand writes its end to the
schedule only if the schedule came due beside it (an end before that is not written); a helper of an agent's run is now
listed as one of the agent's runs (`latest_agent_runs`), and its memories and lessons are the agent's.

**Tests.** `tests/smoke/test_background_commands.py`: a command that ends after Stop starts no run, and the owner's next
run is told; one that ends with the STOP file there starts none (both failing on the code before).
`tests/smoke/test_command_runs.py`: the emergency stop ends the run of a real `dotx` child process as one, its ask and
mark gone after. `tests/unit/test_emergency_marks.py`: the marks read, add, lapse and go. `tests/smoke/test_campaigns.py`:
a campaign that failed to start after its run was stored leaves that run no campaign; the page's Stop and Mark achieved

off. `tests/smoke/test_schedule_resumed_run.py`: the schedule fires nothing beside its resumed run and gets its end, the

`tests/smoke/test_left_ends.py`: a chat whose last run has an end the store refused takes no run until it is stored.
`tests/smoke/test_delegate_agent_tools.py`: the helper of an agent bound to two tools is offered those and the core ones,
