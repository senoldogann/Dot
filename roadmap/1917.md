### 1917. A pull request that changes ios/ builds the iPhone app once, on macOS

**Status: done (2026-11-26).** Since item 1886 a pull request runs no macOS job, so a Swift compile error in `ios/`
reaches `main`: #1153 broke main's iOS build with a missing `self.` in a test fixture and #1155 had to follow. The lead
chose to give iOS pull requests the one job that would have caught it, at the cost of one macOS runner for about ten
minutes per pull request that touches the app.

What must hold: a pull request that changes `ios/**` or `.github/workflows/ios.yml` compiles DotNext and its tests
(XcodeGen, `build-for-testing`, the String Catalog check) before it merges; nothing else of `ios.yml` runs on a pull
request, and everything on a push to main, the night and a dispatch stays as it was.

What was built: `ios.yml` takes `pull_request` with the push's paths. `engine`, `tests` and `e2e` skip when the event is
`pull_request`, so `build` is the one macOS job. The `ios` summary check passes on a pull request when `build` passed and
the other three were skipped, and fails otherwise (a skipped job still fails it on any other event). The concurrency
group stays `ios-<ref>`, which for a pull request is its own ref, and cancels the run in progress on a new push; main's
runs are still never cancelled. No new permission and no new action: zizmor passes. docs/development.md, CLAUDE.md and
ios/Next/README.md say that an iOS pull request builds once. `main_macos_green.py` reads only the runs of a push to
main, so a pull request's run does not change main's verdict.

Checked: zizmor on the workflow; the pull request's own run, which changes `ios.yml` and so shows `build` running and the
other jobs skipped.
