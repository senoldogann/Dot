### 1754. Waiting for a run that is still being launched waits for its end

**Status: done (2026-11-25).** `RunManager.wait` returned the stored record at once when the run had no handle yet. A
run is stored (`create_run`, status `queued`) and only registered several awaits later (its chat's first choices, its
instructions, its parking), so a caller that found the run in the store in between — a helper's report waking its
chat, then a wait on the run it started — was handed it `queued`. `tests/smoke/test_helper_wake.py` failed so under
`-n 4` (`assert 'queued' == 'done'`), as item 986 had found for the reactions' follow-up runs and fixed in the test's
helper alone; `routes_agents.py` and the evals wait on runs the same way.

What changed (`agent/manager.py`): from the return of its store to its registration a run holds an event in
`_launching`, set once its handle is registered or its start failed (and was ended as not started); `wait` waits for
that first, then for the handle's end. Left: the moment between the row's insert and `create_run`'s return, before the
event is put in; a wait that reads the run from the store in it is handed it `queued` still. Closing it would mean
taking the run's id before it is stored. The test's own race goes too: it waited for "told or waiting", and a report is in the manager's list for
a moment on its way to the run that wakes, so a case that wakes waits for that run and one that does not for the list,
and, when the plan's window resets later, for the wake at the reset, which is set once the run's end is read, after the
report is in the list (it failed so once in 5 runs).

Checked: `test_helper_wake.py` failed 2 runs in 3 under `-n 4` before (an `IndexError` and the `queued` run), 5 in 5
green after; `dotx eval check`.
