### 595. The iMessage channel works when the Mac and the iPhone use different Apple IDs, and says what it sees

**Status: parts A and B done (2026-10-23, and changed on the reviewer's word the same day: no waiver, one command for a
message kept as two rows, a warning beside each paired handle); part C, reads that see the write-ahead log, waits for
the owner's test.** The owner's first real try of the channel (item 572) got no answer. This Mac's Messages is signed in
with the MacBook's own Apple ID (A), the iPhone with the owner's personal one (B), and Messages in iCloud is off. The
owner paired B's iCloud address (Dot sent the code from A to B, and the owner typed it back) and wrote to Dot from the
iPhone, B to A. The message shows in Messages on the Mac. Dot's state was: on, database granted, automation allowed, no
problem, no run ever started, the cursor of `channels.imessage` still 307 half an hour after pairing, and in the log
only `channel_switched_on`, `imessage_code_sent` and `imessage_paired`.

Two causes, one item:
1. **The channel did not read this setup.** It read only rows with `is_from_me = 1`, the owner's own conversation with
   themselves under one Apple ID. Here the owner's messages arrive as `is_from_me = 0`, from handle B, in the one-to-one
   chat named B. (Part A.)
2. **The channel did not say what it saw.** `read_new` moves the cursor to the table's newest row even when no row
   matches, so a cursor that stays put means the daemon's read-only connection saw no new row at all, yet a message had
   arrived. Nothing on the tab told this from "no message came". The suspicion is the write-ahead log (`chat.db-wal`): a
   read-only connection may not see rows that Messages has written there and not yet checkpointed. (Part B shows it;
   part C, only if the owner's test says the log is the cause, makes the reads see it.)

**What must hold, and what only informs** (written before the code, item 540). This changes who may command Dot, so each
input has its verdict and what holds it. Part B informs and gates nothing.

| Input | Verdict | Held by |
| --- | --- | --- |
| a row `is_from_me = 0` in the one-to-one chat named for a paired handle, whose sender (`handle.id`, lower case, as `normalize_handle` writes it) is that same handle, over iMessage, no reaction, no change of the chat | a command | the query of `read_new` and `sender_is` (`channels/imessage.py`) |
| the same row from another handle in that chat, from no handle, in a group (even one named like the handle), in the chat of a handle that is not paired, by SMS, a reaction, a change of the chat | never read | the same |
| a received row that starts with `◆`, holds rich content that is not a link preview's, or is only a link of Dot's own | let go, as a sent row is | `IMessageChannel._handle`, unchanged |
| a received row dated in the window of a step that sends a message, or flagged as sent later | told, never run: judged as a sent row is, since that Messages keeps no received copy of what this Mac sends to the owner's own address cannot be shown | `IMessageChannel._not_the_owners`, which holds every row alike |
| a sent row and a received row in one chat with the same words, dated at most 10 s apart (with one Apple ID Messages may keep a message to oneself as two rows) | one command: the second is let go and logged; each row is the copy of one row only; two rows of one kind, other words, another chat or more than 10 s apart are two commands | `IMessageChannel._copy_of` |
| words and a link preview that are not both received or both sent | never joined into one command: two authors | `IMessageChannel._takes_a_link` |
| a row `is_from_me = 1` in a chat named for a paired handle (the one-Apple-ID case, and the Mac's own sends in the two-ID one: Dot's replies, a run's sends, the owner typing on the Mac) | as before: the marker, the window, Send Later, the links | unchanged |
| the code that pairs a handle | as before: sent to the handle, typed back in Settings › Channels | `IMessageChannel.confirm`, unchanged |

**Why a received row is the owner's.** Apple authenticates the sender of an iMessage: only the holder of B's Apple ID
can make a row from B, `is_from_me = 0`, in B's chat on this Mac. A run of Dot can send only through this Mac's
Messages, as the Mac's account A, and so writes rows `is_from_me = 1` only; and a run cannot write `chat.db` itself,
which `[policy] sealed_paths` closes to a command (the limits of that are the sandbox's, in `docs/safety.md`). The
pairing is the proof it was before: the code reached B and the owner typed it back. What this rests on: that
`is_from_me` is the account's own (a message sent by any device of the Mac's Apple ID is `is_from_me = 1`, one from
another Apple ID is 0), and that Messages does not write a received copy of what this Mac sends. Neither was seen on a
real Mac (the owner's database was not opened), so nothing waives the window or Send Later for a received row: it is
judged as a sent one is, and costs the owner a message told "send it again" now and then. (The first build waived them,
on the ground that a run writes sent rows only; the review took the safe side, since a run's send that came back as a
received row would pass for the owner's.)

**A paired handle is now trusted in both directions.** A row from it is a command, as a row to it was. Pairing a number
that is not the owner's own, with its holder's help, would hand the holder Dot. The tab and the docs say to pair only
your own number or Apple ID address, the one your iPhone writes from (the conversation is named for it on the Mac), and
what changes: with two Apple IDs it is the messages from that handle that are commands. Each paired handle carries the
line *Messages from this address run as you* in the tab, and `channels.md` says plainly that pairing someone else's
address gives them Dot.

**What only informs (part B).** The tab and `GET /api/channels` show what the channel sees of `chat.db`: the newest row
it saw and when, the cursor, when it last looked, the size and time of the last change of `chat.db` and `chat.db-wal`,
the last row it took as a command, and the last error. None of it decides what is run. A warning says the log changed
while nothing Dot can read did, for two minutes. **Check now** polls at once.

**As built.**
- *A. Two Apple IDs* (`channels/imessage.py`). The query of `read_new` no longer asks for `is_from_me = 1`: it joins
  `handle` (`message.handle_id`) and returns the rows of the one-to-one chats named for a paired handle, over iMessage,
  that are not reactions or changes of the chat, each with its flag (`Row.received`) and its sender. `sender_is` keeps a
  received row only when `normalize_handle(sender)` is the handle its chat is named for, so a row of another handle in
  the chat, of no handle, or of a handle that is no number or address, is dropped (a sent row needs no sender).
  `_takes_a_link` joins words and a link preview only when both are received or both sent. The marker, rich content and
  the links of Dot's own apply to every row, so that a copy of Dot's words coming back received is let go as a sent one
  is. Dot answers in the chat the row came from, as before. The window and Send Later hold a received row as they hold a
  sent one. `IMessageChannel._copy_of` keeps the rows that may be commands in mind (the last 20, each with its words,
  date and kind) and lets go the second of a sent row and a received row in one chat with the same words dated at most
  `COPY_S` (10 s) apart, in either order and in the same poll or a later one, logging `imessage_message_let_go` with
  `copy_of` the row it copies. A row is the copy of one row only (`_Heard.copied`), so words said again run again; and
  it is judged before the intake, so a copy neither counts against the flood nor is told a second time (the copy of a
  row told for the window is let go, not told again). The tab shows *Messages from this address run as you* beside each
  paired handle.
- *B. What the channel sees* (`channels/seen.py`, new). Each look at the database (the loop's poll, or Check now) leaves
  a `Look`: the newest row and its date (`look_at`), the state of the newest 30 rows (their delivered and read marks,
  found by column name), and `os.stat` of `chat.db` and `chat.db-wal`, read after the rows. `Watch` follows the looks:
  the newest row and when it was first seen, when Dot last looked, the files, the last command (kept in the store under
  its own key, `channels.imessage.command`: the channel's state could not take a new field and be read by an older Dot)
  and the last error (a failed look or send, with its time; masked of the secrets Dot holds in the view). `GET
  /api/channels` carries it as `seen`.
- *The warning, and why it reads the state of the newest rows.* The brief's rule is: the log changed since Dot last saw
  a new row, and that has lasted more than two minutes. Taken as it stands it would stand after every answer Dot sends:
  Messages marks the sent row delivered, then read, in the log, minutes after the row was seen, and no new row follows.
  So a change of the log counts only when nothing Dot can read changed with it: a new row, or a change in the state of
  the newest rows (a receipt), shows that Dot reads what Messages writes and clears it. The log's change is taken at its
  own time; the rows are read before the files, so a write between the two reads as newer than the rows and is cleared
  by the next look if the rows show it. A log that is gone (Messages quit, folded it in) clears it. It is said once in
  the log, `imessage_wal_unseen`, with the sizes and times, and in the tab with the brief's words.
- *Check now* (`POST /api/channels/imessage/poll`, `Channels.poll_now`). With the channel on and a number paired it is a
  poll with the router's `receive`, as the loop makes; with it off, or nothing paired, `IMessageChannel.look` only
  looks, so that the switch keeps its meaning. `poll` and `look` take one lock, so that the loop's poll and the press
  never read the same cursor twice, and the route waits for a switch or a pairing step under way (`Channels.changing`,
  as the other routes do), so that no message is run after the switch said off.
- `imessage_newest_row` (info) when the newest row changes, at most once a minute, with the row's number and date and
  nothing of what it says or who wrote it.
- *The tab* (`views/channels.js`, `channelfacts.js`): **What Dot sees in Messages** under the permissions, the facts as
  rows, **Check now** (on a phone it goes under the text), the warning as a note, and a toast of what was seen. The
  pairing text says which handle to pair with two Apple IDs. Docs: `channels.md` (what is read, what Dot sees, who may
  command, the table of what the tab says), `safety.md` (the paragraph on channels), `daemon.md` (the route and the
  view), the comment of `[channels]` in `defaults.toml`.

**Measured (for part C).** A writer in another process kept a WAL-mode database open (`wal_autocheckpoint = 0`, every
insert committed to `-wal` only; `chat.db` stayed 4 KB while the log grew from 20 to 41 KB), and a fresh process read it
as `open_messages_db` does (`file:…?mode=ro`, not immutable) after each insert: it saw every row at once, on Python
3.13's SQLite 3.53.1, before and after the writer closed. So a read-only connection does see the log of a live writer
there. What could keep it from seeing the owner's rows is what this experiment lacks (macOS's own SQLite, the rights on
`-shm`, Messages' locking mode, the way Tahoe's Messages writes); the facts and the warning now show which, on the
owner's Mac. Part C is not built.

**Questions for the reviewer (security).**
- *The window holds a received row too* (it was waived in the first build and the review took it out). With one Apple ID
  and a paired own address, a run's message to oneself would come back as a received row if Messages kept such a copy;
  that could not be seen on a real Mac, so nothing relies on it. The cost is a message told "send it again" now and
  then.
- *A paired handle is a commander in both directions now.* A handle of someone else, paired with their help, would hand
  them Dot. The tab, `channels.md` and `safety.md` say to pair only your own, and which one.
- *The copy rule can swallow a deliberate repeat across the two kinds.* Words typed on the Mac and the same words sent
  from the iPhone within 10 s are one command. Nothing else is lost to it: two rows of one kind, another text, another
  chat and rows more than 10 s apart all run. That Messages keeps a message to oneself as two rows is not known to
  happen; the log says which kind a command was (`imessage_message_read`, `received`).
- *The handle the iPhone writes from.* A conversation is named for one handle: pairing the iCloud address while the
  iPhone writes from the number reads nothing. The tab says to pair the one the conversation on the Mac is named for;
  the newest row it shows tells the owner a message arrived.

Not built: part C; a check that tells the owner which handle a conversation was written from (it would show the handles
