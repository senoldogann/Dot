### 1351. A message ends a run's wait on its helpers, and the helper's report reaches the chat when it ends

**Status: done (2026-11-23).** The owner's report: while a run waits for a subagent, a message they send does not make
the run go on; it keeps waiting for the helper's result though the helper could work in the background. And their
question: is the logic of a coding harness the better one, where a session that waits on a subagent or a background
task simply stops (idle) and is brought back when the awaited result arrives?

What was wrong: `delegate` is a tool call that blocks until the helper's run ends (limit four hours). A steer is read by
the loop before its next step, which never comes while the call is blocked, so the run looked stuck. A command in the
background has the opposite shape since item 229: the run is told at its next step, a chat with no run gets a run
started to tell it.

**The logic that suits Dot.** Such a harness parks a session because a coding harness has one agent and one conversation: when
that agent has nothing to do, idle is the truth, and a wake-up is cheap. Dot is the owner's autonomy on a Mac: it has
other work (the owner's next message, other chats, schedules), the owner talks to it while it works, and what it waits
on is often a helper that does part of one goal. A wait that is a blocked tool call costs no model tokens, so parking
saves nothing there; what it costs is that the owner's words are not read, a run place is held (up to four hours), and a
restart cuts the wait. So the answer is a mix, in this order:

1. **Release on a message (A).** A message that reaches the run while it waits ends the wait of every `delegate` call of
   the turn together (the call returns with the helper's id and that it keeps working; the helper is not cancelled;
   the run reads the message). The test is the one a model call gives way to (item 509): `RunInbox.asks()`, so the
   steer, a queued message sent on, the answer to a question and a note of Dot's all count and a 👍 does not.
2. **Report to the chat (B).** When a helper that no one waits for ends, its report is told the way a background
   command's end is (item 229, the same guards): the run at work in the chat reads it at its next step, as a note of
   Dot's; with none, a run is started to read it (`wake_for_helpers`, as `wake_lead` of item 1075 does for a work
   order), unless a run works or ends there, the queue holds or waits, the chat's newest run did not end done or the
   emergency stop is on. Then it is kept (`RunManager._untold`, and the store's key `detached_helpers`) and the next
   run of the chat reads it at its first step. The report is `render_outcome`'s own text (fenced as third-party content
   when the helper read some, with the Verification note), the note marks the reader as that content does, and the run
   started for it starts untrusted when the helper or the chat's last run ended so.
3. **Parking, by the model's choice (C).** `delegate(wait=false)` starts the helper and returns at once. A run that has
   nothing left but to say what it waits for ends its turn: the chat is idle, no model call and no blocked tool call,
   and the helper's end wakes it by 2. The model decides, since only it knows whether other work is left; the default
   stays to wait, so every existing flow is unchanged. The tool's description says it in a few words.
4. **The line (D).** "Waiting on N subagents" over the composer shows only while the run is blocked on them; a helper
   the run stopped waiting for reads "N subagents keep working in the background"; nothing when none work. A
   `helper_released` event of the parent (stored) says which helpers were let go, so a page loaded again says the same.

Guarantees kept: a Stop of the run still stops its helpers, those it waited for (the cancellation of the call, as
before) and those it let go (`_stop_detached_of`, run before the run's own end is stored, item 197), and what a stop
ended is told to nobody; a run that fails or is cancelled stops them too, a run that ends done leaves them at work. A
helper cannot delegate (unchanged check), and starts as untrusted as its parent. The plan step: the release and the late
report close nothing (`closing_step` ignores a result whose first line ends in "keeps working in the background."; the
note says the step stays as it is and the run marks it itself). Research-run limits, `fan_out`, `message_agent` and
the work orders are untouched. A chat lets at most eight helpers work in the background
(`MOST_DETACHED_PER_CHAT`): past that the call is refused and the new helper stopped.

**Restart.** The kept list is the store's key `detached_helpers`: a helper is added when it is let go and removed when its
report is handed to a run (or its parent's end stopped it). When the daemon stops, every helper ends with it, as every
run does, and the followers tell nothing; the next start (`RunManager.tell_helper_reports`, after the resume of the
runs the stop cut off) reads the list and tells each chat what the helper reported or that the stop cut it off, from the
helper's own run record, so a report that was told before the restart and one told after read the same, and a helper that
ended between its end and its telling is not lost. What a restart cannot do is keep a helper working: its run is cut
off, as any run is, and the chat is told that it ended cancelled.

**Not done, and why.** A true park of a run that still has a blocked `delegate` call (the run's task ending
while the call is open, to be started again when the helper ends) was not built: the run's state (its step in flight,
its parallel calls, its tool call ids) is in the task's memory, and what a restart would then have to rebuild is exactly
what resume already does for a run it cut off, with a note. `wait=false` gives the same result without that: the run
ends its turn between steps, where there is nothing in flight. A release is judged on the inbox alone, so when another
tool of the same step (a shell command) still runs, the delegate call returns but the step ends with that tool. The page
says nothing for a chat whose run ended while its helpers work (the line is the run's); the helpers' own rows and the
Activity list show them. `fan_out` and `message_agent` still wait as before. The eval set has no case that delegates,
so none was added.

Checked: `tests/smoke/test_helper_wake.py` (a message ends the wait and the helper's report starts a run in the idle chat;
one message releases both calls of a turn; `wait=false` reports to the run that goes on working, no run started; a Stop
while waiting and a Stop after the release stop the helper before the run's end, nothing told; a report not told when the
daemon stopped is told by the next start; a chat that cannot be woken has its next run read the report first; and, in
Chrome, wide and light then on a phone and dark, the line says "Waiting on 1 subagent", then "1 subagent keeps working
in the background" after the message, and the same on a page loaded again), `tests/unit/test_helper_reports.py` (the
words, the fence, the step, the kept list, the tool's description), `tests/js/waitcounts.test.js` (which subagents the
line counts); `tests/smoke/test_context_budget.py` raised by 100 for the `wait` field (30,132 measured); `ruff`, `mypy`,
`npm run check`. A `dotx` command does not let a helper go: it ends with its run, so it waits as it always did.
