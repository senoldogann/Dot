### 1720. OpenCode's agent gets every tool of Dot's a run on the Claude plan gets, and a test holds the three harnesses' tools together

**Status: done (2026-11-24).** The audit of 2026-11-24 (A3, D1) found that a run on one of Zen's free models (the
`opencode` provider, which goes whole to OpenCode's own agent) got only five groups of Dot's tools besides OpenCode's own
(`browser`, `desktop`, `schedule`, `memory_admin`, `pages`, and five core tools): no `theme_*` (item 1656),
`watch_video`, `draft_message`, `wait_until`, `skill_save`, team, mail and calendars, office, recall, `web_crawl`.
A run on the Claude plan had them all (item 1063). The audit took `opencode_go:deepseek-v4.1-flash`, the owner's main
model, for such a run; it is not: `opencode_go` is an API provider of Dot's own loop, which has every tool (its runs
called `theme_*` 47 times in the owner's store). The gap was Zen's alone, which ran once in 14 days (it failed:
"inference service is overloaded").

What changed (`agent/handover.py`, `opencode/run.py`, `claude_code/run.py`):

- `door_tool` and the loop's own tools (`LOOP_OWN`) moved from `claude_code/run.py` to `agent/handover.py`, which both
  programs' runs share, with `withheld_out` (the tools Dot's own loop withholds from a run as it starts: no accounts, no
  skills, no helpers; items 1063 and 1068), which a Zen run did not apply.
- `opencode.run.bridged(name, delegated)` is `door_tool` without `OPENCODE_OWN`: the tools OpenCode's own do (files,
  `shell`, `web_fetch`, `web_search`) and `finish` (a Zen run ends with the agent's last answer, item 283). A delegated
  run's agent gets none of what a delegated run may not use, as on the Claude plan.
- `tests/unit/test_harness_tool_parity.py` builds every tool Dot may have (each switch on), and for each mode,
  delegated or not, fails when the Claude plan's door or OpenCode's lacks a tool of Dot's own loop that its list does
  not name with why.

Cost: OpenCode puts every tool of a server in its prompt; the bridged definitions grow from 43 tools (40,616
characters) to 92 (75,473), measured on the packaged defaults.

Checked: the new test and `tests/unit/test_opencode.py` (a delegated run, a bounded agent), `test_claude_code.py`, the
OpenCode and Claude Code smoke tests, `tests/unit/test_freedom_contract.py` (each bridged call goes through the run's
gate as before; a yolo or free run asks nothing new). Before: `bridged("theme_apply")` was False.
Not done: a Zen run still gets none of Dot's prompt, recalled memory, skills listing, lessons or goal check (audit A1,
gap 1): giving them needs a live probe of whether OpenCode's prompt API takes a system text and whether Zen's free tier
still answers with one, and the Claude plan's prompt work (branch item-harness-parity) was not pushed to share. A
`wait_until` here is not cut short by the owner's message (item 1685 passes no marker for OpenCode: it does not say
when it takes a message in).
