### 1092. A start of OpenCode's server that hangs is started afresh

**Status: done (2026-11-09).** Asked by the owner: a run on one of OpenCode Zen's free models sometimes failed with
"OpenCode's server did not start in time".

Found: Dot's log has one such start in three days (2026-11-09 20:19), and OpenCode's own log
(`opencode/data/opencode/log/opencode.log`) shows it read its three config files and then wrote nothing for the 60 s
Dot waits; the start twelve minutes later answered in half a second, as starts do (0.5 to 4 s, measured on a copy of
the home: cold, with no catalog, with the web refused, with a proxy that never answers, and with 30 busy processes,
at most 7.4 s). The Mac was loaded far past its cores then (load 60 to 130, other sessions' builds). What the process
waited on is not known: Dot's own log of the server is written afresh at each start, and the error kept nothing of it.

Now:
- A server that does not answer in `start_timeout_s` is stopped and started afresh once, each timed-out start told as a
  warning (`opencode_server_start_timed_out`); a second one fails the run as before.
- The error of a start that timed out says what the process was doing (`ps`: running, asleep or waiting on the disk,
  its CPU share, memory and CPU time), the Mac's load and the last of what the server wrote, so that the next one
  shows its cause.
- A look at the starting server's health waits 5 s at most (it waited up to 60 s, past the start's own deadline, on a
  server that took the connection and answered nothing).
- `opencode_server_started` says how long the start took.

Checked: `tests/smoke/test_opencode_start.py` (a stand-in `opencode` that hangs at its first start runs at its second;
one that hangs twice fails with the process asleep and its line written; both fail on main), `tests/unit/test_opencode.py`
and the OpenCode bridge and run tests.
