### 585. Learned skills: a higher bar, versions, rest by disuse and merging

**Status: done (2026-10-23).** The owner asked how learned skills are managed: whether the ones nobody uses are removed
and whether one can be updated. Read in the code (the counts of their own Dot were read by another session, read-only,
and are not checked here): a skill is written from any task run that ended done after `skill_min_steps` (4) acting
steps, so a one-off question becomes one; the only retirement is `MAX_FAILURES` (two runs in a row read it and failed),
and a skill taught by the owner is never retired; a later run of the same kind (the same name, or 0.85 by embeddings,
`_SAME_KIND`) rewrites the steps whole, the evidence keeps every run and nothing keeps the steps it replaced;
overlapping skills are never merged. A skill that teaches a later run to weaken Dot's own policy is not marked and is
offered like any other; the owner chose to keep the one they have, and the bar below stops new ones. This entry was
written before the code, as item 540 asks: what must hold, where it is held, and what only asks.

**Approach.**

- **The bar** (`agent/playbooks.py`, `agent/review.py`). `PlaybookReply` is the writer's answer: a `PlaybookDraft` with
  one more field, `recurs` (required, so a model that leaves it out is asked again): whether the steps are a procedure a
  later task of the owner will likely need again, as against a question answered, a lookup or a job done once. A
  `recurs` of false writes no skill and the log says why (`playbook_skipped`, with the model's judgement). The taught
  path (`teach.py`) keeps `PlaybookDraft`. The owner's **Save from a chat** is not asked this question (they chose), but
  a chat-mode run and a run that changed Dot itself are refused there too.
- **Versions.** `PlaybookMeta` gains `version`, `versions` (a note per version: its number, when, the run that made it,
  how it came to be, its mark) and the fields below; fields with a default, as the earlier ones, so every record already
  written reads. The first rewrite after this item archives the file as it is as the version it had (1). A skill written
  before it has one version and no note of how it was made. `GET /api/skills/learned/{name}/versions` lists them with
  their steps, the page diffs a version's steps against the skill's own and offers **Restore**,
  `dotx skills versions NAME` and `dotx skills restore NAME N` do the same.
- **Rest by disuse.** `PlaybookMeta` gains `last_read_at` (dated where the read happens, by `date_reads`: the `skill`
  tool and the opening of a run that has a skill picked, whatever the run is; at most once an hour for a skill, under
  the lock of the playbooks, never going back, and a date that cannot be written is logged and never fails the read;
  `record_use` keeps the counts, which judge how task runs of their own ended, and only moves the date forward),
  `rested_at` (the owner's rest, or a merge's), `woken_at`, `pinned` and `merged_into`. A skill rests when it is not
  pinned and either `rested_at` is set or nothing touched it (a read, a rewrite, a wake) for `skill_rest_days`. A record
  that counts uses and has no `last_read_at` yet (it was read before the date was kept) is not rested for want of one;
  the reflection gives it one, the day it first sees it, so such a skill rests after the days pass, not at the first
  start. A resting skill is no skill of the catalog a run is offered (`offered_to_run`: the prompt's list, `skill`,
  `find_help`, the picks, a site's skills), is listed on the page and by `dotx playbooks list` as resting, and never
  retired for it. **Wake** and **Pin** are the owner's; a taught skill rests too and is never retired.
- **Merging.** After the memory's work, the reflection embeds the kinds of the active, awake, unpinned, learned (not
  taught) skills of one owner, takes the pairs whose cosine is at least `[agent] skill_merge_similarity` (0.75), the
  closest first, each skill in one pair at most (a pair above the same-kind bar, `_SAME_KIND`, can be there too: two
  skills written while the embeddings were off, say) and asks the review model whether each pair is one procedure
  (`judge_overlaps`); for each yes, at most `[agent] skill_proposals_per_night` (3) a night and at most ten waiting, a
  second call writes the merged steps (`revise_skill`, a `PlaybookDraft`), and the proposal waits as a card on Customize
  › Skills. **Merge** writes the draft as a new version of the one it names, marked if either was, with the runs and the
  use counts of both, and rests the other, `merged_into` naming it. A pair the owner dismissed is not proposed again
  until one of them is rewritten.
- **For item 586.** `propose_rewrite(runtime, name, words)` writes a proposal to change a skill as the owner says (the
  same `revise_skill` call and card, applied only on their yes), `pin_playbook`, `rest_playbook` and `wake_playbook`.
  They are functions with tests; no route or button calls the rewrite yet.

**Data.** Additive: new fields with a default in `playbook.json`, a hidden `.versions` and `.proposals` in a skill's
folder and the playbooks' folder. A record written by this item is not readable by a Dot from before it (the model
refuses unknown fields), which skips the skill with `playbook_unreadable`; rolling back is a thing to say.
