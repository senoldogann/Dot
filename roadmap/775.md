### 775. A login goes into a form that names no method, which Dot then sends by POST

**Status: done (2026-10-28).** **Measured:** on 2026-10-28 a run of the owner's tried to sign in to LinkedIn with
`browser_fill_login`, in two steps. Dot refused both: "the form of the field sends what is typed in the page's address
(its method is GET, or it names none)". LinkedIn's form names no method, which a browser reads as GET. Its script sends
the form itself, as most of today's sign-in pages do. Since item 621, a password went into no such form, so the run
could not sign in at all.

The run then told the owner that the vault held no password. It had read Dot's database, whose `fields` are `{}` for
all 381 logins, and found no internet password for `linkedin.com` in the Keychain. Both were the wrong places. A vault
login's password is in the login Keychain, in the item of the service `dot-vault` whose account is the login's id
(`vault/secretstore.py`), and nothing of it is in the database. The import of a password manager's file (item 621)
leaves out every row without a password ("no password" in its count), so each of the 381 had one when it came in.

**What must hold** (the contract, `docs/safety.md`): no address holds a password or a code. Before, a form that would
send one by GET got none. Now the password goes in, and the form no longer sends by GET.

**The approach.** Before a password or a code goes into a field of a form, Dot makes the form send by POST, at three
points:

- **Its method.** A form whose method is GET (by its attribute, by none, or by a word no browser knows) gets
  `method="post"`. A submit control of it that names `formmethod` GET loses that attribute. A dialog form is left
  alone: it sends nothing.
- **At submission.** A browser reads the method once the `submit` event has run its listeners. Dot listens on the
  window, first (capture) and last (bubble), and puts the form back to POST there. A script of the page that set GET
  again before or while the form is sent is undone. A form in a shadow root, whose `submit` never reaches the window,
  gets the two listeners on its root too.
- **Its own properties.** A control named `method`, `elements` or `setAttribute` hides the form's own of that name, so
  Dot reads them from the prototypes (a form with a hidden input `name="method"` would otherwise stay GET).
- **Its `submit()`.** `form.submit()` fires no event, so Dot gives the form an own `submit` that sets POST before the
  browser's. When a control named `submit` hides the form's `submit`, nothing is given: the page cannot call it either.

A page whose script sends the form itself, as LinkedIn's does, is not changed by any of this: it sends what it sends,
as before. A request it sends whose address carries the value is refused by the guard of Dot's Chrome (item 621), as
before. The username goes into any form, as before. The body of a form sent by POST is in Chrome's session files while
Chrome runs, and Dot deletes them once Chrome has exited, as for any login form that posts (item 621).

**What is not held:**

- A page whose script calls `HTMLFormElement.prototype.submit` itself after setting the form back to GET, or whose own
  listener of `submit` sets GET and stops the event before it reaches Dot's last listener, sends by GET.
  Only the login's own site can do this, and it has the password anyway. The address then stands masked in every view,
  as a page that moves the tab to such an address does now (the contract's "what is not stopped").
- A site that takes its sign-in by GET alone gets a POST, and the sign-in fails rather than putting the password in an
  address.

**The tools' words.** `browser_logins` and `browser_fill_login` now say where the password of a vault login is: in the
Keychain, never in Dot's database or in a file a run reads. `browser_fill_login` says when a login has none ("the
Keychain holds no password for the login …", `vault/items.py`). A run that reads `fields` then does not conclude that
there is none.

**Checked.**

- `tests/smoke/test_vault_fill.py`: each of these forms takes the password and sends it by POST, in the body; no
  address that holds it reaches the site:
  - a form that names GET;
  - one that names no method;
  - one whose button names `formmethod` GET;
  - one whose button's script sets GET again and calls `form.submit()`;
  - one whose `submit` listener sets GET again;
  - one with a hidden input named `method`;
  - one in a shadow root whose `submit` listener sets GET again.
- `tests/smoke/test_vault_items_fill.py`: a form that names GET or none and whose label holds a div. The ref of the
  input and the ref of the div both fill the input. Go sends the password by POST, in no address, and it is in no file
  of Chrome's profile and no record of the run once Chrome has exited.
