### 955. A repair session goes on when main moves by merged pull requests, and renumbers its item when main took it

**Status: done (2026-11-03).** **Asked** by the owner after two of the night's fixes stalled on 2026-11-03: #764 took
item 945 while another session merged its own 945, so GitHub could not merge it and ran no check, and the session
ended at "main moved"; #752 and #764 both ended so when main moved under them by merged pull requests. The owner: when a
repair's checks fail, it fixes them and merges again.

**What must hold (the approach, before the code).**
- Dot merges only what passed every check on the head it merges, and only when main on GitHub stands where that head
  was brought up to: main moving after that sends the session round again; nothing merges on a stale check.
- Main moving by commits that are no merged pull request's, or going anywhere but forward (set back, or onto another
  history, which commits of merged pull requests may make up), a push past the protection, still ends the session
  (`main_moved`), and so does any change of the owner's checkout (its files, its commit off main, its git config, its
  hooks): those are the owner's to look at, as before.
- Main moving by merged pull requests is expected: the session is told what main took, brings its branch up to main
  in its own checkout (a rebase onto main, which Dot fetches in the owner's checkout, never the session's, whose git
  config the session could have set to run a command with Dot's sign-in; the checkouts share their commits),
  resolving what conflicts, and moves its
  items to new numbers when main holds an entry of one of its own: Dot takes them (`scripts/next_item.py`, which reads
  main, the open pull requests and the pushed branches, where the session has no way) and names each in the brief;
  the session moves its files, the references to them and its commits' subjects. A pull request GitHub cannot merge
  (`mergeable` CONFLICTING), which runs no check, is the same case.
- The branch is pushed again through the hook only, which reviews the rewritten commits whole; the push replaces the
  branch with a lease on the commit Dot pushed last (`--force-with-lease`), so that a branch the session or anyone
  else pushed to is refused, as the check before the push already refuses it.
- A failed check goes back to the session with its log, as before (item 921); every bringing up to main counts as a
  round, so a session that keeps being overtaken ends at `[repair] rounds`, as one whose checks keep failing does (the
  hook's own count of three BLOCKs, by ancestry, starts again after a rebase: the rounds bound the session).

**What only asks.** Nothing new: what needs the owner's look (REVIEW.md's paths) still ends the session `needs_owner`.
