### 1020. The pre-push review reads every branch of a push, and only the branch's own change

**Status: done (2026-11-07).** **Found** by the same hook's review of its copy in AI-Notepad
(senoldogan-labs/AI-Notepad#291), which has the same code.

**What was wrong.**
- **Important:** the hook reads git's list of refs from its stdin with `while read`, and the `claude -p` call inside
  the loop inherited that stdin. `claude -p` appends a piped stdin to its prompt, so it swallowed the refs after the
  first: `git push origin a b` reviewed `a` and pushed `b` unreviewed.
- A branch that took main in and then got a commit of its own had its remote tip as an ancestor, so it was reviewed
  from that tip, and the pull requests main took meanwhile were read as the branch's change.
- The "only brings main in" shortcut trusted the remote tip's change without asking whether that tip had passed
  review here; one pushed with `--no-verify` or from another checkout vouched for nothing.

**Built.** `.claude/hooks/pre-push-review.sh`: `claude -p` reads `/dev/null`; the review starts where the branch
leaves main whenever that point moved since the remote tip; the shortcut holds only for a remote tip with a `.pass`
here, and the reviews live in one folder for all worktrees (`--git-common-dir`), so a tip that passed in one
worktree vouches in another. The owner's checkout runs it once it pulls.

**Checked.** `tests/unit/test_pre_push_hook.py`: a push of two new branches reviews both (with a stand-in that reads
its stdin, as `claude -p` does); a merge of main plus a commit is reviewed without main's change; a merge of main
over a remote tip that was not reviewed here is reviewed. The three fail on the old hook.
