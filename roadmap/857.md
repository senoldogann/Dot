### 857. A run asks for a secret on a card of its own; the value never reaches the chat, the store or the model

**Status: done (2026-10-30).** **Asked** by the owner, with a screenshot of another agent's card. The card was titled
"Cloudflare API token (Account Analytics: Read)" and had three parts: why the token is wanted and how to make it, step
by step; a box for the token with **Save securely**; and the line "Kept out of chat, in a private file this agent's
commands can read for 24 hours". The owner asked: "bu sistem bizde de resimdeki gibi çalışıyor değil mi?". It did not:
a run that needed a key asked with `ask_user`, the owner pasted the key into the chat, and it stood in the chat's
history, the approvals table and every later prompt. Asked whether to build one, the owner said yes ("evet onaylıyorum
gizli bilgileri … sorma katmanını kur").

**What must hold.** The code holds this, whatever the model or a page asks.
- The value the owner types is in exactly two places:
  - a file of the chat's own, mode 0600, under Dot's home (`held-secrets/<thread>.json`), for 24 hours from when it
    was given;
  - the environment of the chat's commands (`shell`, `terminal_open`), under the name the run asked for.
- It is never anywhere else:
  - not in an event or an approval's note or arguments;
  - not in the chat's history or a prompt;
  - not in a tool's result or a log line.
- From the moment it is saved it is among the secrets Dot masks (`hold_filled`), so a command that prints it shows it
  masked. A daemon started again reads the chat's file and masks its values again. A value shorter than the masks reach
  (8 characters) is refused, since it would stand bare where printed.
- The card is an approval of severity `secret`. The value comes only through `POST /api/approvals/{id}/secret`, which
  takes it once:
  - The plain decision of an approval (`/decision`) refuses to approve such a card: an empty yes would tell the run a
    secret was given.
  - A skip is the decision's `approve: false`, as any.
  - A card nobody answers expires as any question does, and the value is never asked for in chat.
- The name is an environment variable's:
  - `[A-Z][A-Z0-9_]{1,63}`;
  - none of the names the shell or the loader reads (`PATH`, `HOME`, `SHELL`, `USER`, `PWD`, `TMPDIR`, `IFS`, `ENV`,
    `BASH_ENV`, `ZDOTDIR`, `PS4`, `PYTHONPATH`, `NODE_OPTIONS` and the `DYLD_`, `LD_`, `GIT_`, `SSH_` prefixes,
    among others, and the proxy, CA and TLS names such as `HTTPS_PROXY`, `SSL_CERT_FILE`, `SSLKEYLOGFILE`), so that a
    secret given cannot change how a command runs or where its connections go.
  - A name already held in the chat is asked for again only to replace it.
- A run reads the names the chat holds, never their values: the tool's result after a save gives only the name and
  how long it holds.
- No run outside `yolo` reads or changes the folder of the chats' files: it is among `_guarded_files`, which the
  guard and the sandbox refuse to every command and file tool, as `.env` is. A chat's command reads its own secrets
  from its environment alone. A `yolo` run may read any file (the owner's word), this one too: every secret Dot holds
  is masked in what a tool returns, every chat's read from their files as well (a `dotx run` is a process of its own),
  and a name written into a file that the shell or the loader reads is not given to a command.
- The terminal of `dotx run` takes no secret: a yes there would be a yes with no value. It says to give it on Dot's
  page, and Enter declines.
- The value is held without the spaces and line ends around it, as it is masked: a value pasted with a line end would
  otherwise stand bare where a command prints it.

**What only asks.** What a command does with the variable is the command's. A copy it makes of the value (a project's
`.env`, a tool's login) is masked while the secret holds and the daemon runs; after 24 hours and a restart it is not,
as Dot keeps the value no longer than it said. A command that sends the variable to the
network is judged as any command is (the guard reads `$NAME`, not the value), and its run's taint checks are as they
were. The docs say so: the secret is for the commands of the chat that asked, and the owner gives it knowing that.

- `agent/held_secrets.py` (new): the file of a chat's secrets: save, read the live ones, drop the expired, and mask
  them all (`hold_filled`).
- `tools/meta.py`: `ask_secret(name, label, why)`. It asks the owner on a card and waits as `ask_user` with `wait`
  does. In a run nobody watches it leaves the card and goes on, and the secret, once given, holds for the chat's later
  runs. Its result says the name to use, never the value.
- `tools/shell.py`, `terminal`: the chat's live secrets join the command's environment.
- `server/routes_runs.py`: `POST /api/approvals/{id}/secret {value}`; `/decision` refuses to approve a `secret` card.
  The value is held before the card is answered, so that the woken run finds it, and taken back when the card was
  answered otherwise meanwhile: the secret it replaced is put back, and another tab's value saved since is left.
- `runtime.py`: the folder is among `_guarded_files`.
- `agent/executor.py`: every secret Dot holds (`known_secrets(filled=True)`, the chats' given secrets among them) is
  masked in what any tool returns, before the run, its history or a
  later prompt reads it. The end-to-end test found the first draft leaking there: a command that printed the value had
  it masked in the events but whole in the chat's history.
- The tool's own description tells the run to ask for a secret with it, never in a message or with `ask_user`. It is
  a core tool, kept by every agent and not offered to a delegated run. A fresh run's first step grows by 256 tokens:
  `test_context_budget.py` and the small window of `test_scaffold.py` are raised, saying why.
- `approvals.js`, `icons.js`, `tools.js`, `app.css`: the card, with its title, why and how in the run's words, a
  password box,
  **Save securely** and **Decline**, and "Kept out of the chat, for this chat's commands, for 24 hours".
- `docs/safety.md`, `docs/runs.md` and the API table of `docs/daemon.md` say so.

**Checked.**
- `tests/unit/test_held_secrets.py`: the file's mode and expiry; masking after a save and after a restart; the names
  refused; a value's spaces stripped; a forgotten one gone; the folder among the guarded files.
- `tests/smoke/test_ask_secret.py`, on a real server and a scripted run:
  - the card is asked;
  - the value saved through the route reaches the next command's environment;
  - it is found in no event, approval, message or tool result, and in no file of the home but the chat's own;
  - `/decision` refuses to approve the card;
  - a skip tells the run so;
  - a value pasted with spaces and a line end is held and masked without them;
  - a run of another chat that reads the folder, by a command and by `list_dir`, is refused; a `yolo` one reads it
    masked, in its events and its history.
- The card in Chrome: its title, why and how, a box of type password, where the secret goes, Decline. A value too
  short to mask is kept on the card, unsent. Once saved, the card leaves the conversation, the run ends done, and the
  page holds the value nowhere.
- With the executor's mask taken out, the end-to-end test fails on the chat's history.
