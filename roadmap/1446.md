### 1446. Foreground quiet: the app draws no banner for the chat the owner is reading

**Status: done (2026-11-24).** With the activity lease (item 1440) the daemon keeps the end of a task from a phone whose app is in
front of the owner, but it still pushes what asks something (an approval, a question, a secret) whatever the lease says, and the
app's `willPresent` drew every alert it was given, banner, list and sound, also for the chat the owner was reading: a question
Dot asked in the chat on the screen rang over its own card. A good agent app's phone keeps its ordinary alerts quiet in the
foreground the same way; the lease and the app should agree.

What changed: `Core/ForegroundQuiet.swift`. `ForegroundQuiet.presentation(appIsActive:runIdsOnScreen:alertRunId:)` is `quiet` only
when the app is active, a chat is on the screen and the run the alert's route names (`#/runs/<id>`, read by `runId(inRoute:)`,
which moved from `AppModel.swift` to `Core/Policy.swift` so that its tests run without the app) is one of that chat's runs or
its helpers'; everything else is a `banner`: an alert about another chat, one that names no run (a campaign, a schedule, Dot's own
message: it is not known to be about the chat), every alert while the app is inactive (a system sheet, the app switcher: the
owner may not be reading) and every alert while the list or Settings is on the screen. `NativeStore.runIdsOnScreen()` gives the
runs of the chat on the screen (the roots and helpers the chat's state holds, and the newest run the list names; the chat on the
screen is the one the lease says, `chatOnScreen`). `AppDelegate`'s `willPresent` answers `[]` for `quiet` (no banner, no sound, not
added to the list of alerts) and `[.banner, .list, .sound]` for `banner` (as before), on the main actor and at once (item 1114's
rule: the completion handler form, called on the main thread); what the alert may have changed (item 1442) is read after the
answer, not before it, so a banner never waits for the network.

Checked: `ios/DotTests/ForegroundQuietTests.swift` (8 cases: the chat's own run and a helper's are quiet; another chat's run, no
chat on the screen, an inactive app and an alert about no run are banners; the routes that name a run and those that do not; the
one quiet of the lease and the app) and the existing `runId(inRoute:)` cases of `ChatStateTests`. `xcodebuild test` on the iPhone 17 Pro simulator (iOS 26.5), the whole suite: 368 tests, 0 failures, this item's 8 new cases among them.
Not checked: on a phone. `willPresent` and its answer need a real alert (the simulator gets no APNs; `xcrun simctl push` was not
used), so that no banner shows for the chat on the screen and one shows for another was not seen; that a helper's alert names a run
the open chat has loaded (a helper not yet read by the chat is a banner, which is the safe side).
