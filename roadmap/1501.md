### 1501. `code_run`: Python the model writes calls its tools through the run's own gate, as a shell line to the policy

**Status: done (2026-11-24).** The tool of code mode (the design is in `roadmap/1500.md`): the model writes Python, the
code calls the run's tools in the sandbox of item 1500, and only what it prints reaches the model.

**As built.** `codemode/tool.py` is `code_run` (`code`, `title`, `timeout_s`; modes `task` and `chat`, not parallel, the
step's limit an hour). Its action is `ActionInfo(kind="shell", risk="medium", summary="Run code: <first line> (N
lines)", target=<the scratch folder>, body=<the whole code>)`, the kind and the risk of the same text run as `python3 -c`
(a test asks `assess_shell` for the risk and holds the two equal), so every approval mode, the owner's rules (their
expressions are matched against the summary, the target and the body) and the review treat it as they treat a command.

*The path of a call.* The executor (`agent/executor.py`, which the loop and the doors of Claude Code and OpenCode share)
gives the tool `code_run`, and no other, a `NestedCalls` in `ToolContext.nested` (`codemode/inner.py`): an object of its
own (`_Nesting`) that runs each call the code makes through `_execute_one` itself, with the run's own registry, context and
real gate, the run's tool list (`run_tools`, in the run's mode) and the tool's own timeout. So a nested call is validated,
classified, checked against the other runs, judged by `RunGate.authorize_recorded` (with the call's arguments: the secret
a tainted run would send out is refused here as for the model), run, observed for taint, masked of every secret Dot holds
(`known_secrets`), and recorded in its two events, the undo journal where a tool writes files, and the facts of the run:
there is no second path. `_execute_one` takes a `parent` (the id of the `code_run` call) that adds `"via": "code"` and
`"parent_call_id"` to the two events and makes the call's id the parent's, a dot and its number; `ToolOutcome` gains
`waited_s`, `refused` (the gate, the owner or the review refused it) and `nested` (the calls a tool made in it), and
`with_nested` flattens them for `with_outcomes` in `agent/loop.py`, so that the facts the run checks its answer against
(the files written, the failed calls) include what its code did. A call made in code is handed no nesting of its own
(`parent is not None`): code cannot start code, which a test shows with the deny list switched off, and which the first
version of this item did not hold (an inner `code_run` ran: found by that test, fixed in the same commit).

*What the code is told.* A call the code makes is answered by the bridge: refused where `codemode/deny.py` says
(`code_run`, `finish`, `ask_user`, `ask_secret`, `browser_captcha`, `use_tools`, `update_plan`, `mark_plan_step`, `react`,
`delegate`, `consult`, `message_agent`, `assign_work`, `work_orders`, `review_work`, `create_agent`, `create_team`,
`send_to_chat`, `pass_reply`, `wait_until`, the four `campaign_*` and the families `terminal_`, `meeting_` and `phone_`,
each with its reason, and without the gate being asked), or run as the run's own. A refusal by the gate, the owner or the
review comes back as `dot_tools.ToolRefused` with the gate's words (`PolicyDenied`, `ApprovalRejected`, its subclasses
`ApprovalNoted` and `ApprovalParked`, and `HandedOff` are the refusals: `ToolOutcome.refused`), a failure as
`dot_tools.ToolError`. A result marked untrusted marks the run tainted as the call ends, so the next call of the same code is
judged under it, and marks the result of the `code_run`. An approval asked from code reaches the owner as any other and the
code waits, the wait not counted against its time. The results the code reads are not cut to the model's budget: the
nested context has `output_chars = [code] result_chars` (5,000,000, config), so an MCP answer is not spilled to a file
(item 494) and a page is not paged; masking still comes before the cut. A picture a tool gives is written into
`scratch/images/` (through `Tree`) and replaced by its path.

*What the model reads.* `result_of`: what the code printed (stdout and stderr in order, a head and a tail with a note
when long: `[code] output_chars`, 8,000), a footer `[N tool calls, X s]`, and for each way a code can end that is not its
own end a headline that says why and what to do (its traceback, with Dot's paths said short: `<tools>`, `<scratch>`,
`<python>`, `<workspace>`, `<dot home>`, `~`; its own time; its memory; its calls; a frame that is not a call; the run's
Stop; its output; its scratch folder; a sandbox that did not start). A code that fails to end by itself is an error
result.

*Where it is offered.* `runtime._tool_groups` (while `[code] enabled`); `group_of("code_run")` is the core group, which
`test_tool_groups` names now. The door of Claude Code gives it as it gives every tool of its mode. The system prompt
teaches it in a static section when the run has the tool (`agent/prompt.py:code_section`, also in the door's prompt
through `team_sections`); the tool's description is 1,064 characters. The `[code]` table is added here, since the tool
reads it (`CodeConfig`, `defaults.toml`): `enabled`, `max_seconds` (1 to 900), `max_mb`, `output_chars`, `max_calls`
and `result_chars`. `dot_tools` gains `call(tool, **arguments)` and a catalogue (`dot_tools/_catalog.json`, made by
`codemode/catalog.py`) that `search_tools` and `list_servers` read; the tool is called by its bridge name here, and the
typed function of each tool is item 1502.

**Checked by** `tests/unit/test_code_run_gate.py` (22 tests, the real executor over a gate that records what it is asked
and stand-in tools, the real interpreter in the real sandbox; macOS 26.6.2): the action is a shell line and `medium`
as `python3 -c` is; each call of the code is judged by the gate, one by one, with the arguments it carried, and the gate is
asked the same of each as of the same call made by the model; a refused call reaches the code with the gate's words and
its tool never runs (and the same refusal read directly says the same words); an owner who takes longer than the whole of
the code's time (1 s) to say no, and one who says yes, are both waited for; an untrusted result taints the run before
the next call and marks the result; the events (`via`, `parent_call_id`, ids, order) and the code step's own record; results
are not cut for the code and are for the model, and are cut at `result_chars`; a secret Dot holds is masked in what the code
reads, what it prints and the events; every name on the deny list, with its reason, without the gate asked, and each a tool
Dot has; `code_run` from code with the list switched off; 201 calls (the gate sees exactly 200); the run's Stop while a step
waits for the owner; nothing runs without the executor's caller, with `[code] enabled = false`, or where the sandbox cannot
start, and the twin runs; the facts include what the code did; a traceback tidied and no path of Dot's home; the output
cap; a picture; a tool the run was not given; `search_tools` and `list_servers`; a poll and a filter over 10,000 rows. And
`test_code_run_result.py` (the result for each ending, the paths, the cap, the settings and their bounds, the Python names of
the tools and a server named `dot`, the removal of old folders), `test_code_bridge.py` (a fault in answering a call kills
the code at once and is raised: found by the first run of the test above, where the code waited out its 120 s),
`test_prompt_cache_stable.py` (the section is the same whoever started the run, and absent without the tool),
`test_tool_groups.py`. The whole unit suite (8,350 tests) passes; `dotx eval check` passes.

Not verified: a run on the Claude plan or OpenCode that calls `code_run` (the door calls `execute_calls` as the loop does,
and the facts are Dot's own loop's alone); the approval card shows the nested step as any other, with no word that it comes
from code; the web UI draws the nested calls as rows of their own after the code step's row (item 1507 nests them).
