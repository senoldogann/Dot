### 1959. The owner's own Safari, driven like Dot's Chrome: a page's elements with refs, batches of steps, the same policy

**Status: done (2026-11-26).** The owner's word: "make computer use and browser use fast, without losing quality".
Their Apple Developer run (run_mwxgssp4_e1839b) signed in through Safari's AutoFill and then drove Safari's pages with
the desktop tools: 53 calls in 322 s, 208 s of it the model's (3.7 s a call), 24 `desktop_act` (49.3 s), 13
`desktop_screenshot` (35.8 s, one of 21.9 s) and 9 `desktop_snapshot` (5.5 s); the pages' part alone was 33 calls and
about 166 s. Safari was a good place to go (the owner's session, their AutoFill); Dot drove it far worse than Chrome.

#### What must hold, and the choice

- Safari is driven in the owner's real tab, with their session: that is why a run goes to Safari at all.
- Turning a Safari setting on is the owner's one-time step: Dot finds it off, says exactly where, and never flips it.
- A step is classified exactly as `browser_act`'s is (the same flags: a payment, a message sent, a public post, a
  credential); a password or card field follows Chrome's rule; Dot's vault is not filled into Safari.
- No new ask and no new wait in yolo or free mode.
- A page Dot's Chrome may not open is not read nor acted on in Safari: Dot's own interface above all, where the owner
  may be signed in and a run could press its own approvals.

Two ways were tried, each in a throw-away folder, without touching the owner's windows:

| | `safaridriver` (WebDriver) | AppleScript `do JavaScript` in the owner's tab |
| --- | --- | --- |
| The owner's session | No: a separate automation window with its own ephemeral data (no cookies, no sign-ins, no AutoFill); one session at a time; touching the window ends it | Yes: the page of the tab the owner has open |
| Setting | Develop › "Allow remote automation" (off here); a session asked for while it is off still starts Safari: 2.8 s, then "session not created" | Settings › Developer › "Allow JavaScript from Apple Events" (off here); Safari answers `do JavaScript` with "You must enable 'Allow JavaScript from Apple Events' … (8)", in English, measured on this Mac |
| Pointer and keyboard | WebDriver's own input in its window | none: the script acts in the page, so nothing waits for the owner to step away (item 1890) |
| What it reaches | every frame | the page, frames of its own site, open shadow roots; not a frame of another site, nor Safari's own windows |

Chosen: `do JavaScript` in the owner's tab. Without the session there is no reason to use Safari over Dot's Chrome, and
WebDriver has none.

Reliability, measured: the page script, run in WebKit (Safari's engine, Playwright's build) against a fixture page,
passed every case: a read of 12 controls in 35 ms (a page of 3,000 controls: 182 ms, 300 listed), a field that keeps its
value in the page's own state as React does (the native setter and an input event), a checkbox drawn by its label, a
dropdown by its label, a contenteditable editor, a field and a button in a frame of the same site, a button in a shadow
root, a `div` with a pointer cursor, Enter that sends a form, a ref the page lost and the refs kept from one read to
the next (12 of 12). The way to Safari: `osascript` with a script for automation takes 0.12 to 0.3 s a call here; a live
probe opened a window of its own in Safari (5.8 s with Safari's launch), met the setting's refusal on the read (0.6
s), closed its window and quit Safari, which was not running before (Safari's "reopen windows" is off on this Mac, so
nothing of the owner's was lost).

#### What was built

- `dotagent/safari/`: the page script (`page_script.py`, one command a call, a JSON answer), its answer's models
  (`types.py`, validated before any field is read: the page is untrusted) and the adapter (`desk.py`, `SafariDesk` on
  the runtime as `runtime.safari`): a chat keeps the tab it started in (the front window's current tab the first time,
  by Safari's window id and the tab's place), opens an address in a tab of its own (a new tab the first time, then that tab while it still shows what Dot
  last saw there; a tab of the owner's is never loaded over) and waits for it to load, and
  runs a step only while the tab shows the address it was read on; a closed tab or one moved to another page makes the
  run read again. A step carries the name its element was read with, and the page refuses it when the element no
  longer shows it. No script is sent to a tab whose address `check_browser_url` refuses (Dot's own interface, a
  blocked host, a host outside `allowed_hosts`), and a document's own address is judged again before its answer is
  used, so a page still loading over the one before cannot stand in for it.
- `tools/safari.py`: `safari_open`, `safari_read` (elements and text, with a query) and `safari_act` (click, fill,
  select, check, uncheck, press, scroll_into_view; `expect_text` per step). A batch's result says per step what was
  verified (a field holds what was written, a box is ticked, the expected words showed) and shows what changed: the
  new or changed elements and the new lines of text, or the whole page when it went to another address, where the
  batch stops.
- The classification is browser_act's own: its tail (the typed judge on a click whose label no pattern knows, one
  payment a call, one paced public action a call, a payment's amount from its labels and the page's total) is now
  `judge_batch` in `tools/browser.py`, which both tools call; each step is assessed by `assess_step`, Enter in a field
  by the buttons of its form or of its nearest small ancestors (`near`, as `controls_near` reads Chrome's snapshot),
  and a key that names no field goes where the batch last put the focus (`keys_go_to`). No line under `policy/`
  changed.
- A field the page marks secret (`password`, or an autocomplete token of a password, a one-time code or a card) takes
  text as in Chrome: in a yolo or free run with `credential` or `financial` on the record through the gate, in every
  other mode only text the owner wrote in the run. A secret field's value is shown by its length alone, in every mode:
  Safari's AutoFill puts the owner's own passwords there, which no model reads, as none reads a login filled from
  Dot's vault.
- The setting off: the call says "Settings… › Advanced › Show features for web developers, then Settings… › Developer
  › Allow JavaScript from Apple Events", and to tell the owner and go on with the desktop tools or Chrome; Dot's
  Automation permission refused (-1743) says where in System Settings.
- The tools are in the desktop group and exist where the desktop's do; the prompt's Desktop section names them.

The review of the first push (fixed in this item): an open took the chat's tab by its place alone and could load
over a tab of the owner's; an answer of the page that failed to validate, and an error a page made the script throw,
were quoted in the error, which reaches the model unfenced (now the page's words never are, and the script clips
every field it sends); `docs/runs.md` named the desktop group without the Safari tools; the Safari tools now count as
the browser's channel, in `dotx stats`' acts and the one-step steer; a batch starts steps for 75 s at most, inside its
120 s timeout, and reports the steps it left; an error after a step went out keeps the batch's report, with the error
on the step it stopped at.

What the page script cannot promise: it runs in the page's own world, so a page that wants to can misname its elements
to it, as it can to Chrome's snapshot through its labels; Safari's own windows (AutoFill, the password sheet, a
download prompt) and a frame of another site stay with the desktop tools; its key presses are a script's, so they put
no character in a field (text goes in with fill).
