### 808. Browser isolation: the cheap boundary now, the expensive one only if an agent needs it

**Status: done (2026-10-28).** The owner answered the isolation question: "En performanslı, en karışmayacak, en doğru
düzen ne ise o olsun. Aşırı mühendisliğe gerek yok." The audit's P1 said every run shares one Chrome profile; a per-run
context would isolate cookies but make the owner sign in again in every run, and a profile per agent would need a Chrome
restart and a profile picker.

- **Decision.** Normal task and research runs keep the shared profile: one sign-in, one Chrome, tabs per conversation
  already separate (`ThreadTabs`). Eval attempts already run in a throw-away `DOT_HOME` with `DOT_CHROME_DIR` under it,
  so they start with no cookies and never touch the owner's profile.
- **The risk is named, not hidden.** A malicious page or prompt injection in one run can use the cookies of another
  run on the same profile; the answer stays page-level trust, approvals before sensitive actions, and the vault.
- **The later path.** If the owner wants a stronger boundary, start with a profile per agent (`[browser] profile`), not
  a context per run: it keeps sign-ins, gives Chrome's strongest boundary, and changes one page (the agent picker). The
  cost is a restart when two agents with different profiles run at once, which is why it is not the default.
- **Measured.** `tests/unit/test_browser_isolation.py` proves an eval attempt gets `DOT_HOME` and
  `DOT_CHROME_DIR=<home>/chrome`, and the process environment is restored; `docs/browser-isolation.md` records the
  decision. No runtime code changed, because the cheap boundary was already there and the expensive one is not what
  the owner asked for.
