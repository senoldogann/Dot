### 1361. Dot for iPhone, second slice: new chats, a chat's model and level, older messages, a step's detail, a message's actions, drafts, dictation, and a chat opened from the Live Activity

**Status: done as a second slice (2026-11-23); what is left is listed at the end.** The owner asked for the iPhone side
of Dot to be a complete native SwiftUI app, the web UI staying. The first slice (item 1353) listed what it left to the
web UI; this takes the first three of those and the Live Activity's tap. Read `ios/README.md` for how each part works;
what follows is what was decided, what was found and what was measured.

**What was decided.**

- **A new chat is `POST /api/runs`, written as the web's home writes it** (`views/runs.js`, item 1350): `goal`, `mode`
  `auto`, `model` and `effort` when picked (left out otherwise: the daemon's own), `thread_id` null (a message from the home
  starts a chat of its own, never the last one's), `agent_id` for an agent's first message, a `key` that is kept while the
  same words are sent again after a lost answer. A 422 that names a `model` and a `problem` (item 1350's refusal) is read
  into its words and its `fallback`: the words stay in the box and a button sends them on the default model.
- **A chat's model and level are the chat's, kept by the daemon**, not a default: `PATCH /api/threads/{id}` with `choices`
  (all six keys, nulls included: the daemon requires them), the chat's `RunDetail.choices` read back. The daemon starts a
  message on what the message names, so every message of the chat now carries the chat's choices and its `agent_id`, as the
  web composer's do. Before this, a message from the phone in an agent's chat ran as Dot's (no `agent_id`) and always as a
  task on the default model.
- **Older messages need a cursor the daemon did not have**: item 1360 adds `before` to `GET /api/runs`. Pages of twenty,
  put above the first row; the transcript is scrolled back to the row that was first, so the reader keeps their place (built on `scrollTo(anchor)` when the first row's id changes; the simulator test reads the pages and reaches the chat's first message, but no test measures the place held: a finger keeps dragging through the insertion, and it was not verified numerically).
- **A step's detail is read on demand from its two events**, not kept: the cache slims results to 240 characters, and a
  detail is rare. The row keeps the id of its call event, so the read starts there and ends at the result (five pages of
  200 at most).
- **A hold on a message is a context menu** (Copy, Select text, React, Edit from here), with the text selection that a
  hold used to start moved to its own sheet: the two cannot share a gesture. Reactions are the web's seven on what Dot said
  (`answer`, `step-n`); Edit from here is `rewind` with the files kept, asked first, not while a run works, and a chat
  rewound to nothing leaves its words in a new chat's box.
- **Dictation never sends audio away**: `requiresOnDeviceRecognition`, and a language with no on-device recognizer fails
  with words instead of falling back to Apple's servers. Permissions are asked at the first press.
- **A Live Activity opens a chat by `dotagent://run/<run id>`** (`CFBundleURLTypes`; the widget's `widgetURL` for the card
  and `Link` for each row; the card opens the run that waits for the owner, else one at work, else the first). A URL scheme
  is a door any app may knock on: the link is parsed strictly (`DotDeepLink`) and opens a run's chat and nothing else.

**What was found by running it** (the iPhone 17 Pro simulator, iOS 26.5, a scratch daemon with a scripted model; XCUITest
taps):

- **The open-a-run path of slice 1 cancelled its own request.** `ChatListView` cleared `pendingRunId` before reading the
  run, and the task is keyed on that id, so SwiftUI cancelled the request (`-999`) and the tap showed "Could not open that
  run" (every time in the simulator test, at the mercy of timing otherwise). It clears the id once the chat is open now,
  and a cancelled task says nothing.
- **A page cursor rounded to the microsecond repeated the run it was read from** (item 1360).
- **Dictation stopped the app with an actor assertion** at the first permission prompt: a closure formed in a main-actor
  class and called by the system on its own queue. The permission requests, the audio tap and the recognizer's handler are
  built outside the actor (Swift 6).
- **The simulator has no usable recognizer**: with both permissions given, a press of the microphone ends in "Dictation is
  not available now"; listening itself is not verified here (no real iPhone).

**Checked.** `xcodebuild test -scheme Dot` (the unit tests: 70 of slice 1 and 55 new: the requests as the daemon takes them,
the choices rules, older runs in the state and in the session against a stand-in network, the step's detail and its
clipping at a character boundary, the message actions, the drafts and their file, dictation's gate and words, the links
and the card's choice of a run) and `xcodebuild test -scheme DotUI` (ten tests, taps in the simulator, on a scratch daemon and an app installed fresh: the older messages read page by
page down to the chat's first message, a step's detail, a hold's menu and a reaction that stands (the daemon's list checked),
a new chat on the model and level picked (the run's record checked) and one chat only, an agent's first message (the run
carries the agent), a chat's model and level kept by the daemon (its `choices` checked), a draft that comes back after the
app was terminated, a link that opens a run's chat, the microphone with the permission refused and with it given);
`tests/unit/test_runs_before.py`; `ruff`, `mypy`.

**Not done, in the order they should come:** (1) a secret's card and the web's other kinds of a message (a draft for a
message to send, a file); a queued message's edit; (2) agents (make, pause, resume) and teams, campaigns, memory, rules, the
vault; (3) pasted images and files beyond photos; (4) iPad and landscape layout; (5) a SwiftData or SQLite store if the JSON
files outgrow their 400 events; (6) a Live Activity row that is its own control (an approval answered from it); (7) a real
iPhone's check of listening, of a tap on the Live Activity and of the notification's Open action: the simulator draws no
Live Activity and receives no push.
