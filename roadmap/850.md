### 850. In a chat Dot opened on its own initiative, a message, a post or a release waits for the owner, yolo too

**Status: done (2026-10-30).** **Asked** by the owner, through the agent of their AI-Notepad project, after a day of
Dot's own initiative (item 715) on Gistsmith:
- a local build put live by hand, `wrangler pages deploy` of a `build:local` folder: every canonical address said
  `localhost`;
- a post on the owner's LinkedIn that said of the product what it does not do;
- a channel's rule never checked;
- the posting plan's own hours not kept;
- a branch switched in that project's main checkout, where other agents worked.

Asked the scope, the owner chose (AskUserQuestion, 2026-10-30):
- "Yolo yine bir şey sormasın ama sadece önemli kritik durumlarda bir soru sorulması çok da problem değil, email gibi
  veyahut bir proje etkileyen şey gibi".
- Of where: "Sadece Dot'un inisiyatifi sorsun". Their own chats and schedules, which send mail and job applications
  on their own, ask nothing, as before.

Measured in the store:
- Every run of the day was yolo.
- The post (`browser_act` insert and click "Yayınla" on linkedin.com/sharing/compose) carried `public_post` and was
  waived as yolo waives it (item 443).
- The deploy (`npx wrangler pages deploy`) carried no flag of its own.
- The run that posted was not the initiative's run: it was the run the owner's answer to its question started in the
  same chat ("Ben yayınlayayım"), source `ui`. A rule of the initiative's runs alone would not have held it.

**What must hold.** The kernel and the code hold this; no model and no rule of the owner's answers it:
- In a chat whose first run was Dot's own initiative (`INITIATIVE_SOURCE`), every run asks before a step that carries
  `message_send`, `public_post` or `release` (below). That covers the initiative's runs, the runs the owner's answers
  start there, and the runs they delegate.
- It asks the owner whatever the run's approval mode, yolo and auto included. The review model never answers it, and
  an owner's rule that allows the step does not let it through. A rule that hands the step off is stricter, and a
  refusal stands.
- The question is the guard's own (item 429): the card shows the step as the policy reads it, and the owner's yes is
  for that step alone. A kept answer holds for the same fingerprint (item 483), as for any question, and no other
  step.
- Nobody watches such a run. Its question waits while the run waits; unanswered in time it is a refusal, and the run
  goes on with what is left. With `[policy] unanswered = "park"` a release is kept for the owner in the chat (item
  482); a message or a post never is, as a later yes covers no step that reaches other people (item 483).
- The chat is one Dot opened on its own initiative by the source it was made with (`threads.source`), which nothing
  changes, a rewind neither.

**What only asks: the release names.** The shell guard reads `release`, a project's change put live, from the names it
can read:
- `wrangler deploy`, `wrangler pages deploy`, `wrangler versions deploy` (and their `publish`), a runner's pinned
  version too (`npx wrangler@3`);
- `vercel` with `--prod`, `vercel promote`;
- `netlify deploy --prod`;
- `firebase deploy`;
- `fly deploy`, `flyctl deploy`;
- `gh pr merge`;
- a `git push` that names `main` or `master` (or `HEAD:main`, `--all`, `--mirror`).

Outside a chat of Dot's initiative, `release` changes nothing: it is no question of any mode or preset.

What the guard does not read, as the docs say:
- a `git push` with no branch named, from a checkout on main;
- a deploy run by a script or a `package.json` script (`npm run deploy`);
- an API called with `curl`;
- a web console clicked in the browser.

Those go by the run's instructions (item 851), not by the guard. No spelling is chased past these names (item 540).

**What the instructions say (item 851).** For every run:
- publish through CI;
- say only what the product's own source says;
- work in a worktree of one's own in another project;
- keep one's own plan or say first.

Rules that a guard cannot read go there, not into the kernel.

- `policy/types.py`: the flag `release`. `policy/shell.py`: the release names as `release` (a push to main keeps its
  `upload` too).
- `policy/engine.py`: `initiative_guard(info)`: the owner's question for a step of `message_send`, `public_post` or
  `release`, outside the preset's sets and rules.
- `agent/gate.py`: `RunGate(..., owners_word=...)`: such a step goes to the owner in every mode, never waived, never
  to the review model, its question or a stricter hand-off alike. `agent/manager.py`: set for a run of a chat made by
  the initiative (`Store.opened_by`), and for the helpers of such a run.
- `docs/safety.md`, `docs/proactive.md` say so.

**Checked.**
- `tests/unit/test_shell_release.py`: each name read as `release`, its look-alikes not (`wrangler dev`,
  `vercel` without `--prod`, `gh pr view`, `git push origin feature`).
- `tests/smoke/test_initiative_asks.py`, on a gate of such a chat:
  - a step of each flag asks the owner, in every mode;
  - an auto step does not reach the review model;
  - a rule that allows it does not answer;
  - a hand-off (a rule's, or a step's that also carries a credential) reaches the owner as a hand-off in yolo too;
  - a refusal stands;
  - outside such a chat the same yolo step is waived as before.
- The same file, on real runs: the initiative's run and the run of the owner's answer in its chat both wait for the
  owner before a release, and a chat of the owner's does it at once in yolo.
- The independent security review of the first push found the hand-off going through in yolo, and a runner's pinned
  version (`npx wrangler@3 deploy`) hiding the name. Both are fixed and tested; the yolo hand-off test fails without
  the fix.
