### 1401. A schedule counts the firings skipped in a row, and says it where the owner looks

**Status: done (2026-11-24).** Found by the autonomy audit (`workspace/autonomy-audit-2026-11-23.md`, finding 5). The
loop that merges pull requests (`*/10 * * * *`) was skipped 27 times in one day, the next schedule 11 times, because
the chat a firing goes on in had a run at work (`schedule_skipped_chat_busy`, item 723: no failure, nobody told). The
only trace was the schedule's last status, and item 1355 already made the chat's Automations say "Last firing
skipped"; how many in a row needed a field of the store.

What changed: `schedules.skipped_in_row` (`INTEGER NOT NULL DEFAULT 0`, added at open like the columns before it, so a
schedule from before has skipped none; `ScheduleRecord.skipped_in_row`, 0 by default). Every firing that starts no run
adds one: those `record_schedule_skip` moves on (the emergency stop, a paused agent, a task still going, a late firing)
and the one the chat-busy path refuses after the claim (`count_schedule_skip`, which also writes the status). The first
firing that starts a run clears it (`clear_schedule_skips`, called where the run's status is written, whether or not
the run is still at work), and switching the schedule on again or changing it starts it afresh, as item 458's row of
failed runs does; a run by hand is no firing and leaves it. The count is every skip's, not the busy chat's alone: the
status beside it names the reason of the last, and a count that left out "the previous task was still going" would
disagree with it.

Where the owner sees it: the chat's Automations say "Skipped 5 in a row" for the last result (Turkish: "Üst üste 5
çalışma atlandı") from two on, where one skip keeps "Last firing skipped"; the Schedules page's row has an amber badge
"Skipped 5 in a row" beside the last status, from two on; `dotx schedule list` and the model's `schedule_list` add
"(5 skipped in a row)" to the last result. The record carries `skipped_in_row` in `GET /api/schedules` and in a chat's
automations.

Checked: `tests/unit/test_schedule_skips.py` (the store counts both kinds of skip, a skip that finds the schedule
changed counts nothing, a start clears, none to clear writes nothing, a deleted schedule counts for nobody; switching
on or changing starts afresh, switching off keeps it; the line says it from two on), `tests/unit/test_store_schema.py`
(the new digest is pinned, and a schedule stored before the column reads 0 and counts on from there),
`tests/smoke/test_scheduler.py` (three skips for a busy chat count 1, 2, 3, the emergency stop's makes 4, the firing
that starts a run ends it at 0; the overdue and emergency-stop tests and `tests/smoke/test_agent_pause.py` say 1),
`tests/js/automationwords.test.js`, and `tests/smoke/test_schedule_skips.py` in Chrome at 1280 light and 390 dark (the
Automations line and the Schedules badge, none for a single skip, nothing wider than the screen). `ruff`, `mypy`,
`npm run check`.
Not done: a one-time schedule that is held ("waiting: ...") is waiting, not losing firings, so it is not counted; the
iPhone app is a client of its own and is not changed here.
