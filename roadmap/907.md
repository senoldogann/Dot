### 907. Work orders: the lead hands work out, keeps track of it, judges what comes back and chases what stalls

**Status: done (2026-11-01).** **Asked** by the owner (2026-11-01): Dot should run its agents as a CEO runs staff: hand
work out, keep track of it, review what comes back, send it back or reassign, chase what stalls, and report.

What there was: `message_agent` blocks the sender for up to an hour for the answer and leaves no record (no status, no
count of tries, no due time); `agents_now` and `read_agent_chat` show a snapshot.

- Store: the `work_orders` table and `WorkOrderRecord` (id `wo_…`, agent, title, brief, what done means, objective,
  status, tries and the run of each, the run and chat that assigned it, the run that started the newest try, due time,
  `tainted`, last note); `move_work_order` moves it only the ways `WORK_ORDER_MOVES` allows, and only when it stands
  where the caller read it and (for an end) the run is its newest try's, so that a try ending late cannot undo a
  verdict and two verdicts at once do not both apply.
- `agent/orders.py`, `WorkDesk` (one per run manager, `manager.desk`): `assign` records the order and starts the try as
  `message_agent` starts a run (`RunManager.delegate`, a delegation of the lead's run, as untrusted as it is), without
  waiting: the task that follows the run belongs to the order, so the lead's turn may end while the agent works;
  `review` is the lead's verdict (`accept`, `return`, `reassign`, `escalate`, `cancel`; the third return goes to the
  owner, a reassignment after six tries too); `follow_up` is the scheduler's tick, with no model: an order `working`
  whose run failed, was cancelled or was lost with a daemon that stopped, one whose run never started and one past its
  due time go to `in_review` with a note. A try's end sends the order to `in_review` and tells the lead in a note
  (`manager.tell(…, "note", taints=…)`) when a run of its chat is at work (`RunManager.live_run_in`); a lead that is
  not at work finds the order in `work_orders`, and the morning brief lists the orders that wait for review for more
  than a day and those waiting for the owner.
- Tools `assign_work`, `work_orders`, `review_work` (`tools/work_orders.py`), core group, offered where `message_agent`
  is (dropped with it when there is no agent and none may be made; never for a delegated run), classified as a
  delegation, safe, as `message_agent` is: nothing in the policy widened. `dotx run` refuses them (its runs end with the
  process). An agent that leads sees and judges only the orders its own runs handed out. Secrets Dot holds are masked
  in what an order stores.
- Taint: a try that read content third parties can author marks the order and its note (the answer is fenced and the
  note taints the run that reads it, as item 902's does); `work_orders` fences such an order and marks its reader; the
  lead's own taint marks the order, the title of a tainted order is counted and not quoted by the brief and the look;
  the owner's escalation tell leaves the lead's words out for such an order. An agent's answer is never the owner's
  words: the notes vouch for nothing.
- Stop: the run manager tells the desk when a run of a chat ends cancelled (`_stop_orders_with`, `WorkDesk.lead_ended`):
  the owner's Stop or the emergency stop stops the attempts at work on that chat's orders and cancels them, as a run's
  Stop stops what it delegated (the pre-push review: the desk's task had made the lead's cancel miss them); a turn
  that ends on its own, or the daemon's stop, leaves them. An attempt the emergency stop ended cancels its order.
  A return or reassignment whose start fails leaves the order `in_review` with a note, an order left `assigned` or
  `returned` by a process that died is sent to review by the follow-up, and a return on an `assigned` order says so
  in a `ToolInputError`.
- Second pre-push review: an attempt of a tainted order starts untrusted whatever run starts it
  (`RunManager.delegate(tainted=…)`, `RunOpening.tainted`), `review_work` marks the calling run as `work_orders` does,
  and the notes of an end or a follow-up use the order's taint with the attempt's; escalating an order at work is
  refused, an escalated order allows only `cancel` (the moves table too), a Stop also cancels an order in review whose
  run still works, the return count says it counts every try, and the limits on open orders are checked and inserted
  under a lock so that orders given in one step cannot pass them together.
- `GET /api/work-orders` and a read-only **Work orders** part on the Agents page (`js/workorders.js`, the words in
  `js/workwords.js`, tested in `tests/js/workwords.test.js`).
- The lead's prompt (`_team_section`) says how to manage: orders with a clear brief and acceptance, in parallel,
  judged against it, returned with notes, reassigned or escalated after repeated failure, the state told to the owner in
  one short first-person line.
- The context budget of a fresh home rose by 1,250 tokens for the three tools, the objectives' three (item 908) and the
  lead's paragraph (25,356 measured).
- `docs/agents-and-campaigns.md` (Work orders), `docs/runs.md`.

**Checked.** `tests/smoke/test_work_orders_for_real.py` plays it whole in the real loop with a scripted model (twice,
the second with the first try reading outside content): `assign_work` returns while the agent's run is at work and
the lead goes on; the order is `working`, then `in_review` and the lead's inbox holds the note with the answer; the
lead returns it and the second try's goal holds the brief, what done means, the earlier answer (fenced) and the notes;
the second answer is accepted and the order closed; the notes vouch for nothing and are tainted only when the try read
outside content; a cancel stops the run at work and its late end changes nothing; the lead ending while the agent works
leaves the run going and the next run finds the order in `work_orders`; the owner's Stop of the lead stops the
attempt and cancels the order. `tests/unit/test_work_orders.py` (the store's
moves, the desk with a stand-in manager: three returns escalate with no fourth run, reassignment, cancel, the follow-up
for a lost run, a late one and one never started, a lead that ended not told, the escalation tell leaving a tainted
lead's words out). `dotx eval check`; `npm run check`.

**The pre-push review, round 3.** The orders a Stop ends are ended under the same shield as the run's end, so a second
Stop meanwhile cuts nothing short (the tabs, the front app, the chat's queue still follow). Accepting or escalating an
order past its due time stops its run still at work, as the other verdicts do. A relay that ended is let go. Opening a
done or dropped objective again is held to the limit of active objectives (item 908). Round 4's nits: a reassignment
that cannot start leaves the order with the agent that had its attempts, and an older attempt let go when a newer one
began still marks the order when it read outside content.
