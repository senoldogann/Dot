# Dot voice conversation design

Design proposal · 2026-11-26 · Repository snapshot `5a4aae70b`

Repository links are relative to the roadmap copy in the checkout.

Open a foreground voice call with a specific bot on DotNext or on the Mac. The owner can speak while Dot is speaking, see live captions, and find both sides of the conversation in the chat. Requests for work enter Dot's normal run path. Scope covers one owner and one bot per call, with the same chat and run semantics as typed messages.

## Recommendation

Start with **B, Mac-based speech and Dot's existing model connectors**, with Apple speech at both ends. It shares one audio and chat flow across DotNext and Mac/web, keeps microphone audio on the owner's devices, and makes Turkish and English available without a new paid service. Put device-level capture, echo cancellation and playback in the client. Keep the normal run manager responsible for tools and approvals. Prototype warm recognition and synthesis with real recorded turns on the paired phone before freezing the public contract. A future iPhone-local audio path or an explicitly selected paid speech provider can use the same turn semantics once measured.

### Slice 1 result

The [Swift probe](../tests/smoke/voice_conversation_probe.swift) feeds 20 ms PCM frames in real time, waits 250 ms for the end of the turn (plus an optional synthetic silent tail), and uses a fixed 330 ms reply fixture standing in for the text model. The frame measurement ends at the first buffer with signal, before network downlink and speaker playback. No model or paid service is called.

Measured on an Apple M4, macOS 26.6.2, on a quiet Mac (load average under 25 at the start, `say` fixtures, Turkish Yelda and English Samantha). Values are milliseconds. "First use" is a fresh process with a cold analyzer and synthesizer (language assets already installed); "prepared" is the same process after `prepareToAnalyze` and one earlier turn, nine trials per language (three per tail length).

| Locale and phase | Endpoint to final text | Synthesis to first signal | Last speech frame to first signal |
| --- | ---: | ---: | ---: |
| Turkish, first use | 52 | 452 | 1,115 |
| Turkish, prepared | 22 (12–34) | 15 (9–26) | 638 (620–655) |
| English, first use | 74 | 496 | 1,168 |
| English, prepared | 50 (39–67) | 15 (10–29) | 666 (653–685) |

The last column contains the 250 ms end-of-turn wait and the 330 ms reply fixture, so what the speech components themselves add is about 60 ms (Turkish) and 85 ms (English) when prepared, against about 530 ms and 585 ms on first use. Warm-up when the call opens therefore matters more than anything inside a turn: the first reply of a call pays roughly 0.5 s of cold synthesis that every later reply does not. An earlier run of the same probe while the Mac was at load average 100–300 (builds and simulators) gave prepared medians of 542 ms to text and 663 ms to first signal, with maxima of 5.5 s and 7.2 s; so the numbers above are the quiet-Mac case and a call needs the p95 measured under load before it is promised anything.

The last word was correct in all 20 turns of the quiet run, including the trials with no synthetic tail (0 ms) and with 200 ms, because per-turn end of input finalizes the analyzer; `test_voice_conversation_probe` asserts it for every trial. Three trials per tail length on two synthetic fixtures do not justify removing the 800 ms tail from production; repeat with real recorded speech, background noise and the paired phone. Timestamped finalization at the last sample of an open input stream stalled; per-turn end of input completed reliably and the prepared probe keeps the backing model across turns.

Transport: the existing authenticated `POST /api/voice/streams/{name}/audio` path on Mac loopback accepted twenty 50 ms batches in order, with request round trips of 1.3–7 ms (median about 1.8 ms) in two quiet runs and 5.8–370.8 ms (median 22.5 ms) under heavy load. The stand-in finalization request took 8–20 ms quiet and 267 ms loaded. Over the tailnet, ten discovery pings to a physical iOS peer took the direct path at 8–11 ms; discovery RTT is not media RTT, and a physical iPhone media trace remains open. The downlink (SSE control, captions and PCM chunks) is not part of slice 1.

Reproduce with `uv run pytest tests/smoke/test_voice_live.py -m live -k conversation_probe -q -s` and `uv run pytest tests/smoke/test_voice_routes.py -k fifty_millisecond -q -s` in a scratch Dot home.

### Latency and quality gates

Measure warm latency from **last audible owner phoneme to first audible Dot speech** on the client. Track session open to audio-ready, first completed turn, first spoken answer, and time from first confirmed interruption to last audible old response separately. A short task acknowledgment counts only against the task-ack measure. It must describe a real start, queue entry or wait state. An earcon or spinner is useful feedback and does not count as speech.

| Warm path for a short reply | Initial engineering allocation |
| --- | ---: |
| Endpointing after the last phoneme, while STT is already running | 250 ms |
| Last mic batch uplink and STT finalization remainder | 120 ms |
| Text model to first usable, redacted clause, including reply routing | 330 ms |
| Warm TTS to speech-bearing PCM | 100 ms |
| Downlink, jitter buffer and audio render | 150 ms |
| **Total target** | **950 ms** |

These are design allocations. Start end-of-turn tuning at roughly 250 ms with a short word-tail pre-roll/history and test 250–450 ms under normal pauses. Keep the synthetic tail if testing shows it preserves final words. Warm locale assets and synthesizers when opening the call, mark the UI ready only once capture and playback are usable, and record warm-up time. Test a warm analysis instance with `finalize(through:)` and stable audio timestamps. Apple documents that the result stream may still need draining after finalization returns. Only change to rolling helpers or keep an analyzer across turns after measuring correctness and resource use. [Apple finalization](https://developer.apple.com/documentation/speech/speechanalyzer/finalize(through:)) · [Analyzer preheating](https://developer.apple.com/documentation/speech/speechanalyzer)

Run at least 30 annotated warm turns per primary route across Turkish and English on Mac loopback, Wi-Fi/direct tailnet, and phone on cellular, with relay status tracked independently. For launch, aim for p50 under 1 s and p95 under 1.5 s on the direct path, with p95 local barge-in under 150 ms. Publish relay, Bluetooth, cold-start and task-start distributions separately. Record endpoint cuts, false interrupts, final-word accuracy, overlap, word error rate and proper-name/task-argument errors. Build a small owner-approved listening set with Turkish names, suffixes, numbers, English technical names, pauses, speakerphone and background audio. Score intelligibility and naturalness blind. Timestamp stages monotonically and correlate by IDs without collecting transcript or audio in logs. [Tailnet direct and relayed paths](https://tailscale.com/docs/reference/connection-types)

### Session, transport and audio

- Open a session scoped to the authenticated client, bot and chat. Core state is preparing, listening, responding and ended, with mute and playback tracked independently. Use monotonic input sequences and turn/generation identifiers. Bound frames, reorder window, playback buffer, idle time and session duration. Tear down audio and helpers on End, background, connection loss and paired-phone revocation. Reconnect creates a fresh audio session and restores chat state. Committed turn IDs survive transport retries.
- **Existing HTTP path first.** Test short, bounded, numbered HTTP audio batches carrying 16 kHz mono PCM, with 20 ms frames batched around 40–60 ms where practical, and authenticated SSE downlink for control, captions and bounded base64 PCM chunks. Keep media SSE separate from replayable run events. Use existing Tailscale Serve HTTPS and bearer headers and the existing revocation-aware HTTP guard. Use bounded pipelining or coalescing within the measured budget when RTT exceeds a batch interval. Validate the ordering and backpressure behavior on a physical phone and Mac webview before fixing frame sizes. At 16 kHz upload is 32 kB/s raw and roughly 43 kB/s after base64. At 24 kHz mono output is 48 kB/s raw and roughly 64 kB/s after base64, before headers. Slow links visibly end the media session once its bounds are exceeded.
- Dot's existing live run/chat stream is SSE. `LocalGuard` closes non-HTTP scopes, including WebSocket. If HTTP measurements miss the target, bring a separate binary media transport proposal to review with concrete RTT and backpressure traces, covering browser authentication, Origin checks, revocation, and lifetime binding. Keep pairing and guard semantics in force. [LocalGuard](../src/dotagent/server/guard.py) · [SSE](../src/dotagent/server/stream.py) · [Tailnet Serve integration](../src/dotagent/tailnet.py)
- On iPhone use one foreground `AVAudioSession` with `.playAndRecord` and `.voiceChat`, plus engine voice processing or Voice Processing I/O. Route mic and the output player through the processed audio graph so the system has a playback reference. Existing input route preference can inform selection. Test built-in speaker, receiver, wired and Bluetooth HFP, interruptions from calls/Siri and route changes on hardware. On web/Mac request browser echo cancellation and noise suppression, and use an AudioWorklet-controlled player so it can flush immediately. Speakerphone echo cancellation in Safari, Chromium and the Tauri webview needs separate validation. [Apple voiceChat](https://developer.apple.com/documentation/avfaudio/avaudiosession/mode-swift.struct/voicechat) · [Apple voice processing](https://developer.apple.com/documentation/avfaudio/avaudioionode/setvoiceprocessingenabled(_:))
- For barge-in, use near-end speech after AEC, with a short confirmation window tuned against missed syllables and false interrupts. Stop the player and drop queued PCM locally as soon as speech starts. Send the playback position and cancel the reply generation and synthesis for that generation. Ignore late packets for it. Keep the first words of the new turn via bounded capture pre-roll. For completed playback segments, the client acknowledges playback. Persist the interrupted assistant prefix through the last confirmed segment and label the turn interrupted. Where playback stops within a segment, record the interruption position in session state and avoid claiming exact audible text. Persist the entire committed owner utterance and completed assistant turn through normal chat history.

### Chat, tasks, settings and UI

- Give final owner speech a stable turn ID and use Dot's existing chat send or queue service with an idempotency key. Use the bound chat/bot settings, recent context and masked assistant text. A voice-specific reply should be short and generated without action tools. Prototype whether an ordinary streaming chat run can provide a suitably fast path. For a clear request for action, send the original committed words through normal task/queue handling. A prototype can classify with a constrained reply-or-handoff decision from the same fast model call, or use the existing explicit chat/task controls during the prototype. Dot's current composer Auto chooses task for most messages. Measure routing accuracy, queue timing and the first natural clause before choosing the production routing contract. [Mode rules](../src/dotagent/agent/mode_words.py) · [Run start](../src/dotagent/server/routes_runs.py) · [Thread queue](../src/dotagent/server/routes_queue.py)
- The voice session holds no direct tool privileges. An explicit owner utterance can request a normal run. Treat assistant playback, transcript fragments, background audio and captions as data. Use the run manager's actual acceptance as the source of a brief localized status such as “I started it” or “I added it to the queue,” with a visible link to the run when available. While a task works, the call can continue listening. End and barge-in cancel media/reply playback. Explicit run controls manage work. Route same-chat contention through normal queue semantics and surface a linked chat if normal routing starts work beside the current chat. Require normal UI approval for pending actions and show it on screen. Spoken “yes” may be conversation text. The standard approval UI records the decision.
- Persist final chat turns once with their ordinary role, provenance and turn/run linking. Persist neither partial captions nor audio. For an interruption, preserve the acknowledged assistant prefix and avoid appending the canceled text later. For a task handoff, let normal run creation own the submitted user message and link the in-call status to it, avoiding duplicate chat bubbles. Use a durable send key and drop empty/no-speech turns. Verify user transcript, assistant speech and task references agree after app reload or lost acknowledgments.
- Place **Voice**, **Speed** and **Language** per bot in DotNext's bot profile and equivalent Mac/web settings. Reuse a typed preference in the daemon's existing key-value store, including for the built-in Dot, so the selection follows the bot across devices without requiring a new table. Treat the exact schema, ranges and availability as prototype output. Suggested controls are locale-specific tested voice IDs with preview, bounded speed, and Auto / Turkish / English. Capture effective settings at call start. Filter against installed and tested voices and report missing assets clearly.
- **Auto language** needs explicit audio evaluation. Set the initial recognition hint from the last confirmed language or configured locale. Apple `DictationTranscriber` is instantiated with a locale. For first-turn and consecutive Turkish/English switching, evaluate a lightweight on-device audio language classifier (including confidence and early routing) against competing prewarmed Turkish/English recognizers if the Mac can sustain both. Use bounded pre-roll to replay to the selected recognizer when a confident switch arrives. Reply in the per-turn selected language and choose the corresponding installed voice; short or mixed utterances use the confirmed conversation language and keep recognized code-switched words. Display the active language and let the owner correct it. Test real bilingual speech before advertising Auto. The installed batch Whisper CLI timing makes it unsuitable for the critical path in its measured form.
- DotNext adds a call button to bot chat, opens a full-screen view with the bot name and call state, waveform, mute, End and captions, and returns to the same chat. Play a single audio stream, compact long captions, offer explicit replay from the chat if applicable, and show a run link or queue status. Respect VoiceOver and Reduce Motion. Closing the call releases the microphone and player. Mac/web uses the same call controls and captions in a focused view in the browser and Dot.app. Provide keyboard access and a visible focus target on return to chat. Test microphone-denial, unavailable assets, dropped tailnet and busy/paused bot states.

### Human review and data

The proposed local slices can use the existing HTTP guard, pairing, key-value store and policy as written. [REVIEW.md](../REVIEW.md#always-needs-a-human) requires the owner's review for changes to guard/pairing, secret handling, approvals/policy, dependency declarations and listed desktop capability/build/release surfaces. A new WebSocket authentication path, packaged Swift helper changes, a new dependency or provider-key handling may enter those paths. Keep those changes in their own reviewable slice if they prove necessary. Use the repository's usual pre-push review and applicable tests during implementation.

Mic authorization remains the system's foreground prompt. Normal run approval rules remain in force. Cloud audio activation, cost limits and data retention require a decision from the owner. Local mode uses bounded in-memory audio; only final chat content follows existing chat retention. Log event types, outcomes and timing, with no raw audio, utterance bodies or tokens. Any library that would transfer audio to a provider needs explicit configuration before a session starts.

## Implementation slices

1. **Measure a warm local call.** Done in item 1968: a private Mac prototype streams fixtures through a prepared analyzer and a synthesizer and measures end-to-transcript, first speech-bearing PCM and the last word on Turkish and English, comparing synthetic tail lengths, with a fixed-delay stand-in for the model and the existing HTTP upload at 50 ms batches. Still open, and carried into slices 2 and 3: the same timing trace from the paired phone, a p95 under load, real recorded speech, and the decision whether the HTTP design and the selected text model fit the budget.
2. **Daemon voice session, chat and task handoff.** Add bounded authenticated media/session endpoints and adopt existing run/chat send paths. Integration-test regular reply, same-chat busy queue, real task acceptance, cancel/replay and late packets, launch idempotency on lost acknowledgments, phone revocation, slow readers, and durable transcript through restart. Use stand-ins for model and speech services in ordinary CI.
3. **DotNext foreground call.** Add the bot call entry, continuous capture and cancellable playback, captions, waveform, mute and End. Test the state machine with fixtures, then measure speaker and Bluetooth barge-in, Siri/call interruptions, background and reconnection on a paired phone. Compare direct and relayed tailnet results.
4. **Mac/browser call and synchronized bot preferences.** Reuse the session in Dot.app and supported browsers, add voice and speed previews, and ship Turkish/English selection. Validate Auto on bilingual fixtures and paired devices before enabling it for general use. Check settings across clients, local-only playback, audio cleanup and keyboard/VoiceOver interactions.
5. **Release acceptance and tuning.** Run the cross-device Turkish/English timing, interruption and naturalness matrix, including first-session and first-voice measurements. Tune the measured bottlenecks, update voice/privacy docs and publish the release gates. If local speech quality falls short, ask the owner to authorize a capped paid comparison using the same corpus and gates before deciding on a provider.

## Owner decisions · 2026-11-26

- **Local audio first.** The first version is a local pipeline: streaming speech-to-text on the Mac, Dot's own model for the reply, streaming text-to-speech on the Mac. A limited paid OpenAI or Gemini realtime comparison comes later, only if Turkish naturalness or barge-in misses the release target, and only after the lead has been asked for a spend cap. No paid call is made before that cap is given, and the intended provider and audio handling are confirmed at that point.
- **First release scope.** The app stays in the foreground with one selected bot. Screen-lock calls and phone-to-Mac call handoff are later work.
- **Task completion.** Write the full result in the chat through the normal run path. While the call remains active, announce completion in one short sentence at the first pause. Wait for the floor and let a new owner turn interrupt the announcement.
